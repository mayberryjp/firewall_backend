## WireGuard Peer Enabled Toggle

- Summary: user asked whether a WireGuard peer can be toggled on and off and then
  asked me to build it. Before this, a peer had only keys, endpoint, allowed
  networks, keepalive and metadata, so stopping one meant deleting it.
- Contract: `Peer.enabled` boolean, serde default true when omitted (like static
  routes); `null`/non-boolean rejected. Disabled peers stay in configuration, history
  and exports and are removed from `Config::operational_value()`, so native apply
  replaces the device's peer set without them. Only installed peers appear in
  runtime. Peer identity remains the public key. Toggling needs the existing
  `wireguard.write`.
- Validation decision: disabled peers are still fully validated (key, endpoint,
  keepalive, canonical networks, IPv6 policy, unique key) so re-enabling cannot be
  invalid. Allowed-network uniqueness is enforced within a peer and among **enabled**
  peers only; this deliberately lets a disabled spare share a network with an active
  peer, which the previous rule forbade. That is a behavior relaxation for disabled
  peers only.
- Implementation notes: the projection uses `get_mut` chains so interfaces without a
  `wireguard` object are not given one (indexing a null value mutably would insert an
  object). Native code needed no change beyond the projection because the WireGuard
  settings reader ignores the extra `enabled` key and a remaining peer set is
  verified and re-applied exactly as before.

  [authorization/transaction test](../../crates/netcontrol-core/src/engine_tests.rs),
  [kernel test](../../crates/netcontrol-native/src/linux/integration.rs),
  [CLI test](../../crates/netcontrold/tests/cli.rs),

  [native guide](../../crates/netcontrol-native/README.md) and

## WireGuard Key Creation Flags

- Summary: user saw the interface field text "name of the key stored on the
  appliance, not the key itself" and asked how to store a key and whether to add a
  key-store command. `key_ref` is a file name in the key directory that the operator
  created by hand; the daemon's reader enforces owner, `0600`, size and key
  validity. A first answer documented a `wg genkey` shell command; the user then
  said they do not want to install additional packages, which **supersedes** that
  approach (the shell command was removed from the docs).
- Implemented `netcontrold --create-wireguard-key NAME` and
  `--wireguard-public-key NAME` on the installed binary, reusing `--keys`. They run
  before logging/startup, print only the public key, and never start the daemon,
  touch networking or read/write saved state. Creation uses the daemon's own
  `wireguard-control` key generation, writes a temporary `0600` file, `fsync`s and
  publishes it with a hard link that fails if the name exists (no overwrite, no
  partial file), then syncs the directory. The directory must pass the reader's
  trust check (owner, not group/world-writable); a missing one is created `0700`.
  Both flags conflict with each other. Private bytes are zeroed after writing.
- Finding: the native `safe_name` accepts dots, but core validation (and the
  frontend contract) allow only letters, digits, `_` and `-`. Creation follows the
  stricter contract rule, which also keeps its hidden temporary name from colliding
  with a real key. The reader itself was not tightened.
- Components: [key creation and tests](../../crates/netcontrol-native/src/linux/wireguard.rs),
  [crate wrappers](../../crates/netcontrol-native/src/lib.rs),
  [linux module](../../crates/netcontrol-native/src/linux.rs),
  [daemon flags](../../crates/netcontrold/src/main.rs),
  [binary test](../../crates/netcontrold/tests/startup.rs),
  [install guide](../BUILD_AND_INSTALL.md#creating-a-wireguard-private-key),
  [CLI guide pointer](../CLI.md) and [changelog](../../CHANGELOG.md).
- Validation passed in Linux Docker (stable Rust, locked): four WireGuard key unit
  tests (mode `0600`, public key matches the daemon's own `private_key` reader,
  no overwrite and unchanged contents, dangling symlink and invalid names refused,
  no leftover temporary files, untrusted directory refused, missing directory
  created `0700`) and the startup suite (five tests, including a new test that runs
  the real binary: stdout is exactly the 44-character public key plus newline,
  stderr empty, private key never printed, `0600`, second run fails with empty
  stdout and unchanged file, `../escape` and a missing key fail, both flags together

  dotted names to be rejected by `safe_name`; I fixed the creation rule, not the

## MQTT Host Health Sensors

- Summary: user asked whether host health was streamed over MQTT (it was not: the
  publisher read only `/api/v1/statistics`), then chose per-core CPU and
  per-sensor granularity. Added host-health sensors from the existing
  `GET /api/v1/statistics/host` snapshot, read internally with `state.read`.
- Entities: fixed memory/swap, load, host uptime, OOM kills and PSI sensors;
  per CPU core and total busy percent; per thermal zone and per hwmon
  temperature/fan sensor; per local filesystem total/used/available. Disks and
  per-disk I/O were not added (not requested).
- Decisions: Home Assistant cannot derive a rate from raw ticks, so the daemon
  computes busy percent from consecutive samples (total = user..steal, busy =
  total - idle - iowait; guest not double-counted), keeps a baseline only within a
  session and clears it on reconnect, boot-id change, counter decrease, missing
  CPU or zero elapsed ticks. Unavailable values publish null (unknown), never
  zero. Entity names are stable and id-based so a transient read failure does not
  rename entities. If a whole section cannot be enumerated its previous
  definitions are carried into the new discovery payload and are not removed by
  the component manifest. Dynamic kinds are capped (256/64/128/64) and the
  existing 4096-entity and 1 MiB limits still apply. The two snapshots are read
  under separate engine locks, so a slow storage read does not extend the
  statistics hold.
- Components: [sensor mapping and tests](../../crates/netcontrold/src/mqtt_host.rs),
  [publisher](../../crates/netcontrold/src/mqtt.rs),
  [module registration](../../crates/netcontrold/src/lib.rs),

  [README](../../README.md#home-assistant-mqtt-statistics) and
  [changelog](../../CHANGELOG.md). The existing `telemetry` state-class argument
  became explicit; existing sensors are unchanged.
- Validation passed in Linux Docker (stable Rust, locked): four new
  `mqtt_host` unit tests (two-sample utilization, reset handling, units/precision/
  unknown values, retained-kind behavior, entity caps) and the existing MQTT tests;
  the ignored `mqtt_native_persistent_reconnect_and_confirmed_disable` passed in a

## Durable DHCP-dependent static route recovery

- Summary: investigated a state-read `503` caused by an enabled static route
  missing from the live protocol-242 route set. Current state did not establish
  the original deletion trigger. Found and fixed lifecycle gaps: DHCP address
  removal could invalidate static routes without restoring them, and normal
  configuration apply cached route presence before address changes.
- Components:
  [DHCP worker/lease plan and unit tests](../../crates/netcontrol-native/src/linux/dhcp_client.rs),
  [route installation, scoped reconciliation and readback](../../crates/netcontrol-native/src/linux/networking.rs),
  [native verification/apply](../../crates/netcontrol-native/src/linux.rs),
  [kernel lifecycle/integration tests](../../crates/netcontrol-native/src/linux/integration.rs),
  [native guide](../../crates/netcontrol-native/README.md),
  [frontend contract](../../FRONTEND_SPEC.md#64-routes) and
  [changelog](../../CHANGELOG.md).
- Decisions/contract: enabled IPv4 static routes on DHCP-managed interfaces are
  lease-dependent. Without a valid matching lease, retain configuration but
  suspend kernel installation/expectation. Acquisition/renewal/address changes
  restore only that interface's configured routes, after DHCP routes; direct
  static routes precede gateway static routes. Lease loss removes them. IPv6,
  other interfaces and disabled routes are excluded from this recovery.
  Static gateway values are never rewritten; unreachable gateways and foreign
  conflicts fail explicitly. Adds do not replace existing routes; identity,
  ownership and readback remain enforced. No read-time writes or generic
  drift-repair loop. Lease intent/rollback covers restoration; failed cleanup
  retains the lease record for recovery. Route plans derive from persisted
  current settings and publish under the existing shared lease lock.
- Native configuration apply now rereads actual route presence after interface
  and address mutations, rather than skipping routes that the kernel removed.
  Existing startup reconciliation remains responsible for missing owned routes
  when the updated daemon starts; no reset, migration, new persistence schema,
  external worker or dependency was introduced.
- Validation passed in the existing Linux Docker toolchain/cache, stable Rust
  and the committed lockfile:

    in a privileged container, disposable isolated namespaces (all 15 passed).
  - `cargo +stable test --workspace --locked --offline -- --quiet`
    (266 passed, 23 intentionally ignored; native integrations run separately).
  - `cargo +stable clippy --workspace --all-targets --locked --offline -- -D warnings`.
