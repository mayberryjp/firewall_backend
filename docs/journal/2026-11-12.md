## Accept zero-source DHCP requests with on-link client addresses

### Summary and affected components

The user reported DHCPREQUEST receipt/rejection pairs from container clients
with peer `0.0.0.0:68` and reason `invalid_client_address`. The current worker
unconditionally rejected zero-source packets whenever the DHCP header's client
address (`ciaddr`) was nonzero. That admission check is stricter than necessary
for a relay and explains the reported pattern; the exact client implementation
and original packet/header values were not captured or inspected.

- [Admission and portable tests](../../crates/netcontrol-services/src/dhcp.rs):
  extract one address-admission helper. Allow zero source with zero `ciaddr` or
  valid on-link unicast `ciaddr`; nonzero sources must still match `ciaddr`.
  Reuse existing subnet/network/broadcast/relay/unicast checks. Preserve the
  original client address, flags, options and transaction identity; existing
  request transformation changes only hops/giaddr.
- [Native packet fixture](../../crates/netcontrol-native/src/linux/integration.rs):
  raw AF_PACKET injection of zero-source DHCPREQUESTs with nonzero on-link
  `ciaddr`, broadcast flag clear/set, complete server-forward/ACK delivery,
  telemetry, and negative off-link/network/broadcast/relay cases. Preserve the
  existing ordinary renewal, firewall permits, restart, disable and rollback
  checks in the same fixture.
- [Services README](../../crates/netcontrol-services/README.md),
  [canonical frontend contract](../../FRONTEND_SPEC.md#dhcp-relay-diagnostics),
  [changelog](../../CHANGELOG.md) and
  [handoff 2026-11-12-01](../frontend-handoffs/2026-11-12.md#2026-11-12-01-zero-source-dhcp-requests-with-existing-client-addresses):
  explain admitted packets and the remaining rejection rules.

### Decisions and current contract

Accept zero-source requests at the protocol level, not through a Docker/MAC
allowlist, configuration knob or log suppression. Nonzero `ciaddr` must remain
on-link unicast, not the receiving interface's relay address, subnet network or
broadcast address. A nonzero source cannot claim another `ciaddr`; a zero
`ciaddr` still requires zero source. Existing ingress, ports, destinations,
packet shape, upstream identity, transaction/reply correlation and target
validation remain unchanged.

[RFC 1542 section 4.1](https://www.rfc-editor.org/rfc/rfc1542#section-4.1)
requires relays to accept zero-source BOOTREQUESTs; section 4.1.1 preserves
other BOOTP fields while updating hops/giaddr. Do not clear `ciaddr` to bypass
validation: it is needed for upstream processing and reply matching/delivery.
This fix does not claim that every possible container DHCP implementation or
state machine conforms to every client-side RFC requirement.

**Release impact/recommended bump:** fix; next automatic calendar version.
No HTTP routes, schemas, statuses, permissions, counters, configuration,
persisted state, polling or retention changes. Existing rejected events remain
historical observations; genuinely invalid addresses still report the same
reason. No lease reset, migration or automatic container reconfiguration.

**Frontend impact: optional** explanatory diagnostics/help; no client types,
forms or validation changes required.

## Isolate DHCP failures and expand relay diagnostics

### Summary and affected components

Following the zero-source admission fix, code review identified three more
relay failure paths: valid DHCPNAKs failed request-header matching, one send
failure could stop the shared worker and prevent healthy upstream delivery,
and matching XID/MAC transactions on different VLANs overwrote one another.
The user requested all three fixes and better troubleshooting observations.
These are code findings, not observations of the deployed firewall.

- [Relay and portable tests](../../crates/netcontrol-services/src/dhcp.rs):
  accept validated NAK-specific zero-address/flag behavior while retaining
  strict ACK/Offer matching; scope transactions by relay address plus XID/MAC;
  isolate upstream and client send failures and classified asynchronous UDP
  transport errors. Broken sockets still fail explicitly for worker recovery.
- [Telemetry and tests](../../crates/netcontrol-services/src/dhcp_telemetry.rs):
  add bounded explanatory detail and validated DHCP header metadata, retain
  transaction identity/header fields on expiry, and rate-limit send warnings
  in ordinary Netcontrol tracing without dropping API events or counters.
- [Native namespace regression](../../crates/netcontrol-native/src/linux/integration.rs):
  verify real NAK delivery, strict ACK flag matching, simultaneous same-XID/MAC
  exchanges on two VLANs, an unreachable first/healthy second upstream, and
  oversized downstream L2 send failure followed by another successful exchange
  without a worker-generation change.
- Updated [services README](../../crates/netcontrol-services/README.md),
  [canonical frontend contract](../../FRONTEND_SPEC.md#dhcp-relay-diagnostics),
  [changelog](../../CHANGELOG.md) and
  [handoff item 03](../frontend-handoffs/2026-11-12.md#2026-11-12-03-dhcp-relay-reliability-and-diagnostic-detail).
  Preserved the earlier zero-source fix and separate sysstat installer work.

### Decisions and current contract

NAKs must have zero `ciaddr`/`yiaddr` and are broadcast downstream; their
`ciaddr`/broadcast flag need not equal the original request. Existing endpoint,
packet, server and transaction checks remain, as do strict ACK/Offer checks.
Relay addresses are already required unique; using that address in the
transaction key separates overlapping client identities across interfaces.
An individual failed send is reported and does not prevent trying later
upstreams or processing other clients. Only explicitly classified transport
receive errors continue; invalid/broken sockets still trigger recovery.

Diagnostic events add required `detail` (up to 512 characters), nullable IPv4
`client_address`, `offered_address`, `relay_address`, nullable `broadcast`, and
nullable `hops` (0..255). Valid zero addresses are strings, not null. Header
fields are null without a validated packet. Forward/send-error metadata
describes the forwarded wire header. Tracking expiry retains request identity
and explains that relay tracking expiry is not DHCP lease expiry.
`send_errors` includes classified asynchronous transport errors and is not an
exact lost-packet count. Warnings are limited to one per interface/error
category per 30 seconds; diagnostic API events/counters are not suppressed.
No packet payloads, arbitrary DHCP options or per-packet success tracing added.
Existing RAM-ring capacity/retention, routes, permissions and configuration
remain unchanged.

**Release impact/recommended bump:** fixes plus additive diagnostic response
fields/semantics; next automatic calendar version, Unreleased. No migration,
compatibility shim or hand-edited version.
**Frontend impact: required** client types and diagnostic rendering/help;
[handoff item 03](../frontend-handoffs/2026-11-12.md#2026-11-12-03-dhcp-relay-reliability-and-diagnostic-detail)
remains **Pending frontend review**, not sent or acknowledged.
