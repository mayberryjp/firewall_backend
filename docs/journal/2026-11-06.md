## Large Sando imports rejected by the netfilter send buffer

### Summary and components

Investigated the reported HTTP 500 with netfilter `EMSGSIZE` and successful
previous-configuration restoration. The locked rustables sender submits the
entire firewall batch through an unchanged default-size socket, so valid large
imports can exceed the datagram limit.

- [Netfilter transport](../../crates/netcontrol-native/src/linux/netfilter.rs):
  reserve and verify per-socket send capacity for the entire atomic datagram;
  use `SO_SNDBUFFORCE` with existing `CAP_NET_ADMIN` only if ordinary
  `SO_SNDBUF` is clamped. Validate batch ordering, request only the last
  operation's success ACK, retain all kernel error checks, and include request
  length/OS error on send failure.
- [Firewall apply/removal](../../crates/netcontrol-native/src/linux/firewall.rs):
  use the checked transport for ordinary rules, existing destination-rewrite
  encoding and bootstrap removal instead of the default rustables sender.
- [Native regressions](../../crates/netcontrol-native/src/linux/integration.rs):
  apply the maximum 4,096 ordered imported rules, read their counters, reject
  a large replacement with a non-final missing-chain error without changing the
  live fingerprint/ownership, reopen and repair, then roll back to empty rules.
  Transport tests cover malformed framing/order, ACK selection and send capacity
  above the ordinary socket limit.
- [Native documentation](../../crates/netcontrol-native/README.md),
  [Sando frontend contract](../../FRONTEND_SPEC.md#sando-one-time-imports)
  and [changelog](../../CHANGELOG.md): document atomic large-update behavior.

### Decisions and current contract

Keep the complete firewall update in one kernel transaction; never split imports
into partially applied chunks or change global buffer sysctls. Socket allocation,
capability and kernel failures remain explicit ordinary apply errors with existing
transaction restoration. No schema, validation limit, permission, HTTP method,
status code or confirmation changes. A failed/restored import does not advance
the committed import report.

Release impact/recommended bump: **runtime fix; next automatic calendar version**.
Unreleased. **Frontend impact: none**: existing transaction/error handling applies;
no client work or new handoff is required.

SSH, add firewall permits or configure networking itself. Manual simulator/lab
deployments require an explicit socket path. Lost key output cannot be recovered;

## Active VLAN ownership recovery

### Summary and components

Fixed the reported retained-intent failure during explicit VLAN ownership
handoff. Read-only device diagnostics showed matching visible VLAN identity,
MTU/up state and static IPv4 configuration. The backend compared complete raw
address packets, including kernel creation/update timestamps. Its own recovery
reapplies addresses and changes those timestamps, so byte comparison could
reject an otherwise identical recovered link.

The user explicitly requested active ownership rather than manually reconciling
every transient external-manager change. The selected-VLAN recovery step now
checks identity, relinquishes networkd management, reapplies captured settings
and verifies the resulting configuration.

- [Native recovery](../../crates/netcontrol-native/src/linux.rs): replace
  pre-handoff frozen-settings checks with selected-VLAN identity checks; reapply
  captured address/MTU/up settings after handover. Resume also works when native
  ownership was saved before core persistence completed.
- [Networking](../../crates/netcontrol-native/src/linux/networking.rs): share
  VLAN identity validation, normalize only address timestamps/ordering for
  comparison, retain raw recovery snapshots and report actual mismatched fields.
- [Kernel fixture](../../crates/netcontrol-native/src/linux/integration.rs):
  introduce external address/MTU changes, restore captured settings, assert raw
  timestamps changed, verify semantic equality and repeat restoration/retry.
- [CLI guide](../CLI.md#correcting-an-initially-untagged-factory-lan),
  [native guide](../../crates/netcontrol-native/README.md#explicit-existing-vlan-adoption),
  [frontend spec](../../FRONTEND_SPEC.md#explicit-existing-vlan-adoption) and
  [changelog](../../CHANGELOG.md): active handover and interrupted recovery.

No device addresses, MACs, boot identifiers or raw runtime snapshots are
recorded here. Regression fixtures use synthetic values.

### Decisions and current contract

Mutable address/MTU/up changes between capture and handover no longer require
manual reconciliation: the explicit operation overwrites them on the selected
VLAN. Wrong VLAN/parent identity, replacement devices, invalid snapshots and
actual post-apply configuration mismatches still fail. Prefix/scope/flags/
lifetimes and all other address attributes remain significant; only kernel
creation/update timestamps and dump ordering are excluded from equality.
Unrelated saved configuration/interfaces are not reset.

This fixes the active handoff/recovery stage, not arbitrary inherited route
support or whole-host takeover. Existing initial capture prerequisites remain.
No persisted receipt schema change or manual journal edits are required.
Startup resumes a retained ownership intent; afterward the operator must still
submit and confirm the actual LAN-role/firewall/NAT change.

Release impact/recommended bump: **runtime fix; next automatic calendar version**.
No HTTP fields, permissions or status codes change. **Frontend impact: optional**

[handoff 2026-11-06-04](../frontend-handoffs/2026-11-06.md#2026-11-06-04-active-vlan-ownership-recovery),

## Shared physical-interface and VLAN ownership

### Summary and affected components

Extended the preceding active VLAN takeover to physical-interface inheritance:
identity check, networkd exclusion, captured address/MTU/up restoration and
semantic verification now share one implementation. Restart reasserts exclusions
for all still-owned physical interfaces, including those without an initial
inheritance receipt. Ordinary startup still applies saved desired configuration,
not original bootstrap addressing; unrelated links are not discovered or claimed.

Changes: [native ownership](../../crates/netcontrol-native/src/linux.rs),
[networkd handover](../../crates/netcontrol-native/src/linux/adoption.rs),
[snapshot restoration/comparison](../../crates/netcontrol-native/src/linux/networking.rs),
[mixed kernel fixture](../../crates/netcontrol-native/src/linux/integration.rs),
[host lifecycle fixture](../../crates/netcontrol-native/src/linux/host_integration.rs),
[native documentation](../../crates/netcontrol-native/README.md),
[CLI](../CLI.md), [frontend contract](../../FRONTEND_SPEC.md) and
[changelog](../../CHANGELOG.md).

### Decisions and contract impact

Persist exclusions even for owned links without networkd runtime state, but
only invoke D-Bus/relinquishment verification for links that have runtime state.
Filesystem inspection errors and actual manager handover failures remain errors.
This avoids requiring networkd just to reopen previously unmanaged host links.

Finite address lifetimes age from capture, expire normally and remain checked;
allow at most one second of kernel/capture rounding without treating all finite
leases as equivalent. Permanent/deprecated distinctions and identity checks
remain enforced.

Release impact/recommended bump: **runtime fix; next automatic calendar version**.

## Pending VLAN adoption with a DHCP-backed WAN

### Summary and evidence

The subsequent appliance attempt downloaded verified release `v2026.11.06.7`
but failed during daemon startup with WAN address drift while resuming the
retained VLAN adoption. The deployment helper restored the previous binary.
Earlier attempts had refused replacement while the old service was activating;
stopping the service and its activation socket allowed replacement to proceed.

Code investigation confirmed that core startup finishes pending adoption before
ordinary backend repair. The native finisher verified the existing configuration
with a new, empty DHCP runtime map. It therefore treated an existing valid
leased address as an unexpected static address. Initialize committed DHCP
clients, including valid durable lease/intent restoration, before that check.

Affected [native finisher](../../crates/netcontrol-native/src/linux.rs),

runtime state and manager files cannot affect the invoking environment.

## DHCP Offers discarded for zero server reply hops

### Summary and evidence

An operator packet capture shows a Discover relayed with hops `1` and a matching
server Offer with hops `0`, correct transaction/client identity and giaddr.
The native relay required reply hops `1` and would discard this Offer.
RFC 2131 table 3 specifies zero for server Offers, ACKs and NAKs.
The capture was on another host's VLAN interfaces, so it does not prove receipt
by the firewall socket or exclude additional filtering/offload problems.

Removed the reply-hop equality requirement, keeping request chaining protection
and all existing server/transaction/client/flags/giaddr/on-link checks.
Do not broaden firewall input or alter server configuration for this mismatch.

Affected [worker/tests](../../crates/netcontrol-services/src/dhcp.rs),
[services README](../../crates/netcontrol-services/README.md),
[frontend spec](../../FRONTEND_SPEC.md) and [changelog](../../CHANGELOG.md).

### Decisions and release/frontend impact

Reply hops are not used to route or authenticate a server response; ignore them
while retaining strict request-hop validation. Regression tests cover zero and
nonzero reply hops, Offer/ACK/NAK, broadcast/unicast selection, wrong giaddr,
non-replies and downstream request chaining.

Release impact/recommended bump: **protocol fix; next automatic calendar version**.
Unreleased; not included in the observed appliance version `2026.11.06.8`.
No configuration schema, HTTP method/path, authentication or status changes.
**Frontend impact: optional** troubleshooting help in

## Bounded MQTT discovery and state topics

### Summary and affected components

Investigated the reported `MQTT payload limit exceeded`: aggregate Home Assistant
discovery or state JSON was capped at 1 MiB even when the entity count was valid.
The user explicitly selected splitting telemetry across bounded topics instead
of increasing the existing limit.

Implemented standard per-sensor retained discovery and nonretained metric
shards/structured-section topics in the [publisher/tests](../../crates/netcontrold/src/mqtt.rs).
Metrics start in SHA-256-prefix buckets and subdivide as needed; discovery
declares the exact state topic and is refreshed when a bucket splits/joins.
Every sample part carries its shared collection timestamp; full values, exact
counter strings, nulls and health/source sections remain represented.

Updated [README/operator notes](../../README.md#home-assistant-mqtt-statistics),
[frontend contract](../../FRONTEND_SPEC.md#614-home-assistant-mqtt-streaming),
[changelog](../../CHANGELOG.md) and
[handoff 2026-11-06-06](../frontend-handoffs/2026-11-06.md#2026-11-06-06-bounded-mqtt-topic-publications).

### Decisions and current contract

- At most 4096 entities and 1 MiB serialized bytes per message remain. Aggregate
  samples may exceed 1 MiB. Oversized indivisible configurations, metric values
  or structured sections fail explicitly with payload class, actual size and
  limit; no truncation or partial sample enqueue.
- Discovery is `homeassistant/sensor/netcontrol_<device_id>/<component_id>/config`.
  Metric state is `netcontrol/<device_id>/state/metrics/<hash-prefix>`; other
  sections are `netcontrol/<device_id>/state/<section>`. No aggregate `/state`
  or former monolithic discovery publication. Same stable IDs, device grouping,
  expiry, credentials and retained availability/LWT.
- Durable discovery manifest remains write-before-publish and finalizes only
  after full batch acknowledgments. Deletion uses one bounded empty retained
  message per removed entity, repeatable after interruption. Failed source
  enumerations retain discovery, without fabricating measurement values.
- Only changed discovery publishes between samples; reconnect/birth force fresh
  discovery. Online queues after all state parts; running/last-published success
  requires acknowledgment of the entire batch.

Release impact/recommended bump: **breaking MQTT topic/payload contract; next
automatic calendar version**. Unreleased; not published or deployed by this task.
No HTTP/API configuration schema, permission or response changes.
**Frontend impact: required deployment/custom MQTT-consumer work; optional UI
help**, [handoff 2026-11-06-06](../frontend-handoffs/2026-11-06.md#2026-11-06-06-bounded-mqtt-topic-publications)
is **Pending frontend review**.

Broker administrators must coordinate publisher disable/stop, clear the former
retained device-discovery topic, update ACLs/subscriptions and deploy/enable the
new publisher. No compatibility publisher, automatic broker-state conversion or
persisted-state migration was added. Keep private identity/password state.
Actual Home Assistant entity-registry/customization continuity needs acceptance.
