## Transactional Cisco-inspired CLI and custom SSH server

### Summary and decisions

- User requested Cisco-like configuration management with the same atomic
  workflow, available through a custom SSH server. Added an in-process interpreter
  and SSH transport, not an operating-system shell or supervised sshd.
- Sessions stage private full-configuration candidates based on committed
  revisions. Complete-schema typed JSON-pointer editing complements familiar
  interface/global commands. Apply/confirmation/rollback/restore/repair use
  the existing engine and scoped permissions; no per-command live writes or
  parallel commit path. This remains rollback-aware reconciliation, not a
  whole-kernel atomic transaction.
- SSH is opt-in (`--ssh-listen`), with persistent Ed25519 host identity
  (`--ssh-host-key`, default `<state>.ssh-key`). Fixed username `apikey` and
  existing API keys avoid making device-account passwords networking credentials.
  Shared authentication preserves setup/health/revocation behavior.
- CLI `enable` is mode-only; readonly keys cannot acquire write permissions.
  Disconnect/discard does not confirm or cancel engine-owned pending transactions.
  Existing HTTP schema/state formats and custom package payloads are unchanged.
- SSH has bounded admission/authentication, five-minute idle and 30-minute
  absolute lifetimes, PTY-required interactive shells and single-command exec.
  Ctrl-C cancels input only; Ctrl-D exits without confirming pending work.
  Rendered output above 4 MiB produces an explicit error/nonzero exec status,
  never partial successful configuration JSON; the error warns that execution
  may already have completed. Exact limits and host-key requirements are in the
  [CLI guide](../CLI.md#ssh-transport-limits).
- Recommended feature bump: minor; aggregate Unreleased remains major. No
  release baseline/version, commit, push or publication is assigned.

## Host-managed appliance networking

### Summary and decisions

- User clarified the appliance must configure its real host interfaces, not
  require manually provisioned isolated networking. This supersedes the
  earlier isolated-lab product scope; isolation remains an optional test tool.
- Native host networking and physical Ethernet/veth selection are being wired
  into the same full-candidate/confirmation/rollback engine. No external network
  manager or shell command is introduced.
- Added read-only `GET /api/v1/interfaces/discovered` and
  `show interfaces discovered`, independent of configured-state/worker
  observation. The existing interfaces endpoint remains managed configuration.
  Discovery never assigns roles or automatically takes interface ownership.
- Configuration accepts `ethernet` for existing NICs, including DHCPv4 relay;
  main routing table 254 is accepted for routes/policy targets/monitors alongside
  reserved tables. Existing validation and scoped permissions remain.
- Package OpenRC arguments select native Linux host mode; the bare daemon
  remains simulator-by-default for development. Root host configuration can
  sever management connectivity: provisional confirmation and console access
  remain essential. There is no DHCP client or DNS server.
- Recommended bump: major for native scope/deployment semantics. Baseline
  remains unknown; no version, release or frontend notification is assigned.
- Correction to the interim progress update: proposed forwarding controls were
  removed before final validation. Changing IPv4 forwarding or IPv6 RA/forwarding
  has collateral kernel device-state effects that are not safely captured for
  rollback. The current API/CLI still reject those settings; forwarding remains
  an operator prerequisite, not a completed host-management capability.
