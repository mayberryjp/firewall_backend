## Routed BGP speakers and authorized next hops

Separate a routed BGP speaker's session endpoint from the directly connected
host that forwards its advertised networks. The former direct-peer-only
validation/import rule rejected this topology.

Affected [configuration/validation/tests](../../crates/netcontrol-core/src/bgp.rs),
[simulator](../../crates/netcontrol-core/src/simulator.rs),
[transaction persistence/rollback tests](../../crates/netcontrol-core/src/engine_tests.rs),
[native sockets/import/diagnostics/tests](../../crates/netcontrol-native/src/linux/bgp/mod.rs),
[example validation](../../crates/netcontrol-core/src/model_tests.rs),
[new synthetic transaction](../../examples/bgp-routed.json),
[canonical contract](../../FRONTEND_SPEC.md#native-ipv4-bgp),
[README](../../README.md), [native README](../../crates/netcontrol-native/README.md)
and [changelog](../../CHANGELOG.md).

Decisions/current contract:

- Per-neighbor `multihop_ttl` 1..255 defaults to 1 and applies to active and
  accepted sockets. Shared listeners use the maximum configured TTL for the
  SYN-ACK before peer identification. This explicitly replaces the former OS
  default transmit TTL, not an inbound TTL-security feature.
- Per-neighbor `allowed_next_hops` defaults to empty (peer-only). Nonempty lists
  replace implicit peer authorization; at most 32 unique usable IPv4 hosts on
  the selected static subnet(s), excluding the firewall itself and off-link
  gateways. `/31` hosts supported. Routed non-WireGuard speakers require TTL
  greater than 1 and a nonempty list, plus independent bootstrap/return routing.
  WireGuard retains empty lists, peer-only NEXT_HOP and existing AllowedIPs.
- Install the received authorized gateway unchanged; no recursive resolution,
  address override, external daemon or new dependency. Reuse existing route
  ownership, audit, cleanup/recovery and transaction lifecycle.
- Expose nullable `last_rejection` with prefix, NEXT_HOP and reason alongside
  cumulative rejection counts, rather than silently discarding diagnostic
  context. Latest diagnostic survives successful updates/reconnects, resets on
  worker restart, and does not become an accepted route or session failure.
- Release impact: additive configuration/status and changed explicit transmit
  TTL default; next automatic calendar version, no manual bump.
- Frontend impact: required forms/types/diagnostics; see
  [2026-11-16-01](../frontend-handoffs/2026-11-16.md#2026-11-16-01-routed-bgp-speakers-and-authorized-next-hops),
  Pending frontend review, not sent/deployed/UI-verified.

Decisions/current contract:

- Per-neighbor `enabled` is a boolean, default true. Disabled entries retain
  their fully validated configuration (including up interface, enabled
  WireGuard peer and bootstrap coverage) and count toward configured limits.
- Skip disabled peers when building shared listeners, admitting passive BGP,
  reconnecting/processing sessions, choosing learned paths and listing exports.
  Remove owned learned routes/dynamic AllowedIPs through existing shutdown/
  reconciliation, preserving all static configuration and bootstrap routes.
- Native and simulator status expose boolean `enabled` and `state:"disabled"`.
  Disabled peers do not degrade native health; an enabled all-disabled worker
  is healthy and idle without listeners. MQTT configured totals still include
  disabled peers; no new MQTT control surface or mutation endpoint.
- Preserve full transaction authorization, persistence, confirmation and
  rollback. Applying changes restarts the entire BGP worker, so other enabled
  peers may briefly reconnect and ephemeral counters/diagnostics reset.
  Re-enable/rollback starts fresh sessions and relearns routes.
- Release impact/recommended bump: additive configuration/status contract,
  next automatically generated calendar version; no manual version changes.
- Frontend impact: required toggle/types/status and reconnect warning; handoff
  03 is Pending frontend review, not sent/deployed/browser-verified.
