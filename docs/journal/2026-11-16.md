## Routed BGP speakers and authorized next hops

Separate a routed BGP speaker's session endpoint from the directly connected
host that forwards its advertised networks. The former direct-peer-only
validation/import rule rejected this topology.

Decisions/current contract:

- Per-neighbor `multihop_ttl` 1..255 defaults to 1 and applies to active and
  accepted sockets. Shared listeners use the maximum configured TTL for the
  SYN-ACK before peer identification. This explicitly replaces the former OS
  default transmit TTL, not an inbound TTL-security feature.
- Per-neighbor `allowed_next_hops` defaults to empty (peer-only). Nonempty lists
  replace implicit peer authorization; at most 32 unique usable IPv4 hosts on
  the selected static subnet(s), excluding the firewall itself and off-link
  gateways. `/31` hosts supported. Routed non-WireGuard speakers require TTL
  greater than 1 and a nonempty list, plus independent bootstrap/return routing.
  WireGuard retains empty lists, peer-only NEXT_HOP and existing AllowedIPs.
- Install the received authorized gateway unchanged; no recursive resolution,
  address override, external daemon or new dependency. Reuse existing route
  ownership, audit, cleanup/recovery and transaction lifecycle.
- Expose nullable `last_rejection` with prefix, NEXT_HOP and reason alongside
  cumulative rejection counts, rather than silently discarding diagnostic
  context. Latest diagnostic survives successful updates/reconnects, resets on
  worker restart, and does not become an accepted route or session failure.
- Release impact: additive configuration/status and changed explicit transmit
  TTL default; next automatic calendar version, no manual bump.
- Frontend impact: required forms/types/diagnostics; see
  [2026-11-16-01](../frontend-handoffs/2026-11-16.md#2026-11-16-01-routed-bgp-speakers-and-authorized-next-hops),
  Pending frontend review, not sent/deployed/UI-verified.

## Correction: WireGuard separate speaker and next hop

The user clarified that the session in the first task runs over WireGuard.
The initial implementation incorrectly excluded that topology by rejecting
every nonempty WireGuard `allowed_next_hops` list. The earlier peer-only
WireGuard decision, frontend disabling instruction and unqualified statement
that the requested topology was supported are superseded by this correction.
The observed missing TCP SYN-ACK remains a separate connectivity issue; this
change does not claim to diagnose or resolve it.

Decisions/current contract:

- Permit the existing per-neighbor next-hop list on WireGuard. Retain the same
  unique/unicast/not-local checks, 32-address bound and empty-list peer-only
  semantics for all interfaces. Non-WireGuard on-link validation is unchanged.
- Each listed WireGuard next hop must be covered by the referenced enabled
  peer's static AllowedIPs, independently of the session address's bootstrap
  coverage. Reject coverage by another enabled peer's static AllowedIPs.
  An off-subnet tunnel next hop is valid when statically peer-covered: no
  Ethernet/ARP assumption applies to a point-to-point WireGuard interface.
- Keep the existing shared import authorization, real advertised NEXT_HOP in
  route rows, device-only kernel routes, and learned-destination AllowedIPs on
  that same referenced forwarding peer. Do not select another key, override
  the gateway, steal prefixes or add recursive resolution.
- No new fields, permissions, endpoints, dependencies, storage format or
  compatibility paths. Bootstrap/underlay/return routing and TCP permits remain
  operator prerequisites. Release impact: fix/additive WireGuard authorization;
  next automatic calendar version, no manual bump.
- Frontend impact: required. Remove the blanket WireGuard disable and use
  static peer-coverage validation, not Ethernet subnet validation. Item 02 is
  Pending frontend review; no delivery, deployment or UI acceptance claimed.
