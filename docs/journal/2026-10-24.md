## Per-Interface DHCPv4 Retry

- Summary: user requested an API to retry DHCP on one interface. Added
  `POST /api/v1/interfaces/{name}/dhcp/retry`, API-key authenticated with
  `interfaces.write`. No transaction/state-read permission is required for the
  action itself. Body is absent or `{}`, no query parameters; strict configured
  name syntax. Returns `202 {interface, status: "retrying"}` after worker
  initialization, not lease acquisition. Runtime polling requires `state.read`.
- Decisions/contract: reject any active/recovering transaction, committed down
  interface or absent DHCP client with `409`; unknown interface `404`, malformed
  input `400`, unsupported method `405`, permission `403`, invalid key `401`.
  Native scope/committed ownership/recovery-intent/Ethernet identity guards apply;
  typed ownership drift is `409`, backend/start/stop failures `503`. Simulator
  explicitly reports unsupported, never a fabricated lease. Desired state,
  revision/history and transaction journal are unchanged.
- Native behavior: targeted restart, retaining worker ownership on a 15-second
  stop deadline and waiting up to 10 seconds for startup acknowledgment. No second
  worker before join, no DHCPRELEASE. Fresh discovery retains a valid tracked
  lease/address/routes/resolver until replacement, expiry or rejection. Normal
  lease-update WAL recovery/rollback is reused; ordinary retry does not reapply
  cached kernel state. Unrelated failed as well as healthy clients are excluded
  from both removal and startup selection. Other protocol workers are untouched.
