## CI repair: daemon-owned startup listener ports

- Summary/why: the user requested watching CI, fixing failures and repushing.
  [Run 45533406454](https://github.com/mayberryjp/firewall_backend/actions/runs/45533406454)
  failed the real-daemon HTTP/SSH startup test with a connection reset reading
  `/auth/status`; native/services/local-control, GNU installation and signed
  packaging jobs passed. The same startup test had returned an unexpected
  `404` during the preceding local validation.
- Evidence/decision: the startup fixture bound port zero, dropped that listener,
  launched the daemon later, and accepted any successful TCP connection as
  readiness. This left an unowned-port interval where a different listener could
  satisfy readiness. Remove that isolation defect rather than serialize tests,
  add sleeps, retry HTTP assertions or weaken CI. The failed CI response did not
  identify the peer that reset the connection.
- Components: [daemon readiness](../../crates/netcontrold/src/main.rs),
  [startup tests](../../crates/netcontrold/tests/startup.rs),
  [diagnostic documentation](../../README.md#persistent-log-viewing),
  [changelog](../../CHANGELOG.md).
- Implementation: launch successful listeners with port zero and read their
  actual addresses from the child's structured diagnostics under a 15-second
  deadline. Emit `HTTP listener enabled` only after the server handle reports
  its bound address; reuse the existing SSH listener event. Drain stderr with a
  joined fixture thread and preserve failure diagnostics. Keep the deliberately
  occupied HTTP socket for the bind-failure regression; discover that child's
  real SSH address before verifying shutdown. Preserve all HTTP/status/body,
  SSH banner/stable-key, watchdog and failed-startup assertions.
