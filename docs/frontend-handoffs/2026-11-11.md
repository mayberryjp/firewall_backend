### Exact API and frontend tasks

Previously only relay configuration/status and generated firewall counters were
available. New endpoints require existing `state.read`:

1. `GET /api/v1/services/dhcp-relay/log` accepts no body. Optional query:
   `limit=1..500` (default 100, canonical decimal), `interface` (valid interface
   name; may refer to retained history for removed links), `cursor` (opaque
   `<32-lowercase-hex-epoch>:<canonical-u64-sequence>`). Maximum query 1024 bytes;
   duplicate/unknown fields, malformed values, body and same-epoch future cursor
   -> `400`; non-GET -> `405`; absent auth/permission -> `401`/`403`;
   unavailable/native-unsupported simulator -> `503`.
2. `GET /api/v1/statistics/dhcp-relay` accepts no query/body and returns
   shared-worker status, totals, configured-interface counter rows, epoch,
   attempt generation, counter start/read timestamps and log retention metadata.
   Invalid query/body -> `400`, non-GET -> `405`; existing auth/service errors
   apply. Simulator returns simulated/disabled rows and null measurements,
   not fake zeros. Existing status/runtime envelopes remain unchanged.

Poll the log approximately once per second while visible; no SSE. The daemon
keeps the most recent 2048 events in RAM across all relays, without age retention,
disk writes or packet payload/hostname/option-value logging. Restart clears
history; worker retries/reconfiguration/repair/rollback retain it. Begin without
cursor; append oldest-first pages using `next_cursor`, immediately drain bounded
pages while `has_more`, and retain the same interface filter. Changing filters
starts a new un-cursored view. Empty filtered pages still advance the cursor.
Display `gap` when the global cursor is overwritten; `reset` means a new epoch,
so clear previous-epoch UI history. `overwritten` counts evicted events, not
kernel packet loss; no minimum retained duration is promised.

Synthetic log page:

```json
{"scope":"native-example","epoch":"0123456789abcdef0123456789abcdef","events":[{"sequence":"1","generation":"1","timestamp":"2026-11-11T00:00:00Z","interface":"vlan10","event":"requests_forwarded","reason":"","peer":"192.0.2.10:67","message_type":1,"transaction_id":"0000002a","client_mac":"02:00:00:00:00:01"}],"next_cursor":"0123456789abcdef0123456789abcdef:1","reset":false,"gap":false,"has_more":false,"capacity":2048,"overwritten":"0"}
```

Extend types from the canonical spec's `DHCPRelayLogPage`,
`DHCPRelayStatistics` and `DHCPRelayCounters`. Numeric DHCP message type is
nullable, transaction ID/MAC are nullable strings, interface/peer nullable for
unattributed/shared events. Timestamp is UTC RFC3339. Render receipt, successful
forward, rejection reason, send error, tracking expiry and worker lifecycle
events distinctly. Reasons/error text are display data, never HTML.

Counters are unsigned decimal strings (u64, saturating): requests/replies
received, requests/replies forwarded, packets rejected, send errors, tracking
entries expired, pending entries and sparse rejection-reason counts. Server
fan-out counts each successful send. Totals include unattributed packets.
Pending tracks transaction-ID/MAC entries; responses do not remove entries, and
expiry after 120 seconds is not a failed lease. No kernel/pre-worker drop count,
lease-success inference or collector/client acknowledgment.

Counters reset on every preparation attempt, including retry/restart/repair/
configuration/rollback. Reset rate baselines on epoch or generation changes;
both generation and sequence are decimal strings, so preserve exact values.
`counters_since` is attempt-start time (null before any attempt), not worker
readiness. Stopping clears pending but retains last attempt totals. Disabled
interface counters and unavailable/simulated measurements are null. Render
worker errors/retrying state alongside counts; never equate retained values
with active forwarding. Add shared-worker summary and per-interface diagnostics,
pause/visibility-aware polling, gap/reset notices, and error states that preserve
configuration/drafts. No automatic reconcile/reset actions.

## 2026-11-11-01 Syslog read and relay counters

- **Priority:** normal; **classification:** required syslog status/client update.

### Contract

Authenticated `GET /api/v1/services/syslog/status` and `GET /api/v1/runtime`
retain `state.read`, existing envelopes, HTTP statuses and error behavior.
No new route, request/query fields, configuration validation, permissions,
credentials or persisted schema. Status has the syslog row in `instances`;
runtime has it in `appliance_services`.

Previously `captured_records` counted local appends, `forwarded_records`
required all destinations to succeed and `failed_deliveries` counted missed
per-destination sends. These remain. The native worker adds:

- `received_records`: nonnegative numeric u64 journald datagrams read, including
  subsequent validation/local-write failures.
- `forwarded_deliveries`: nonnegative numeric u64 successful per-destination
  sends, including partial fan-out.

Synthetic row fragment after one record reaches one of two destinations:

```json
{"name":"syslog","state":"running","received_records":1,"captured_records":1,"forwarded_records":0,"forwarded_deliveries":1,"failed_deliveries":1}
```

All five counters saturate at u64 maximum, initialize/reset to zero on every
execution attempt, including automatic recovery, explicit repair, configuration
restart and daemon restart. They are not persisted totals. Observed counts
remain visible after processing failure until the next attempt. HTTP preserves
existing number encoding; MQTT service sensors export lossless decimal strings
with records/deliveries units and unavailable values when not running.
Fields can be absent on disabled/simulated/unavailable rows.

Successful sends mean local transport writes, not remote collector receipt,
parsing, storage or acknowledgment; UDP can lose records after a successful
send. Local append is not per-record durable fsync. No queue/replay, new source,
remote syslog listener or delivery guarantee is added.

### Frontend tasks and acceptance

  **Remote sends** (`forwarded_deliveries`) on syslog status.
- Optionally show **Locally captured**, **Relayed to all destinations** and
  **Missed sends** from the existing fields; do not relabel all-destination
  records as the number of successful destination sends.
- Reuse visible-page non-overlapping 2-5 second polling. Show missing counters
  as unavailable rather than zero. Reset any rate baseline when `started_at`
  changes or counters decrease.
- Keep row errors/destination warnings local; retain configuration access and
  drafts during collector outages. Do not compute loss by subtracting sends
  from reads, because fan-out uses different units.
- Check one-destination success, partial two-destination failure, recovery
  without replay, attempt reset, stopped/disabled/simulated rows and processing
  failure retaining already observed counts.

Deploy the backend to obtain the new native observations; no new operator
prerequisites beyond existing systemd/journald activation and enabled syslog.
Frontend deployment may follow; do not invent samples before backend
availability. No migration or compatibility window.

Previously rows exposed numeric `exported_flows`, capture drops and other

optional, non-null, unsigned decimal-string fields (range 0..18446744073709551615):

| Field | Meaning/unit |
| --- | --- |
| `exported_packets` | Successfully sent export UDP datagrams |
| `exported_bytes` | UDP payload bytes, including templates/padding; no UDP/IP/link headers |
| `exported_flow_packets` | Sampled packets represented by successfully sent records |
| `exported_flow_bytes` | Sampled layer-3 bytes represented by successfully sent records |
| `export_errors` | Failed export batches, including encode/send/deadline errors |

`exported_flows` remains a JSON number counting successfully sent unidirectional
records, not distinct lifetime connections. A batch can span multiple datagrams.
Successful chunks count even if a later chunk fails; unsent chunks do not count.
Export errors propagate to the existing supervised worker error/retry path.

Synthetic status row fragment:

```json
{"name":"office","state":"running","exported_flows":30,"exported_packets":"1","exported_bytes":"1464","exported_flow_packets":"300","exported_flow_bytes":"13200","export_errors":"0"}
```

Initialize export counters at zero at execution entry. Update after each export
batch and shutdown flush; retain final observations in error/stopped rows until
the next attempt resets them. Reset on supervised retry, service reconcile,
configuration restart and daemon restart; no persistence. Use `started_at` as the
observation-period marker. Absent fields on disabled/simulated/unavailable rows
mean unknown, not zero. Values saturate at u64 maximum. Sampling is not scaled;
active unexported flows do not contribute. UDP success means local socket
acceptance, **not collector receipt/acknowledgement**.

The same five counters are added to existing per-instance Home Assistant MQTT
discovery/state, with `total_increasing` class and packets/B/errors units.
Preserve decimal strings; non-running MQTT counters are null/unknown, even when
HTTP retains last observations. Existing entity identity and instance caps stay.

Synthetic response (not appliance evidence):

{"source":"netcontrol","entries":[{"sequence":"1","timestamp":"2026-11-11T00:00:00+00:00","message":"{\"source\":\"backend\",\"component\":\"native\",\"message\":\"synthetic convergence event\"}"}],"next_cursor":"0123456789abcdef0123456789abcdef:1","oldest_cursor":"0123456789abcdef0123456789abcdef:0","gap":false,"reset":false,"has_more":false,"retention_bytes":8388608,"max_message_bytes":65000,"capture":{"state":"running","retrying":false,"error":null}}

Fields/types:

- `source`: `syslog|netcontrol`; `entries`: array, at most limit and 512 KiB of
  serialized entry data; complete response under 1 MiB.
- Entry `sequence`: positive decimal u64 string; `timestamp`: UTC capture

  Netcontrol text is JSON diagnostics; individual tracing fields are not a new

- `capture:{state:string,retrying:boolean,error:string|null}`. History may
  remain readable while socket collection is unavailable/stopped/error.

Without a cursor, show the newest bounded page, chronological by numeric
sequence. With a matching cursor, return records strictly after it.
Empty polls preserve the cursor; `has_more` governs forward paging even when
entry count is below limit. `gap` marks expired intervening records. A foreign
stream cursor sets `reset` and returns the new stream's newest page. Stream
identity/sequences survive normal restart; use separate cursors per endpoint.
Use `oldest_cursor` to start retained-history browsing, not as the ID of its
first record. Byte retention is not a fixed hours/days promise.

### HTTP contract and fields

Affected paths and authentication are unchanged:

- `GET /api/v1/interface-capabilities`: API key with `state.read`; cached
  snapshot or null, never a scan.
- `GET /api/v1/interface-capabilities/refresh`: API key with `state.read` and

Preserve existing 400/401/403/405, maintenance 409, fatal discovery 503 and

Previously RSS only reported table support and null activation. Now each

with queue IDs 0..4095. Details unreadable means null fields plus diagnostics,
while prior supported evidence is retained.

RSS `enabled:true` means multiple observed default-table queue targets with
identified active hashing. `false` means an observed table with at most one
target, i.e. no RSS queue spreading; it does not assert hashing hardware is off.
Unknown hash activation with multiple targets or failed detailed reads remains
null. Multiple channels/queues alone do not prove activation, and activation
does not prove distinct interrupt CPUs or balanced traffic.

Nullable interface `interrupts` contains device IRQs, including event IRQs:
`irq:number`, nullable `description:string`, `effective_cpus:number[]`,
`counts:[{cpu_id:number,interrupts:string}]` and `errors:string[]`.
CPU IDs are logical kernel IDs. Counts are exact cumulative unsigned decimal
strings, not packets/rates/utilization; use exact formatting or BigInt rather
than JavaScript Number. Unreadable counts or affinities are null independently.
An observed empty affinity list is not unknown.

Queues add `irqs:number[]|null` and `irq_mapping_reason:string|null`. Populate
only when an exact unshared driver action uniquely identifies the queue:
`INTERFACE-TxRx-N`, `INTERFACE-rx-N`/`INTERFACE-Rx-N`,
`INTERFACE-tx-N`/`INTERFACE-Tx-N`. A combined action maps the RX/TX queues with
the same index to the same IRQ. Unknown/shared/ambiguous names stay null with
diagnostics; never assign IRQs by array order. Join IRQ IDs to interface rows.
No observed hardware/IRQ inventory, lab namespaces and simulator mean null
interrupt observations, not fake zero IRQs. Virtual queues do not inherit RSS
or hardware IRQs; existing VLAN RPS source metadata remains separate.
