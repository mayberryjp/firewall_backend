## 2026-11-08-01 Conntrack controls

**Ownership policy superseded:** the original optional/unmanaged omission and

- **Priority:** medium.

- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not committed, published or deployed.

### Exact contract and affected requests

Previously conntrack keys were unsupported. The existing kernel string maps now
accept nine keys: host-global `net.netfilter.nf_conntrack_max` (1024..16777216
entries), and namespace TCP established/close/close-wait/fin-wait/last-ack/time-wait
and UDP unreplied/stream timeout keys (1..604800 seconds). The
[canonical spec](../../FRONTEND_SPEC.md#conntrack-limits-and-timeouts) lists every
full name. No new fields, nullability/default changes or separate write API.
Values must be nonnull canonical decimal strings, not JSON numbers.

Affected methods/paths:

- `GET /api/v1/kernel/tunables/catalog`: existing array adds nine integer entries
  with scope, inclusive min/max, count 1 and warnings. Requires API key and
  `state.read`.
- `GET /api/v1/kernel/tunables`, `GET /api/v1/runtime`,
  `GET /api/v1/state`, `GET /api/v1/revisions/latest` and
  `GET /api/v1/revisions/{revision}`: preserve these keys in their existing
  kernel maps; runtime inspection distinguishes applied/observed/original values.
  Requires `state.read`.
- `POST /api/v1/transactions`: full candidate, current `base_revision`,
  confirmation timeout 10..300 seconds. Requires `transactions.write` plus
  `kernel.host.write` for entry limits and/or `kernel.namespace.write` for
  timeouts, and other changed-resource permissions.
- `POST /api/v1/transactions/{id}/confirm`, `/rollback` and
  `POST /api/v1/revisions/{revision}/restore`: existing permissions/workflow apply.

Small valid synthetic fragment only; not a full request or recommendation:

```json
{"kernel":{"host":{"net.netfilter.nf_conntrack_max":"65536"},"namespace":{"net.netfilter.nf_conntrack_tcp_timeout_established":"432000","net.netfilter.nf_conntrack_udp_timeout":"30"}}}
```

Type/null errors `400`; wrong scope, noncanonical/out-of-range or unsupported
keys `422`; authentication/permissions `401`/`403`; stale/busy `409`; native
preflight/write/readback failures use existing `500`; observation unavailability
`503`. Submit `202` remains provisional, confirm/rollback `200`.

## 2026-11-08-04 Firewall drop traffic tags

**Correction:** the server-side tag queries and filter/paging instructions below

- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not committed or deployed.
- **Contract/recommended release:** additive HTTP telemetry/filters; breaking

### Exact methods and current contract

`GET /api/v1/firewall/deny-log`, API key and `firewall.logs.read` only, remains
read-only with no body and `Cache-Control: no-store`. Existing filters/cursors,
authentication `401`/`403`, method `405`, validation `400`, unavailable backend
`503` and normal error envelope remain unchanged.

Previously records had no TCP flags/tags and queries had no traffic filters.
New always-serialized fields:

- `tcp_flags:integer|null`: 0..255 low eight TCP flags; FIN=1, SYN=2, RST=4,
  PSH=8, ACK=16, URG=32, ECE=64, CWR=128. NS/reserved bits excluded.
  Null for non-TCP/noninitial fragment/unavailable fixed header, not zero.
- `tcp_payload_length:integer|null`: IP-advertised TCP payload bytes, not
  packet capture length or a flow total; null when no flags or fragmented.
- `tags:string[]`: required, no default, possibly empty, independent badges.
  Canonical order: `tcp_finish`, `tcp_reset`, `tcp_ack_only`,
  `tcp_connection_attempt`, `ipv4_broadcast`.

FIN/RST tags test the corresponding bits. ACK-only requires flags exactly ACK
and known zero payload; SYN-attempt requires SYN with ACK/FIN/RST clear.
None proves confirmed closing, benign traffic, or an admitted connection.
Broadcast tagging is protocol-independent: limited `255.255.255.255` or a
explicit kernel-reported IPv4 broadcast or subnet broadcast calculated from
live IPv4 address/prefix metadata (prefix <=30) in the managed namespace.
It also works when the kernel omits the explicit broadcast attribute.
Snapshots include dynamic/unmanaged interfaces and refresh per capture window;
failure/timeout stops capture explicitly. Tags remain historical across
subsequent interface changes. Unknown remote broadcast subnets are not inferred;
IPv6/multicast are not tagged broadcast. `.255` alone is insufficient.

New optional query fields:

- `tag`: one exact tag; retain records containing it.
- `exclude_tags`: comma-separated distinct tags; exclude ANY matching record.
  Empty values/elements, whitespace, unknown tags, duplicates and duplicate
  parameters return `400`; filters combine with AND before pagination.
  Including and excluding the same tag yields a valid empty result.

Synthetic record fragment, not actual traffic:

```json
{"protocol":6,"packet_length":40,"tcp_flags":17,"tcp_payload_length":0,"tags":["tcp_finish"]}
```

Synthetic broadcast record fragment:

```json
{"destination":"192.0.2.255","protocol":17,"tcp_flags":null,"tcp_payload_length":null,"tags":["ipv4_broadcast"]}
```

Example requests (encode query components through the client):

- Hide FIN/RST: `GET /api/v1/firewall/deny-log?exclude_tags=tcp_finish,tcp_reset`
- Hide both kinds: `GET /api/v1/firewall/deny-log?exclude_tags=tcp_finish,tcp_reset,ipv4_broadcast`
- Broadcast-only: `GET /api/v1/firewall/deny-log?tag=ipv4_broadcast`

Discord embeds now show hexadecimal flags or `unavailable` and tags or `none`.
There is no changed Discord endpoint/configuration or suppression setting:
identity remains exactly source/destination IP, destination port and protocol.
Deny-log filters do not suppress notifications or change recorded drops.

  Complete ownership is a no-op, not a revision on every boot.

## 2026-11-08-08 Discord notification category flags

- **Priority:** medium.

### Exact behavior and affected methods

Previously globally enabled alerts permitted every newly captured tuple.
Now two independent nonnull booleans default to false:
`discord.notify_broadcast` and `discord.notify_tcp_closures`.
Global `enabled` and usable capture remain prerequisites. A synthetic configuration
fragment with a placeholder reference, not a complete transaction:

```json
{"discord":{"enabled":true,"notify_broadcast":false,"notify_tcp_closures":false,"webhook_ref":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}}
```

- `notify_broadcast:true` permits records tagged `ipv4_broadcast`, including
  limited and live directed IPv4 broadcast; this is not a multicast switch.
- `notify_tcp_closures:true` permits `tcp_finish`, `tcp_reset` and
  `tcp_ack_only`: FIN, RST, and exactly ACK with known zero TCP payload bytes.
  Unknown payload length does not imply empty ACK. SYN/data-bearing ACK remains
  eligible unless separately tagged FIN/RST. Tags describe observed packets,
  not confirmed connection state or harmlessness.
- Records in both categories require both switches enabled. Other newly seen
  drops remain eligible. Filters run at enqueue and again at current-policy
  delivery; excluded queued records are discarded. Suppressed tuples remain
  permanently seen and never backfill after flag changes, repeat packets with
  different tags or restart. Logging/history, frontend visibility and verdicts
  are unchanged. Suppression increments neither delivery nor failure counters.
- `POST /api/v1/transactions`, `POST /api/v1/transactions/{id}/confirm`,
  `POST /api/v1/transactions/{id}/rollback` and
  `POST /api/v1/revisions/{revision}/restore`: existing confirmed full-candidate
  workflow, `transactions.write` and `discord.write`, plus other changed-area
  permissions. Flag-only changes need the same authorization. No new named
  CLI command; generic `set /discord/notify_broadcast true` and
  `set /discord/notify_tcp_closures true` use the same confirmed workflow.
- `GET /api/v1/state`, `GET /api/v1/revisions/latest` and
  `GET /api/v1/revisions/{revision}` (`state.read`): configuration includes both
  booleans; each defaults false when omitted and has no units or numeric limits.
  Wrong types/nulls/unknown fields reject `400`, semantic config errors `422`,
  auth/permissions `401`/`403`, stale/busy `409`, native apply failure `500`.
  Existing provisional `202` and confirm/rollback `200` remain unchanged.
- `GET /api/v1/services/discord/status` (`state.read`, no query/body) adds
  nonnull `notify_broadcast:boolean` and `notify_tcp_closures:boolean`.

  already accepted Discord messages cannot be withdrawn.
