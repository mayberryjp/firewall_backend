## 2026-10-18-01: Cross-origin networking API

- Priority: medium; optional frontend deployment/client improvement.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased; no release or commit assigned.
- Recommended bump: minor for cross-origin client support. Baseline unknown;
  aggregate Unreleased recommendation remains major.

### Contract and previous versus new behavior

Previously browser clients needed a same-origin API/proxy: no CORS headers or
unauthenticated preflights were provided. Now all `/api/v1/` GET and POST
endpoints in both auth modes allow any origin with
`Access-Control-Allow-Origin: *`, including errors. Authentication and endpoint
permissions are unchanged; device keys still need completed onboarding.

- `OPTIONS /api/v1/{path}` with `Origin` and
  `Access-Control-Request-Method: GET` or `POST` returns empty `204`, without a
  bearer key or cookie. Allowed request headers are `Authorization` and
  `Content-Type` (case-insensitive). Unsupported methods return `405`;
  unsupported requested headers return `400`.
- Non-preflight OPTIONS retains normal authentication/method handling.
- Exposed response headers: `Location`, `WWW-Authenticate`, `Retry-After`.
- Actual GET/POST requests retain bearer authentication, existing permissions,
  validation, JSON fields/types/defaults, and status/error shapes.
  Examples: `GET /api/v1/state` requires `state.read`; submitting
  `POST /api/v1/transactions` requires `transactions.write` and changed-area
  permissions. Preflight success does not establish endpoint availability.
- Example unsupported-header error (synthetic):
  `{"error":"unsupported cross-origin request header \"X-Custom\"","transaction":null}`.
- No `Access-Control-Allow-Credentials`; `/auth/` and website assets have no CORS.
  Key creation and sign-in remain on the firewall origin.

### Frontend tasks and deployment coordination

1. Optionally configure a trusted absolute API base for direct firewall access;
   relative `/api/v1` remains valid for same-origin deployment. Do not take
   target URLs from untrusted query parameters/imports.
2. For direct requests use `credentials: "omit"` and an explicit bearer
   Authorization header; JSON writes use Content-Type application/json.
   Do not add unsupported custom request headers.
3. Preserve existing handling of 401, 403, validation errors, and uncertain writes.
   Treat Location as an API-relative path resolved against the configured
   firewall origin, not the dashboard origin.
4. Continue opening the firewall's own website for account/key management.
   Do not attempt cross-origin cookie-based setup or key management.
5. Deploy the updated backend before enabling direct browser access. Use HTTPS
   with trusted certificates and operator-provided management reachability.
   Browser mixed-content and local/private-network restrictions still apply;
   no private-network CORS opt-in is advertised. Retain a trusted management
   proxy where the browser/environment requires it.

### Acceptance and validation

- Check browser preflight followed by authenticated state GET and transaction
  POST; read Location and confirm/rollback through the existing workflow.
- Check readable 401/403 errors, revoked keys, incomplete onboarding, unsupported
  methods/headers, and absence of cross-origin auth cookie access.
- Automated backend results and limitations: see the
  [daily journal](../journal/2026-10-18.md#cross-origin-networking-api).
- Browser-to-physical-firewall TLS and private-network acceptance remains pending;
  backend httptest checks alone do not prove browser deployment readiness.

## 2026-10-18-03: Direct HTTP onboarding on all IPv4 interfaces

- Priority: high; required deployment/documentation alignment.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased; no release or commit assigned.
- Recommended bump: major for default management exposure. Baseline unknown.
- Supersedes HTTPS-required/loopback-only deployment prerequisites in earlier
  handoffs, including item 2026-10-18-01. Other CORS/API-key contracts remain.

### Contract changes

- CLI and Alpine OpenRC defaults change from `127.0.0.1:8080` to
  `0.0.0.0:8080` over HTTP. Non-loopback HTTP no longer fails startup.
  Operators browse to `http://<appliance-LAN-IP>:8080/`; no SSH tunnel or
  certificate is required. This is IPv4 wildcard binding, not LAN discovery or
  LAN-only filtering; any WAN-facing IPv4 interface is also covered.
- TLS remains optional using both `-tls-cert` and `-tls-key`. Incomplete pairs
  still fail startup. Plain HTTP startup emits an explicit warning.
- HTTP methods/paths and request/response fields, types, nullability, defaults,
  units, validation, status codes, authentication and permissions are unchanged:
  `/auth/` still requires exact-origin JSON mutations and account sessions;
  `/api/v1/` still requires API keys and existing permissions after setup.
- HTTP cookies retain HttpOnly, SameSite=Strict, `/auth/` scope, and expiry, but
  are not Secure. HTTP passwords, cookies, and API keys are unencrypted.
- Persistence/native-network configuration is unchanged; installation still
  defaults to simulator mode and does not configure a LAN address or native
  boot recovery. No saved state reset is required.

### Required frontend/operator tasks and acceptance

1. Update setup instructions to direct browser access at the appliance address.
   Configure API base URLs using the real address, never `0.0.0.0` as a target.
2. Do not label the default connection secure. For HTTP key-copy failures retain
   the existing manual selection/copy fallback; clipboard APIs may be unavailable.
3. Keep account setup on the device origin, and preserve API-key authentication
   and CORS behavior. No client types or payload changes are needed.
4. An HTTPS dashboard can still be blocked from calling an HTTP appliance by
   mixed-content/private-network browser rules. Coordinate a suitable same-origin
   deployment/proxy or optional TLS; allow-all CORS does not bypass these rules.
5. Operators provide reachable Alpine networking and control management exposure.
   There is no automatic WAN restriction. Default package configuration is for
   newly installed configuration; inspect the active OpenRC configuration when
   installing over a locally customized package. No coordinated schema change.
6. Verify direct HTTP setup, key creation/completion, authenticated API reads,
   invalid-key 401, restart, and optional TLS. Test real-browser LAN connectivity,
   cookies, manual copy, and dashboard mixed-content behavior on target devices.

Backend startup, cookie/onboarding, authentication and full Go checks passed on
Windows; actual Alpine/OpenRC and browser/LAN checks remain pending. See the
[journal](../journal/2026-10-18.md#all-interface-http-management).

## 2026-10-18-04: Rust-only backend and native packaging cutover

- Priority: high; required client/runtime/deployment alignment.
- Status: Pending frontend review. Not sent, acknowledged or integration-verified.
- Backend availability: Unreleased working tree; no approved release or commit.
- Recommended bump: major for persisted schemas, CLI, packaging and runtime
  contracts. Baseline unknown; Cargo `0.0.0` is development metadata only.
- Supersedes Go implementation links, APK installation, single-hyphen CLI flags,
  external daemon supervision, process/PID states, and old persistence details
  in earlier handoffs. Their earlier validation remains historical, not evidence
  for the Rust implementation. API-key naming, wildcard API CORS and the default
  `http://<appliance-LAN-IP>:8080/` onboarding workflow remain.

### Methods, authorization and request/response changes

The [canonical spec](../../FRONTEND_SPEC.md#13-rust-request-and-persistence-contract)
defines current required JSON fields. Existing networking paths remain under
`/api/v1`, API-key authenticated with the existing scoped permissions. Account
sessions still authorize only `/auth/`; generated keys need completed onboarding.
Preflight is unauthenticated; actual API operations are not.

1. `POST /api/v1/transactions` and
   `POST /api/v1/revisions/{revision}/restore` require explicit confirmation
   timeout and structurally required fields. Unknown fields and nulls for
   nonoptional fields/collections return `400`; semantic invalidity returns
   `422`. Omitted defaultable collections are empty; optional WireGuard/VLAN/
   policy objects may be null. Omitted `allow_all_icmp` defaults true, explicit
   null is invalid. Build complete current configuration, not a partial patch.
   Submit/confirm/rollback/restore still require their existing transaction and
   affected-area permissions. Read/confirm/rollback transaction responses no
   longer contain `kernel_before`/`kernel_after`; kernel inspection/runtime owns
   that information.
2. `GET /api/v1/state` and observed resource reads can return `503` for native
   observation or failed enabled workers. They never report worker failure by
   silently flipping configured `enabled` flags. `GET /api/v1/runtime` remains a
   separate diagnostic read. All six bodyless
   `POST /api/v1/services/{softflowd,dhcp-relay,gateway-monitoring,ntp,syslog,vnstat}/reconcile`
   actions retain all-enabled-service permission checks and reject networking
   drift with `409`. Preserve drafts on errors; do not force-repair networking.
   The repair precheck excludes worker health but retains network/kernel
   ownership checks, allowing a failed worker to be restarted on healthy
   networking even when ordinary observed reads return `503`.
3. Service status/runtime rows describe native workers: `disabled`, `running`,
   `error`, `stopped`, and simulator `simulated`; no `pid`. Gateway `process_state`
   uses these states, while `sample_status` is disabled/simulated/stopped/
   warming_up/available/unavailable. Preserve nullable gateway measurements.
   `GET /api/v1/statistics/gateways` retains `{sample,monitors}`; its single-name
   endpoint retains `{sample,monitor}`.
4. `GET /api/v1/statistics/vnstat`, `/api/v1/statistics/vnstat/host`, and
   `/api/v1/statistics/vnstat/managed` require `state.read`. Base returns both
   databases; scoped paths only the selected database. Every query is `400`,
   unknown suffix `404`, non-GET `405`, and disabled/unready/failed/simulator
   measurement `503`. Counter values are decimal strings, not JSON numbers.
   Synthetic empty shape only, not a measured result:

   ```json
   {
     "schema":"netcontrol-services/counters/v1",
     "scope":"linux:11111111-1111-4111-8111-111111111111:4:4026533000",
     "scopes":{
       "managed":{
         "schema":"netcontrol-services/counters/v1",
         "scope":"managed",
         "interfaces":{},
         "history":[]
       }
     }
   }
   ```

   Treat top-level scope as opaque. Database interface records contain ifindex,
   boot/namespace identity, last/raw and cumulative counters, resets, last-seen
   timestamp and presence. History contains timestamp/interface/delta/reset;
   exact examples are in the [service field reference](../../crates/netcontrol-services/README.md#json-field-reference).
   Sampling/publication is every five seconds; first sample is only a baseline.
   Retains 10,000 per-interface sample records and cumulative totals, not calendar
   aggregates. Never sum overlapping interfaces/scopes or fabricate missing data.
5. NTP status adds optional signed `offset_ms`, bounded `requested_slew_ms`
   (+/-500), `uncorrected_offset_ms` (sample minus requested correction),
   nonnegative `delay_ms`, server, collected-at, `discipline: "slew_only"` and
   warming-up/available/unavailable sample status. Available is not synchronized;
   correction is asynchronous and large residuals need continued polling.
   No step, NTS, server consensus or remote-delivery acknowledgment is supplied.
6. Flow configuration `capture_filter` supports exactly empty/ip/ip6/tcp/udp/
   icmp/icmp6, not arbitrary BPF. Fragments/jumbograms are excluded; versions
   1/5 are IPv4, 9/IPFIX dual-family. V5 sampling maximum is 16383; V1 exposes
   `sampling_metadata:false` and sampled counters are not artificially expanded.
   Existing `softflowd` field/path names identify the native exporter contract,
   not an external executable.
   Unsupported filters and v5 sampling above 16383 fail central configuration
   validation with `422`, including simulator submissions, not a deferred worker
   failure. The current VLAN example uses an empty filter for both families.
7. `/auth/` paths and one-time `POST /auth/keys` response field `token` remain.
   Username is 1..64 UTF-8 bytes, setup password 12..72, key name 1..80;
   names trimmed/control-free, key names case-sensitive unique. Maximum 100 keys
   (`400`) and 32 sessions (`409`). Fixed 1800-second sessions use
   `netcontrol_session`, HttpOnly, Strict, `/auth/`, Secure only for actual TLS.
   Setup/login bodies maximum 4096 bytes; others 1 MiB; ten-second read timeout
   currently returns `400` body-too-large. Unknown/missing/null/trailing JSON
   returns `400`. A credential-write failure fails closed until restart:
   auth operations report service unavailable; API-key lookup returns
   `503 {"error":"credential store unavailable","transaction":null}`.
   Other failures retain documented `401/403/404/409/415/429/500` handling.

### Required frontend and deployment tasks

1. Update required-field/null validation, runtime state unions and rendering;
   remove PID controls and transaction kernel-original fields. Keep desired,
   draft, runtime and observation errors distinct.
2. Add traffic-history client types and error/empty/unavailable states; preserve
   decimal counters, reset boundaries, timestamps and opaque scope identity.
   Charting is optional; correct support/availability labels are required.
3. Restrict flow filter forms; add fragmentation/version/sampling limitations.
   Render NTP sample age and bounded-slew information without a synchronized badge.
4. Update appliance documentation to static Rust `.ncpkg` installation with
   `netcontrol-package`, not APK. CLI uses `--long-options`; external program,
   child-identity/runtime-directory and custom syslog-CA flags are removed.
   Backend log source is `<services-state-dir>/backend.log`, TLS uses system CA.
5. Deploy frontend/backend current contracts together; there is no old-contract
   compatibility window. Network state requires `netcontrol-rust-state-v1`;
   identity/scoped-auth files require `schema:1` (scoped root contains
   `credentials`, not a bare array). Unsupported data fails explicitly; preserve
   it for operator review, never delete/reset it or promise automatic import.
6. Operator supplies namespace, physical networking, reachability, forwarding,
   key files, capabilities, trust roots and exclusive host-service ownership.
   Installer neither creates a native firewall nor enables startup. Default
   remains simulator/HTTP wildcard; WAN exposure and plaintext credentials are
   unchanged warnings. OpenRC starts one Rust process, no protocol daemons.
7. Before distributing binaries, review GPL-3.0-or-later `rustables` obligations
   and project licensing. No project distribution license was assigned; package
   upload is disabled by default and needs explicit manual opt-in.
