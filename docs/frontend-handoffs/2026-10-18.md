# Frontend handoff: 2026-10-18

## 2026-10-18-01: Cross-origin networking API

- Priority: medium; optional frontend deployment/client improvement.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased; no release or commit assigned.
- Recommended bump: minor for cross-origin client support. Baseline unknown;
  aggregate Unreleased recommendation remains major.

### Contract and previous versus new behavior

Previously browser clients needed a same-origin API/proxy: no CORS headers or
unauthenticated preflights were provided. Now all `/api/v1/` GET and POST
endpoints in both auth modes allow any origin with
`Access-Control-Allow-Origin: *`, including errors. Authentication and endpoint
permissions are unchanged; device keys still need completed onboarding.

- `OPTIONS /api/v1/{path}` with `Origin` and
  `Access-Control-Request-Method: GET` or `POST` returns empty `204`, without a
  bearer key or cookie. Allowed request headers are `Authorization` and
  `Content-Type` (case-insensitive). Unsupported methods return `405`;
  unsupported requested headers return `400`.
- Non-preflight OPTIONS retains normal authentication/method handling.
- Exposed response headers: `Location`, `WWW-Authenticate`, `Retry-After`.
- Actual GET/POST requests retain bearer authentication, existing permissions,
  validation, JSON fields/types/defaults, and status/error shapes.
  Examples: `GET /api/v1/state` requires `state.read`; submitting
  `POST /api/v1/transactions` requires `transactions.write` and changed-area
  permissions. Preflight success does not establish endpoint availability.
- Example unsupported-header error (synthetic):
  `{"error":"unsupported cross-origin request header \"X-Custom\"","transaction":null}`.
- No `Access-Control-Allow-Credentials`; `/auth/` and website assets have no CORS.
  Key creation and sign-in remain on the firewall origin.

### Frontend tasks and deployment coordination

1. Optionally configure a trusted absolute API base for direct firewall access;
   relative `/api/v1` remains valid for same-origin deployment. Do not take
   target URLs from untrusted query parameters/imports.
2. For direct requests use `credentials: "omit"` and an explicit bearer
   Authorization header; JSON writes use Content-Type application/json.
   Do not add unsupported custom request headers.
3. Preserve existing handling of 401, 403, validation errors, and uncertain writes.
   Treat Location as an API-relative path resolved against the configured
   firewall origin, not the dashboard origin.
4. Continue opening the firewall's own website for account/key management.
   Do not attempt cross-origin cookie-based setup or key management.
5. Deploy the updated backend before enabling direct browser access. Use HTTPS
   with trusted certificates and operator-provided management reachability.
   Browser mixed-content and local/private-network restrictions still apply;
   no private-network CORS opt-in is advertised. Retain a trusted management
   proxy where the browser/environment requires it.

### Acceptance and validation

- Check browser preflight followed by authenticated state GET and transaction
  POST; read Location and confirm/rollback through the existing workflow.
- Check readable 401/403 errors, revoked keys, incomplete onboarding, unsupported
  methods/headers, and absence of cross-origin auth cookie access.
- Automated backend results and limitations: see the
  [daily journal](../journal/2026-10-18.md#cross-origin-networking-api).
- Browser-to-physical-firewall TLS and private-network acceptance remains pending;
  backend httptest checks alone do not prove browser deployment readiness.

## 2026-10-18-02: Name the firewall credential API key

- Priority: low; required frontend terminology alignment.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased; no release or commit assigned.
- Recommended bump: patch for wording correction; aggregate Unreleased remains
  major, with no release baseline assigned.
- The firewall access credential is **API key**, not bearer token or API token.
  The embedded setup website already uses API-key terminology.

### Contract and frontend tasks

- All existing GET/POST `/api/v1/` methods/paths, permissions, key validation,
  setup requirements, and CORS behavior are unchanged.
- Missing/invalid API keys still return `401`, but the error changes from
  `valid bearer credential required` to `valid API key required`:
  `{"error":"valid API key required","transaction":null}`.
  `WWW-Authenticate: Bearer` and the Authorization Bearer scheme are unchanged.
- `POST /auth/keys` still returns plaintext in the string field `token`;
  `token_sha256` remains the auth-file hash field. No schema/type/nullability,
  defaults, validation limits, units, persistence, or session changes.
- Label connection inputs, help, reconnect prompts, and user-visible errors
  **API key**. Handle authentication failures by status, not matching old prose.
- No coordinated deployment or new operator prerequisite is required: request
  headers and fields are unchanged. This is naming, not a new auth mechanism.
- Acceptance: missing/invalid API keys show API-key wording; valid keys still
  authenticate; device-account passwords/session cookies do not become API keys.
- Backend `go test ./internal/httpapi`: passed, including exact 401 wording and
  unchanged Bearer challenge. Broader dashboard rendering remains unverified.

## 2026-10-18-03: Direct HTTP onboarding on all IPv4 interfaces

- Priority: high; required deployment/documentation alignment.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased; no release or commit assigned.
- Recommended bump: major for default management exposure. Baseline unknown.
- Supersedes HTTPS-required/loopback-only deployment prerequisites in earlier
  handoffs, including item 2026-10-18-01. Other CORS/API-key contracts remain.

### Contract changes

- CLI and Alpine OpenRC defaults change from `127.0.0.1:8080` to
  `0.0.0.0:8080` over HTTP. Non-loopback HTTP no longer fails startup.
  Operators browse to `http://<appliance-LAN-IP>:8080/`; no SSH tunnel or
  certificate is required. This is IPv4 wildcard binding, not LAN discovery or
  LAN-only filtering; any WAN-facing IPv4 interface is also covered.
- TLS remains optional using both `-tls-cert` and `-tls-key`. Incomplete pairs
  still fail startup. Plain HTTP startup emits an explicit warning.
- HTTP methods/paths and request/response fields, types, nullability, defaults,
  units, validation, status codes, authentication and permissions are unchanged:
  `/auth/` still requires exact-origin JSON mutations and account sessions;
  `/api/v1/` still requires API keys and existing permissions after setup.
- HTTP cookies retain HttpOnly, SameSite=Strict, `/auth/` scope, and expiry, but
  are not Secure. HTTP passwords, cookies, and API keys are unencrypted.
- Persistence/native-network configuration is unchanged; installation still
  defaults to simulator mode and does not configure a LAN address or native
  boot recovery. No saved state reset is required.

### Required frontend/operator tasks and acceptance

1. Update setup instructions to direct browser access at the appliance address.
   Configure API base URLs using the real address, never `0.0.0.0` as a target.
2. Do not label the default connection secure. For HTTP key-copy failures retain
   the existing manual selection/copy fallback; clipboard APIs may be unavailable.
3. Keep account setup on the device origin, and preserve API-key authentication
   and CORS behavior. No client types or payload changes are needed.
4. An HTTPS dashboard can still be blocked from calling an HTTP appliance by
   mixed-content/private-network browser rules. Coordinate a suitable same-origin
   deployment/proxy or optional TLS; allow-all CORS does not bypass these rules.
5. Operators provide reachable Alpine networking and control management exposure.
   There is no automatic WAN restriction. Default package configuration is for
   newly installed configuration; inspect the active OpenRC configuration when
   installing over a locally customized package. No coordinated schema change.
6. Verify direct HTTP setup, key creation/completion, authenticated API reads,
   invalid-key 401, restart, and optional TLS. Test real-browser LAN connectivity,
   cookies, manual copy, and dashboard mixed-content behavior on target devices.

Backend startup, cookie/onboarding, authentication and full Go checks passed on
Windows; actual Alpine/OpenRC and browser/LAN checks remain pending. See the
[journal](../journal/2026-10-18.md#all-interface-http-management).
