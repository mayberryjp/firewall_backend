## 2026-10-29-01 Date Versions and Daily Release Checks

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
  Backend availability: unreleased build `2026.10.29.1`; not published/deployed.
  Breaking API/state contract, replacing SemVer release labels and numeric
  configuration counters with UTC `yyyy.mm.dd.iteration`. Supersedes version
  rules in [2026-10-24-07](2026-10-24.md#2026-10-24-07-signed-ubuntu-self-upgrade);
  it does not mark that item's remaining UI work complete.
- Affected methods/paths, with existing API-key authentication/permissions:
  - `GET /api/v1/state`, `GET /api/v1/runtime`, revision/transaction reads and
    DNS diagnostic responses: revision values are strings, not JSON numbers.
    Existing `state.read` and diagnostic `diagnostics.run` permissions remain.
  - `POST /api/v1/transactions`: required string `base_revision`; existing
    `transactions.write` and changed-resource permissions.
  - `POST /api/v1/transactions/{id}/confirm` and `/rollback`: unchanged actions/
    permissions; transaction response adds `committed_revision:string|null`.
  - `GET /api/v1/revisions`, `/latest`, `/{revision}`:
    `state.read`; string revision/detail/cursor fields. `before_revision` is an
    exclusive canonical date-version string; `limit` remains default 50, 1..100.
  - `POST /api/v1/revisions/{revision}/restore`: date-version path and required
    string base; existing state/transaction/changed-resource permissions.
  - `POST /api/v1/system/upgrade`: `system.upgrade`; date-version request instead
    of SemVer. `GET` on that path retains `state.read` and existing job envelope,
    whose version fields now use the same public date format.
  - MQTT configuration revision and software-version sensors now publish date
    strings. SSH show/restore arguments use exact date-version IDs.
- Format: real Gregorian UTC date, year 0001..9999, zero-padded month/day,
  unpadded iteration 1..4294967295. Compare numeric components, not strings
  (`.10 > .9`). No prerelease/build suffix or `v` in API values. Release tags
  are `v<version>`. Software/configuration version sequences are independent.
  Initialization starts at iteration 1; same-day confirmed commits increment;
  first commit on a later UTC day starts at 1. Rollback never advances IDs;
  confirmed restore creates a new revision. Never derive result revision as
  base plus one: read `committed_revision`, null before successful commit.
- New saved master-config object, read using `GET /api/v1/state` at
  `desired.software`, or `/api/v1/revisions/latest` at `config.software`
  independently of live network observation. Synthetic successful example:

  ```json
  {"version":"2026.10.29.1","repository":"example/netcontrol","latest_version":"2026.10.29.2","update_available":true,"last_checked_at":"2026-10-29T22:00:00Z","error":null}
  ```

  All fields are always serialized. `version:string`; repository/latest/time/
  error are `string|null`; availability is `boolean|null`. Time is RFC3339 UTC.
  Repository null means disabled. Configured pending has null result/time/error.
  Success sets latest/time and true only when newer than running. Failure sets
  time/error and clears latest/availability to null. A false result means a
  successful check found no newer release, not a failed/disabled check.
- Daemon-managed metadata is saved atomically without network apply or a new
  configuration revision. Startup resets it to the running build plus disabled/
  pending state. Pending confirmation and restores retain current software
  metadata. Historical snapshots may contain historical check data; current
  revision detail returns current metadata. No metadata-write or refresh route.
- Errors/status: existing envelopes and authorization remain. Numeric/missing/
  malformed revision inputs and invalid date-version upgrade requests: `400`.
  Valid stale base: `409`. Nondefault changed `config.software`: `422`; omit
  metadata from requests rather than echoing a potentially stale daily result.
  Clock regression/iteration exhaustion during confirm: explicit `503`, no
  commit and rollback remains available. Upgrade at/below either running or
  last successful version: `409`. Accepted upgrade remains `202`, not success.
  Daily HTTP/API/no-release/malformed-tag errors live in `software.error` and
  logs; availability becomes unknown, not a successful no-update result.
- Frontend tasks:
  - Replace uint64 revision adapters/unquoted-number serializers with ordinary
    validated JSON strings across client types, URLs, drafts, conflict checks,
    history pagination, result links and imports/exports.
  - Show read-only running version and distinct available/up-to-date/pending/
    disabled/error states. Show last-check time and explicit errors. Omit
    `software` from submitted drafts; do not provide edit controls for it.
  - Keep existing normal state polling; reads do not trigger checks. Do not
    add automatic installs or imply signed assets were verified by discovery.
  - Update upgrade forms, validation and confirmation messaging for date
    versions; preserve existing job-ID, outage and superseded-job handling.
- Deployment/operator coordination: backend/frontend must agree on string
  revision contracts. Current journal is `netcontrol-rust-state-v2`; numeric
  v1 journals are refused unchanged. Do not reset/delete journals or automate
  conversion; an existing appliance needs a separately reviewed operator plan
  and private backup before this breaking deployment. Keep UTC accurate.
  Daily checks require the existing trusted Ubuntu self-upgrade configuration/
  repository and optional operator-managed token, plus GitHub HTTPS access.
  No secrets or repository selection belong in frontend requests. No release
  was published or handoff sent/acknowledged by this work.
- Acceptance: numeric IDs/missing bases reject; valid stale IDs conflict;
  provisional changes/rollback do not advance IDs; commit/day boundary/restore/
  restart/history pagination preserve exact IDs. Validate null committed result
  before confirmation and correct assigned result after it. Verify available,
  current, older, disabled, pending and error displays; daily metadata changes
  must not invalidate configuration revisions or restore historical software.
  Backend automated results and outstanding real GitHub/appliance/browser
  checks are recorded in the [journal](../journal/2026-10-29.md#date-based-versions-and-daily-release-discovery).

## 2026-10-29-02 Sando One-Time Import Settings and State

- Priority: normal. Classification: **required**. Status: **Pending frontend review**.
  Backend availability: **unreleased**, embedded build `2026.10.30.1` (UTC date;
  this document uses the user's local date). Additive settings/permission contract;
  release labeling follows the approved calendar-version policy, not SemVer.
  No frontend implementation, delivery, publication or deployment is claimed.
- Summary: implement **Settings > Sando** (`/settings/sando`) with a Sando API
  base-URL form and **Import hosts** / **Import rules** preview-and-confirm
  actions. Data acquisition and mapping happen entirely in the browser. The
  backend stores only a URL and separate confirmed-import reports, not device
  objects, credentials, connection data, failed fetches or synchronization jobs.
- Exact Netcontrol HTTP surfaces, existing API-key authentication:
  - `GET /api/v1/revisions/latest`: read `config.sando`; `state.read`.
  - `GET /api/v1/state`: read `desired.sando`; `state.read`; the revision endpoint
    avoids depending on live network observation.
  - `POST /api/v1/transactions`: save the **full** current reviewed config with
    string `base_revision`; `transactions.write` and new `sando.write` for
    Sando changes, plus `firewall.write` for imported host/rule changes and
    permissions for any other changed section.
  - `POST /api/v1/transactions/{id}/confirm` and `/rollback`: existing workflow,
    `transactions.write` plus the same changed-resource permissions.
  - Existing revision detail/history reads and
    `POST /api/v1/revisions/{revision}/restore` also carry versioned Sando state;
    normal read/restore/changed-resource permissions apply.
  - No dedicated Sando HTTP endpoint, backend fetch/proxy or sync timer exists.
- Previous versus new: configuration previously had no Sando state. It now
  always serializes `sando`, defaulting to the following synthetic valid example:

  ```json
  {"api_url":"","hosts_import":null,"rules_import":null}
  ```

  A synthetic populated `sando` value:

  ```json
  {
    "api_url":"http://192.0.2.10:8044",
    "hosts_import":{
      "source_url":"http://192.0.2.10:8044",
      "import_count":1,
      "last_import_at":"2026-10-30T00:00:00Z",
      "status":"partial",
      "imported_count":2,
      "skipped_count":1
    },
    "rules_import":null
  }
  ```

- Fields and validation:
  - `api_url:string`: empty means unconfigured. Otherwise absolute lowercase
    HTTP(S) base URL, max 2048 UTF-8 bytes, host required; optional proxy path.
    No credentials, query, fragment, whitespace/control characters, backslashes
    or port zero. `source_url:string` uses identical nonempty validation.
    These are bases preceding `/api`, not endpoint URLs.
  - `hosts_import` / `rules_import`: nullable typed records, default null;
    all record fields required once present.
  - `import_count`: browser-reported positive unsigned 32-bit operation count
    for that kind; increment once per confirmed logical import.
    `imported_count` / `skipped_count`: unsigned 32-bit latest-import item counts.
    Ordinary JSON numbers, max 4294967295, not quoted counters.
  - `last_import_at:string`: browser-reported RFC3339 time, years 1970..9999,
    offsets accepted and output UTC. `status` is `succeeded` (zero skipped,
    including an empty successful import) or `partial` (both item counts
    positive). There is no persisted failed-attempt status.
  - Reports are client-reported versioned snapshots, not verified audit records.
    URL changes/clearing retain prior records; display their `source_url` even
    if it differs from current settings. Historical restore can restore earlier
    reports/counters. Host/rule edits and reports commit or roll back together.
- Status/error behavior: submit `202`, confirm/rollback `200`; standard
  `{error,transaction}` errors. Existing `401` unauthenticated, `403` permission,
  `400` invalid typed JSON/missing record fields/out-of-range unsigned integers/
  timestamp encoding/status, `422` URL or semantic outcome/range validation,
  `409` stale revision/active transaction/drift and existing backend/persistence
  failures remain. Preserve existing unknown-field ignored-pointer reporting.
  Browser fetch errors are local UI state, not backend import reports.
- Concrete frontend tasks:
  1. Add client types and defaults from the
     [canonical spec](../../FRONTEND_SPEC.md#sando-one-time-imports); save through
     the shared draft, preserving unrelated configuration and omitting
     daemon-managed `software` from writes. Expose `sando.write` in scoped
     credential/permission controls; retain separate firewall authorization.
  2. Add URL validation/form, independent host/rule latest-result panels and
     explicit staged versus confirmed labels; disable unconfigured/in-flight
     import actions. Show operation counts, latest item counts, time, status and
     source provenance. Do not increment on fetch/retry or record cancellation.
  3. Fetch Sando `GET /api/localhosts` for inventory, and
     `GET /api/ignorelist/ip/<encoded-IP>` for selected-host rule candidates.
     Preserve a configured reverse-proxy base path when appending routes.
     `/api/devices` is a category list, not inventory. Upstream returns raw
     database values: runtime-validate/normalize rather than assume rigid types.
     The browser may retain the complete device object for display, but only
     existing firewall host/rule fields are sent to Netcontrol.
  4. Review/deduplicate against current hosts/rules and existing canonical IP,
     unique ID/name and capacity constraints. Do not delete manual entries,
     choose permissive policy defaults or silently widen unsupported rules.
     **Sando ignorelist is alert suppression, not an authoritative allowlist.**
     Its host query matches both directions; only matching source entries can
     suggest that host's outbound rules. Skip/report ambiguous destinations,
     unsupported protocols/ports/wildcards and do not infer universal permits.
  5. Confirm reviewed edits with the corresponding staged import report in one
     full transaction. Until confirmation, show prior committed statistics.
     Handle uncertain writes via transaction recovery, not blind duplicate
     imports. Discard/failure/rollback leaves the previous report untouched.
- Deployment/operator prerequisites: grant the new permission to appropriate
  users/scoped credentials; existing permissions do not implicitly gain it
  except full-admin behavior. Browser must directly reach Sando with suitable
  CORS, local-network policy and compatible HTTP/HTTPS origin configuration;
  HTTPS dashboards can reject HTTP sources as mixed content. Do not send
  Netcontrol keys/cookies to Sando. No backend proxy, source credentials or
  automatic synchronization is included. Sando documents trusted-network use;
  do not expose an unauthenticated source publicly. No compatibility migration
  or deployment window is introduced.
- Acceptance: save/clear URL and display retained provenance; import/review/
  deduplicate hosts and rule suggestions; verify happy success and partial
  records, empty inventory without destructive deletion, cancelled/failed fetch,
  pending/confirmed/rollback/restart/restore state, read-only and missing-domain
  permission refusals, malformed fields/URLs and stale-revision recovery.
  Validate browser CORS/mixed-content and live Sando behavior separately.
  Backend validation and limitations are recorded in the
  [journal](../journal/2026-10-29.md#sando-one-time-import-state).

  (`src/routers/localhosts.py`, `src/database/localhosts.py`,

## 2026-10-29-03 Software Check Now

- Priority: normal. Classification: **required**. Status: **Pending frontend review**.
  Backend availability: unreleased build `2026.10.30.2`. Additive HTTP contract;
  calendar-version build label advanced once. Extends item `2026-10-29-01` and
  supersedes its absence of a manual refresh action, not its other versioning/
  metadata requirements. No delivery, release or frontend implementation claimed.
- Summary: add **Check now** beside software availability. Previously discovery
  could only run at startup or every 24 hours; now the user can request the
  existing trusted-repository discovery worker immediately. This never installs.
- Exact HTTP contract:
  - `POST /api/v1/system/upgrade/check`; existing API-key authentication and
    `system.upgrade`. No new permission. Empty body and no query parameters;
    `{}`, version, repository, URL, token and force inputs are rejected.
  - `202 {"status":"check_requested"}` and
    `Location: /api/v1/revisions/latest` acknowledge queuing, not completion.
  - Poll `GET /api/v1/revisions/latest` at `config.software`, or
    `GET /api/v1/state` at `desired.software`, with `state.read`.
    No response-field/type/nullability changes: timestamp/error/latest/
    availability use the existing metadata contract. No job ID or persisted
    checking flag is introduced.
  - Standard `{error,transaction}` errors: `401` missing/invalid authentication,
    `403` missing permission, `405` non-POST methods, `400` nonempty body/query,
    `409` a manual/scheduled check already queued or running, `503` unconfigured
    checking or unavailable worker. Authentication/authorization precede method/
    input handling. `409` does not queue another request.
- Semantics: one shared worker/guard prevents overlapping checks. The saved
  previous result remains until a new result is persisted. Source/network/API
  failures after acceptance update `software.error` and `last_checked_at`,
  clearing latest/availability to null; never display them as up to date.
  Metadata updates do not allocate revisions, apply networking, invalidate drafts
  or change pending configuration transactions. Manual checks do not reset the
  daily schedule. Shutdown cancels queued/in-flight requests without replacing
  the last saved result. No assets, signatures or installation are processed.
- Frontend tasks:
  1. Add an empty-body POST client method and a permission-aware **Check now**
     button. Require configured checking and `system.upgrade`; use `state.read`
     for result polling. Disable repeat clicks while locally awaiting results.
  2. Capture the prior `last_checked_at`, show prior data as checking/stale and
     use normal polling to observe a changed completion timestamp and success/
     error fields. Handle `409` as already checking rather than resubmitting.
  3. Use a bounded wait longer than the 30-second network timeout plus scheduling/
     persistence overhead. A timeout/restart with no changed result is uncertain,
     not success; surface it and allow an explicit retry. Keep `401`, `403`,
     disabled/unavailable and discovery errors distinct.
  4. Do not create an install job, confirmation or automatic upgrade from a
     check. Existing explicit version selection/signed-install workflow remains.
- Deployment/operator coordination: requires the new backend endpoint and
  existing trusted `--upgrade-config` repository/signing configuration, optional
  server-managed token and outbound GitHub HTTPS. No browser-supplied repository/
  credentials, reset/migration or compatibility window. Existing `system.upgrade`
  credentials can trigger checks without new grants.
- Acceptance: authorized POST returns `202`; read-only/anonymous requests fail;
  empty-body validation/method/query refusals match above; repeated clicks and
  a scheduled in-flight check give `409`; disabled/closed worker gives `503`.
  Verify success/error rendering, unchanged revision/draft/pending transaction,
  unchanged daily schedule, shutdown cancellation and local timeout recovery.
  Automated worker/HTTP checks and remaining live-browser/GitHub limitations
  are in the [journal](../journal/2026-10-29.md#manual-software-release-check).

## 2026-10-29-04 Offline Date-Revision Recovery

- Priority: high. Classification: **required deployment coordination**.
  Status: **Pending frontend review**. Backend availability: unreleased build
  `2026.10.30.3`; operator recovery fix under the approved calendar-version policy.
- Summary: after a reported numeric-v1 startup failure, the user requested a fix
  without requiring old configurations to be discarded. The explicit offline
  converter now supports `--date-revisions`, preserving configuration and history
  with private backups. This supersedes item `2026-10-29-01`'s lack of an
  available numeric-to-date conversion tool, not its current API requirements.
- HTTP contract: no methods, routes, permissions, request/response fields,
  limits or HTTP status codes change. Existing API-key authentication and
  date-string revision contracts remain. The daemon still refuses v1 startup;
  no automatic API/startup migration or numeric-revision alias is added.
- Persisted state: explicitly convert `netcontrol-rust-state-v1` to v2 offline.
  Numeric 0 maps to initialization UTC date iteration 1; each committed revision
  follows the existing next-date allocator using its saved UTC commit date.
  Transaction base/result/restore references are rewritten consistently.
  IDs, actors, timestamps, configuration snapshots and rollback history remain.
  Empty retired policy fields may be removed; nonempty rules/invalid state
  block conversion. The private manifest includes the exact old/new mapping.
- Frontend tasks: ensure item `2026-10-29-01` string-revision support is ready;
  after operator conversion reconnect/refetch state and history, discard cached
  numeric revision IDs/cursors and explicitly review stale drafts rather than
  posting a numeric/stale base. Do not offer state deletion/reset as recovery.
  No new network client method, import UI or persisted-state upload is required.
- Deployment/operator coordination: use a local console or independent OS SSH,
  build the converter before stopping, preview and explicitly apply with a new
  private backup, then install/start the matching new binary while the old
  service remains stopped. Refuse locked/pending/corrupt/incomplete state and
  recover pending work with the previous binary first. On interrupted conversion
  or deployment failure, keep the service stopped and restore **all** manifest
  originals before returning to the previous binary; binary-only rollback is
  insufficient. Do not share journals, backup contents or runtime credentials.
- Acceptance: preview is non-mutating; valid empty/history/native fixtures load
  under the new contract; dates, restore/rollback references and exact originals
  survive. Invalid history/clock order, unknown/mixed fields, active/locked
  journals and nonempty retired policy rules must fail without source writes.
  Verify actual appliance startup, connectivity and frontend state reload
  separately; synthetic tests do not establish deployment success.
