## 2026-10-29-01 Date Versions and Daily Release Checks

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
  Backend availability: unreleased build `2026.10.29.1`; not published/deployed.
  Breaking API/state contract, replacing SemVer release labels and numeric
  configuration counters with UTC `yyyy.mm.dd.iteration`. Supersedes version
  rules in [2026-10-24-07](2026-10-24.md#2026-10-24-07-signed-ubuntu-self-upgrade);
  it does not mark that item's remaining UI work complete.
- Affected methods/paths, with existing API-key authentication/permissions:
  - `GET /api/v1/state`, `GET /api/v1/runtime`, revision/transaction reads and
    DNS diagnostic responses: revision values are strings, not JSON numbers.
    Existing `state.read` and diagnostic `diagnostics.run` permissions remain.
  - `POST /api/v1/transactions`: required string `base_revision`; existing
    `transactions.write` and changed-resource permissions.
  - `POST /api/v1/transactions/{id}/confirm` and `/rollback`: unchanged actions/
    permissions; transaction response adds `committed_revision:string|null`.
  - `GET /api/v1/revisions`, `/latest`, `/{revision}`:
    `state.read`; string revision/detail/cursor fields. `before_revision` is an
    exclusive canonical date-version string; `limit` remains default 50, 1..100.
  - `POST /api/v1/revisions/{revision}/restore`: date-version path and required
    string base; existing state/transaction/changed-resource permissions.
  - `POST /api/v1/system/upgrade`: `system.upgrade`; date-version request instead
    of SemVer. `GET` on that path retains `state.read` and existing job envelope,
    whose version fields now use the same public date format.
  - MQTT configuration revision and software-version sensors now publish date
    strings. SSH show/restore arguments use exact date-version IDs.
- Format: real Gregorian UTC date, year 0001..9999, zero-padded month/day,
  unpadded iteration 1..4294967295. Compare numeric components, not strings
  (`.10 > .9`). No prerelease/build suffix or `v` in API values. Release tags
  are `v<version>`. Software/configuration version sequences are independent.
  Initialization starts at iteration 1; same-day confirmed commits increment;
  first commit on a later UTC day starts at 1. Rollback never advances IDs;
  confirmed restore creates a new revision. Never derive result revision as
  base plus one: read `committed_revision`, null before successful commit.
- New saved master-config object, read using `GET /api/v1/state` at
  `desired.software`, or `/api/v1/revisions/latest` at `config.software`
  independently of live network observation. Synthetic successful example:

  ```json
  {"version":"2026.10.29.1","repository":"example/netcontrol","latest_version":"2026.10.29.2","update_available":true,"last_checked_at":"2026-10-29T22:00:00Z","error":null}
  ```

  All fields are always serialized. `version:string`; repository/latest/time/
  error are `string|null`; availability is `boolean|null`. Time is RFC3339 UTC.
  Repository null means disabled. Configured pending has null result/time/error.
  Success sets latest/time and true only when newer than running. Failure sets
  time/error and clears latest/availability to null. A false result means a
  successful check found no newer release, not a failed/disabled check.
- Daemon-managed metadata is saved atomically without network apply or a new
  configuration revision. Startup resets it to the running build plus disabled/
  pending state. Pending confirmation and restores retain current software
  metadata. Historical snapshots may contain historical check data; current
  revision detail returns current metadata. No metadata-write or refresh route.
- Errors/status: existing envelopes and authorization remain. Numeric/missing/
  malformed revision inputs and invalid date-version upgrade requests: `400`.
  Valid stale base: `409`. Nondefault changed `config.software`: `422`; omit
  metadata from requests rather than echoing a potentially stale daily result.
  Clock regression/iteration exhaustion during confirm: explicit `503`, no
  commit and rollback remains available. Upgrade at/below either running or
  last successful version: `409`. Accepted upgrade remains `202`, not success.
  Daily HTTP/API/no-release/malformed-tag errors live in `software.error` and
  logs; availability becomes unknown, not a successful no-update result.
- Frontend tasks:
  - Replace uint64 revision adapters/unquoted-number serializers with ordinary
    validated JSON strings across client types, URLs, drafts, conflict checks,
    history pagination, result links and imports/exports.
  - Show read-only running version and distinct available/up-to-date/pending/
    disabled/error states. Show last-check time and explicit errors. Omit
    `software` from submitted drafts; do not provide edit controls for it.
  - Keep existing normal state polling; reads do not trigger checks. Do not
    add automatic installs or imply signed assets were verified by discovery.
  - Update upgrade forms, validation and confirmation messaging for date
    versions; preserve existing job-ID, outage and superseded-job handling.
- Deployment/operator coordination: backend/frontend must agree on string
  revision contracts. Current journal is `netcontrol-rust-state-v2`; numeric
  v1 journals are refused unchanged. Do not reset/delete journals or automate
  conversion; an existing appliance needs a separately reviewed operator plan
  and private backup before this breaking deployment. Keep UTC accurate.
  Daily checks require the existing trusted Ubuntu self-upgrade configuration/
  repository and optional operator-managed token, plus GitHub HTTPS access.
  No secrets or repository selection belong in frontend requests. No release
  was published or handoff sent/acknowledged by this work.
- Acceptance: numeric IDs/missing bases reject; valid stale IDs conflict;
  provisional changes/rollback do not advance IDs; commit/day boundary/restore/
  restart/history pagination preserve exact IDs. Validate null committed result
  before confirmation and correct assigned result after it. Verify available,
  current, older, disabled, pending and error displays; daily metadata changes
  must not invalidate configuration revisions or restore historical software.
  Backend automated results and outstanding real GitHub/appliance/browser
  checks are recorded in the [journal](../journal/2026-10-29.md#date-based-versions-and-daily-release-discovery).

  ```json
  {"api_url":"","hosts_import":null,"rules_import":null}
  ```

  A synthetic populated `sando` value:

  ```json
  {
    "api_url":"http://192.0.2.10:8044",
    "hosts_import":{
      "source_url":"http://192.0.2.10:8044",
      "import_count":1,
      "last_import_at":"2026-10-30T00:00:00Z",

      "imported_count":2,
      "skipped_count":1
    },
    "rules_import":null
  }
  ```

- Fields and validation:
  - `api_url:string`: empty means unconfigured. Otherwise absolute lowercase
    HTTP(S) base URL, max 2048 UTF-8 bytes, host required; optional proxy path.
    No credentials, query, fragment, whitespace/control characters, backslashes
    or port zero. `source_url:string` uses identical nonempty validation.
    These are bases preceding `/api`, not endpoint URLs.
  - `hosts_import` / `rules_import`: nullable typed records, default null;
    all record fields required once present.
  - `import_count`: browser-reported positive unsigned 32-bit operation count
    for that kind; increment once per confirmed logical import.
    `imported_count` / `skipped_count`: unsigned 32-bit latest-import item counts.
    Ordinary JSON numbers, max 4294967295, not quoted counters.
  - `last_import_at:string`: browser-reported RFC3339 time, years 1970..9999,
    offsets accepted and output UTC. `status` is `succeeded` (zero skipped,
    including an empty successful import) or `partial` (both item counts
    positive). There is no persisted failed-attempt status.
  - Reports are client-reported versioned snapshots, not verified audit records.
    URL changes/clearing retain prior records; display their `source_url` even
    if it differs from current settings. Historical restore can restore earlier
    reports/counters. Host/rule edits and reports commit or roll back together.
- Status/error behavior: submit `202`, confirm/rollback `200`; standard
  `{error,transaction}` errors. Existing `401` unauthenticated, `403` permission,
  `400` invalid typed JSON/missing record fields/out-of-range unsigned integers/
  timestamp encoding/status, `422` URL or semantic outcome/range validation,
  `409` stale revision/active transaction/drift and existing backend/persistence
  failures remain. Preserve existing unknown-field ignored-pointer reporting.
  Browser fetch errors are local UI state, not backend import reports.

  3. Fetch Sando `GET /api/localhosts` for inventory, and

     `/api/devices` is a category list, not inventory. Upstream returns raw

     The browser may retain the complete device object for display, but only

  4. Review/deduplicate against current hosts/rules and existing canonical IP,

  5. Confirm reviewed edits with the corresponding staged import report in one
