## 2026-11-15-03 Pooled DNS and passive RTT percentiles

- Priority: normal; classification: required client/rendering work.
- Status: Pending frontend review. Backend availability: unreleased; not sent,
  deployed or UI-verified. Additive summary fields/populated nullable timings
  and telemetry storage change; next automatic calendar version.
- `GET /api/v1/statistics/host-experience/summary`, authenticated `state.read`.
  No body; address/interface/limit/cursor, default 25/max 256, status/error
  contract, read limits and scoring are unchanged. Latest/history JSON unchanged.
- Previously hourly RTT/DNS percentiles were always null. Now nullable numeric
  `tcp.rtt_remote.p50_ms`/`p95_ms`, `tcp.rtt_host.p50_ms`/`p95_ms`,
  `dns.response_time_p50_ms`/`response_time_p95_ms` are pooled 32-bin histogram
  estimates in milliseconds. Never label them exact raw-observation quantiles.
- Each RTT object and `dns` gains `timing_observed_slots`/`timing_missing_slots`
  (numbers 0..360), `timing_samples` (decimal string), and
  `timing_coverage_complete` (boolean). These count available/partial source
  slots, not the whole hour. Complete means at least one retained eligible
  histogram and no eligible missing histograms; capture/source coverage may
  still be incomplete. A valid empty distribution counts as observed.
- DNS also gains nullable numeric `min_ms`/`max_ms`, decimal-string
  `variation_pairs`; its existing nullable numeric
  `response_time_variation_mean_ms` uses actual retained pair sums/counts.
  RTT scalar counts/extrema/variation still include usable older rows, so use
  `timing_samples` to label percentile evidence, not RTT `samples`.
- RTT `percentile_unavailable_reason` / DNS `timing_unavailable_reason` changes
  from fixed strings to nullable strings: null when timings exist,
  `per_bucket_distributions_not_retained` when no eligible histogram exists,
  `no_timing_observations` when eligible histograms exist but are empty.
  Null percentiles remain unknown, never zero; no response timing is promised
  for encrypted/unobserved DNS or traffic without usable TCP ACK evidence.

## 2026-11-15-04 NTP server-reported time

- Priority: normal; classification: optional NTP diagnostic rendering.
- Status: Pending frontend review. Backend availability: unreleased; not sent,
  deployed or UI-verified. Additive runtime field; next automatic calendar version.
- Affected reads: `GET /api/v1/services/ntp/status` (`instances` NTP rows) and
  `GET /api/v1/state` (`runtime.appliance_services` NTP rows), authenticated
  `state.read`, no body. The same row appears in other runtime envelopes.
  NTP configuration GET/draft fields and write permissions are unchanged.
- Previously the runtime row exposed the selected server, offset/delay/slew
  measurements and firewall-clock `collected_at`, but no server-reported time.
  Now `server_time?: Timestamp` is an optional RFC3339 UTC string decoded from
  that selected response's transmit timestamp, with fractional seconds truncated
  to nanoseconds. It is absent before an accepted sample, not nullable or defaulted
  to local time. No new validation limit or HTTP status/error change.
- This is the server's time when it transmitted that sampled reply, not its
  current clock at each HTTP read. `collected_at` remains firewall-clock sample
  publication time and may be incorrect. Era decoding still uses the local date
  as reference; the focused regression covers a three-day local clock error.
  No authenticated-time/server-consensus guarantee or change to slew-only policy.
- Failed polling preserves the previous `server_time` alongside other sample
  fields with `sample_status:"unavailable"` and an error; recovery replaces it
  on the next accepted sample. Do not display stale data as current/synchronized.

## 2026-11-15-05 Immediate full NTP clock correction

- Priority: high; classification: required status/client/MQTT updates.
- Status: Pending frontend review. Backend availability: unreleased, not
  deployed or UI-verified. Breaking runtime and operational contract; next
  automatic calendar version, no manual bump. Supersedes slew-only descriptions
  in earlier NTP handoffs, including item 2026-11-15-04; the sampled
  `server_time` diagnostic itself is preserved.
- Affected reads: `GET /api/v1/services/ntp/status` and
  `GET /api/v1/state`, authenticated `state.read`, no body. The NTP row also
  appears in existing runtime response envelopes. Configuration
  `GET /api/v1/services/ntp`, full-configuration transactions and
  `POST /api/v1/services/ntp/reconcile` keep their paths, existing permissions,
  request shapes and HTTP status behavior. No new settings or persisted schema.
- Previous behavior: 64-second polling, corrections limited to +/-500 ms and
  applied gradually. New behavior: immediate startup polling, then polling every
  900 seconds after each round, with unchanged three-second per-server deadlines.
  Lowest-delay valid sample immediately sets the whole host clock forward or
  backward with no correction-size cap. The target compensates estimated network
  delay and monotonic elapsed time while querying the remaining servers.
- Remove optional numeric `requested_slew_ms`, `uncorrected_offset_ms`;
  replace with optional signed numeric `requested_step_ms` in milliseconds.
  Change `discipline` literal from `"slew_only"` to `"step"`.
  `requested_step_ms` equals the full measured `offset_ms`, published only
  after successful Linux clock setting. `offset_ms` is the pre-step offset,
  not residual error. Fields are absent before a successful sample; no null
  defaults or zero-filled failures. `server_time`, `delay_ms`, `collected_at`
  and sample-status/stale-data semantics remain.

- MQTT service discovery removes the requested-slew/uncorrected-offset gauges,

- Frontend tasks: update client types and discipline rendering; replace
  "Requested slew" with "Requested clock step", remove "Uncorrected offset",
  label offset as pre-correction, and never infer failed synchronization from a
  large historical pre-step offset. Display sample timestamps/freshness separately.
  Explain immediate forward/backward clock jumps and fifteen-minute sampling.
  Preserve row-local unavailable/error warnings without blocking configuration.
- Deploy matching backend/frontend status rendering together; no legacy aliases
  or compatibility window. Existing CAP_SYS_TIME, explicit host-clock ownership
  and trusted configured servers remain prerequisites. No NTS or server-consensus

- Acceptance: synthetic +/-three-day errors request the full immediate target,

## 2026-11-15-06 Operation after backward clock correction

- Priority: high; classification: required revision/error-handling review.
- Status: Pending frontend review. Backend availability: unreleased, not sent,
  deployed or UI-verified. Fix to revision/error and reporting contracts; next
  automatic calendar version.
- Affected primary operations: `POST /api/v1/transactions`,
  `POST /api/v1/revisions/{revision}/restore` and
  `POST /api/v1/transactions/{id}/confirm`; existing `transactions.write` plus
  affected configuration permissions remain required. All revision-allocating
  paths, including VLAN adoption/internal ownership commits, share this rule.
  `GET /api/v1/state`, revisions and transaction reads expose the same field
  types. No new request/response fields, auth, limits or persisted schema.
- Previously a UTC date before the saved revision caused `503` before new
  changes/confirmation. Now use the saved revision date as a nondecreasing
  high-water mark and increment its iteration; actual `committed_at` remains
  corrected UTC. Submission/restore can return normal `202`, confirmation `200`.
  When UTC advances beyond that date, its first confirmation starts iteration 1.
  Preserve `400` validation, `403` permission, `409` conflict/expiry and `503`
  genuine backend/iteration-exhaustion errors. No retries are implied.

- Frontend tasks: treat revision IDs as opaque server-issued conflict tokens
  with numeric-component ordering; do not require their date to equal the
  current/commit date. Remove any editing lock inferred solely from a future
  revision. Keep confirmation deadlines/server state authoritative, preserve
  draft conflict handling and real errors, and do not manually re-date archives.
  Historical commit times may go backward; sort revisions by IDs, not timestamps.
- Deployment: backend first, no state rewrite/reset/backfill/migration. Preserve
  corrected host/RTC time and private configuration history. Restart/restore
  validators use the same high-water rule. Old binaries are not promised to read
  archives containing newer backdated-commit/high-water revision combinations.
  Software build versions retain strict full-Git-history clock checks.
- Daily traffic reporting: a future `last_report_date` no longer postpones the
  corrected date's local 23:59 attempt. Same-date polling/restart stays suppressed;
  re-entering a prior date after another clock change may repeat an export.
  Collector deduplication remains name/interface/date. Accounting and stored
  history are not re-dated/reset. No new report fields.
- Hourly host experience retains its explicit temporary clock-discontinuity
  protection; do not present old future-dated evidence as current or reset its
  database. Normal new observations resume; full-hour summaries recover after
  the discontinuity window, not after the old calendar date catches up.
- Acceptance: a three-day future revision can be reopened, restored, edited,
  confirmed and rolled back at corrected UTC; every new ID increases, old commit
  timestamps remain intact, cross-day corrections do not extend monotonic
  confirmation budgets, and a genuinely newer date resets iteration to 1.
  Daily exports resume at corrected 23:59 and remain suppressed after same-date
  restart with totals/history preserved.
- Validation: 4 focused core clock tests, 5 services clock tests and 4 existing
  software build-version tests passed; one selected privileged NTP fixture ignored.
  Scoped formatting passed. No full workspace suites/Clippy/build, Linux native
