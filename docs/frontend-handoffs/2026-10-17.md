## 2026-10-17-01: Allow all IPv4 ICMP

- Priority: high; required frontend update.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased working-tree implementation; no release or
  commit assigned.
- Compatibility: recommended major bump, baseline unknown. The enabled default
  can override existing forwarding ICMP drops, including on upgrade.

### API contract

- New field: `config.firewall.allow_all_icmp`, boolean, default `true` when
  omitted or `null`; normalized output is an explicit boolean. No units or
  numeric limits apply. Non-boolean, non-null input is rejected with HTTP 400.
- Write through `POST /api/v1/transactions` with a full configuration package;
  toggling requires `transactions.write` and `firewall.write`.
- Confirm/rollback through `POST /api/v1/transactions/{id}/confirm` and
  `POST /api/v1/transactions/{id}/rollback`, with the same change permissions.
- Read through `GET /api/v1/firewall/rules`, `GET /api/v1/state`,
  `GET /api/v1/revisions/{revision}`, and
  `GET /api/v1/transactions/{id}` detail/candidate snapshots.
  Reads require `state.read`.
- `GET /api/v1/firewall/hosts` and
  `GET /api/v1/firewall/interface-policies` do not synthesize implicit entries.
- Revision restoration uses the existing
  `POST /api/v1/revisions/{revision}/restore` workflow and preserves explicit
  values; it additionally requires `state.read`. Older snapshots without the
  flag now mean enabled.
- Existing statuses/errors otherwise remain: submission 202, confirm/rollback
  200, missing change permissions 403, stale base/managed drift 409, invalid
  configuration 422, and runtime/observation errors 500.

Example `firewall` fragment (not a complete transaction):

```json
{
  "allow_all_icmp": false,
  "policy": "drop",
  "rules": [],
  "nat": {"masquerade": []}
}
```

Previously, forwarding rules/defaults alone could block new IPv4 ICMP. Now an
enabled exception accepts IPv4 protocol 1 before legacy or host/interface rules.
Input and output get owned accept-default chains with the same exception.
Every namespace interface is covered, including future interfaces; all ICMP
types/codes match. ICMPv6 is unchanged. Other nftables tables can still drop it.
Disabling removes exceptions, not a blanket block.

### Required frontend tasks

1. Add the boolean to client configuration types, parsers, draft state, and full
   payload serialization. Use nullish defaults, never `value || true`.
2. Add an accessible global toggle in both firewall policy modes; permission-gate
   editing, include it in review diffs, and preserve explicit `false`.
3. Explain protocol 1 versus ICMPv6, all-interface input/output/forward scope,
   precedence over drops, and removal-not-block semantics.
4. Do not render the implicit exception as editable interface-policy rows.
5. Warn about migration: omitted values and historical snapshots enable ICMP.
   Display startup/observation failures rather than claiming successful apply.

### Rollout and acceptance

- Deploy frontend support before operators use clients that might omit the flag.
  There is no automatic compatibility window or feature gate beyond this flag.
- Backend restart migrates older saved configurations automatically, even when
  they previously blocked ICMP. Explicit `false` is preserved; pending
  transaction candidates control live behavior. Migration refuses unrelated
  firewall drift and remains retryable on failure.
- Existing Linux namespace/nftables privileges remain necessary; no new
  forwarding sysctls, routes, NAT, or external firewall rules are provisioned.
- Verify initial true, explicit false, omitted/null defaulting, confirmation,
  rollback, restart, revision reads/restores, and permission errors.
- Verify toggle/diff accessibility and preservation of false across unrelated
  edits. Check no synthetic host/interface rows appear.
- Linux integration must verify protocol 1 acceptance in input/output/forward
  before catch-all drops, on all interfaces; protocol 58 and unrelated traffic
  must remain governed by existing behavior. Other tables may still block.
- Backend validation results and environment limitations are tracked in the
  [daily journal](../journal/2026-10-17.md).

## 2026-10-17-02: Required WAN/LAN interface roles

- Priority: high; required frontend update.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased working-tree implementation; no release
  assigned. Recommended major bump for the required schema field; baseline unknown.
- Greenfield policy: implement the new contract directly. Do not add migrations,
  default roles, fallback values, or a dual old/new client contract.

### API contract

Each entry in `config.interfaces` requires `role`, a lowercase string enum
`"wan"` or `"lan"`, with no default and no null/empty value. Applies to dummy,
VLAN, and WireGuard alike. Multiple interfaces can share either role.
Example managed interface fragment:

```json
{
  "name": "edge0",
  "kind": "dummy",
  "role": "wan",
  "mtu": 1500,
  "up": true,
  "addresses": ["192.0.2.2/24"]
}
```

- Write: `POST /api/v1/transactions` using a complete configuration package.
  Role-only edits require `transactions.write` and `interfaces.write`.
- Confirm/rollback:
  `POST /api/v1/transactions/{id}/confirm` and
  `POST /api/v1/transactions/{id}/rollback`, with the same change permissions.
- Read: `GET /api/v1/interfaces`, `GET /api/v1/vlans`,
  `GET /api/v1/wireguard`, `GET /api/v1/state`,
  `GET /api/v1/transactions/{id}`, and `GET /api/v1/revisions/{revision}`.
  Reads require `state.read` and preserve the role.
- Restore: `POST /api/v1/revisions/{revision}/restore`; requires `state.read`,
  `transactions.write`, and permissions for the changes, including
  `interfaces.write` when roles change.
- Successful submission is 202; confirmation/rollback is 200. Missing role,
  null/empty, uppercase, or unknown role values return 422. Non-string/non-null
  JSON types return 400. Existing permission/conflict/runtime errors remain.
- Saved configurations and transaction snapshots must also contain valid
  roles; loading fails explicitly otherwise. No automatic conversion is added.

Previously there was no classification field. The new field is descriptive
configuration metadata only: it does not generate firewall, routing, NAT, or
kernel link changes. Linux observed roles are sourced from expected configuration,
not independently detected. Read-only adopted parents are not managed interfaces
and remain outside this role schema.

### Required frontend tasks and acceptance

1. Add required `role: "wan" | "lan"` to managed-interface types, draft state,
   parsers, serializers, and create/edit forms. Display WAN/LAN labels.
2. Require explicit selection for every managed interface; block incomplete
   submissions. No name-based or inherited role, truthy default, or migration.
3. Add a role column/filter and highlight role changes in review diffs.
   Gate editing with `interfaces.write` and transaction permission.
4. Preserve roles during unrelated edits, confirmation, rollback, restart,
   historical reads/restores, and all interface-kind views.
5. Explain metadata-only semantics; do not auto-configure NAT/firewall/routing,
   claim independent role detection, or edit protected parents.
6. Verify 422 for missing/invalid roles, 400 for wrong JSON types, and 403 for
   unauthorized role edits. Test WAN-to-LAN edits independent of interface name.

Coordinate frontend/backend deployment around this single current contract;
there is no compatibility window or feature gate. Standard Linux namespace
privileges still apply; no additional infrastructure is required.

Backend targeted tests, full Windows suite, vet, and Windows/Linux builds pass.
Linux tests compile but native namespace execution remains pending.

## 2026-10-17-03: Per-interface DHCPv4 relay

- Priority: high; required frontend update.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased working-tree implementation.
- Feature-level release recommendation: minor for new functionality; the full
  Unreleased set still contains earlier major contract changes. No version assigned.
- User selected configuration plus a managed operator-installed relay daemon,
  IPv4 only. Implement the current greenfield contract without migrations.

### Configuration contract

Each managed interface now includes:

```json
{
  "dhcp_relay": {
    "enabled": true,
    "servers": ["198.51.100.10", "198.51.100.20"]
  }
}
```

This is a fragment, not a complete transaction. The object defaults to
`enabled: false`, `servers: []`; normalized reads emit it explicitly.
Valid server entries persist when toggled off. Enabled relay requires:

- One or more distinct canonical numeric unicast IPv4 server addresses.
  Entries remain validated when disabled. No hostnames, ports, prefixes, IPv6,
  unspecified, loopback, link-local, multicast, or broadcast addresses.
- An administratively up dummy/VLAN interface with at least one unicast IPv4
  address. WireGuard cannot be a relay client-facing link.
- A unique selected local relay address among enabled interfaces. Selection is
  the first IPv4 address in lexicographically sorted canonical address prefixes.
  Display this address/subnet rather than silently choosing another.

Server ordering is normalized; every server receives requests (not ordered
failover). WAN/LAN role does not choose upstream links or limit relay enablement.
This does not enable a DHCP server, DHCPv6, DNS, or automatic firewall/NAT/routes.

### API and permissions

- Write settings through `POST /api/v1/transactions`, with full configuration,
  `transactions.write`, and `interfaces.write`.
- Confirm/rollback via existing
  `POST /api/v1/transactions/{id}/confirm` and
  `POST /api/v1/transactions/{id}/rollback` with original change permissions.
- Read settings through `GET /api/v1/interfaces`,
  `GET /api/v1/interfaces/{name}`, `GET /api/v1/vlans`,
  `GET /api/v1/wireguard`, `GET /api/v1/state`,
  `GET /api/v1/transactions/{id}`, and `GET /api/v1/revisions/{revision}`.
  Reads require `state.read`.
- Normal revision restore remains
  `POST /api/v1/revisions/{revision}/restore`, requiring read/transaction and all
  changed-area permissions. Relay settings survive revision workflows/restarts.
- New `GET /api/v1/services/dhcp-relay/status` returns
  `{ "interfaces": DHCPRelayStatus[], "error": string }`, requiring `state.read`.
- `GET /api/v1/runtime` adds `dhcp_relay: DHCPRelayStatus[]`.
- New bodyless `POST /api/v1/services/dhcp-relay/reconcile` returns `RuntimeState`.
  Requires `state.read`, `transactions.write`, and `interfaces.write`.
  Since repair acts on all enabled services, also require `softflowd.write`
  when softflowd is enabled. Existing softflowd repair now also requires
  `interfaces.write` when a relay is enabled. Checks run under the engine lock
  against committed/pending settings, not the draft.

Submission remains 202; confirm/rollback/repair success is 200. Wrong JSON
types are 400; invalid settings or absent native integration are 422; missing
permissions 403; stale revision, drift, or blocked recovery 409.
Native daemon syntax/startup/bind/privilege failures are explicit runtime errors
(500), with normal transaction rollback; observation/runtime endpoint failures
can return 503. A status read can return 200 with individual error states.

### Runtime and operator prerequisites

`DHCPRelayStatus` has `interface`, `state`, optional `pid`, `started_at`, and
`error`. Render disabled, simulated, unavailable, not_running, running, unhealthy,
and exited; missing data is Unknown. Keep top-level errors visible.
Enabled links share one PID because dnsmasq serves all bindings. Server,
selected-address, or enabled-interface-set changes restart the shared process
and can briefly disrupt relay on other interfaces.

Running verifies child identity, namespace, PID file, and owned UDP 67 socket.
It does not prove lease delivery or upstream reachability. Process failure turns
observed `enabled` false and creates drift; do not overwrite desired enabled
settings from failed observation.

Operators must install relay-capable dnsmasq and configure
`-dhcp-relay-binary`, `-dhcp-relay-runtime-dir`, `-dhcp-relay-uid`, and
`-dhcp-relay-gid`. The service account/group must exist and be non-root.
The root-owned binary/runtime and namespace/procfs privileges must meet the
[README prerequisites](../../README.md#relay-operator-setup).
Do not launch another DHCP service on UDP 67 in that namespace.
Upstream routes, server return paths, and other firewalls' UDP 67/68 permissions
remain operator responsibilities. No package installation or identity editing
is exposed through the frontend.

### Required frontend work and acceptance

1. Extend interface models, decoders, drafts, serializers, and review diffs.
2. Add an accessible enable toggle and multi-server editor; preserve disabled
   server lists and validate all entries. Show selected relay address/subnet.
3. Validate interface kind/up/IPv4 prerequisites and enforce permissions.
4. Add per-interface runtime rows with shared-process disruption warnings.
   Simulator must never be labeled real relay activity.
5. Offer explicitly confirmed service repair using stored settings only.
   Check permissions across all enabled services and never auto-retry.
6. Verify multi-server persistence, toggling off/on, confirmation, rollback,
   restart, revision restore, invalid input, and forbidden writes/repairs.
7. On an isolated Linux test host, run the daemon lifecycle and packet test:
   one request must reach both upstream servers and an offer return to the client.
   Also verify failures/exits, disable/removal, recovery, and rollback.

Windows targeted/full tests, vet, and build pass; Linux tests compile and Linux
vet/build pass. Live Linux daemon/packet execution remains unverified here.
Race tests could not run because no C compiler is available.

## 2026-10-17-05: Native gateway monitoring

- Priority: high; required frontend contract/editor/monitoring work.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased working-tree implementation.
- Recommended feature bump: minor. Aggregate Unreleased remains major.
- Scope: IPv4/IPv6 native ICMP, JSON API only; no dpinger dependency, automatic
  failover, route changes, Prometheus, or persistent metrics history.

### Configuration and authorization

Add `Config.gateway_monitors: GatewayMonitor[]`, normalized to `[]` and sorted
by name. Resources have unique case-sensitive names (1..32 alphanumeric,
underscore/hyphen characters, max 64), enabled toggle, explicit interface,
source address, gateway, target, routing table, and integer timing/threshold
settings. Full shape/defaults/bounds are in
[section 6.1.2](../../FRONTEND_SPEC.md#612-gateway-health-and-rtt-variation)
and the [README](../../README.md#native-gateway-monitoring).
Use the [complete dual-stack transaction](../../examples/gateway-monitoring.json).

Enabled monitors require configured up interface/source, route through the
specified gateway/table, and source-policy rule. Source/gateway/target must be
canonical numeric same-family addresses; no hostnames or input zones.
IPv6 link-local gateway/target is scoped by the selected interface.
Disabled monitors retain valid settings without live network references.
Do not infer behavior from WAN/LAN metadata or silently create network policy.

All reads require `state.read`. Monitor changes require `transactions.write`
and `gateway_monitors.write`, plus other changed-area permissions. This applies
to confirmation, rollback, and restore too. No direct monitor write endpoint:
use the complete shared-draft transaction workflow.

Every service repair endpoint repairs all enabled services, requiring permissions
for enabled gateway monitoring, softflowd, and DHCP relay. Gateway repair itself
always requires `gateway_monitors.write`, `transactions.write`, and `state.read`.
Do not authorize from the unsaved UI draft; server uses stored active settings
under lock. Preserve drafts and surface 403 without automatic retries.

### API and measurement contract

| Method | Path | Shape |
| --- | --- | --- |
| GET | `/api/v1/gateway-monitors` | Observed `GatewayMonitor[]` metadata |
| GET | `/api/v1/statistics/gateways` | `{sample, monitors}` |
| GET | `/api/v1/statistics/gateways/{name}` | `{sample, monitor}` |
| GET | `/api/v1/services/gateway-monitoring/status` | `{monitors, error}` |
| POST | `/api/v1/services/gateway-monitoring/reconcile` | No body; `RuntimeState` |

`RuntimeState.gateway_monitors` contains monitor statistics.
Combined `/statistics` has optional nonempty `gateways`.
Statistics endpoints reject all query parameters; single unknown name is 404.
Statistics are cached and independent of full configuration observation.
Poll at the existing 2-5 second non-overlapping cadence; no probe per GET.

Each record has `name`, `process_state` (native worker, not child PID),
`sample_status`, `health`, nullable timestamps (`started_at`, `collected_at`,
`health_changed_at`, `last_success_at`), integer window counts (`sent`,
`received`, `lost`, `pending`, `variation_pairs`), optional `error`, and nullable
JSON numeric `loss_percent`, `rtt_min_ms`, `rtt_max_ms`, `rtt_avg_ms`,
`rtt_stddev_ms`, `rtt_p50_ms`, `rtt_p95_ms`, `rtt_variation_ms`.
These values are **not quoted counter strings or revision uint64s**.

- Loss denominator is received + lost, excluding pending.
- RTT standard deviation is population deviation; percentiles are nearest-rank.
- **RTT variation** is mean absolute RTT difference only between adjacent
  transmitted probes that both replied. It is not one-way/RTP jitter.
- Never bridge a lost/pending probe or replace loss with zero RTT.
- No successes means null RTT; no completed probes means null loss; no adjacent
  successful pair means null variation. Real numeric zero is valid.
- Counts cover the rolling window, not lifetime totals; do not derive traffic
  rates. `sent = received + lost + pending`.
- Last success is since worker start, potentially older than the current window.
- Row `collected_at` is measurement time; envelope timestamps are retrieval time.

### Required frontend work and acceptance

1. Add configuration/runtime/statistics models, decoders, shared editor/draft,
   complete serializers, normalized name identity, review diffs, revision views.
2. Validate explicit route/source/table requirements and exact timing/window
   bounds. Preserve disabled settings and never fabricate a path/default WAN.
3. Render independent lifecycle, sample availability, and health columns:
   disabled/simulated/not_running/running/exited worker;
   disabled/simulated/warming_up/available/stale/unavailable sample;
   unknown/up/degraded/down health.
4. Show loss, RTT/percentiles/variation, counts, freshness, last success, errors,
   units, and null gaps. HTTP 200 can contain individually failed monitors.
   Stale after max(1 second, 3 probe intervals) is Unknown, not a current success.
5. Explain default full-window 30-second warmup, 3-second failure hold, 5-second
   recovery hold, 100% finalized loss Down, 20% loss / 150 ms mean RTT Degraded,
   optional variation threshold disabled. Window effects add to hold time.
6. Keep simulated/no-data/error states neutral; a local route/socket failure
   is not remote Down. Configured enabled is not proof of worker health.
7. Add explicit confirmed repair of stored settings with shared-service
   permissions. Never use it to apply a draft or automatically repeat on errors.
8. Verify persistence, disable/re-enable, confirmation/rollback/restart/restore,
   invalid settings and permissions, null/zero distinctions, warmup/loss/recovery,

Settings persist; measurements reset on affected config/network changes,
repair/restart. Health does not change enabled settings, routes, or modeled
configuration drift. Keep monitoring state separate from configuration drafts.

## 2026-10-17-06: Appliance NTP, syslog, and vnStat

- Priority: high; required frontend configuration/status/authorization work.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend: Unreleased working tree. Recommended feature bump minor; aggregate
  Unreleased remains major, no version assigned.

### New contract

Add `Config.ntp: {enabled: boolean, servers: string[]}`,
`Config.syslog: {enabled: boolean, servers: SyslogServer[]}`,
`Config.vnstat: {enabled: boolean}`. All enabled flags default false; normalized
lists are `[]`, not null. Disabled lists are retained and validated.
`SyslogServer = {host: string, port: number, transport: "udp"|"tcp"|"tls"}`.
Port/transport are explicit, no zero/default port.

NTP/syslog lists accept 0..8 unique entries disabled, 1..8 enabled. Host strings
are canonical global-unicast/private/ULA/loopback IPs or lowercase ASCII DNS
labels (1..63 per label, total <=253). No URI/embedded port/zone/mapped address/
whitespace/trailing dot. Syslog uniqueness is transport+host+port; port 1..65535.
NTP servers normalize lexically; syslog destinations by transport/host/port key.

For each service `ntp`, `syslog`, `vnstat`:

| Method | Path | Response |
|---|---|---|
| GET | `/api/v1/services/{service}` | Configuration metadata |
| GET | `/api/v1/services/{service}/status` | `{instances: ApplianceServiceStatus[], error: string}` |
| POST | `/api/v1/services/{service}/reconcile` | No body; `RuntimeState`, repairs all enabled services |

All reads need `state.read`. Full transaction changes/confirmation/rollback/
restore need `transactions.write` and changed-area `ntp.write`, `syslog.write`,
`vnstat.write`. Repair also needs read+its endpoint write permission, and the
permissions for **all enabled services**, including existing softflowd, DHCP and
gateway monitoring. This rule applies to old repair endpoints too. The server
authorizes stored committed/pending settings under lock, not the draft.
Existing 401/403/404/405/409/422 and native runtime-error responses apply.

`RuntimeState.appliance_services` always includes names `ntp`, `syslog`,
`vnstat-host`, `vnstat-managed`. Fields: `name`, `scope: "host"|"managed"`,
`state: "disabled"|"simulated"|"unavailable"|"not_running"|"running"|"unhealthy"|"exited"`,
optional numeric `pid`, timestamp `started_at`, `database_directory` for vnStat,
and `error`. Status endpoints filter to one instance or two vnStat scopes.
HTTP 200 may contain failed rows; render top-level and per-row errors.

### Required UX and deployment cautions

1. Add shared draft models, editors, complete serializers, validation, review
   diffs, history/restore views and permission hints. Never submit just a service
   fragment as a complete network replacement.
2. NTP uses host networking and changes the **whole appliance clock**, slew-only,
   client-only, no NTS. Running is not proof of sync. Rollback restores settings,
   not past clock state. No NTP offsets/synchronization metrics are exposed.
3. Syslog owns whole-appliance logging, including system/kernel/internal and
   backend log-file messages. Host networking; TLS trust required; UDP/TCP are
   unencrypted and UDP has no acknowledgment. DNS destinations use IPv4;
   canonical IPv6 literals select IPv6. Running is not delivery verification;
   no durable queue or acknowledgment guarantee is provided.
4. Warn explicitly that disabling/rolling back the managed logger can stop local
   system logging, not just remote forwarding. An alternative logger is an
   operator responsibility. Do not auto-enable/disable services on UI navigation.
5. vnStat's single toggle covers all interfaces in both namespaces, including
   loopback/unmanaged and dynamically created links. Show separate PIDs/database
   scopes. Inventory/poll/update is 5 seconds; save/rescan is 1 minute, so new
   manually inserted interfaces may take up to a minute to collect. Never sum
   overlapping physical/VLAN/veth/loopback/scopes as device-wide traffic.
6. No HTTP vnStat historical metrics are exposed yet. Database paths/status are
   diagnostic information, not traffic numbers. History persists across graceful
   restart/repair; changed boot/managed-namespace identity uses a different DB.
7. Poll visible status non-overlapping every 2-5 seconds. Keep disabled/simulated/
   error states distinct. Simulation never changes time or creates real history.
   Process failures do not rewrite desired enabled or create drift by themselves.
8. Offer confirmed explicit repair of stored settings only; do not apply drafts,
   create revisions, automatically retry, or hide cross-service 403 errors.
9. Operator setup is required: trusted packages/binary paths, explicit
   `-allow-host-services`, exclusive host ownership, raw namespace/clock/kernel-log
   capabilities, arranged backend log source, trust bundle, host DNS/routes,
   and stopping competing clock/logging daemons. No arbitrary host commands or
   package/OpenRC management are exposed through the API.

### Acceptance and validation

Verify multi-server persistence/disabled retention; exact limits/invalid hosts/
ports/transports; complete-package confirmation/rollback/restart/restore;
scoped authorization and shared repair; two-scope status, simulated data and
errors; deployment warnings; no invented sync/delivery/history metrics.

Windows full tests/vet/build and Linux compilation/vet/static architecture builds
pass. Native compiled tests cover all-interface discovery, real loopback traffic/
history, lifecycle/repair and DB isolation. Actual Linux/race/Alpine syntax/APK
execution is **not verified locally**; CI includes those checks. Real clock
discipline and whole-system remote delivery require a prepared disposable
appliance and trusted endpoints.
