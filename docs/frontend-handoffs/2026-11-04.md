## 2026-11-04-01 DHCP-following route gateways

- Priority: high. Classification: **required** gateway selector/validation and
  lifecycle messaging. Status: **Pending frontend review**.
- Backend availability: **Unreleased**, local changes only. Contract impact:
  additive `gateway` string value, no new fields/endpoints. Recommended release:
  next automatic calendar version; no manual version bump.

### Affected API and previous versus new behavior

Existing API-key authentication and permissions remain:

| Method/path | Permission | Impact |
| --- | --- | --- |
| `POST /api/v1/transactions` | `transactions.write`, `routes.write`, plus permissions for other changes (`interfaces.write` when changing DHCP/interfaces) | Route `gateway:"dhcp"` accepted under the constraints below; normal `202` provisional apply and explicit confirmation |
| `GET /api/v1/routes` | `state.read` | Configured gateway string can now be `"dhcp"` |
| `GET /api/v1/state` | `state.read` | Same token in `desired.routes`; native `runtime.dhcp_clients` retains existing leases/errors |
| `GET /api/v1/runtime` | `state.read` | Unchanged native `dhcp_clients:{leases,errors}`; no new per-route resolved/installed field |
| `GET /api/v1/revisions`, `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{revision}` | `state.read` | Saved routes preserve the token through history/export |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | `transactions.write`, `routes.write`, plus permissions for other changes | Unchanged lifecycle; rollback resolves the target configuration against its applicable lease |

Previously gateway accepted only a literal address or omitted/empty for direct.
New exact lowercase `"dhcp"` opts into the interface lease's IPv4 default gateway.
No automatic conversion of literal routes, per-route write endpoint, lease
fallback, initial-state adoption, reset or persisted-state migration.

### Shape, validation and errors

Synthetic route fragment, requiring matching configured Ethernet `eno1` and
`dhcp_clients.eno1`:

```json
{"enabled":true,"destination":"203.0.113.10/32","gateway":"dhcp","interface":"eno1","table":254,"metric":10}
```

- `gateway` remains a non-null string when supplied: omitted/`""` means direct;
  canonical numeric IP means pinned; `"dhcp"` means dynamic. No new defaults.
  Reject null/non-string with `400`. Other spellings are not aliases.
- `"dhcp"` requires IPv4 and DHCPv4 on the same managed Ethernet interface,
  even for disabled routes. IPv6, blackhole targets and DHCP-less selections
  reject with `422`. Prefix, table 254 or 10000..19999, metric 1..2147483647,
  duplicate identity and enabled/metadata rules are unchanged.
- Select the lowest-metric table-254 IPv4 default route in the valid matching
  lease; equal-best defaults must agree on one numeric unicast gateway. Classless
  lease routes suppress the Router option normally. No usable default, a direct
  default, invalid gateway or ambiguity is an explicit backend/worker error.
- No valid lease means suspended installation, not an invalid configuration.
  Acquisition/renewal/site or gateway changes update only owned routes, retaining
  destination, table, metric, interface, enabled, saved `"dhcp"` and revision.
  Expiry/NAK removes dependent routes. Failed updates use durable lease rollback;
  foreign routes are never replaced as a fallback.
- API reads and history keep `"dhcp"`; lease `routes` still describe numeric/direct
  DHCP-learned routes, not resolved configured routes. Use lease validity/errors
  for lifecycle; do not claim installed/working traffic from a config read.
- Existing `401`/`403`, stale/busy transaction `409`, apply/recovery `500` and
  observation/worker `503` behavior remains. Never auto-confirm on lease presence.

### Concrete frontend work and deployment coordination

1. Change IP-only gateway validation/types to allow the exact token. Offer
   Direct / Static address / DHCP gateway, restricting DHCP selection by the
   draft interface's DHCP configuration and IPv4 destination.
2. Keep `"dhcp"` when editing disabled routes, loading revisions/exports,
   comparing drafts and rolling back; never replace it with a runtime literal.
3. Keep the existing table/metric. Explain waiting for DHCP and explicit
   lease/default-gateway errors using current applied runtime leases/errors.
   Do not add a fabricated resolved-gateway API field or overwrite drafts.
4. Require backend support before submitting the token. Coordinate with an
   operator using local console/independent OS SSH when changing WAN/endpoint
   routing; existing drift guards can still block recovery edits.
5. For WireGuard endpoint host routes, verify underlay reachability and routing
   policy prevent recursion. No table selection, policy-rule changes, AllowedIPs
   changes or automatic route removal are included. Literal-route conversion is
   an explicit operator-reviewed transaction, not a deployment side effect.

### Acceptance and validation

- Configure DHCP IPv4 host routes in main/custom tables; confirm only after
  connectivity verification. Preserve chosen destination/table/metric.
- Renew with a new gateway on the same subnet, then change the lease subnet;
  confirm numeric kernel next hops follow while desired `"dhcp"` stays unchanged.
- Verify waiting/expiry/reacquisition, missing/direct/ambiguous defaults and
  foreign-route conflict errors. A pinned literal must not change.
- Verify permission denial, invalid IPv6/DHCP-less/disabled configurations,
  pending-confirmation rollback, restart, native intent recovery and CLI edits.
- Backend checks/results and remaining appliance/browser acceptance are in the
  [daily journal](../journal/2026-11-04.md#dhcp-following-route-gateways).
  Frontend implementation and real-site/WireGuard validation remain pending.

## 2026-11-04-02 GET capability refresh and API Explorer registration

- Priority: high. Classification: **required** API client and API Explorer
  registration. Status: **Pending frontend review**.
- Backend availability: **Unreleased**, local changes only. Contract impact:
  **breaking HTTP method change**, next automatic calendar version; no manual
  version bump. No field, configuration or saved-state schema changes.
- Supersedes only the refresh method in
  [item 2026-10-31-01](2026-10-31.md#2026-10-31-01-interface-capability-inventory);
  its hardware evidence/types and optional inspector work remain relevant.
- User reports that the frontend explorer supports only GET execution and omits
  both capability routes. This report is not a verified frontend implementation
  audit; the frontend source/explorer is not changed by this backend task.

### Exact API contract and previous versus new behavior

| Method/path | API-key permissions | Behavior |
| --- | --- | --- |
| `GET /api/v1/interface-capabilities` | `state.read` | Unchanged: `200 InterfaceCapabilitySnapshot \| null`; read only the saved snapshot, no scan |
| `GET /api/v1/interface-capabilities/refresh` | `state.read` and `interfaces.write` | Previously 405; now one synchronous passive scan and durable save, then `200 InterfaceCapabilitySnapshot` |
| `POST /api/v1/interface-capabilities/refresh` | Normal API-key authentication/method checks | Previously scan/save; now unsupported, normally 405. No POST alias |

Both GETs accept **no request body**, not even `{}`, and no query parameters:
invalid input returns `400`. Authentication and permissions remain `401`/`403`.
Unsupported methods include POST and HEAD (`405`); no refresh occurs. Existing
pending restart/upgrade guards return `409` for refresh despite GET, while the
cached-read path remains available. Fatal scan errors return `503`; persistence
errors return `500`. Both retain the previous snapshot. Successful partial
scans return `200` with diagnostics and replace the old snapshot.

Response type/nullability, units and semantics are unchanged. Synthetic valid
empty simulator snapshot:

```json
{
  "collected_at": "2026-11-04T05:10:00+00:00",
  "scope": "simulator",
  "inventory": {
    "source": "simulator",
    "status": "simulated",
    "kernel_release": null,
    "boot_id": null,
    "errors": [],
    "interfaces": []
  }
}
```

`collected_at` is UTC RFC3339; native inventory uses nullable kernel release and
boot identity and name-sorted interface rows. Speeds are Mbps; support/enabled,
driver/PCI/link/channel/queue nullability and explicit unknown/partial evidence
remain as defined in the canonical spec. Cached reads before discovery return
the literal JSON `null`, not this empty object.

### Concrete frontend tasks

1. Register **both full paths** as GET entries in the explorer:
   - "Read saved interface capabilities": `state.read`, nullable response.
   - "Refresh interface capabilities": `state.read` + `interfaces.write`,
     non-null response on success; visibly label **scans hardware and saves**.
2. Change refresh client calls from POST to GET and send no body/query. Continue
   using existing API-key handling; do not broaden permissions or embed keys
   in URLs. Disable/hide refresh execution for read-only users.
3. Execute refresh only on explicit user action, single-flight. This intentionally
   state-saving GET must not enter automatic polling, prefetch, retry,
   cache-warming or bulk "run all GETs". Server responses are already
   `Cache-Control: no-store`; disable client/proxy result caching as well.
   Every explicit refresh should reach the server and perform a fresh scan.
4. Render timestamp/scope, null-before-first-refresh, unknown/simulated/partial
   evidence and detailed errors. On failure retain old displayed data as stale,
   not newly collected. On successful partial refresh replace old evidence.
5. Do not copy inventory into desired configuration, drafts or transaction
   submissions. Refresh neither applies networking nor allocates a revision,
   changes NIC ownership or enables hardware acceleration.

### Deployment and acceptance

- Deploy the backend and GET refresh client contract together. There is no

  will fail; GET against a pre-change backend will also fail.
- Confirm explorer entry visibility and permissions; cached GET before refresh
  is null, explicit GET refresh is 200, subsequent cached GET returns the saved
  data without scanning. Verify POST/HEAD 405 and query/body 400.
- Verify 401/403, restart/upgrade 409, partial handling and scan/persistence
  failures preserve prior data. No prefetch/poll/retry/cache request should

- Backend routing/HTTP tests verify auth, methods, no-store, persistence, repeated
  GET collection and maintenance/restart protection. Final commands/results are
  in the [journal](../journal/2026-11-04.md#get-capability-refresh-and-api-explorer-handoff).

## 2026-11-04-03 Performance diagnostics and transactional RPS

- Priority: high. Classification: **required** client types, full-package
  preservation, explicit tuning review and transaction UX; performance
  visualization/before-after comparison is recommended UI work.
- Status: **Pending frontend review**. Backend availability: **Unreleased**,
  local implementation only. Contract impact: **additive**, next automatic
  calendar version; no manual version/seed bump. No frontend code was changed.
- Why: single-RX-queue hardware can benefit from CPU steering when measurements
  establish CPU pressure; supported-but-disabled RPS alone is insufficient.

### Methods, permissions and changed behavior

| Method/path | Permissions | Change |
| --- | --- | --- |
| `GET /api/v1/statistics/performance` | API key, `state.read` | New passive host CPU/IRQ/softnet, topology, physical RX-queue and RPS trial evidence; no body/query |
| `GET /api/v1/kernel/tunables`, `GET /api/v1/runtime`, `GET /api/v1/state` | `state.read` | Kernel maps can include RPS; state desired remains committed while runtime/configured can be provisional |
| `GET /api/v1/revisions`, `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{revision}` | `state.read` | Complete saved configuration preserves `kernel.rps` |
| `POST /api/v1/transactions` | `transactions.write`, `interfaces.write`, `kernel.host.write`, plus other changed areas | Complete candidates can explicitly configure/disable/release RPS queues; normal provisional `202` |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback`, `POST /api/v1/revisions/{revision}/restore` | Same permissions for the RPS changes | Existing confirmation/deadline/recovery lifecycle; no tuning-specific bypass |

Previously there was passive capability inventory only, without RPS tuning.
Capability cached read and explicit scan/save GET contracts are unchanged:
never substitute/poll capability refresh for performance diagnostics.

### Request fields and errors

Synthetic configuration fragment, **not a full transaction or hardware
recommendation**:

```json
{"kernel":{"rps":{"eno1/rx-0":"c"}}}
```

- Optional nonnull `kernel.rps:Record<string,string>`, omitted/empty = unmanaged;
  serialized empty maps are omitted. Preserve it in every full-package edit.
- Maximum 64 queues. Key: managed physical Ethernet `INTERFACE/rx-N`, canonical
  RX index 0..4095. Use the physical parent, not VLAN/tunnel/dummy/veth.
- Mask: canonical lowercase Linux hexadecimal, highest word unpadded and
  following 32-bit words eight digits, CPUs 0..8191. `c` selects CPUs 2/3.
  `0` explicitly disables RPS; removing the key restores the captured original
  mask and releases ownership. These are different actions.
- Native preflight requires online selected CPUs, actual writable physical
  sysfs queues, host mode and operator `allow_host_tunables` with its exclusive
  lock. `tuning_available` is only operator opt-in, not caller authorization.
- Known type/null errors `400`; invalid mask/key/limit/interface references
  `422`; authentication `401`/`403`; stale/busy transaction `409`.
  Live preflight, readback and recovery failures retain normal explicit
  `500` transaction errors. Diagnostic GET failures are `503`, or `200` with
  partial source evidence. Wrong GET body/query `400`, unsupported method `405`.
  Never blindly retry or auto-confirm mutation.

### Response types and presentation

The [canonical contract](../../FRONTEND_SPEC.md#performance-diagnostics-and-rps-tuning)
defines every section, counter field, nullability, unit, threshold and bound.

- New schema `netcontrol-performance/v1`: `sample`, evidence-wrapped `sections`,
  nullable `interfaces`, `configured_rps`, `tuning_available`, `recommendations`,
  committed `config_revision` and nullable provisional `transaction_id`.
- Scope is host, not container/cgroup-sized networking; allowed CPU scope is the
  collector thread. All cumulative counters/deltas are exact decimal strings.
  Rates/percentages and source intervals are nullable numbers. Never sum
  softirq invocations into packet totals or convert unknown sources to zero.
- CPU/NET_RX/IRQ intervals are independently measured. First/reset/unavailable/
  unstable-identity samples have no usable rates. `identity_stable` includes
  final boot/online/allowed/isolated rechecks; collection remains non-atomic.
- IRQ affinity/action/layout/CPU changes invalidate relevant baselines.
  Historical softnet rows can have no CPU identity or rates. Surface nested
  section/row errors and simulator status explicitly.
- Physical rows show RX masks and sysfs NIC IRQ IDs. VLAN parent references
  identify where to tune; veth peer indices are not physical-parent references.
- Recommendations are `trial` with an explicit proposed mask/evidence, or
  `insufficient_evidence` with null mask and explanatory reason; always
  `automatic:false`. No recommendation is a verified performance improvement.
  Native captured `rps_identity` is read-only and must not enter desired forms.

### Concrete frontend tasks and deployment

1. Register the new read-only GET in API Explorer; preserve existing capability
   refresh's explicit scan/save warnings. No GET enables tuning.
2. Extend kernel client/draft/history/import types without dropping `rps`.
   Add explicit CPU mask review/editor, Disable and Restore original actions.
   Gate by transaction/interface/host permissions and operator prerequisites.
3. Show measured source status, boot/CPU scope, timestamps, reset baselines,
   per-CPU utilization, NET_RX activity, softnet drops/time-squeeze and NIC IRQ
   distribution. Keep partial data/errors visible.
4. Sample at operator-selected intervals suitable for 1..30-second source
   comparisons. Recommendations additionally require ready CPU/NET_RX/IRQ
   evidence, measured pressure and safe local non-sibling idle target cores;
   never synthesize masks from CPU count alone.
5. Before/after view: capture samples under the same load, correlate existing
   interface throughput, link queue/drop diagnostics and gateway latency/loss.
   These comparison records are frontend-owned, not persisted by the new API.
6. Submit a complete reviewed candidate; retain current base revision and
   pending deadline/actions. Confirm only after independent management,
   VLAN/WireGuard reachability and performance checks. Failure may leave a
   recovery intent requiring authorized retry, not a successful no-op.

Deploy backend before clients submit RPS fields. Provision writable host sysfs
and opt-in through normal operator configuration; remove conflicting external
RPS tuning. No migration, automatic hardware tuning, IRQ changes, datapath
bypass, RFS/RSS/XPS, offload, qdisc or XDP/DPDK work is included. Physical-NIC
performance/connectivity acceptance and frontend/browser acceptance remain
required; fixture/container tests do not establish an appliance speedup.

Acceptance: verify permissions/type/mask/online/queue errors; first/reset/partial/
simulated views; exact recommendation boundaries and unavailable-evidence
abstention; explicit apply/confirm, timeout/restart rollback, original restoration
and readback failure recovery. Backend execution/results and limitations:
[journal](../journal/2026-11-04.md#performance-diagnostics-and-transactional-rps).

## 2026-11-04-04 Physical-interface descriptive aliases

- Priority: normal. Classification: **optional** UI explanation; no client
  schema or endpoint change.
- Status: **Pending frontend review**. Backend availability: **Unreleased**,
  local implementation only. Contract impact: **additive**, next automatic
  calendar version; no manual version/seed bump.
- Previously physical display names were saved annotations only. Native Linux
  now also derives one cosmetic kernel alias from the display name and role,
  without renaming interfaces or changing routing/firewall identifiers.

### Exact affected API and fields

- `GET /api/v1/interfaces` and `GET /api/v1/state`: existing API-key
  `state.read`; unchanged configuration-derived names, roles and metadata.
- `POST /api/v1/transactions`, `POST /api/v1/transactions/{id}/confirm`,
  `POST /api/v1/transactions/{id}/rollback` and
  `POST /api/v1/revisions/{revision}/restore`: existing API-key,
  `transactions.write` and `interfaces.write` for interface edits, plus other
  changed-area permissions. Existing complete-candidate, confirmation and
  rollback workflows/statuses remain unchanged.
- No request/response field, type, nullability, default, permission or endpoint
  is added. Existing metadata type/default errors remain 400 and semantic
  validation remains 422. Backend label failures use existing transaction 500
  failure/recovery behavior; do not treat them as successful saves.

Synthetic **configuration fragment, not a complete transaction**:

```json
{"name":"eno1","kind":"ethernet","role":"wan","metadata":{"display_name":"Office uplink","description":""}}
```

This produces `alias Office uplink [WAN]` under the unchanged `eno1` link.
Empty/omitted `display_name` produces `WAN`, `LAN` or `UNASSIGNED`, according
to the configured role. Linux has one alias, not multiple labels or an actual
`WAN@eno1` name. Names remain nonunique annotations with the existing
128-Unicode-scalar limit; descriptions do not affect aliases. If the combined
label exceeds 255 UTF-8 bytes, shorten only its display-name prefix at a
character boundary, retaining the whole role suffix and full saved name.

### Optional frontend work, coordination and acceptance

1. Explain the combined Linux alias in the existing Ethernet display-name/role
   editor, including role-only fallback and possible kernel-only shortening.
   Preserve complete metadata in drafts/history and keep selectors/references
   keyed by the technical interface name. No new form field is needed.
2. Do not infer a rename or parent relationship from this presentation, or
   represent a configuration-derived label as an independently observed kernel
   alias. There is no new runtime alias observation field or polling endpoint.
3. Keep normal provisional/confirm/rollback and failure UX. Display-name-only
   changes update labels without network or worker restarts. Managed physical
   down links are included; unmanaged and configured virtual links are untouched.

No synchronized frontend deployment or operator interface rename is required.
The backend applies labels on startup repair and configuration apply. Preserve
native alias state/intents in normal state backups; no state reset or migration
is required. Original labels are restored on unmanagement and update failures,
with interrupted updates recovered before further work. Cosmetic alias drift
does not block network edits.

Acceptance: verify named/unnamed WAN/LAN/unassigned labels, Unicode shortening
without saved-text changes, clear-name and role edits, untouched virtual/
unmanaged links, unchanged addresses/routes/workers on label-only edits, rollback,
restart repair, interrupted-update recovery and original-label restoration.
Backend unit/workspace and privileged isolated namespace tests passed; actual
appliance/frontend acceptance remains pending. Exact commands/results:
[journal](../journal/2026-11-04.md#physical-interface-descriptive-aliases).
