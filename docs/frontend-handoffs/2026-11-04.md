# Frontend handoffs - 2026-11-04

## 2026-11-04-01 DHCP-following route gateways

- Priority: high. Classification: **required** gateway selector/validation and
  lifecycle messaging. Status: **Pending frontend review**.
- Backend availability: **Unreleased**, local changes only. Contract impact:
  additive `gateway` string value, no new fields/endpoints. Recommended release:
  next automatic calendar version; no manual version bump.

### Affected API and previous versus new behavior

Existing API-key authentication and permissions remain:

| Method/path | Permission | Impact |
| --- | --- | --- |
| `POST /api/v1/transactions` | `transactions.write`, `routes.write`, plus permissions for other changes (`interfaces.write` when changing DHCP/interfaces) | Route `gateway:"dhcp"` accepted under the constraints below; normal `202` provisional apply and explicit confirmation |
| `GET /api/v1/routes` | `state.read` | Configured gateway string can now be `"dhcp"` |
| `GET /api/v1/state` | `state.read` | Same token in `desired.routes`; native `runtime.dhcp_clients` retains existing leases/errors |
| `GET /api/v1/runtime` | `state.read` | Unchanged native `dhcp_clients:{leases,errors}`; no new per-route resolved/installed field |
| `GET /api/v1/revisions`, `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{revision}` | `state.read` | Saved routes preserve the token through history/export |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | `transactions.write`, `routes.write`, plus permissions for other changes | Unchanged lifecycle; rollback resolves the target configuration against its applicable lease |

Previously gateway accepted only a literal address or omitted/empty for direct.
New exact lowercase `"dhcp"` opts into the interface lease's IPv4 default gateway.
No automatic conversion of literal routes, per-route write endpoint, lease
fallback, initial-state adoption, reset or persisted-state migration.

### Shape, validation and errors

Synthetic route fragment, requiring matching configured Ethernet `eno1` and
`dhcp_clients.eno1`:

```json
{"enabled":true,"destination":"203.0.113.10/32","gateway":"dhcp","interface":"eno1","table":254,"metric":10}
```

- `gateway` remains a non-null string when supplied: omitted/`""` means direct;
  canonical numeric IP means pinned; `"dhcp"` means dynamic. No new defaults.
  Reject null/non-string with `400`. Other spellings are not aliases.
- `"dhcp"` requires IPv4 and DHCPv4 on the same managed Ethernet interface,
  even for disabled routes. IPv6, blackhole targets and DHCP-less selections
  reject with `422`. Prefix, table 254 or 10000..19999, metric 1..2147483647,
  duplicate identity and enabled/metadata rules are unchanged.
- Select the lowest-metric table-254 IPv4 default route in the valid matching
  lease; equal-best defaults must agree on one numeric unicast gateway. Classless
  lease routes suppress the Router option normally. No usable default, a direct
  default, invalid gateway or ambiguity is an explicit backend/worker error.
- No valid lease means suspended installation, not an invalid configuration.
  Acquisition/renewal/site or gateway changes update only owned routes, retaining
  destination, table, metric, interface, enabled, saved `"dhcp"` and revision.
  Expiry/NAK removes dependent routes. Failed updates use durable lease rollback;
  foreign routes are never replaced as a fallback.
- API reads and history keep `"dhcp"`; lease `routes` still describe numeric/direct
  DHCP-learned routes, not resolved configured routes. Use lease validity/errors
  for lifecycle; do not claim installed/working traffic from a config read.
- Existing `401`/`403`, stale/busy transaction `409`, apply/recovery `500` and
  observation/worker `503` behavior remains. Never auto-confirm on lease presence.

### Concrete frontend work and deployment coordination

1. Change IP-only gateway validation/types to allow the exact token. Offer
   Direct / Static address / DHCP gateway, restricting DHCP selection by the
   draft interface's DHCP configuration and IPv4 destination.
2. Keep `"dhcp"` when editing disabled routes, loading revisions/exports,
   comparing drafts and rolling back; never replace it with a runtime literal.
3. Keep the existing table/metric. Explain waiting for DHCP and explicit
   lease/default-gateway errors using current applied runtime leases/errors.
   Do not add a fabricated resolved-gateway API field or overwrite drafts.
4. Require backend support before submitting the token. Coordinate with an
   operator using local console/independent OS SSH when changing WAN/endpoint
   routing; existing drift guards can still block recovery edits.
5. For WireGuard endpoint host routes, verify underlay reachability and routing
   policy prevent recursion. No table selection, policy-rule changes, AllowedIPs
   changes or automatic route removal are included. Literal-route conversion is
   an explicit operator-reviewed transaction, not a deployment side effect.

### Acceptance and validation

- Configure DHCP IPv4 host routes in main/custom tables; confirm only after
  connectivity verification. Preserve chosen destination/table/metric.
- Renew with a new gateway on the same subnet, then change the lease subnet;
  confirm numeric kernel next hops follow while desired `"dhcp"` stays unchanged.
- Verify waiting/expiry/reacquisition, missing/direct/ambiguous defaults and
  foreign-route conflict errors. A pinned literal must not change.
- Verify permission denial, invalid IPv6/DHCP-less/disabled configurations,
  pending-confirmation rollback, restart, native intent recovery and CLI edits.
- Backend checks/results and remaining appliance/browser acceptance are in the
  [daily journal](../journal/2026-11-04.md#dhcp-following-route-gateways).
  Frontend implementation and real-site/WireGuard validation remain pending.
