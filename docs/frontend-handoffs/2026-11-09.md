# Frontend handoffs - 2026-11-09

## 2026-11-09-01 Install and source-upgrade MOTD cleanup

- **Summary:** installation and full source upgrades now remove Ubuntu MOTD output.
- **Priority:** medium.
- **Classification:** required operator-help update; no API client or UI form work.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not committed, published or deployed.
- **Contract/recommended bump:** breaking deployment policy; next automatic calendar version.

### Contract and frontend tasks

Previously the scripts left MOTD services, PAM output, files and generators alone.
Now both scripts stop/disable and persistently mask standard MOTD units, remove
active `pam_motd.so` lines from regular PAM configuration files and delete the
standard content/generator/cache paths listed in the
[installation guide](../BUILD_AND_INSTALL.md#motd-cleanup). Absent units are also
masked. Targeted custom MOTD content is deleted; packages/distribution unit
definitions are not purged. Other authentication/session modules, credentials,
firewall state, `/etc/issue`, SSH `Banner` settings and embedded SSH greetings
remain unchanged.

**Affected HTTP methods/paths: none.** In particular, `POST /api/v1/system/upgrade`
and automatic HTTPS self-upgrades do not run this cleanup. Request/response
fields, types, nullability, defaults, units, limits, HTTP status/error behavior,
authentication and permissions are unchanged; there is no new JSON payload.

Update install/full source-upgrade operator instructions to disclose deleted
custom MOTD content and suggest saving wanted banners separately beforehand.
Distinguish full deployment from `upgrade.sh --build-only`, HTTP/automatic
self-upgrades, signed-package installs and standalone hardening/reset, which
do not add this policy. No client types, forms, rendering, polling or state
handling changes are needed.

### Deployment and acceptance

Requires the existing root/sudo Ubuntu/systemd deployment prerequisites. Cleanup
occurs before provisioning/binary replacement and aborts deployment on inspection,
unit-control, PAM-write or removal failures. Changes already made to the host
are not undone by binary rollback. Unsafe parent symlinks and non-regular/symlink
PAM files are errors; leaf MOTD symlink targets are preserved. Later package or
operator changes can recreate files/PAM lines; the next full script run cleans
them again. No API deployment ordering or compatibility window is required.

Acceptance: fresh install/full source upgrade leaves listed units stopped and
persistently masked, removes listed paths and active PAM MOTD entries, retains
unrelated login modules/banners and allows normal OS login without MOTD. Repeat
cleanup succeeds; failures prevent deployment. Confirm excluded upgrade paths
do not promise this policy.

Backend validation: Bash syntax checks and the full mocked installer regression
suite passed in an isolated network-disabled Linux container, including MOTD
removal/repeat cleanup, service-state failures, symlink safety, PAM mode/content
preservation, deployment ordering and binary recovery. Actual Ubuntu/systemd,
OS SSH/console login and package-reinstall acceptance are not run.

## 2026-11-09-02 Discord device names and full firewall name

**Label-source policy superseded:** use description-only labels as specified in
[item 03](#2026-11-09-03-discord-local-description-only-labels). Firewall identity,
message limits and the other behavior below remain unchanged.

- Classification: **optional**; priority normal.
- Status: **Pending frontend review**. Not sent or acknowledged.
- Backend availability: **Unreleased**.
- Contract impact/recommended bump: additive notification metadata; next
  automatic calendar version. No HTTP or persisted-schema changes.

### Behavior and affected surfaces

Previously Discord endpoints displayed only IPs/ports and used the firewall's
hostname in the title. Now the embed title is `New firewall drop` and its author
is `system.hostname` plus `.` plus `system.domain` when both are configured.
An empty domain uses hostname only; an empty hostname uses `Firewall`, even if
a domain exists. Source/destination endpoints append known names, for example
`192.0.2.10:53000 (Camera) -> 192.0.2.20:443 (Server)`.

Exact IP matches in committed `firewall.policies.hosts` take precedence over
cached Sando host names. Sando cache must match current `sando.api_url`; retained
names remain usable with sync disabled or a failed refresh. Unknown endpoints
retain IP/port only. No live lookup, subnet guessing or new identity inference.
Long names split messages within ten embeds/6000 total embed characters;
mentions remain disabled. Deduplication, notification flags and best-effort
delivery semantics are unchanged. Configuration is checked before each split
message and during delivery/retry; interrupted claimed entries are not replayed.

No affected HTTP methods/paths, authentication, permissions, request/response
fields, validation, status codes or errors change. Existing configuration
transactions, `GET /api/v1/sando`, webhook upload and Discord status remain as
documented. No new form/client types or polling are required.

### Optional frontend tasks and deployment

Update Discord help/export disclosure to mention device names as additional
third-party metadata and the full configured firewall name. Explain that names
are cached/configured labels, not authoritative device identification.
No frontend/backend deployment coordination is required for this presentation
change. Existing native-host, private-store and outbound DNS/HTTPS prerequisites
remain; Sando fallback requires an available matching cache.

### Acceptance and evidence

Verify named IPv4/IPv6 endpoints, configured-name precedence, unnamed endpoints,
hostname/domain combinations, current-source-only cache and disabled-cache
retention. Verify long names remain complete, each message respects Discord
limits and mentions are disabled. Backend unit/loopback tests cover these
behaviors; real Discord/appliance and frontend integration remain unverified.
Actual validation results are recorded in the journal below.

## 2026-11-09-03 Discord local-description-only labels

- Summary: Discord device labels use Sando `local_description` only.
- Priority: normal; classification: **optional** help/disclosure update.
- Status: **Pending frontend review**. Not sent or acknowledged.
- Backend availability: **Unreleased**, no approved release or commit.
- Contract/recommended bump: notification-label correction; next automatic
  calendar version. Supersedes item 02's configured-name/Sando-hostname policy.

### Exact contract and frontend tasks

Previously configured firewall host names took precedence over cached Sando
hostnames. Now only a nonblank Sando `local_description` for an exact endpoint IP
is appended in parentheses. This value already exists in the Sando snapshot as
nullable `classification:string`, with a 512-byte limit. Missing/null/empty/
whitespace-only descriptions leave IP/port only, even when DNS/DHCP/lease
hostnames or a configured firewall host name exist.

For example, a synthetic cached device with `host_name:"camera.test"` and
`classification:"Living room camera"` produces an endpoint such as
`192.0.2.10:53000 (Living room camera)`, never `camera.test`.
Only the current `sando.api_url` cache is eligible; disabled-sync/failed-refresh
retention is unchanged. Both source and destination use the same policy.
Firewall `hostname.domain`, exact first-seen identity, allowed mentions,
message-size splitting and best-effort delivery are unchanged.

Affected HTTP methods/paths: **none changed**. `GET /api/v1/sando` (`state.read`)
still exposes distinct `host_name` and `classification` fields; this task does
not rename fields or change their types, nullability, defaults or validation.
Discord status/upload, configuration transactions, authentication/permissions
and status/error behavior are unchanged. No client types, forms, polling or
state-handling changes are required.

Optionally update Discord help/export disclosure to say **Sando local
description**, not DNS name or configured-host-name fallback. No deployment
ordering or new operator prerequisites; existing private cache and native-host
outbound DNS/HTTPS requirements remain. Without a matching cached description,
messages are intentionally unlabelled.

### Acceptance and validation

Verify a description wins when DNS/DHCP/lease names also exist, both IPv4/IPv6
addresses use the same description, and missing/null/blank descriptions never
fall back to those names or configured hosts. Verify source mismatch excludes
cache and retained disabled cache remains usable. Verify complete 512-byte
descriptions fit split messages within Discord's limits with mentions disabled.

Daemon library tests: **96 passed, 5 ignored, 0 failed**. Strict daemon Clippy,
format check and daemon build passed. Real Discord/appliance and deployed
frontend acceptance were not run.
