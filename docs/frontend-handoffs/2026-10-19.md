# Frontend handoff: 2026-10-19

## 2026-10-19-01: Optional transactional configuration CLI over SSH

- Priority: medium; optional frontend/operator-help enhancement.
- Status: Pending frontend review. Not sent or acknowledged.
- Backend availability: Unreleased working tree; no approved release/commit.
- Recommended bump: minor for the added management interface. Aggregate
  Unreleased remains major for the Rust cutover; baseline is unknown.

### Contract and previous versus new behavior

Previously networking configuration was available through the HTTP API only.
Operators can now opt into a separate in-process SSH interpreter with
`--ssh-listen ADDRESS` (example `0.0.0.0:2222`). SSH is disabled by default.
Optional `--ssh-host-key PATH` requires SSH and otherwise defaults to
`<state>.ssh-key`. The private persistent Ed25519 host key is a separate new
deployment file, not an HTTP field or a change to the identity/state schema.

- SSH username is the literal `apikey`; its password is an existing API key,
  not the device-account password. Device keys require completed onboarding.
  Scoped keys retain their permissions and restart-based file reload behavior.
  Every command checks current credential validity; managed revocation blocks
  subsequent commands. `enable` changes CLI mode, not permissions.
- Every shell has a private candidate and captured committed base revision.
  `commit confirmed SECONDS [DESCRIPTION]` submits one complete package through
  the existing engine; seconds must be integer 10..300. `confirm`/`rollback`
  act on a transaction ID (or the last successful local transaction).
  Candidate commands are not immediate networking edits.
- SSH disconnect discards local draft only; a submitted pending transaction
  retains its durable confirmation deadline. The CLI does not auto-confirm,
  auto-merge, bypass permissions, or silently reset incompatible data.
- All HTTP methods/paths and their request/response fields, nullability,
  units, defaults, authentication, CORS, permissions and status/error handling
  are unchanged. CLI and API share revision/transaction guards:
  `GET /api/v1/state`, `GET /api/v1/transactions[/ID]` and
  `GET /api/v1/revisions[/NUMBER]` can observe CLI changes.
  Existing POST transaction/confirm/rollback/restore/reconcile endpoints are
  also used internally by the interpreter with the authenticated key's actor
  and permission set.
- Continue existing `401/403`, revision/active-transaction `409`, validation
  `400/422`, observation `503`, provisional `202` and uncertain-write handling.
  There is no new frontend terminal endpoint, web SSH proxy, event stream,
  capability/version endpoint, or JSON client schema.
- Interpreter errors are textual, with existing engine status/error/transaction
  details; they are not new HTTP response types. Commands are limited to
  65,536 bytes, private candidates to 1 MiB. Typed JSON-pointer edits cover
  the complete current configuration schema, including fields without a
  dedicated Cisco-style shortcut.
- Interactive shells require a PTY; exec accepts one command, not a configuration
  script. Ctrl-C cancels only input; Ctrl-D exits without confirming pending
  work. Rendered output is limited to 4 MiB: overflow returns an explicit error
  and nonzero exec status, never partial successful JSON. Execution may already
  have completed, so inspect state/transactions before retrying.

### Concrete frontend/operator tasks

1. Optionally link the [CLI guide](../CLI.md) from operator help. Explain
   `configure terminal`, candidate staging, `commit check`, provisional
   `commit confirmed`, independent connectivity verification and explicit confirm.
2. Keep existing polling/conflict handling for another management session.
   Preserve a browser draft when CLI changes advance the committed revision;
   do not auto-rebase, replace it from observed state, or auto-confirm a CLI
   transaction. Authorized operators may recover it through either surface.
3. If help covers SSH, describe the fixed username/API-key password prompt,
   host-key fingerprint trust and optional listener enablement. Never put an
   API key in an SSH URL, command-line example or browser storage.
4. No required frontend/backend coordinated schema deployment. Operators deploy
   the updated daemon, explicitly choose SSH exposure/port, preserve its host
   key and arrange management access. Existing system SSH need not be replaced;
   the interpreter does not offer a system shell, SFTP or forwarding.
5. Native namespace/physical networking/host-service prerequisites remain
   unchanged. SSH encryption does not make HTTP onboarding encrypted or make
   wildcard addresses LAN-only. Custom package payload paths are unchanged.

## 2026-10-19-02: Host networking and physical NIC onboarding

- Priority: high; required frontend work for host appliance management.
- Status: Pending frontend review. Not sent, acknowledged or frontend-verified.
- Backend availability: Unreleased working tree; no release/version assigned.
- Recommended bump: major for deployment/scope and configuration semantics.
  This supersedes the isolated-lab deployment limitation in the Rust cutover
  handoff, not its remaining runtime acceptance or licensing requirements.

### Contract changes

Native Linux mode now defaults to the daemon's current network namespace.
On Alpine this is the machine's host networking; in Docker it is the
container's namespace, not the Windows/Docker-host adapters. An explicit
`--namespace NAME` remains an optional isolated-lab selection.
The package's OpenRC arguments now select `--backend linux`; the bare daemon's
development default remains simulator. Operators must review exposure,
competing network managers and console recovery before starting host mode.
Host mode also requires a persistently provisioned 32-hex-character
`/etc/machine-id`; empty/missing/invalid identity fails startup. Preserve that
identity and the state location; no reset/import is supplied for mismatched
old host/lab state.

- New **`GET /api/v1/interfaces/discovered`**: normal API key and `state.read`;
  no cookie authorization, no new permissions. Returns a JSON array:

  ```json
  [
    {
      "name": "eth0",
      "kind": "ethernet",
      "index": 2,
      "mac": "02:00:00:00:00:01",
      "mtu": 1500,
      "up": true,
      "addresses": ["192.0.2.10/24"],
      "ownership": "unmanaged"
    }
  ]
  ```

  Synthetic example, not a captured host. `name`/`kind` are strings;
  native `index` is a kernel integer, simulator `index` is null; `mac` is a
  string (possibly empty) natively or null in simulation; MTU is bytes, `up` is
  administrative state, addresses are prefix strings, ownership is `managed`,
  `unmanaged` or `loopback`. Read-only adopted parents are unmanaged in this
  inventory. All array fields are present. No WAN/LAN role is guessed.
  Unsupported kinds and loopback are visible but not editable as Ethernet.
  Simulator returns simulated inventory only.
- Discovery is read-only and independent of configured-state/service health:
  `200` inventory, `400` query parameters, `401` invalid/missing key,
  `403` missing permission, `405` POST, `503` read failure. Preserve errors;
  never replace them with an empty inventory.
- Existing **`GET /api/v1/interfaces`** retains managed-configuration semantics;
  it is not broadened into host inventory. Other observed-state endpoints
  retain their observation error behavior.
- Existing **`POST /api/v1/transactions`** accepts interface `kind: "ethernet"`
  for an already-existing Ethernet/veth device. Same required name, role
  (`wan`/`lan`), MTU 1280..65535, `up` boolean and static `addresses` fields.
  No MAC-change, DHCP-client or hardware-create/delete field is added.
  Ethernet supports the existing DHCPv4 relay constraints.
  `interfaces.write` and `transactions.write` remain required;
  routes/relay/services retain their existing change-specific permissions.
- Route `table`, policy-rule `table`, and monitor `routing_table` now accept
  **254** (main) as well as 10000..19999. Policy-rule priorities remain
  10000..19999. Other request shapes, confirmation 10..300-second units,
  revisions, rollback, status/error envelopes and CORS remain unchanged.
- Forwarding remains an operator prerequisite. Forwarding sysctls stay
  unsupported because collateral device/RA changes are not yet safely captured
  for rollback; do not expose a supported forwarding toggle or promise complete
  host-subsystem management. Roles do not acquire DHCP or install NAT.
- Ethernet identity is name/kernel-kind/MAC, plus index within the same boot;
  a reboot may change index. Snapshots restore selected NIC settings, not the
  state of a competing DHCP/routing manager. Kernel-connected/autoconfiguration
  route effects intrinsic to selected-interface edits are not a separate
  reversible foreign-routing snapshot. Unrelated links are not taken over.

### Required frontend tasks and coordination

1. Add a discovered-NIC inventory separate from the managed draft. Refresh via
   the new endpoint and show current link identity, state and addresses.
2. Offer explicit **Manage this interface** for eligible Ethernet/veth NICs;
   add `ethernet` to client unions and editors. Require an explicit role and
   review static addresses. Do not import all discovered links or assign WAN
   from an interface name. Discovery values can fail candidate validation.
3. Include Ethernet in VLAN-parent and DHCP-relay eligible choices. Permit
   main table 254 in route/policy/monitor forms while preserving other bounds.
   Keep unsupported forwarding controls disabled and explain the prerequisite.
4. Explain that changing a management NIC can disconnect the UI/SSH connection.
   Keep the draft on transport errors, reconcile transactions before retrying,
   and never auto-confirm or treat a provisional apply as committed.
   Removing Ethernet means releasing managed settings, not deleting hardware.
5. Deploy the matching backend before enabling these forms. Do not reset
   incompatible state or propose migration/compatibility windows. Operators
   preserve console access and stop competing managers on selected NICs.
   No claim that simply starting a container configures host routing is valid.
