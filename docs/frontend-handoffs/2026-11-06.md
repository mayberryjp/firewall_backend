## 2026-11-06-01 Browser-free local API-key setup

- **Priority:** normal. **Classification:** optional operator-help update.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased local changes; no publication or deployment
  claimed.
- **Contract impact/recommended release:** additive, next automatic calendar
  version. No HTTP or persisted-identity schema change.

### Behavior and affected surfaces

Previously normal device key creation required website onboarding. A Linux root
console can now run `sudo netcontrold --create-api-key console` against the
running daemon, then connect with `ssh -p 2222 apikey@127.0.0.1` using the displayed
key as its password. Fresh devices prompt for username and hidden password twice.
An atomic credential update saves the completed account/key; existing account
passwords, keys and sessions are preserved. Existing pending onboarding is
completed, making its pending keys usable. This command creates a full-permission
device key, not a scoped key or an SSH account password.

No HTTP methods/paths are added or changed. Existing surfaces remain:

- `GET /auth/status`: existing stage/authenticated/configured/username schema.
  Browser-free setup makes `configured` true; an unauthenticated browser uses
  the existing login stage without gaining a session or API key.
- `POST /auth/login`: existing device username/password authentication.
- `GET /auth/keys` and `DELETE /auth/keys/{id}`: existing authenticated device
  session required; local keys are listed/masked and revoked normally.
- API-key-authenticated `/api/v1/*` and SSH: existing permissions and revocation
  behavior; device onboarding remains a gate, now also completed locally.

No response types, nullability, units, request defaults or HTTP status codes
change. Local validation retains username 1..64 bytes, password 12..72 bytes,
key name 1..80 bytes, trimmed/control-free names, unique key names and 100-key
limit. Password confirmation mismatch and invalid input fail without mutation.
Key output cannot be retrieved again; unknown outcomes require inspecting and
revoking the named key, not automatic retries.

### Optional frontend tasks and deployment

- Add browser-free root-console setup instructions to onboarding/help.
- Explain that the account password is for website login; the API key is the
  SSH password. Never embed passwords or generated keys in URLs or telemetry.
- Continue deriving onboarding from `/auth/status`; do not assume every completed
  account was configured in this browser.
- Link key listing/revocation for lost displayed output and warn against terminal
  recording, redirected output or shared default passwords.

Deploy the updated daemon first. Linux host device mode automatically provides
root-owned `/run/netcontrol/control.sock` (directory 0700, socket 0600), with
root peer-credential checks; explicit custom paths must match daemon/client.
Non-Linux and externally managed `--auth-file` mode are unsupported. SSH must
still be enabled/reachable; no firewall permit or network configuration is added.
No frontend/backend simultaneous rollout or compatibility window is required.

### Acceptance and evidence

- Fresh local setup: hidden/confirmed password, key works immediately, subsequent
  web login/key listing works with the configured device account.
- Existing account: password unchanged; new key works and revocation invalidates
  it. Pending account completion activates its previously pending keys.
- Browser without a session: configured login stage, no automatic authorization.
- Non-root, insecure paths, malformed framing, password mismatch, duplicate names,
  key limit and credential persistence failure must remain explicit failures.
- See [journal](../journal/2026-11-06.md) for actual backend results and remaining
  browser/native-appliance acceptance.

## 2026-11-06-04 Active VLAN ownership recovery

- **Priority:** high for affected operator troubleshooting.

### Previous and new behavior

Affected `POST /api/v1/interfaces/adopt-vlan` and root `--configure-lan` ownership
recovery. Previously raw address-packet comparison included kernel timestamps
and dump ordering. Reconfiguration or the recovery code's own address restoration
could cause a false 503 and retain an intent that could not progress.
The old check also required mutable settings to stay frozen before handover.

Recovery now verifies immutable VLAN identity, releases networkd ownership,
reapplies captured settings on that VLAN and verifies their configuration.
External address/MTU/up changes during handover are overwritten on the selected
VLAN. Raw snapshots remain available for recovery, while comparison excludes
creation/update timestamps and ordering. Genuine identity/configuration changes
after apply still fail explicitly. Unrelated saved state/interfaces are retained.

The request remains exactly `{name,parent,id}`, for example:

```json
{"name":"vlan50","parent":"eth1","id":50}
```

Existing API-key authentication and `interfaces.write` plus `transactions.write`
remain required. Existing `200 {revision,interface}`, validation/auth/conflict
errors and 503 recovery/native failures remain unchanged. No new fields, defaults,
units, nullability or validation limits. See item 03 and the canonical spec.

## 2026-11-06-05 DHCP relay server reply hops

- **Priority:** high for DHCP interoperability troubleshooting.
- **Classification:** optional operator help; no client types/forms change.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working-tree fix, not in `2026.11.06.8`.
- **Contract/recommended release:** protocol fix; next automatic calendar version.

### Previous and new behavior

The relay required server replies to echo BOOTP hops `1`. RFC 2131 table 3
specifies hops `0` for DHCPOFFER, DHCPACK and DHCPNAK. Such replies could arrive
from the configured server with correct transaction/client identity and giaddr
yet be discarded before downstream delivery.

Ignore hops on server replies. Request hop/chaining checks, configured upstream
and UDP source port, transaction/client identity, flags, giaddr and on-link
checks remain. No configuration edits, additional permits or state reset are
required solely to correct this protocol mismatch.

No HTTP methods/paths, request/response fields, nullability, defaults, units,
permissions, authentication or status/error codes change. Existing per-interface
`dhcp_relay` configuration and `GET /api/v1/services/dhcp-relay/status` remain.

### Frontend tasks, deployment and acceptance

- Optionally update troubleshooting help: a running worker and a captured
  upstream Offer do not prove downstream delivery. Correlate transaction ID,
  client MAC, giaddr and downstream UDP 68 traffic.
- Deploy the fixed backend using the normal validated release upgrade. Do not
  instruct operators to change server hops, reset state or allow all firewall
  input. No frontend rollout coordination or operator schema conversion.
- Acceptance: Offer/ACK/NAK with zero reply hops reach the client; wrong giaddr
  and non-replies remain rejected. Validate a full Discover/Offer/Request/ACK
  exchange and lease acquisition on the affected topology.
- Backend: six focused DHCP tests, services all-target Clippy, daemon build and
  formatting passed. Actual server/relay/client packet delivery remains unverified.

## 2026-11-06-06 Bounded MQTT topic publications

- **Superseded:** [2026-11-06-07](#2026-11-06-07-consolidated-mqtt-with-32-mib-payloads)
  restores consolidated publications at the user's request. The following
  describes the historical split-topic decision, not the current contract.

- **Priority:** high; resolves oversized discovery/state collection failures.
- **Classification:** required deployment/MQTT-consumer changes; optional UI help.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree, not published/deployed.
- **Contract/recommended release:** breaking MQTT topic/payload change;
  next automatic calendar version.

### Previous and new contract

Previously one retained device-discovery message and one nonretained state
message each had a 1 MiB limit. Large valid sensor sets could therefore fail
collection before any telemetry reached the broker. The user chose splitting,
not increasing the bounded message size.

New QoS-1 publications:

| Purpose | Topic | Retained | Payload |
| --- | --- | --- | --- |
| Sensor discovery | `homeassistant/sensor/netcontrol_<device_id>/<component_id>/config` | yes | Standard sensor configuration, shared device/origin metadata, stable `unique_id`, templates/expiry and exact `state_topic`; no `components` envelope |
| Metrics | `netcontrol/<device_id>/state/metrics/<hash-prefix>` | no | Collection timestamp and subset of `metrics` |
| Structured section | `netcontrol/<device_id>/state/<section>` | no | Collection timestamp and original section value |
| Availability | `netcontrol/<device_id>/availability` | yes | Existing `online`/`offline` values and LWT |

`<hash-prefix>` starts with two lowercase SHA-256 hex characters of the component
ID and expands as necessary to split oversized buckets. Discovery changes before
a bucket's reassigned state publishes; clients follow its `state_topic`, not a
hardcoded hash. Sensor IDs, units, classes, precision, null/unknown semantics and
three-interval expiry remain. Missing source measurements are not invented.

Synthetic metric-message example (the topic is supplied by discovery):

```json
{"collected_at_unix":1793942400,"metrics":{"uptime":60}}
```

Synthetic structured-section example:

```json
{"collected_at_unix":1793942400,"process_health":{"status":"healthy"}}
```

Sections are `bgp`, `link_diagnostics`, `process_health`, `active_alerts`,
`statistics_available` and `telemetry_sources`, with their existing exact
types/content. All messages for a sample share the timestamp. Publication is not
atomic; QoS 1 can duplicate messages. No aggregate `/state` or monolithic device
discovery is published. Online availability is queued after all state parts;
last-published time requires acknowledgments for the entire batch.

At most 4096 entities, including merged retained entities, and 1 MiB serialized
UTF-8 bytes per message. If one sensor configuration, metric value/envelope or
structured section itself cannot fit, report the payload class, actual size and
limit without contents. Do not truncate or enqueue a partial sample. Discovery
removal is one empty retained message per removed sensor, with the durable
manifest saved before publishing and finalized only after batch acknowledgments.

No HTTP method/path, authentication/permissions, MQTT configuration fields,
request validation/status codes or frontend client types change. The existing
`GET /api/v1/services/mqtt/status` may show the more specific bounded-payload
error. Historical MQTT handoffs describing monolithic topics are superseded by
this item and the canonical spec.

### Required deployment and consumer actions

1. Coordinate a publisher stop/disable, broker cleanup and the new deployment;
   do not leave old and new publishers active with the same identity.
2. Broker administrator: clear the former retained
   `homeassistant/device/netcontrol_<device_id>/config` by publishing an empty
   retained payload. The backend does not implement a compatibility publisher,
   automatic broker-state conversion or persisted-state migration.
3. Allow retained publication/removal on
   `homeassistant/sensor/netcontrol_<device_id>/+/config`, state publication on
   `netcontrol/<device_id>/state/#`, existing availability, and subscription to
   `homeassistant/status`. Brokers must support the bounded packets and QoS 1.
4. Update custom consumers formerly reading `/state` to assemble metric shards
   and sections by timestamp. Missing keys in a shard are not deletions. Follow
   discovery for sensor/topic mappings. Do not assume online alone verifies HA
   ingestion or that messages across topics form an atomic snapshot.
5. Keep device identity/password references/private MQTT store. Verify HA
   rediscovery and entity-registry/customization continuity explicitly; stable
   unique IDs alone are not proof those survive a change in discovery methods.
6. Optional UI/operator help: explain topic/ACL changes, payload size errors and
   unacknowledged-batch failures without exposing credentials or payload contents.

### Acceptance and evidence

- Verify a 4096-entity sample with aggregate discovery and state both over 1 MiB:
  each final payload at most 1 MiB, every entity/value represented once, preserved
  decimal precision/nulls/types, valid sensor mapping and shared timestamps.
- Exercise oversized hash-bucket subdivision, topic reassignment, bounded
  indivisible-unit errors, partial-source retention, entity deletion, restart
  re-announcement and repeated idempotent cleanup.
- Verify broker disconnect/reconnect, withheld acknowledgments, birth refresh
  and confirmed disable/offline behavior. No running/last-published success until
  the entire batch is acknowledged.
- Actual commands/results are recorded in the journal. Real Home Assistant,
  production broker ACLs/limits and the appliance deployment remain unverified.

## 2026-11-06-07 Consolidated MQTT with 32 MiB payloads

### Exact contract

No HTTP method/path, authentication, permission, MQTT configuration schema,
request validation or response/status code changes. Existing
`GET /api/v1/services/mqtt/status` (`state.read`) retains its shape and reports
collection errors through the existing error field.

| Purpose | Previous split topic | Current topic | Retained |
| --- | --- | --- | --- |
| Discovery | `homeassistant/sensor/netcontrol_<device_id>/<component_id>/config` | `homeassistant/device/netcontrol_<device_id>/config` | yes |
| Full state | `/state/metrics/<hash-prefix>` and `/state/<section>` under the device base | `netcontrol/<device_id>/state` | no |

QoS 1 throughout; subscription to `homeassistant/status` remains. Discovery has
shared `device`, `origin`, `availability_topic`, `qos: 1`, the aggregate
`state_topic`, and `components` keyed by existing stable component IDs. Each
component keeps `platform: "sensor"`, `unique_id`, template, units/classes and
three-interval expiry. No hash buckets, per-sensor configurations or separate
section publications remain.

State contains one collection timestamp (Unix seconds), all metrics and all
structured sections. Synthetic shape-only example (values are not live data):

```json
{
  "collected_at_unix": 1793952000,
  "metrics": {"uptime": 60, "revision": "2026.11.06.1"},
  "bgp": {"state": "unavailable", "neighbors": []},
  "link_diagnostics": {"status": "unavailable", "signals": []},
  "process_health": {"status": "unknown"},
  "active_alerts": [],
  "statistics_available": false,
  "telemetry_sources": {
    "network": false, "protocols": false, "host": false,
    "services": false, "bgp": false, "firewall": false, "sando": false
  }
}
```

Existing metric/section types, exact decimal counter strings, nullability and
source-specific unknown semantics remain. The example is not an exhaustive
metric inventory. One message carries the complete sample, not an atomic kernel
read. QoS 1 may duplicate it. Online queues after state; last-published time and
manifest finalization still require the whole batch's acknowledgments.

Limits: 4096 entities including merged retained components; **32 MiB =
33,554,432 serialized UTF-8 bytes** for each complete discovery/state payload.
Outbound MQTT packets allow 4096 additional bytes; inbound remains 1 MiB.
Oversized discovery/state/removal errors expose class, actual size and cap, never
payload contents. No truncation or partial sample enqueue. Removal sends
platform-only component entries in one bounded device-discovery update, then
the current discovery; durable write-before-publish allows retry after restart.

### Required frontend, broker and deployment actions

1. Coordinate publisher stop/disable, cleanup and rebuilt-daemon deployment; do
   not run publishers concurrently with the same identity.
2. Broker administrator: allow the device-discovery topic, aggregate state,
   existing availability and birth subscription. Set any payload limit to at
   least 33,554,432 bytes and packet limit to at least 33,558,528 bytes. Mosquitto
   names these `message_size_limit` and `max_packet_size`. Review memory budgets
   for the broker and subscribers. Netcontrol cannot raise remote broker limits.
3. Before enabling aggregate discovery, clear every retained former sensor
   discovery configuration using an empty retained payload on its exact topic.
   Do not publish to wildcards or clear the current device-discovery topic.
   No automatic broker conversion, compatibility publisher or saved-state
   migration is provided. Keep private identity/password/manifest files.
4. Custom consumers must subscribe to `/state` and read each complete object;
   remove hash/section assembly logic. No HTTP client types or forms change.
5. Verify HA rediscovery and entity/customization continuity explicitly. Stable
   IDs do not guarantee continuity across discovery methods. Do not promise
   consolidation fixes source failures: absent/null measurements and expiry

## 2026-11-06-08 Automatic DHCP relay input permits

- **Priority:** high; resolves DHCP Discover drops despite enabled relay.
- **Classification:** required frontend/operator guidance and generated-counter
  handling; no new form fields or HTTP client types.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree, not published/deployed.
- **Contract/recommended release:** runtime fix with additive generated counters
  and intentional input-policy behavior change; next automatic calendar version.

### Previous versus new behavior

Previously an enabled relay could listen on UDP 67 while input policy dropped
its clients' broadcasts. Operators needed independent manual UDP67 input rules
on client and server ingress interfaces. Enabling relay now derives the following
system-owned IPv4 input accepts before configured input rules, including drops:

| Traffic | Exact scope |
| --- | --- |
| Client requests | Enabled relay ingress interface; UDP source 68, destination 67; destination limited broadcast or selected relay IPv4 address |
| Server replies | Configured server source IPv4 address; UDP source/destination 67; destination that relay's selected IPv4 address; any ingress |

Packet/transaction/source/on-link checks still run in the relay worker. Nothing
opens TCP, other UDP ports, IPv6, management access, forwarding or NAT. Operators
still provide DHCP scopes, routes, server return paths and external firewall
permissions. Core validation, native rules and workers now share the documented
lexicographically sorted canonical-prefix relay-address selection, including
duplicate-selected-address validation.

Derived rules are regenerated in normal apply, startup repair, rollback,
server/address edits and interrupted-intent recovery. Disable/remove relay to
withdraw its exceptions. No manual rule is appended, removed or relabeled.
Existing conntrack established/related behavior is unchanged; disabling relay
does not flush flows or remove existing manual DHCP permits.

### HTTP, authentication and payload contract

- `POST /api/v1/transactions`, followed by
  `POST /api/v1/transactions/{id}/confirm` or
  `POST /api/v1/transactions/{id}/rollback`: unchanged full candidate/envelope,
  authentication, statuses and confirmation semantics. Relay edits retain
  `transactions.write` and `interfaces.write`; changing manual firewall rules
  separately still requires `firewall.write`. No extra permission is needed for
  the narrowly derived service exceptions.
- `GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}` and saved
  configuration keep the existing `dhcp_relay` shape. Derived accepts are not
  inserted into `firewall.input.interfaces`, interface JSON, drafts or packages.
  There are no new fields/defaults/units/nullability or HTTP status codes.
- `GET /api/v1/services/dhcp-relay/status` (`state.read`) and
  `POST /api/v1/services/dhcp-relay/reconcile` retain their existing contract.
  Reconcile repairs workers, not manual/native firewall drift; do not make it
  an automatic retry or a substitute for the normal network transaction.
- `GET /api/v1/statistics/firewall` (`state.read`) adds logical input rows
  `input:generated/input/dhcp_relay/<interface>/clients` and
  `input:generated/input/dhcp_relay/<interface>/servers`. They have
  `config_path:null`, `origin:"system"`, `import_source:null`; client expansion
  is two rules and server expansion is one per configured server. Packet/byte
  counters remain exact decimal strings. Ruleset identity now includes the
  compiled input plan, so relay edits can change `ruleset_id` without editing
  saved firewall JSON. Deny-log rule indexes include generated rules as before.

Synthetic unchanged interface fragment (not a complete transaction):

```json
{"name":"lan0","addresses":["192.0.2.1/24"],"dhcp_relay":{"enabled":true,"servers":["198.51.100.40"]}}
```

### Required frontend and deployment work

1. Replace advice to create manual DHCP input permissions with an explanation
   of automatic, narrowly scoped service exceptions and their precedence over
   input drops. Explain that disabling relay withdraws derived rules only.
2. Do not add, delete or hide user-owned rules automatically. Do not synthesize
   these exceptions into candidate firewall JSON or require `firewall.write`
   solely for the relay toggle.
3. Render generated counters as system-owned/noneditable, linked to the managed
   interface name. Refresh after apply/rollback and treat `ruleset_id` as opaque.
4. Distinguish relay configured/running, firewall admission, server reachability
   and actual lease delivery; none alone proves the others.
5. Deploy this backend before advertising automatic permits. Startup repairs
   existing enabled relays through the existing owned firewall refresh; no
   appliance-state reset, compatibility mode or migration is introduced.

- Restart, server/address changes, rollback, interrupted native intent recovery

- Generated counter layout, identity changes and native drift protections remain
