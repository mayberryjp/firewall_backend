## 2026-11-06-01 Browser-free local API-key setup

- **Priority:** normal. **Classification:** optional operator-help update.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased local changes; no publication or deployment
  claimed.
- **Contract impact/recommended release:** additive, next automatic calendar
  version. No HTTP or persisted-identity schema change.

### Behavior and affected surfaces

Previously normal device key creation required website onboarding. A Linux root
console can now run `sudo netcontrold --create-api-key console` against the
running daemon, then connect with `ssh -p 2222 apikey@127.0.0.1` using the displayed
key as its password. Fresh devices prompt for username and hidden password twice.
An atomic credential update saves the completed account/key; existing account
passwords, keys and sessions are preserved. Existing pending onboarding is
completed, making its pending keys usable. This command creates a full-permission
device key, not a scoped key or an SSH account password.

No HTTP methods/paths are added or changed. Existing surfaces remain:

- `GET /auth/status`: existing stage/authenticated/configured/username schema.
  Browser-free setup makes `configured` true; an unauthenticated browser uses
  the existing login stage without gaining a session or API key.
- `POST /auth/login`: existing device username/password authentication.
- `GET /auth/keys` and `DELETE /auth/keys/{id}`: existing authenticated device
  session required; local keys are listed/masked and revoked normally.
- API-key-authenticated `/api/v1/*` and SSH: existing permissions and revocation
  behavior; device onboarding remains a gate, now also completed locally.

No response types, nullability, units, request defaults or HTTP status codes
change. Local validation retains username 1..64 bytes, password 12..72 bytes,
key name 1..80 bytes, trimmed/control-free names, unique key names and 100-key
limit. Password confirmation mismatch and invalid input fail without mutation.
Key output cannot be retrieved again; unknown outcomes require inspecting and
revoking the named key, not automatic retries.

### Optional frontend tasks and deployment

- Add browser-free root-console setup instructions to onboarding/help.
- Explain that the account password is for website login; the API key is the
  SSH password. Never embed passwords or generated keys in URLs or telemetry.
- Continue deriving onboarding from `/auth/status`; do not assume every completed
  account was configured in this browser.
- Link key listing/revocation for lost displayed output and warn against terminal
  recording, redirected output or shared default passwords.

Deploy the updated daemon first. Linux host device mode automatically provides
root-owned `/run/netcontrol/control.sock` (directory 0700, socket 0600), with
root peer-credential checks; explicit custom paths must match daemon/client.
Non-Linux and externally managed `--auth-file` mode are unsupported. SSH must
still be enabled/reachable; no firewall permit or network configuration is added.
No frontend/backend simultaneous rollout or compatibility window is required.

### Acceptance and evidence

- Fresh local setup: hidden/confirmed password, key works immediately, subsequent
  web login/key listing works with the configured device account.
- Existing account: password unchanged; new key works and revocation invalidates
  it. Pending account completion activates its previously pending keys.
- Browser without a session: configured login stage, no automatic authorization.
- Non-root, insecure paths, malformed framing, password mismatch, duplicate names,
  key limit and credential persistence failure must remain explicit failures.
- See [journal](../journal/2026-11-06.md) for actual backend results and remaining
  browser/native-appliance acceptance.

### Previous and new installation workflow

Previously Ubuntu installation required a manually uploaded Actions artifact,
GitHub CLI authentication and `--run-id`. The installer now resolves the latest
published stable GitHub Release once, downloads that version's existing Ubuntu
binary/manifest, and fetches its systemd unit from the same immutable tag's
source. It verifies manifest schema/target/version, binary size/SHA-256/amd64
ELF, compiled version and required daemon options before installation.

No HTTP API methods/paths, application authentication/permissions, response
fields/types/nullability/defaults/units, status codes, saved configuration or
network provisioning policy change. This is a deployment contract change, not
a new API. No frontend types/forms or JSON examples are needed.

### Optional frontend tasks and operator prerequisites

Replace any run-ID/workflow-dispatch/GitHub-login installation instructions with:

```sh
curl --proto '=https' --tlsv1.2 -fL https://raw.githubusercontent.com/mayberryjp/firewall_backend/main/install.sh -o /tmp/netcontrol-install.sh
# Inspect the script, then run from the local console.
sudo bash /tmp/netcontrol-install.sh
```

Keep optional paired `--wan NAME --lan NAME` and `--lan-address CIDR`. The default
LAN remains `192.168.0.1/24`; initial Ubuntu WAN DHCP/manager prerequisites and
console/disconnection warnings are unchanged.

Ubuntu amd64/systemd, working internet addressing/gateway/DNS and public HTTPS
repository/release access are prerequisites. APT installs Python 3 for metadata
verification in place of GitHub CLI; protocol services remain Rust. No GitHub
login, token or CI run ID is requested. Missing releases/assets/tagged unit,
rate limiting, invalid metadata/hash/version and download errors stop the
installer, with no CI-artifact or source-build fallback. The assets are unsigned;
the trust boundary is verified HTTPS plus the repository/account, not a publisher
signature. Existing signed `.ncpkg` packages are unchanged.

Publish the updated installer through an authorized commit/push before sharing
the raw `main` URL as containing this fix. No coordinated frontend rollout is
required, and no deployment or frontend delivery is claimed.

### Follow-up: retry after failed initial network capture

Status remains **Pending frontend review**. A failed capture can create only
the empty journal lock before it reports an unsupported inherited configuration.
The installer now retains/reuses an existing lock only if no journal or appliance
environment exists and the lock is root-owned, mode 0600, empty, singly linked,
regular, not a symlink and currently unlocked. The `flock` command from Ubuntu's
`util-linux` checks it; failure or missing tooling stops installation.
The daemon independently acquires the same exclusive lock during initialization.

Optional troubleshooting text should recommend correcting the original network
capture error and retrying the updated installer, not deleting locks or appliance
state. An existing journal/environment, active lock or unsafe lock still requires
operator investigation. This changes neither API schemas/authentication nor
saved-state formats and creates no general reinstall/reset path.

The full installer regression suite passed with 14 filesystem/real-lock scenarios,
including retry after lock release and unchanged lock inode/content/metadata.
Actual Ubuntu appliance retry remains unverified. No push/deployment claimed.

## 2026-11-06-03 Interactive and tagged LAN setup

### Exact API contract and required tasks

New `POST /api/v1/interfaces/adopt-vlan`, previously unavailable, requires normal
API-key authentication and `interfaces.write` plus `transactions.write`.
No query parameters or extra JSON fields; all fields are required/nonnullable:

```json
{"name":"vlan50","parent":"enp2s0","id":50}
```

Names are distinct, 1..15 ASCII bytes, letters/digits/underscore/hyphen/dot,
excluding `lo`, `.` and `..`. `id` is an integer 1..4094, with no default or unit.
The parent must be managed Ethernet and the live unmanaged VLAN must match.
Register the request and `200 {revision,interface}` response using existing
canonical revision and `Interface` types. The imported interface is unassigned;
supported live addressing/MTU/settings are preserved, not replaced by defaults.
Refresh saved state/base revision after success. No auto-retry/poll/prefetch.

Expose 400 malformed/query/unknown-field errors, 422 invalid names/ID/parent,
409 busy/already-managed/drift/conflicting recovery, 503 native refusal/failure
and 500 persistence failure. Existing 401/403 auth and 405 method behavior applies.
Render server detail; do not treat failure as an empty inventory or success.
After interruption, explain that recovery may be pending before another write.

This is an explicit ownership operation, not a confirmed network transaction.
Follow it with the existing reviewed confirmed configuration workflow to assign
LAN role/address/firewall/NAT. Rollback retains the imported baseline. A dedicated
UI is optional; do not silently adopt a link merely because it was selected.

### Installer/help and deployment coordination

This supersedes item 02's unprompted default-NIC guidance. Interactive fresh
installation asks for the physical or existing VLAN LAN and IPv4 host/prefix.
Use the actual VLAN name, not `NAME@PARENT`. Unattended installation requires
both `--lan NAME` and `--lan-address CIDR`; `--wan NAME` is independent.
Existing installations are not reinstalled/reset. Updated root CLI can correct
an unchanged factory LAN with `--configure-lan`, then explicit confirmation
within 120 seconds; customized policy is refused.

Publish/deploy a matching daemon before offering adoption or tagged provisioning.
The installer rejects binaries without the VLAN options. Native adoption needs
host mode, networkd/resolved, explicit source `IPv6AcceptRA=no`, no DHCP and only
kernel-connected routes; unsupported settings fail. Do not prescribe deleting
state or external VLANs. After confirmed correction, update the deployment HTTP
listener separately if needed; do not restart/change it before confirmation.
No compatibility window, data reset or migration is introduced.

## 2026-11-06-04 Active VLAN ownership recovery

- **Priority:** high for affected operator troubleshooting.
- **Classification:** optional operator/recovery help; no new client/form work.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working-tree fix; not published/deployed.
- **Contract/recommended release:** runtime recovery fix, next automatic calendar
  version. No schema, authentication, permissions or status-code changes.

### Previous and new behavior

Affected `POST /api/v1/interfaces/adopt-vlan` and root `--configure-lan` ownership
recovery. Previously raw address-packet comparison included kernel timestamps
and dump ordering. Reconfiguration or the recovery code's own address restoration
could cause a false 503 and retain an intent that could not progress.
The old check also required mutable settings to stay frozen before handover.

Recovery now verifies immutable VLAN identity, releases networkd ownership,
reapplies captured settings on that VLAN and verifies their configuration.
External address/MTU/up changes during handover are overwritten on the selected
VLAN. Raw snapshots remain available for recovery, while comparison excludes
creation/update timestamps and ordering. Genuine identity/configuration changes
after apply still fail explicitly. Unrelated saved state/interfaces are retained.

The request remains exactly `{name,parent,id}`, for example:

```json
{"name":"vlan50","parent":"eth1","id":50}
```

Existing API-key authentication and `interfaces.write` plus `transactions.write`
remain required. Existing `200 {revision,interface}`, validation/auth/conflict
errors and 503 recovery/native failures remain unchanged. No new fields, defaults,
units, nullability or validation limits. See item 03 and the canonical spec.

### Frontend tasks, deployment and acceptance

- Optionally update recovery help: deploy the fixed daemon, let startup resume
  retained ownership recovery, then perform/confirm the intended LAN transaction.
  Completing adoption alone does not move LAN role/firewall/NAT.
- Do not advise deleting state/VLANs, resetting the appliance or automatically
  retrying the mutation. Continue showing actual backend errors and refreshing
  saved state/base revision following successful adoption.
- Deploy the backend first. No frontend rollout coordination, schema conversion
  or compatibility window is required. Existing native host/networkd/resolved
  capture prerequisites remain; this fixes the active handoff/recovery stage.
- Acceptance: recover after address reapplication changes timestamps; overwrite
  selected-VLAN address/MTU drift, reject replacement identity, preserve unrelated
  interfaces and verify confirmed LAN behavior after ownership completes.
- Backend: nine focused native VLAN tests passed, including privileged kernel
  restore/retry fixtures; native Clippy passed. Real networkd D-Bus handoff,
  appliance recovery and frontend integration remain unverified.

### Shared physical-interface takeover extension

The same active restore/verification now covers physical-interface inheritance.
Startup reasserts exclusions for every still-owned physical interface, including
those without an inheritance receipt, and reconciles the saved desired
configuration rather than bootstrap addresses. No additional HTTP paths,
request/response fields, permissions, status codes or frontend rollout steps.
Initial manager/capture restrictions remain; this is not arbitrary-stack
takeover. This extends item 04; status remains **Pending frontend review**.

Optional help should explain that physical interfaces and VLANs use the same

### DHCP-backed startup recovery correction

**Backend availability:** additional Unreleased runtime fix, not included in
`v2026.11.06.7`. Recommended release: next automatic calendar version.
This extends item 04; optional operator help remains **Pending frontend review**.

Affected behavior: restarting with a pending adoption from
`POST /api/v1/interfaces/adopt-vlan` or root `--configure-lan`. Previously startup
verified the existing configuration before initializing DHCP runtime. Even a
valid saved WAN lease could then produce address drift, prevent daemon startup
and leave the HTTP/SSH/local-control listeners unavailable.

Recovery now initializes committed DHCP clients and restores valid durable
leases/lease intents before checking the baseline, without accepting arbitrary
live addresses. Existing request/response fields, authentication, permissions,
validation limits and running-daemon status/error contracts are unchanged.
No new HTTP method/path or frontend type/form work.

- Optional help: distinguish daemon startup failure from a LAN request refusal.
  Show actual connection/startup errors; do not advise clearing WAN addresses,
  deleting adoption/lease state or automatically retrying mutations.
- Deploy the additional backend fix before retrying retained-intent recovery;
  no frontend deployment coordination or state conversion is needed. The
  original release alone does not include this correction.
- Acceptance: restart with a valid saved WAN DHCP lease and a pending adoption,
  including native ownership saved before core completion. WAN addressing and
  leased gateway routes remain verified; a genuinely extra WAN address still
  fails. After recovery, perform and confirm the intended LAN move separately.
- Backend validation: the privileged native regression covers cold lease state,
  both ownership-save stages, unchanged durable lease/ownership and rejection of
  an extra live address. It deliberately stops at an unavailable system D-Bus
  boundary; full manager handover/appliance acceptance remains unverified.
