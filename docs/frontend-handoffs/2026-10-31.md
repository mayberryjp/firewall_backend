# Frontend handoffs - 2026-10-31

## 2026-10-31-01 Interface capability inventory

**Method superseded:** [item 2026-11-04-02](2026-11-04.md#2026-11-04-02-get-capability-refresh-and-api-explorer-registration)
changes refresh to GET-only and requires both API Explorer registrations.
The original POST description below is historical; use the current
[canonical contract](../../FRONTEND_SPEC.md#interface-capability-snapshots).

- **Priority:** normal. **Classification:** required client contract review;
  optional capability-inspector UI. **Status:** Pending frontend review.
- **Backend availability:** Unreleased; no commit, release, deployment or
  notification performed. **Contract impact:** additive; next automatic calendar
  version, no manual version bump.
- **Previous behavior:** only live basic inventory at
  `GET /api/v1/interfaces/discovered`; no persisted hardware-capability API.
- **New methods/paths:** `GET /api/v1/interface-capabilities` (`state.read`)
  returns the last persisted snapshot or JSON null before discovery.
  `POST /api/v1/interface-capabilities/refresh` (`state.read` plus
  `interfaces.write`) accepts no body/query, scans once and saves before 200.
  Both use existing API-key authentication. No changes to the existing live
  discovery response, desired configuration, transactions or permission names.
- **Errors:** 400 body/query, 401 authentication, 403 missing permission,
  405 unsupported method, POST 409 during upgrade/restart, 503 fatal discovery,
  500 persistence. Failures preserve the prior snapshot. A completed partial
  scan returns 200 with errors and replaces prior evidence.
- **Response contract:** UTC `collected_at`, backend `scope`, nested `inventory`
  with source/status, nullable kernel release/boot ID, errors and name-sorted
  interface rows. Full types/nullability are in the
  [canonical spec](../../FRONTEND_SPEC.md#interface-capability-snapshots).
  Numeric speeds are Mbps; PCI identity is hex strings; CPU/RX-queue masks are
  hexadecimal strings, table sizes are entry counts, unknown NUMA is null.
  Supported/advertised/partner mode lists retain raw bit IDs and non-speed bits.
  Feature support and nullable enabled state are independent; evidence is not
  an operational test. DPDK and accelerated-RFS readiness remain unknown.

### Frontend tasks and coordination

1. Add nullable snapshot/types and a no-body refresh client method. Inventory
   must not be copied into desired-config forms or transaction submissions.
2. Optional inspector: show NIC driver/firmware/PCI IDs, supported versus current
   speed/duplex, queues and feature support/enabled/evidence/reasons. Keep
   unmanaged/down/virtual links visible. Never imply DPDK readiness from a PCI ID.
3. Refresh only on explicit action; disable overlapping requests. Readers can
   inspect persisted state without `interfaces.write`; hide/disable refresh when
   unauthorized. Show never-scanned, partial and stale/cached states explicitly.
4. Preserve the last displayed snapshot on fatal/persistence errors and display
   the server error. Replace it on successful partial refresh; do not fill
   missing fields from old observations.
5. Backend must be deployed before using the endpoints. No external ethtool,
   bpftool or DPDK package is required for this inventory. Physical identity/
   sysfs queue evidence is host-mode only; lab namespaces report omissions.
   This does not provision capabilities or coordinate datapath switching.

### Acceptance and remaining checks

- GET before refresh is null and never scans; authorized no-body POST returns
  persisted data that survives restart without advancing config revision.
- Verify 401/403, wrong methods, body/query 400, partial rendering and fatal-error
  preservation. Verify unknown enabled/support is not rendered as unsupported.
- Filter supported modes on nonnull speed/duplex; unknown future bit IDs remain
  visible. Keep current/advertised/partner capabilities distinct.
- Backend validation results are recorded in the
  [journal](../journal/2026-10-31.md). Physical NIC/firmware diversity and frontend
  end-to-end acceptance remain unverified.
