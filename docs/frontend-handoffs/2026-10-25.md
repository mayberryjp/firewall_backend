# Frontend Handoffs - 2026-10-25

## 2026-10-25-04 WireGuard peer enabled toggle

- Priority: medium. Classification: **required** (new field and control). Status:
  **Pending frontend review**. Availability: Unreleased. Recommended bump: minor;
  baseline unknown. No release, commit, push, deployment or delivery.
- Previous behavior: a WireGuard peer had `public_key`, `endpoint`, `allowed_ips`,
  `persistent_keepalive_seconds` and optional `metadata`; stopping one meant deleting
  it. New: `interfaces[].wireguard.peers[].enabled` boolean. Omission defaults to
  `true` in requests and saved state; explicit `false` is preserved; `null`, strings
  and numbers return `400`. Responses (`/api/v1/state`, `/api/v1/interfaces`,
  transactions, revisions) always include the boolean.
- Endpoints: none new. `POST /api/v1/transactions` (and revision restore) carry the
  field; permissions are `transactions.write` plus `wireguard.write` for any peer
  change (no new permission). Confirmation, rollback, `202`/`200`/`409`/`422`
  behavior are unchanged.
- Synthetic request fragment (inside a complete candidate):

  ```json
  {"public_key":"AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE=","enabled":false,
   "endpoint":"203.0.113.1:51820","allowed_ips":["198.51.100.0/24"],
   "persistent_keepalive_seconds":25}
  ```

- Semantics: a disabled peer is saved everywhere but not installed on the kernel
  device, so its handshake and traffic stop; `enabled: true` installs it again with a
  fresh handshake. Native runtime (`GET /api/v1/runtime` `wireguard[].peers`) lists
  installed peers only, so a disabled peer has no row or counters. Disabled peers
  must still have a valid, unique public key and canonical allowed networks and obey
  the IPv6 policy. A disabled peer may reuse an allowed network used by an enabled
  peer; enabled peers (and one peer's own list) must not duplicate (`422`).
  `enabled` is not part of identity (identity is the public key).
- Frontend tasks: add `enabled` to the `Peer` type; a per-peer toggle and a disabled
  badge/row style; initialize new peers with `true`; preserve explicit `false`
  through drafts, review, restore and export; do not show handshake or byte counters
  for disabled peers or treat a missing runtime row as an error; warn before
  disabling a peer that carries management traffic; keep the "configured is not
  connected" rule.
- Deployment: rebuilt daemon only. Saved configuration that omits the field loads
  with peers enabled (ordinary defaulting; no rewrite, reset or migration). Existing
  `wireguard peer JSON` clients must send `"enabled": false` to keep a peer
  disabled; resending a peer without it re-enables it.
- Acceptance: toggling off removes the peer from `show runtime` after confirm and
  restores it when re-enabled; unconfirmed changes roll back; disabled spare peers may
  share an allowed network, two enabled may not; `null`/`"no"` are `400`; reload and
  restore keep the flag. Backend results are in the journal; browser and physical
  tunnel behavior are unverified.

## 2026-10-25-03 MQTT host health sensors

- Priority: low. Classification: **optional** (documentation only). Status:
  **Pending frontend review**. Availability: Unreleased. Recommended bump: minor;
  baseline unknown. No release, commit, push, deployment or delivery.
- Previous behavior: Home Assistant MQTT streaming published revision, daemon
  uptime, version, interface counters and gateway summaries. New: the same
  publisher also reads `GET /api/v1/statistics/host` internally (`state.read`) and
  adds host-health sensors. No HTTP path, request/response field, permission,
  configuration field or status-endpoint change; existing MQTT settings and the
  `GET /api/v1/services/mqtt/status` schema are unchanged.
- New Home Assistant entities (all sensors, expiring after three intervals):
  `memory_total_bytes`, `memory_available_bytes`, `memory_used_bytes`,
  `swap_total_bytes`, `swap_used_bytes` (B); `load_1m`, `load_5m`, `load_15m`;
  `host_uptime_seconds`; `oom_kills`; PSI 10-second averages (%); per CPU core
  plus total busy percent; per thermal zone temperature (degrees C); per hwmon
  temperature or fan (degrees C or RPM); per local filesystem mount total, used
  and available bytes. Dynamic entities use a hash of their identity as key, with
  stable id-based names; type/label are not shown.
- Semantics to document for operators: CPU busy percent needs two consecutive
  samples and is unknown after (re)connect, a boot change or a counter reset; a
  failed section, sensor or filesystem is unknown, never zero (zero RPM and
  negative temperatures are real); a section that cannot be enumerated keeps its
  existing entities. Caps: 256 CPU rows, 64 thermal zones, 128 hwmon sensors,
  64 filesystems. Disks, per-disk I/O, most VM counters and scheduler gauges are
  not published.
- Frontend tasks: none required. Optionally mention these sensors and the
  rename-in-Home-Assistant note on the MQTT settings screen; the status endpoint
  and `last_published_at_unix` semantics are unchanged.
- Deployment: rebuilt daemon only; no new permission, setting, dependency or
  broker ACL (same topics). Discovery payload size grows with hardware: a very
  large host can reach the 1 MiB discovery limit, which fails collection and shows
  the existing redacted error state.
- Acceptance: with a real broker and Home Assistant, new entities appear under the
  device, per-core values appear from the second sample, and unplugging/removing a
  sensor yields unknown rather than zero. Backend tests are in the journal; real
  Home Assistant ingestion was not tested.
- References: [contract](../../FRONTEND_SPEC.md#614-home-assistant-mqtt-streaming),
  [sensor mapping](../../crates/netcontrold/src/mqtt_host.rs),
  [publisher](../../crates/netcontrold/src/mqtt.rs),
  [journal](../journal/2026-10-25.md#mqtt-host-health-sensors).

## 2026-10-25-02 DHCP-dependent static route lifecycle

- Priority: P1. Classification: **required**. Status: **Pending frontend review**.
- Availability: **Unreleased**. Recommended bump: **patch** for route lifecycle
  correctness; baseline unknown. No release, commit, push, deployment or delivery.
- Previous behavior: DHCP address removal could remove enabled static routes;
  lease updates restored only DHCP routes, leaving state reads at `503`.
  New behavior: enabled IPv4 static routes on DHCP-managed interfaces are
  suspended without a valid matching lease and restored after lease routes on
  acquisition/renewal/address replacement. Configuration address replacement
  also refreshes route presence before installing missing routes.

### Contract and frontend tasks

- Existing authenticated `GET /api/v1/state`, `GET /api/v1/routes`,
  `GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}` and
  `GET /api/v1/runtime` retain `state.read`, methods, paths, schemas, types,
  defaults and nullable/error fields. No new endpoint, permission or field.
  The device-proxy wrapper belongs to the external frontend, not this backend.
- Configuration reads can now return `200` while a DHCP-dependent static route
  is suspended. `enabled: true` remains configured intent, not proof of kernel
  installation. Runtime `dhcp_clients.leases[interface]` uses existing
  `acquired_at` Unix seconds plus `lifetime` seconds; require a matching current
  client and unexpired lease, and inspect `dhcp_clients.errors[interface]`.
  A lease alone is not proof of forwarding or a valid pinned static gateway.
- Synthetic configured route fragment (unchanged schema):
  `{"enabled":true,"destination":"198.51.100.0/24","gateway":"192.0.2.1","interface":"wan0","table":254,"metric":10}`.
  Without a valid `wan0` lease this stays enabled/configured but is not installed.
  Disabled routes stay disabled. IPv6/other-interface routes are not suspended
  by this DHCP lifecycle.
- Keep existing client types, forms, drafts, validation and enable toggles.
  Render "waiting for DHCP" separately from configured-disabled and worker/error
  states. Never submit `enabled:false` or remove a route to reflect suspension.
  Poll runtime at existing cadence; preserve drafts on errors.
- Existing `POST /api/v1/transactions` and confirmation/rollback paths retain
  `transactions.write`, `routes.write` for route changes and
  `interfaces.write` for DHCP changes. No revision/history writes on lease events.
  Pinned gateways are not rewritten; conflicts/unreachable gateways fail explicitly.
  Ordinary observation failures remain `503` with `{error, transaction}`;
  no blanket automatic drift repair or frontend retry loop.

### Deployment and acceptance

- Deploy the rebuilt backend through the normal upgrade path, retaining state,
  native ownership and lease intents. No migration/reset or new operator
  prerequisites; existing native DHCP privileges and host setup still apply.
  Coordinate status wording with the frontend; no data/schema conversion.
- Verify waiting -> acquired -> renewed -> expired -> reacquired without
  changing the toggle, revision or draft. Check static route recovery after
  address changes; confirm disabled routes/other interfaces are unchanged.
  Verify unreachable pinned gateway and foreign-route conflict remain visible,
  not a success badge. Test transaction rollback and daemon restart.
- Backend: 45 native portable tests and all 15 isolated native integration tests
  passed, including new real-kernel lifecycle/rollback/conflict regressions.
  Workspace test/clippy/fmt/build gates passed with stable Rust and locked,
  offline dependencies. Physical appliance and frontend integration remain.

## 2026-10-25-01 Azure Dynamic DNS

- Priority: P1. Classification: **required**. Status: **Pending frontend review**.
- Availability: **Unreleased**; no release/commit/deployment or notification made
  by this task. Recommended bump: **minor** for new functionality; baseline unknown.
- Previous behavior: no Dynamic DNS configuration/client or credential/status API.
  New behavior: Azure **public DNS IPv4 A records**, selected-interface public
  address or NAT-aware detection, with confirmed configuration and write-only secrets.
  No AAAA/private DNS/other providers/force update.

### API and configuration

- `POST /api/v1/services/dynamic-dns/secrets`, API key with `dynamic_dns.write`.
  Strict body `{"client_secret":"synthetic-example-only"}`; 1..4096 UTF-8 bytes,
  no NUL/extra keys. Returns `201 {"secret_ref":"0123456789abcdef0123456789abcdef"}`.
  Secret never returned/read/listed/deleted. Replacement creates a new reference.
- `GET /api/v1/services/dynamic-dns/status`, API key with `state.read`, no query.
  Returns `200 {"entries":[{"name":"azure-wan","state":"current","address":"8.8.4.4","last_checked_at_unix":1792890000,"last_updated_at_unix":1792890000,"error":null}]}`.
  Nullable IPv4 string/address, nullable integer UTC Unix-second timestamps,
  nullable redacted error. States: waiting/disabled/paused/checking/current/error/
  simulated/unavailable. `current` is control-plane confirmation, not DNS propagation.
- Upload/status errors: invalid body/query `400`, bad key `401`, permissions `403`,
  wrong method `405`, unavailable service/storage/capacity `503`; upload conflicts
  with active configuration/recovery/upgrade `409`.
- Optional `config.dynamic_dns` array, default empty, max 32. All entry fields in
  the example below required/non-null; optional standard metadata defaults empty.
  Name unique 1..64 ASCII alphanumerics/underscore/hyphen; enabled boolean;
  interface valid and up/managed when enabled; source enum interface/public_ip;
  tenant/client UUIDs; reference 32 lowercase hex and locally present; exact public
  Azure zone resource ID; relative lowercase record name or `@` (not FQDN/wildcard);
  TTL 30..86400 seconds, interval 60..86400 seconds. Duplicate zone/A-record targets
  refused, including disabled entries. Full ID/name/metadata limits are in the spec.
- `POST /api/v1/transactions` requires `transactions.write`, `dynamic_dns.write`
  and other changed-resource grants; existing `202` submit, `200` confirm/rollback,
  conflict and revision behavior apply. Known type/null/required-field errors `400`,
  semantic/reference/backend availability errors `422`. Existing unknown-config
  pruning and `ignored_fields` warnings apply; never send inline secrets here.
  Settings/references appear in `GET /api/v1/state`, transaction/revision reads and
  `POST /api/v1/revisions/{revision}/restore`; secret plaintext never does.

Synthetic fragment, not a complete transaction:

```json
{"dynamic_dns":[{"name":"azure-wan","enabled":true,"source_interface":"wan0","address_source":"public_ip","tenant_id":"11111111-1111-4111-8111-111111111111","client_id":"22222222-2222-4222-8222-222222222222","secret_ref":"0123456789abcdef0123456789abcdef","zone_resource_id":"/subscriptions/33333333-3333-4333-8333-333333333333/resourceGroups/dns-rg/providers/Microsoft.Network/dnszones/example.com","record_name":"home","ttl_seconds":300,"interval_seconds":60}]}
```

### Frontend tasks and coordination

1. Extend client types/shared drafts and preserve the array/reference through all
   full-config submissions and restores. Implement list/editor with per-entry
   enable, interface/source selector, Azure IDs, relative hostname/apex, TTL,
   interval and metadata. Validate bounds and inspect `ignored_fields`.
2. Mask replacement secret; upload before storing reference in draft. Clear raw
   secret on success/error/dismiss; no logs, URLs, storage or exported drafts.
   Discarded uploads consume the immutable 256-secret store limit.
3. Poll status every 5..10 seconds while visible; join by name, show nullable
   last-known values/timestamps and errors without claiming stale/current data is
   new or recursive DNS propagation verified. Draft changes are not active.
4. Explain that disabling/deleting does not delete the Azure record, and
   configuration rollback cannot undo external DNS writes already sent/completed.
   Public detection contacts ipify and does not solve CGNAT inbound reachability.
5. Coordinate rebuilt daemon/frontend deployment and Azure operator setup:
   public delegated zone, single-tenant Entra app/service principal, DNS Zone
   Contributor at zone scope, secret **value**/expiry, Linux host mode, privileged
   interface binding, exactly one usable selected-interface IPv4, host DNS/routing
   and HTTPS reachability to ipify/login.microsoftonline.com/management.azure.com.
   Public Azure cloud only. All TLS verified; redirects/proxies disabled. Host DNS
   is not source-interface-bound. No schema migration/reset/compatibility window.
6. Back up `<state>.dynamic-dns` with state/history, preserving owner-only files.
   Secrets are plaintext at rest, not encrypted; no automatic pruning.

### Acceptance and evidence

- Verify upload/ref-only persistence, denied reader uploads/settings edits,
  no activity before confirmation, rollback preserving confirmed settings,
  disable/delete without DNS deletion, and missing reference/interface errors.
- Verify both direct and NAT modes, apex/relative names, TTL-only changes, current
  record avoiding PUT, conditional creation/update, alias/multi-address refusal,
  expired secret/RBAC/throttling/concurrent edits and source-binding failure.
- Backend focused tests and workspace test/clippy/fmt/build gates passed in Linux
  Docker using stable Rust and locked/offline dependencies; see journal for exact
  commands and final results. Local Azure/detector fixtures are synthetic.
- Remaining integration: actual frontend UI, live Azure/TLS/RBAC/expiry,
  WAN/DHCP/NAT changes, recursive propagation, appliance reboot and privileged
  native integration. None claimed verified or delivered.
