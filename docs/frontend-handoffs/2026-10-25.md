# Frontend Handoffs - 2026-10-25

## 2026-10-25-12 Override DHCP DNS servers

- Priority: medium. Classification: **required** to expose the setting; existing clients
  keep working. Status: **Pending frontend review**. Availability: **Unreleased**.
  Recommended bump: minor (new field with a behavior-changing default); baseline unknown.
  No commit, push, release or delivery.
- Previous behavior: each `dns[interface]` entry published its configured servers
  followed by every DNS server learned from the interface's DHCP lease.
- New behavior: `dns[interface].override_dhcp_dns` (boolean, **default true**, always
  present in responses). While true and `servers` is non-empty, lease DNS servers are
  discarded and only the configured ones are used for that interface. False keeps the old
  merge (configured first, then lease). If `servers` is empty the lease servers are kept
  regardless. Search domains are unaffected (`dhcp_clients[].use_domains`). Because the
  default is true, an interface that already has configured servers now stops using its
  DHCP DNS servers after the backend upgrade and the next republish.
- Affected: `DNSConfig` in `config.dns`, `GET /api/v1/state`, transactions, revisions
  and restores. Permission is unchanged (`interfaces.write`). Example:
  `{"dns":{"eno1":{"servers":["192.0.2.53"],"domains":[],"override_dhcp_dns":true}}}`.
- Frontend tasks: add the boolean to the DNS editor (a toggle labelled for ignoring
  DHCP-provided DNS servers, default on, disabled/explained when no server is
  configured), preserve it in full-config submits, and show that DHCP DNS is only
  discarded when at least one server is set. Related backend change: the daemon now
  clears resolved's remembered server so a newly added server is used immediately.
- Deployment: rebuilt backend; coordinate the frontend so saved drafts keep the field.
- Acceptance: with a DHCP lease on the interface, `resolvectl dns IFACE` lists only the
  configured servers when true and configured plus lease servers when false.
  Not verified on a real resolver; unit tests cover the server selection.
- References: [contract](../../FRONTEND_SPEC.md#62-managed-interfaces-and-vlans),
  [code](../../crates/netcontrol-native/src/linux/adoption.rs),
  [journal](../journal/2026-10-25.md#dhcp-dns-override-setting).

## 2026-10-25-11 Non-blocking NTP sample warnings

- Priority: high. Classification: **required** warning/list handling.
  Status: **Pending frontend review**. Backend availability: **Unreleased**.
  Recommended bump: patch; baseline unknown. No commit, release or delivery.
- Previous behavior: after three polling rounds with no valid NTP sample, the
  native worker exited in error. Native configuration observation then failed,
  including unrelated configuration reads and transaction checks.
  New behavior: missing/invalid samples leave `state: "running"` with
  `sample_status: "unavailable"` and a row-local `error`. Polling continues every
  64 seconds after each round (up to 3 seconds per server). An accepted sample
  clears `error` and returns to `sample_status: "available"` without repair.
- Affected HTTP methods/paths: `GET /api/v1/runtime`,
  `GET /api/v1/services/ntp/status` (existing `state.read`), and configuration
  reads including `GET /api/v1/state`, `/api/v1/interfaces`,
  `/api/v1/routes`, `/api/v1/services/ntp`, `/api/v1/services/syslog` and
  `/api/v1/services/softflowd` (existing `state.read` or area metadata permission).
  `POST /api/v1/transactions` and
  `POST /api/v1/transactions/{id}/confirm` retain their existing transaction and
  changed-area permissions, validation, revision/recovery guards and response
  shapes. Missing samples alone no longer cause observation failures/HTTP 500.
  Genuine startup, socket I/O and clock-adjustment errors remain errors.
- No fields, types, nullability, defaults, configuration limits, units,
  authentication or permissions were added/changed. Existing optional row
  `error` is a string. Last accepted sample fields and their original
  `collected_at` are preserved while unavailable; they are stale, not current
  measurements. Before any accepted sample these metrics are absent.
  Synthetic status example before the first sample:
  ```json
  {"instances":[{"name":"ntp","scope":"host","state":"running","sample_status":"unavailable","error":"time.example.test: no valid NTP sample"}],"error":""}
  ```
  The optional `started_at` field is omitted from this small example.
- Frontend tasks:
  - Display a non-blocking NTP warning for running/unavailable rows, not a
    global read-failure notification or editing lock. Continue normal status
    polling at the non-overlapping 2-5 second cadence.
  - Render configured servers from `GET /api/v1/services/ntp`, not from the last
    selected sample's `server`. A missing sample must not become "No servers."
  - Keep unrelated pages and normal transaction actions usable. Label previous
    sample metrics stale; clear the warning on recovery. Preserve drafts on
    actual HTTP errors and retain genuine failure/recovery messaging.
  - No client schema, form validation or request changes are required.
- Deployment: deploy the backend fix and frontend warning handling. No new
  operator prerequisites; existing clock-ownership/CAP_SYS_TIME requirements
  remain. This does not clear an already persisted failed rollback/write block;
  such a block still requires explicit operator recovery. A replacement backend
  must start a new worker to replace one stopped by the earlier implementation.
- Acceptance: with an enabled but silent NTP server, wait beyond three polling
  rounds; status remains running/unavailable, configured servers remain visible,
  unrelated reads work and an otherwise valid transaction confirms. Restore
  replies; warning clears without reconcile. Confirm stale sample timestamps,
  bounded shutdown and visible genuine clock-adjustment failure.
- Backend validation: Linux stable Rust offline/locked tests passed:
  services 48 passed/8 ignored; native 47 passed/18 ignored. Real UDP fixtures
  cover repeated missing samples, preserved stale metrics, automatic recovery
  and shutdown; clock adjustment is injected and never changes the test host
  clock. Services strict Clippy and formatting passed. Full appliance/UI
  acceptance and privileged namespace tests were not run.
- References: [canonical contract](../../FRONTEND_SPEC.md#613-appliance-ntp-syslog-and-vnstat),
  [worker and tests](../../crates/netcontrol-services/src/ntp.rs),
  [native observation guard](../../crates/netcontrol-native/src/linux.rs),
  [service guide](../../crates/netcontrol-services/README.md),

## 2026-10-25-10 Host name and time zone

- Priority: medium. Classification: **required** to expose the settings, **optional**
  otherwise (the backend ignores nothing: the new section defaults to unmanaged).
  Status: **Pending frontend review**. Availability: **Unreleased**. Recommended bump:
  minor (new configuration section, permission and endpoints); baseline unknown. No
  commit, push, release or delivery.
- Previous behavior: no host name or time zone setting existed.
- New behavior: `config.system` = `{"hostname":"","timezone":""}`, always present in
  state, transactions, revisions and restores; empty means unmanaged (default).
  Changes need `transactions.write` plus the new **`system.write`** permission
  (device-account keys have it; scoped credential files must list it). Confirmed values
  are applied by the daemon itself (not the networking apply): it sets the kernel
  hostname and `/etc/hostname`, and links `/etc/localtime` to the zone. A rolled-back or
  unconfirmed transaction never touches the host. Values are enforced (re-applied after
  external drift, at most every 10 s; failures retried every 30 s). Clearing a value stops
  management and does **not** revert the host.
- New endpoints (`state.read`, no query, GET only): `GET /api/v1/system/status` returns
  `{hostname,timezone:{configured,observed,state,error},last_applied_at_unix}`, and
  `GET /api/v1/system/timezones` returns `{"timezones":[...]}`. Setting states:
  `unmanaged|current|applying|error|paused|simulated|unavailable`.
- Validation: hostname is empty or a lowercase RFC 1123 label (1..63, `a-z0-9-`, no
  leading/trailing `-`); timezone is empty or an IANA name shape (at most 64 chars, at
  most 3 parts of `A-Za-z0-9_+-`). `422` also for a **changed** timezone that is not in
  the host database, and for any changed non-empty value on a backend that cannot manage
  the host (namespace lab). SSH `commit check` validates syntax only.
- Synthetic example: `{"system":{"hostname":"fw-1","timezone":"America/New_York"}}`.
- Frontend tasks: add `SystemConfig` and status types; hostname input and a timezone
  selector from `/system/timezones` (disabled with an explanation when empty); explicit
  "Unmanaged" choice with a note that clearing does not revert; status row with
  `observed`, `state`, `error`; permission-aware editing (`system.write`); notice that
  running processes may keep the old zone; preserve `system` in full-config submits.
  Note that `system` has **no** `metadata`, and that `hostname` appears in `system` as
  well as in `dhcp_clients[]`, so do not treat every object with a `hostname` key as a
  DHCP client.
- Deployment: timezone database (`tzdata`) on the appliance for time zones; daemon as root
  with `CAP_SYS_ADMIN`; no competing hostname manager (see the install guide for
  cloud-init). Backend and frontend should be deployed together because the Config now
  always contains `system`.
- Acceptance: with the daemon in host mode, change both values, confirm, and see
  `state:"current"` with matching `observed`; `hostname` in the host and in forwarded
  syslog changes; a rollback before confirmation leaves the host unchanged; an unknown
  zone returns `422`; clearing leaves the host as it was. The simulator returns the
  `simulated` state and a sample zone list.
- Backend validation: unit and CLI tests, strict Clippy, formatting, workspace tests and
  a privileged container test of the real `sethostname` call passed; actual appliance
  behavior was not run.
- References: [contract](../../FRONTEND_SPEC.md#616-host-name-and-time-zone),
  [code](../../crates/netcontrold/src/host_system.rs),
  [journal](../journal/2026-10-25.md#host-name-and-time-zone-settings).

## 2026-10-25-08 Host logging ownership during install and source upgrade

## 2026-10-25-06 NetFlow/IPFIX implementation reference

- Priority: low. Classification: **optional** (documentation; no behavior change).
  Status: **Pending frontend review**. Availability: documentation of the current
  Unreleased backend. Recommended bump: none. No commit, push, release or delivery.
- What it is: [docs/NETFLOW_IPFIX_SPEC.md](../NETFLOW_IPFIX_SPEC.md), a standalone

  wire formats, runtime and status fields, prerequisites, failure behavior, non-goals,
  UI guidance and acceptance checks. It was written from the code, not from the older
  spec text.
- Contract gap it closes: enabled instances already return `scope`, `export_version`,
  `address_family`, `fragments`, `capture_filter`, `sampling_rate`,
  `sampling_metadata`, `active_flows`, `exported_flows`, `excluded_packets`,

  for `dropped_packets`) and the packet counters appear after the first table scan.
  Rows without a worker carry only `name` and `state`. Treat all of them as optional.

  services-visible configuration (IPv6 policy, NTP, syslog, vnStat, interface name/

  native service workers, emptying flow tables and, for v9/IPFIX, choosing a new
  random observation domain; v1 carries no sampling metadata; counters describe
  sampled packets and are not scaled; flows are unidirectional; the collector's own
  UDP traffic is excluded; records have no interface indexes.

  indicator from `active_flows` against `max_flows`, and a note when a change will
  restart all services.
- Deployment: none. Acceptance: compare a running instance's row to section 5 of the

  Recommended bump: minor for the explicit runtime contract/behavior change;
  baseline unknown. No commit, push, release, deployment or external notification.
- Previous behavior: any AF_PACKET drop stopped the native exporter with an error
  and could fail configuration confirmation. New behavior, explicitly selected by
  the operator: continue exporting, with visible cumulative loss and incomplete

  `statistics_complete` (boolean, initial `true`, sticky `false` on observed loss).

## 2026-10-25-04 WireGuard peer enabled toggle

- Priority: medium. Classification: **required** (new field and control). Status:
  **Pending frontend review**. Availability: Unreleased. Recommended bump: minor;
  baseline unknown. No release, commit, push, deployment or delivery.
- Previous behavior: a WireGuard peer had `public_key`, `endpoint`, `allowed_ips`,
  `persistent_keepalive_seconds` and optional `metadata`; stopping one meant deleting
  it. New: `interfaces[].wireguard.peers[].enabled` boolean. Omission defaults to
  `true` in requests and saved state; explicit `false` is preserved; `null`, strings
  and numbers return `400`. Responses (`/api/v1/state`, `/api/v1/interfaces`,
  transactions, revisions) always include the boolean.
- Endpoints: none new. `POST /api/v1/transactions` (and revision restore) carry the
  field; permissions are `transactions.write` plus `wireguard.write` for any peer
  change (no new permission). Confirmation, rollback, `202`/`200`/`409`/`422`
  behavior are unchanged.
- Synthetic request fragment (inside a complete candidate):

  ```json
  {"public_key":"AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE=","enabled":false,
   "endpoint":"203.0.113.1:51820","allowed_ips":["198.51.100.0/24"],
   "persistent_keepalive_seconds":25}
  ```

- Semantics: a disabled peer is saved everywhere but not installed on the kernel
  device, so its handshake and traffic stop; `enabled: true` installs it again with a
  fresh handshake. Native runtime (`GET /api/v1/runtime` `wireguard[].peers`) lists
  installed peers only, so a disabled peer has no row or counters. Disabled peers
  must still have a valid, unique public key and canonical allowed networks and obey
  the IPv6 policy. A disabled peer may reuse an allowed network used by an enabled
  peer; enabled peers (and one peer's own list) must not duplicate (`422`).
  `enabled` is not part of identity (identity is the public key).
- Frontend tasks: add `enabled` to the `Peer` type; a per-peer toggle and a disabled
  badge/row style; initialize new peers with `true`; preserve explicit `false`
  through drafts, review, restore and export; do not show handshake or byte counters
  for disabled peers or treat a missing runtime row as an error; warn before
  disabling a peer that carries management traffic; keep the "configured is not
  connected" rule.
- Deployment: rebuilt daemon only. Saved configuration that omits the field loads
  with peers enabled (ordinary defaulting; no rewrite, reset or migration). Existing
  `wireguard peer JSON` clients must send `"enabled": false` to keep a peer
  disabled; resending a peer without it re-enables it.
- Acceptance: toggling off removes the peer from `show runtime` after confirm and
  restores it when re-enabled; unconfirmed changes roll back; disabled spare peers may
  share an allowed network, two enabled may not; `null`/`"no"` are `400`; reload and
  restore keep the flag. Backend results are in the journal; browser and physical
  tunnel behavior are unverified.

  [model](../../crates/netcontrol-core/src/model.rs),
  [model tests](../../crates/netcontrol-core/src/model_tests.rs),

## 2026-10-25-02 DHCP-dependent static route lifecycle

- Priority: P1. Classification: **required**. Status: **Pending frontend review**.
- Availability: **Unreleased**. Recommended bump: **patch** for route lifecycle
  correctness; baseline unknown. No release, commit, push, deployment or delivery.
- Previous behavior: DHCP address removal could remove enabled static routes;
  lease updates restored only DHCP routes, leaving state reads at `503`.
  New behavior: enabled IPv4 static routes on DHCP-managed interfaces are
  suspended without a valid matching lease and restored after lease routes on
  acquisition/renewal/address replacement. Configuration address replacement
  also refreshes route presence before installing missing routes.

### Contract and frontend tasks

- Existing authenticated `GET /api/v1/state`, `GET /api/v1/routes`,
  `GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}` and
  `GET /api/v1/runtime` retain `state.read`, methods, paths, schemas, types,
  defaults and nullable/error fields. No new endpoint, permission or field.
  The device-proxy wrapper belongs to the external frontend, not this backend.
- Configuration reads can now return `200` while a DHCP-dependent static route
  is suspended. `enabled: true` remains configured intent, not proof of kernel
  installation. Runtime `dhcp_clients.leases[interface]` uses existing
  `acquired_at` Unix seconds plus `lifetime` seconds; require a matching current
  client and unexpired lease, and inspect `dhcp_clients.errors[interface]`.
  A lease alone is not proof of forwarding or a valid pinned static gateway.
- Synthetic configured route fragment (unchanged schema):
  `{"enabled":true,"destination":"198.51.100.0/24","gateway":"192.0.2.1","interface":"wan0","table":254,"metric":10}`.
  Without a valid `wan0` lease this stays enabled/configured but is not installed.
  Disabled routes stay disabled. IPv6/other-interface routes are not suspended
  by this DHCP lifecycle.
- Keep existing client types, forms, drafts, validation and enable toggles.
  Render "waiting for DHCP" separately from configured-disabled and worker/error
  states. Never submit `enabled:false` or remove a route to reflect suspension.
  Poll runtime at existing cadence; preserve drafts on errors.
- Existing `POST /api/v1/transactions` and confirmation/rollback paths retain
  `transactions.write`, `routes.write` for route changes and
  `interfaces.write` for DHCP changes. No revision/history writes on lease events.
  Pinned gateways are not rewritten; conflicts/unreachable gateways fail explicitly.
  Ordinary observation failures remain `503` with `{error, transaction}`;
  no blanket automatic drift repair or frontend retry loop.

### API and configuration

- `POST /api/v1/services/dynamic-dns/secrets`, API key with `dynamic_dns.write`.

## 2026-10-25-09 Journald-only native syslog

- Priority: high. Classification: **required** (deployment help/source labeling).
  Status: **Pending frontend review**. Availability: **Unreleased**, no release,
  commit, push or notification. Supersedes item **2026-10-25-08**, including its
  recommendation to mask journald's dev-log input. Recommended bump: **major**
  for breaking deployment/capture/status contracts; baseline unknown.
- Previous versus new: native syslog previously bound `/dev/log`, read
  `/dev/kmsg` and tailed `backend.log`. It now receives only journald-forwarded
  datagrams from systemd's inherited `/run/systemd/journal/syslog` socket.
  Journald retains `/dev/log`, kernel capture and the local journal. Direct
  kernel/backend-file readers are removed to avoid duplicate forwarding.
  Forwarded text is wrapped in RFC5424 with APP-NAME `journald`; journal-native
  structured metadata/cursor replay is not supported.
- Affected methods/paths: `GET /api/v1/runtime`,
  `GET /api/v1/services/syslog/status` and runtime-returning service reconcile
  responses, including `POST /api/v1/services/syslog/reconcile`, change syslog
  status source metadata. Existing API-key authentication and permissions remain:
  status/runtime need `state.read`; shared repair needs all existing enabled-service
  repair grants. `POST /api/v1/transactions` keeps existing transaction/changed-area
  permissions, including `syslog.write`. No request/config schema/default/limit changes.
- Running syslog status rows add optional non-null `source: "journald"`, change
  optional `host_source` from `/dev/log` to `/run/systemd/journal/syslog`, and remove
  `backend_source` and `kernel_source`. `forwarded_records` remains a nonnegative
  JSON integer counting records sent to all destinations per worker start, not
  acknowledgments. Disabled/simulated/no-worker rows may omit all these fields.
  Synthetic status row fragment:

  ```json
  {"name":"syslog","scope":"host","state":"running","source":"journald","host_source":"/run/systemd/journal/syslog","forwarded_records":12}
  ```

- Errors/status: native syslog requires systemd activation (correct PID, one
  datagram FD named `netcontrol-syslog` at the fixed forwarding path).
  Missing activation fails service preflight before apply stops workers; transaction
  apply uses the existing HTTP 500 error/rollback mapping. Malformed activation
  or wrong descriptor fails daemon startup. Socket-path loss/replacement and I/O
  failures remain explicit service errors. No claim of changed validation HTTP
  codes or automatic rollback recovery. Preserve drafts/errors; never retry writes
  automatically or clear failed-rollback blocks.
- Frontend tasks: update optional source fields/types and source labels; remove
  direct `/dev/log`, `/dev/kmsg` and backend-tail claims. Explain systemd/journald
  requirement and native syslog being unavailable on OpenRC/direct launches.
  Keep existing config forms, limits and polling cadence. Disabling native syslog
  stops remote forwarding, not journald capture. Queued messages may forward on
  later enable; bounded queues, rate limits and restart may lose messages.
  Running is not proof of complete capture or remote delivery.
- Deployment: install reviewed Ubuntu scripts/managed units and journald settings
  before enabling native syslog/deploying an enabled saved config. Scripts publish
  `netcontrol-syslog.socket`, service socket dependencies, and journald forwarding
  configuration; stop/mask competing syslog receivers, start/preserve journald's
  dev-log input and restart journald. No `/dev/log` unlink/takeover. Masks and
  config persist on later deployment failure. `PartOf=netcontrold.service`
  propagates daemon stop/restart to its socket during upgrades/reset. Signed
  API/package upgrades do not provision these host files; build-only changes none.
  No compatibility window/migration is provided. Use independent OS SSH/console.
- Acceptance: synthetic `logger` plus kernel/daemon messages appear once at the
  collector and remain in journald; disabling native syslog retains local logs;
  repair/apply rollback preserves socket ownership; restart/reboot restores activation.
  Missing/wrong FD and custom active receivers fail explicitly without unlinking.
  Rust socket/rollback tests, Linux shell regressions and generated unit verification
  passed. Actual systemd PID 1/reboot/journald capture acceptance remains pending;
  see journal for workspace validation limitations.
