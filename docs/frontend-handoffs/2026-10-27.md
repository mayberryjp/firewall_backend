# Frontend Handoffs - 2026-10-27

## 2026-10-27-02 Watchdog process health and active alerts

- Priority: high. Classification: **required** client/status rendering and MQTT
  coordination. Status: **Pending frontend review**. Backend: **Unreleased**,
  no approved release, commit, notification or deployment claimed. Recommended
  bump: minor for additive runtime fields/endpoint/telemetry; baseline unknown.
- Previously, state/runtime had no platform health/alert aggregate and systemd
  restarted crashes but had no daemon heartbeat. Now successful HTTP
  `GET /api/v1/state` and `GET /api/v1/runtime` include `process_health` and
  `active_alerts`; new `GET /api/v1/platform/status` returns that pair from a cache
  without taking the networking engine lock. Existing bearer API-key auth and
  `state.read`; `401`/`403`, GET-only `405`, query/nonempty-body `400`, `200`
  even for unknown/unhealthy status. Credential-store failure remains `503`.
  Existing genuine state/runtime errors remain errors; use cached platform
  status as a fallback, not invented configuration. Read responses are no-store.
- `process_health`: `status: healthy|unhealthy|unknown`, `healthy: boolean|null`,
  UTC RFC3339 `collected_at: string|null`, `stale: boolean`; optional
  `runtime_available: boolean`, optional `daemon` with numeric PID/uptime seconds,
  local state/nullable health and `watchdog_enabled`. `components` rows contain
  stable ID, component/resource strings, source state, nullable boolean health,
  retrying flag and last-observed UTC timestamp. Sources include native service/
  relay/flow/probe/DHCP errors, MQTT, Dynamic DNS, host settings and manager-task
  completion. Process health is source-reported local execution/status, not
  remote reachability, forwarding, synchronized time or hardware thresholds.
- `active_alerts: ActiveAlert[]` is empty when no observed condition is active.
  Each has stable ID/component, nullable resource, warning/error severity,
  machine code, sanitized message, boolean retrying and nullable first/last-seen
  UTC timestamps. Repeated observations retain first-seen; observed recovery
  clears; unavailable runtime preserves known native failures. No raw secrets,
  provider payloads or unfiltered backend error text are copied into messages.
  Codes include `worker_unavailable`, `service_warning`, `runtime_unavailable`,
  `monitor_stale`, `health_unavailable`; render unknown future codes generically.
- Sampling approximately every two seconds; after 15 seconds without completed
  collection health becomes unknown/stale with a monitor alert. These are
  runtime-only, not config fields, revisions, desired enabled state, acknowledge
  records or stored alert history. A running NTP worker with an unavailable
  upstream is healthy **with a warning**. Unhealthy labels/alerts never block
  editing, confirm/rollback or trigger daemon restarts. Structural guards remain.
  Synthetic response fragment (freshness timestamps omitted):
  ```json
  {"process_health":{"status":"unhealthy","healthy":false,"collected_at":null,"stale":false,"components":[]},"active_alerts":[{"id":"appliance_services:6e7470:worker_unavailable","component":"appliance_services","resource":"ntp","severity":"error","code":"worker_unavailable","message":"appliance_services reports state error","retrying":true,"first_seen_at":null,"last_seen_at":null}]}
  ```
- MQTT: existing `netcontrol/<device_id>/state` QoS 1, nonretained topic gains
  these same objects and `statistics_available: boolean`; discovery on the
  existing retained Home Assistant device topic adds metrics/sensors
  `process_health` and numeric `active_alert_count`. Transport availability and
  last will are unchanged: unhealthy state can be published online; a disconnected
  broker cannot receive new alerts. Failed statistics produce partial samples,
  keeping interface/gateway entities to expire/appear unknown, not deleting or
  zero-filling them. No backlog, command topic or immediate alert push is added;
  the configured publication interval and confirmed-config rules still apply.
- Frontend tasks: extend state/runtime/platform types using the
  [canonical contract](../../FRONTEND_SPEC.md#platform-health-and-active-alerts),
  show aggregate/freshness/component states and active warning/error list,
  deduplicate by ID, preserve unknowns and first-seen timestamps, auto-remove
  resolved items. Never copy runtime alerts/health into drafts or full-config
  submissions. Poll visible state/status non-overlapping every 2..5 seconds;
  fallback to platform status on observation errors, preserving unsaved work.
- Deployment: rebuild backend and deploy packaged systemd unit or full source
  upgrade/drop-in, daemon-reload and restart during an operator-approved window.
  `Type=notify`, 60-second watchdog, five-second failed-process restart, no start
  rate limit, 180-second startup timeout, no core dumps. READY follows HTTP bind;
  heartbeats follow engine progress, never service-health verdicts. Operator
  overrides remain possible. Manual/OpenRC launches lack this systemd watchdog.
  No persisted-schema migration or data reset; durable transaction recovery
  remains required after abrupt watchdog termination. Long engine-blocking work
  needs timeout qualification. No automatic appliance restart was performed.
- Acceptance: HTTP auth/method/query/body/no-store checks; cached status readable
  while engine lock is held; state contains desired config plus runtime objects;
  repeated failures deduplicate, recovery clears, missing/stale samples stay
  unknown. Verify MQTT payload/sensors across reconnect and confirmed disable,
  partial collection, and unchanged transport availability. Daemon private-socket
  readiness/heartbeat/stopping and installer directives are tested; real PID-1
  hang/kill/restart/reboot plus browser/Home Assistant/TLS-broker acceptance remain
  unverified. Actual validation results are in the journal below.

## 2026-10-27-01 Resilient service supervision

- Priority: high. Classification: **required** status/error handling.
  Status: **Pending frontend review**. Backend: **Unreleased**, no release or
  delivery claimed. Recommended bump: minor for additive status fields and
  availability semantics; release baseline unknown. Supersedes fatal-runtime/
  explicit-repair-only statements in 2026-10-25 items 09, 11 and 17, not their
  authorization, deployment prerequisites or packet-validation contracts.
- Affected reads: `GET /api/v1/state`, `GET /api/v1/services/{service}/status`
  for `ntp`, `syslog`, `vnstat`, `mdns`, `dhcp-relay`, `softflowd` and `gateway-monitoring`,
  and `GET /api/v1/statistics/gateways` plus `/{name}`. Existing API-key/session
  authentication and `state.read` stay unchanged. No new method/path or request
  field. Existing full-package transactions, confirmation, rollback, restore and
  bodyless service reconcile retain their permissions and recovery semantics.
- Previously, startup/runtime service errors could stop workers and fail native
  configuration observation/apply/confirmation. Now owned supervisors remain
  active and retry at 1, 2, 4, 8, 16, then at most 30 seconds; an attempt lasting
  60 seconds resets backoff. Service availability alone does not fail those
  operations. Existing successful response/status codes remain; invalid config,
  unauthorized requests, genuine network drift, missing structural prerequisites
  and durable recovery failures are still errors. Do not remove rollback UI.
- Optional worker fields: `retrying: boolean`, `restart_count: number`
  (nonnegative failed/ended attempt count since supervisor creation),
  `last_error: string` (latest failure retained on recovery). No new lifecycle
  enum. `state: "error", retrying: true` means recovering, not disabled. Gateway
  rows use `process_state` and may include these fields when a worker exists;
  waiting-for-DHCP rows need not have them. Current `error` clears at readiness;
  `started_at` is the latest ready attempt. Missing optional fields are not proof
  of failure or success. Preserve stale timestamps without claiming fresh samples.
- Syslog-only optional `destination_errors: string[]`, empty after recovery;
  `captured_records`, `forwarded_records`, `failed_deliveries`: nonnegative numeric
  counters per execution attempt, for local records, records written to every
  destination, and missed per-destination sends. A running row can have errors.
  Destinations reconnect independently, preserving local capture/other collectors.
  Missed records are not replayed; successful UDP/TCP/TLS writes are not receipts.
  Synthetic status fragment, not a complete response:
  ```json
  {"name":"ntp","scope":"host","state":"error","retrying":true,"restart_count":2,"error":"required Linux capability 25 missing","last_error":"required Linux capability 25 missing","sample_status":"unavailable"}
  ```
- Frontend tasks: extend status types; render recovering/service-local warnings,
  optional restart counts and last-error history without a global editing lock.
  Continue non-overlapping 2..5-second polling. Preserve desired enabled settings,
  configured servers and unsaved drafts. Do not demand manual reconcile to retry.
  Show syslog missed-delivery warnings without promising queueing or recovery of
  lost records. Do not map readiness to synchronized time or verified delivery.
- Deployment: rebuild/restart backend; frontend must understand the new semantics
  before coordinated rollout. No persisted configuration change or migration.
  Linux capabilities, explicit service opt-ins, inherited journald activation,
  clock ownership, UDP/5353 ownership, TLS identity verification, firewall/input
  permissions and host DNS/routing prerequisites remain operator responsibilities.
- Acceptance: disconnect/reconnect a collector, lose/restore an mDNS link, and
  deny NTP clock privileges. Status must expose failures while config reads,
  apply/confirmation and rollback remain available absent independent errors;
  recovery must happen without changing desired enabled settings. Syslog local
  capture and other collectors continue, failed sends count, stale samples are
  not displayed as fresh. Invalid schema/permissions/drift/recovery errors remain.
- Backend checks: service suite (63 passed), seven isolated native mDNS fixtures
  and native apply/observe/rollback with NTP in retrying error passed. Full
  workspace tests passed; final lint/format/build results are recorded in the
  [journal](../journal/2026-10-27.md). Browser and real-appliance acceptance remain
  unverified. No frontend acknowledgment, notification or deployment performed.
