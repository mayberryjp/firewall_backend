## 2026-10-30-01 Rule origins and frontend Sando replacement

- **Priority:** high. **Classification:** required frontend work.
- **Status:** Pending frontend review. Not sent, acknowledged or frontend-verified.
- **Backend availability:** Unreleased. Recommended SemVer bump: minor for
  additive rule/response metadata; release baseline unknown. No version changed.

### Current backend contract

All legacy filter, host/interface/input and NAT rule objects serialize
`origin:"manual"|"import"|"system"|"inherited"` and
`import_source:string|null`. Omission on input means manual/null.
Import origin requires a provider ID matching `[a-z][a-z0-9_-]{0,63}`; use
`"sando"` for Sando, not a URL. Other origins require null/omitted import_source.
Unknown/null origin or wrong field types return 400; validly typed but invalid
source/origin combinations return 422 in configuration transactions.

Before: rules had no persisted provider ownership. After: reads, transactions,
revision history, restoration and rollback preserve labels. Labels do not
change packet matching, operational hashes or counter generations. They are
descriptive, not permissions, verified upstream identity or backend protections
against editing/deleting rules.

Exact affected surfaces, with existing authentication/permissions unchanged:

| HTTP method/path | Impact / permission |
|---|---|
| `GET /api/v1/state` | Labels in desired/observed config; `state.read`. |
| `GET /api/v1/firewall/rules`, `GET /api/v1/firewall/hosts`, `GET /api/v1/firewall/interface-policies`, `GET /api/v1/firewall/nat` | Returned rule objects include labels; `state.read`. The rules endpoint returns the whole firewall object, including input. |
| `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{id}` | Revision config includes labels; `state.read`. The revision-list endpoint remains metadata-only. |
| `POST /api/v1/transactions` | Complete candidate accepts/preserves labels; `transactions.write` plus existing affected-component permissions (`firewall.write`, `nat.write`, and `sando.write` for import report changes). Returns normal 202/confirmation workflow. |
| `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}` | Any returned before/after config carries labels; `state.read`. |
| `POST /api/v1/revisions/{id}/restore` | Restores labels using `transactions.write`, `state.read`, affected-component authorization and normal confirmation. |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | Existing workflow preserves committed/restored labels; `transactions.write`. |
| `GET /api/v1/statistics/firewall` | Every logical row adds origin/import_source; `state.read`. Generated bypass/setting/default rows are system/null; configured rows retain their saved labels. Native sample failure remains 503. |

No new endpoints or permissions. Deny-log packet records are unchanged. No
backend fetch, replace, merge or reorder operation, no hourly firewall import,
and no effective-host-rule endpoint.

Example individual rules (synthetic, not full transaction requests):

```json
{"source":"192.0.2.0/24","action":"accept","origin":"manual","import_source":null}
```

```json
{"destination":"198.51.100.0/24","action":"drop","origin":"import","import_source":"sando"}
```

### Frontend tasks

1. Update rule types for all scopes, serialization, editors and counter-row
   types. Default new manually created rules to manual/null. Keep legacy
   `source` IP-prefix matching distinct from import_source.
2. Display ownership/provider labels. When projecting interface ingress rules
   onto a host, display an inherited effect without rewriting that interface
   rule's saved manual/import ownership or persisting derived duplicate rules.
   Generated counter rows display system. Labels never grant edit permissions.
3. Keep browser Sando acquisition/review. Build a successful reviewed candidate
   before replacing anything. Remove only rules with origin import **and**
   import_source sando in affected lists, including previous target lists with
   no new source rules; preserve every manual rule and other import providers,
   even when the upstream Sando URL changes.
4. Keep manual rules first in existing relative order, retain other non-Sando
   rules' relative order, append replacement Sando rules in source order. Review
   removed/new rules and ordering effects. Do not change scope precedence or
   delete/recreate host inventory, defaults, input policy or NAT as an incidental
   consequence of a forwarding import.
5. Save candidate and `rules_import` report together using normal confirmed
   transactions. Show fetch/validation errors without clearing prior rules;
   never treat incomplete/failed fetch as an empty successful source. Review
   skipped/invalid items and any intentionally partial replacement. A genuinely
   empty, successfully reviewed source removes only old Sando-owned rules.
6. Preserve labels in unrelated edits; ownership changes are explicit reviewed
   edits. On revision conflict refresh/rebuild the review, not blind-resubmit
   a stale full package. Handle normal authorization/validation failures and
   transaction rollback.

### Coordination and acceptance

- Deploy label-capable backend before enabling frontend writes relying on these
  fields; older unknown-field pruning is not proof labels were saved. Verify
  returned labels. No state migration, compatibility window or new operator
  prerequisite is introduced. Existing native namespace privileges remain.
- Backend focused tests cover all rule scopes, source validation, round-trip,
  operational equality, authorization, persistence/rollback and generated rows.
  Final workspace tests passed (457 passed, 48 ignored); strict clippy, formatting
  and build passed. The isolated privileged Linux counter test separately passed,
  proving label-only apply preserves packet/byte totals, generation, ruleset ID,
  installed fingerprint and ownership state. See journal for commands/limitations.
- Frontend acceptance pending: two successive Sando imports replace prior Sando
  rules without duplication; manual rules/other providers survive byte-for-byte
  in content and label; ordering stays scoped and manual-first; URL change,
  reviewed empty source, fetch failure, invalid/partial source, cancel, revision
  conflict and rollback behave as above.
- Verify counter display for manual/import/system and inherited interface
  projections. Label-only changes must not clear rate baselines. Do not attach
  current/draft labels to historical deny records.
