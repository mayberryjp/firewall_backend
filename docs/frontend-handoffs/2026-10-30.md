## 2026-10-30-10 Aggregate Host Uptime

- **Priority:** normal. **Classification:** required frontend work.
  **Status:** Pending frontend review.
- **Backend availability:** Unreleased, not deployed/published. Contract impact:
  additive response field, next automatic calendar version, no manual bump.
- **Surface:** `GET /api/v1/statistics`, API-key authentication, `state.read`,
  no query parameters or request body. Existing `200`, `400` (query), `401`
  (authentication), `403` (permission), `405` (method) and `503` (backend failure)
  handling remains. CLI `show statistics` returns the same object.
- **Before / after:** aggregate networking stats had no uptime; now every
  aggregate includes `uptime`. The separate `GET /api/v1/statistics/host`
  response and narrower networking statistics responses are unchanged.
- **New fields:** required object `uptime`:
  - `scope`: nonnullable `"host"` native or `"simulator"` simulated.
  - `collected_at`: RFC3339 UTC string native, null simulated.
  - `status`: `"available" | "unavailable" | "simulated"`.
  - `data`: null unavailable/simulated; otherwise required numeric
    `uptime_seconds` and `idle_seconds`, finite/nonnegative fractional seconds.
    Uptime is since host boot, not daemon start; summed CPU idle can exceed it.
  - `error`: null available; explanatory string unavailable/simulated.
  Failed reads retain other stats, return `200` and set `sample.status` partial.
  Native scope is the daemon-visible host/procfs context even in a networking
  lab; aggregate `sample.scope` still describes the configured network scope.
  `uptime.collected_at` also becomes aggregate `sample.collected_at`.

Synthetic available response fragment:

```json
{
  "uptime": {
    "scope": "host",
    "collected_at": "2026-10-31T03:30:00Z",
    "status": "available",
    "data": {"uptime_seconds": 86400.5, "idle_seconds": 172800.25},
    "error": null
  }
}
```

### Frontend tasks, coordination and acceptance

- Add the required typed object to the aggregate client; show formatted host
  uptime on overview/system stats using `data.uptime_seconds`. Label it host
  uptime, not application uptime. Do not persist it in configuration drafts.
- Use existing statistics polling; no extra full host-health request is needed
  solely for uptime. Respect collection freshness, allow fractional/zero
  seconds, and show unavailable/simulated as unknown rather than zero.
- Preserve other statistics when uptime alone is unavailable/aggregate partial.
  Do not assume a lab/container reports its own boot or cgroup-specific uptime.
- Deploy the rebuilt backend with the frontend update. Operator prerequisite:
  readable daemon-visible Linux `/proc/uptime`; no new services, capabilities,
  state resets, compatibility window or permission.
- Acceptance: available uptime renders correctly; large/summed idle values do
  not change uptime; failed/malformed reads show unknown with other stats intact;
  simulated reads never display development-host uptime. Verify existing
  permission/query/method behavior and narrower response shapes remain.
- Backend tests and remaining browser/deployment checks:
  [journal](../journal/2026-10-30.md#aggregate-host-uptime).

## 2026-10-30-09 Fixed Loopback Role and Static Addressing

- **Priority:** normal. **Classification:** required frontend work.
  **Status:** Pending frontend review.
- **Backend availability:** Unreleased, not deployed/published. Recommended
  bump: minor (additive discovery response fields); baseline unknown, next
  automatic calendar version, no manual version bump.
- **Decision:** user explicitly chose to keep loopbacks read-only. This does
  not introduce editable loopback addresses, MTU/up state, adoption or deletion.
  This item extends, rather than replaces, the pending overview work in
  [2026-10-24-04](2026-10-24.md#2026-10-24-04-live-interface-addresses-and-loopback-visibility).

### Exact surfaces and data

- `GET /api/v1/interfaces/discovered`, API-key authentication, `state.read`.
  Existing `200` inventory array and query/auth/method/read-error behavior remain:
  `400` queries, `401` invalid/missing key, `403` insufficient permission, `405`
  POST, `503` backend failure. No new API path, query, privilege or request body.
- Previously rows had no role/addressing metadata. Every row now includes:
  - `role`: nonoptional nullable string; exactly `"loopback"` on actual kernel
    loopback rows, otherwise `null`.
  - `addressing_type`: nonoptional nullable string; exactly `"static"` on those
    loopbacks, otherwise `null`.
  - These fixed values apply even when down or without active addresses.
    Loopback classification uses kernel flags, not names such as `lo` or `lo0`.
  - All existing fields, names, live CIDRs, MTU units, ownership and simulator
    semantics remain. Simulator rows describe only simulated managed links and
    return null for both new fields; do not invent a simulated host loopback.

  `wan | lan | unassigned`. `POST /api/v1/transactions` still requires
  `transactions.write` and `interfaces.write` for interface edits. A managed
  loopback kind, Loopback role on another kind, or `dhcp_clients.lo` is `422`;
  diagnostics explicitly identify the reserved read-only loopback contract.
  Existing unknown-field projection/`ignored_fields` behavior is unchanged;
  discovery metadata is not an addressing-mode setting.

### Frontend tasks and deployment

## 2026-10-30-08 MQTT Reconnect Diagnostics

- **Priority:** high for diagnosing unstable MQTT connections.
  **Classification:** required frontend status display work.
  **Status:** Pending frontend review.
- **Backend availability:** Unreleased, not deployed/published. Recommended
  bump: minor (additive status fields; related manifest repair is a patch fix);
  baseline unknown, next automatic calendar version. No manual version bump.
- **Before / after:** reconnect failures previously discarded their cause and
  returned one generic message, cleared on every retry. They now expose
  allowlisted, credential-safe reasons, attempt/retry counts, last broker
  connection and historical failure details that remain visible after recovery.
  Also fixed a reproduced manifest mismatch: generated protocol IDs may contain
  uppercase ASCII letters but the reader rejected them after writing. IDs remain
  unchanged; no private-store reset, new configuration or operator migration.

### Exact surfaces and data

- `GET /api/v1/services/mqtt/status`, API-key authentication, `state.read`.
  No new HTTP method/path/query, permission, config field, credential operation,
  MQTT topic, reconnect interval or publication behavior. Existing authentication,
  method and manager-unavailable status/error handling is unchanged.
- Existing `error` remains nullable text but now gives a specific safe reason.
  It stays visible during a retry and clears on connection/publication success,
  disable or stop. Existing states and `last_published_at_unix` are unchanged.
- Add required client fields:
  - `connection_attempts`, `reconnect_count`: nonnullable nonnegative integer
    counts, initially 0, saturating unsigned 64-bit. Attempts include all new
    sessions; retries count failures including those before initial connection.
    Orderly configuration changes, disable and stop do not count as failures.
  - `last_connected_at_unix`: nullable integer UTC Unix seconds, broker CONNACK,
    not proof that telemetry was acknowledged.
  - `last_failure`: nullable object with nonnullable string `category` and
    `message`, nullable signed integer `os_error_code`, and nonnullable integer
    UTC Unix seconds `at_unix`. OS codes depend on the daemon platform.
  - Exact categories and current/historical semantics:
    [canonical MQTT status contract](../../FRONTEND_SPEC.md#614-home-assistant-mqtt-streaming).
    In-memory fields reset on daemon process restart, not every managed-worker
    retry/restart. Failure timestamps record observation, not physical link loss.

  "connection_attempts": 3,

  Show reason/category/time, attempts, retries and last broker connection.
  Format Unix seconds in local time; handle null timestamps/codes explicitly.
  A historical failure while `running` is not a current alarm.
- Render messages as plain text; do not collect/display credentials, password
  references or endpoint URLs as part of diagnostic exports.
- Deploy the rebuilt backend to obtain the fields/warnings, then deploy the
  status display. No new settings, operator privileges or compatibility window.
  Existing source-interface/routing, broker credentials/ACLs and TLS prerequisites
  remain. Do not delete private state to investigate reconnects.
- Broker logs are still needed to distinguish duplicate client IDs, publish ACL

  Categories describe observed symptoms, not unsupported root-cause claims.

## 2026-10-30-07 WireGuard DNS Peer Endpoints

- **Priority:** normal. **Classification:** required frontend work.
  **Status:** Pending frontend review.
- **Backend availability:** Unreleased, not deployed/published. Recommended
  bump: minor for additive endpoint/runtime support; baseline unknown, next
  automatic calendar version. No manual version bump.
- **Before / after:** peer endpoints previously accepted canonical numeric
  sockets only. They now also accept lowercase DNS `hostname:port`, with
  automatic refresh immediately and after each 60-second wait between cycles.
  Numeric endpoints and empty/omitted roaming endpoints retain their contracts.

### Exact surfaces and data

| HTTP method/path | Impact / existing permission |
|---|---|
| `GET /api/v1/state` | Configured/observed hostname strings plus native `runtime.wireguard_dns`; `state.read`. |
| `GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}`, `GET /api/v1/wireguard` | Peer `endpoint` can be a DNS socket string; `state.read`. |
| `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{id}` | Saved endpoint strings remain hostnames; `state.read`. |
| `POST /api/v1/transactions` | Complete candidate accepts DNS endpoints; `transactions.write` and `wireguard.write`, plus permissions for any other changed components. Existing `202` confirmation workflow. |
| `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}` | Before/after configurations retain endpoint names; `state.read`. |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | Existing workflow and affected-component permissions; last-good DNS selections support rollback during DNS outage. |
| `POST /api/v1/revisions/{id}/restore` | Restores configured names through normal revision/transaction permissions and confirmation. |

- No new URL, permission, config flag, interval control or MQTT schema.
- `endpoint?: string` is still nonnullable; omission/empty means no configured
  endpoint. DNS labels are lowercase ASCII letters/digits/hyphens, 1..63 bytes
  each, no leading/trailing hyphen, total <=253 bytes. No trailing dot,
  underscore, whitespace, URL scheme/path, zone or mapped IPv6. Explicit
  canonical decimal port 1..65535; no service-name ports or leading zeroes.
  Numeric IPv6 remains bracketed.
- Wrong types/null return `400`; invalid syntax returns `422`. A syntactically
  valid new name with no usable resolution fails backend apply with normal
  `500` transaction/rollback details. Read that outcome instead of blindly
  retrying. Cached successful selections allow restart/rollback without DNS.
- Refresh retains a still-advertised address; otherwise selects deterministically,
  preferring IPv4. Global IPv6 disablement filters out AAAA/IPv6 results and
  IPv6 resolver addresses. A disabled peer is not resolved or installed.
- Later lookup/no-compatible-answer/kernel-update errors retain the last
  successful selection and expose an error. DNS selection/roaming is runtime
  transport state, not numeric endpoint drift. Static numeric drift checks,
  device/peer identity, keys, keepalive and AllowedIPs/BGP configuration remain.
  Workers join before reconfiguration/rollback/removal; endpoint refresh does
  not create config revisions or rewrite the saved hostname.
- Native `runtime.wireguard_dns` has `running: boolean`,
  `refresh_interval_seconds: 60`, `error: string | null` and `peers: []`.
  Each enabled DNS peer row adds `interface`, `public_key`, configured
  `endpoint`, `ipv6_enabled`, `resolved_endpoint` (numeric socket string),
  `last_attempt_unix_ms`, `last_success_unix_ms` (nonnullable Unix ms numbers),
  and nullable `error`. Rows are absent for numeric/disabled peers.
  Synthetic row:

  ```json
  {
    "interface": "wg0",
    "public_key": "AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI=",
    "endpoint": "vpn.example.test:51820",
    "ipv6_enabled": false,
    "resolved_endpoint": "192.0.2.20:51820",
    "last_attempt_unix_ms": 1793386800000,
    "last_success_unix_ms": 1793386800000,
    "error": null
  }
  ```

### Frontend and deployment tasks

- Replace numeric-only peer endpoint validation in both Interfaces and
  WireGuard editors. Keep the port mandatory; offer clear hostname/numeric
  examples and errors. Preserve names in drafts, diffs, full-package writes,
  import/export, history and restores; never replace them with resolved IPs.
- Show configured name, cached DNS selection and actual runtime peer endpoint
  distinctly. Actual endpoints still live under
  `runtime.wireguard[].peers[].endpoint` and can roam between refreshes.
  Show last success, per-peer errors and worker-level errors separately from
  handshake/traffic; neither DNS success nor a configured peer means connected.
  Missing simulator/native telemetry is unknown, not fabricated success.
- No browser DNS requests, DNS proxy URL, peer-sync flag or refresh interval
  form is needed. Use existing state polling; configuration writes still need
  explicit confirmation and normal rollback/revision-conflict handling.
- Deploy the updated backend before enabling hostname input. Keep private
  native state persistent/owned by the daemon to retain last-good selections.
  First use requires reachable underlay DNS independent of the tunnel.
  The existing native resolver uses `/etc/hosts` and `/etc/resolv.conf`,
  bounded UDP A/AAAA/CNAME replies, no DNS search-suffix/TCP/DoH fallback.
  Use fully qualified names for DNS. No new package, external daemon,
  migration or compatibility window is required.

### Acceptance and references

- Accept numeric/DNS/empty endpoints and reject invalid syntax/types/ports;
  verify the configured name survives confirmed save, restart and rollback.
- Confirm DNS rotation updates the kernel endpoint without changing keys,
  keepalive or static/BGP-owned AllowedIPs. Check IPv4-only filtering and

- Simulate DNS failure: first uncached use fails explicitly; later failures

- Backend unit/transaction suites and isolated WireGuard kernel regressions

## 2026-10-30-06 ICMP and ICMPv6 Firewall Filters

- **Priority:** normal. **Classification:** required frontend work.
  **Status:** Pending frontend review.
- **Backend availability:** Unreleased, not deployed/published. Recommended
  bump: minor for additive protocol/schema support; baseline unknown, next
  automatic calendar version. No manual version bump.
- **Before / after:** host, ingress-interface and management-input filters
  supported Any/TCP/UDP; legacy ordered filters matched only addresses.
  All four now support Any/TCP/UDP/ICMP/ICMPv6. Legacy rules additionally accept
  the same TCP/UDP individual destination-port list as other filter scopes.
  NAT destination rewriting remains TCP/UDP only.

### Exact surfaces and contract

| HTTP method/path | Impact / existing permission |
|---|---|
| `GET /api/v1/state` | Configured/observed filter fields; `state.read`. |
| `GET /api/v1/firewall/rules` | Whole firewall object, including input and legacy fields; `state.read`. |
| `GET /api/v1/firewall/hosts`, `GET /api/v1/firewall/interface-policies` | New protocol values in returned rules; `state.read`. |
| `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{id}` | Saved fields/values in revision config; `state.read`. |
| `POST /api/v1/transactions` | Complete candidate accepts new fields/values; `transactions.write` and `firewall.write` for these edits, plus permissions for any other changed components. Existing `202` confirmation workflow. |
| `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}` | Any returned before/after configs preserve filter fields; `state.read`. |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | Existing confirmed/provisional behavior; `transactions.write` plus affected-component permissions. |
| `POST /api/v1/revisions/{id}/restore` | Restores fields using normal confirmed transactions and existing restore/affected-component permissions. |
| `GET /api/v1/statistics/firewall` | Unchanged shape/permission (`state.read`); address/port expansions retain logical rule identity. |

- No new endpoint, authentication, permission, polling interval or MQTT schema.
- Existing overall MQTT drops include configured ICMP/ICMPv6 DROP rules; only
  generated accepting ICMP exceptions are excluded, not all ICMP traffic.
- `protocol?: string`: exact values `""`, `tcp`, `udp`, `icmp`, `icmpv6`.
  Omission/empty means Any, which matches every IP protocol. Empty values are
  omitted on normalized reads. Null, numeric values and wrong types return
  `400`; unknown strings/aliases return `422`.
- `destination_ports?: number[]`: omitted means empty; empty lists are omitted
  on normalized reads. Null, wrong types and noninteger elements return `400`.
  At most 32 unique integers 1..65535, TCP/UDP only; violations return `422`.
  Units are individual destination ports, not ranges. Legacy expansion is
  limited to 4096 entries; port expansions share one logical counter.
- ICMP is IPv4 protocol 1; ICMPv6 is IPv6 upper-layer protocol 58, including
  extension headers. No type/code selector: both match all types/codes.
  Incompatible explicit prefixes or no compatible host address pair return
  `422`. Dual-stack host references use compatible pairs only.
  ICMPv6 requires `ipv6_enabled: true`, including wildcard rules; otherwise
  configuration validation returns `422`.
- Normalized synthetic legacy rule:

  ```json
  {"origin":"manual","import_source":null,"protocol":"icmp","action":"drop"}
  ```

  Synthetic TCP rule fragment, valid in every filter scope:

  ```json
  {"protocol":"tcp","destination_ports":[80,443],"action":"accept"}
  ```

### Concrete frontend/deployment tasks

- Add ICMP/ICMPv6 choices to host, interface, input and legacy editors.
  Preserve `protocol`/`destination_ports` in legacy client types, drafts,
  full-package writes, import/export, revision views and transaction diffs.
- Show ports only for TCP/UDP. Clear ports explicitly when choosing
  Any/ICMP/ICMPv6, without silently changing addresses or broadening a rule.
  Disable ICMPv6 when global IPv6 is disabled; validate family compatibility,
  destination-host references, port bounds/duplicates and backend error text.
- Preserve rule ordering and source labels. Update Sando import mapping only
  for unambiguous supported protocol/family combinations; reject/report ICMP
  suggestions with ports rather than converting them into broader permits.
- Warn that enabled `allow_all_icmp` precedes all IPv4 ICMP drops and still
  does not accept ICMPv6. Established/related and input loopback precedence
  remain unchanged. Dropping ICMPv6 can break neighbor discovery/error reporting.
- Deploy the rebuilt backend before enabling the new form choices. No
  migration, compatibility window, extra daemon or dependency is required.
  Existing native nftables/Linux privilege prerequisites remain unchanged.

### Acceptance and references

- Save/read/confirm every choice in all four filter scopes; confirm legacy
  ports and source labels survive restart, history and rollback.
- Check invalid types (`400`), aliases/ports/families/disabled IPv6 (`422`),
  valid dual-stack references, explicit empty Any and preserved ordering.
- Verify IPv4 ICMP drops with the global exception disabled, ICMPv6 with/without
  extension headers, accept behavior, live aggregate rule counters and rollback.
  Backend targeted suites and isolated real-kernel checks passed; final full
  workspace results and limitations are recorded in the journal below.
- Browser/frontend integration and appliance deployment remain unverified.

  state nonretained. Consumers must accept the expanded `metrics` map.
- New root `telemetry_sources` read-success booleans are mirrored by
  `source_<name>_readable` sensors. True does not prove service health or an
  available measurement; disabled/simulated/partial statuses still apply.
  Synthetic state fragment:

  ```json
  {
    "telemetry_sources": {
      "network": true, "protocols": true, "host": true, "services": false,

    },

      "source_services_readable": false,
      "vm_pgmajfault": "9",
      "scheduler_procs_blocked": "0"
    }
  }
  ```

- Dynamic metric IDs are `<kind>_<sha256(identity)>_<field>`, preserving existing
  interface/host/flow IDs. Native service identities are service names or
  `udp-broadcast-relay:<instance_id>`; protocol identities are `<source>/<group>`;
  traffic/DHCP identities are interface names; BGP peer identities are names.
  WireGuard peer identity includes interface/public key before hashing, but
  neither raw key material nor endpoint/allowed-prefix inventories are sent.
- **Overall firewall drops:** kind `firewall`, identity `accounting`, fields
  `dropped_packets` and `dropped_bytes` (exact decimal strings, packets/B,
  cumulative for the installed generation). Sum explicit and default-policy
  input/forward DROP matches; do not infer them from sampled/rate-limited deny
  logs or interface receive/transmit drops. Accept/bypass/ICMP/NAT matches are
  excluded. `generation` and `ruleset_id` identify resets/rulesets.
  `rule_match_packets`/`rule_match_bytes` aggregate all matches, not unique
  traffic. `logical_rule_count` counts accounted logical rows, not hits. Only
  these seven aggregate fields are exported: **no per-rule sensors or rows**.
  Unavailable/simulated readings are null, not zero. External firewall tables,
  NIC losses and other kernel drop sites are outside this counter.
- Integer counters preserve exact decimal strings; gauges remain numbers or
  exact source strings. NTP delays/offsets and disk service time are ms, memory/
  traffic are B, disk sectors are 512-byte sectors, VM paging is KiB/pages as
  specified, PSI totals are microseconds and CPU idle time is seconds across
  cores. Per-period vnStat totals are gauges with explicit day/month dates,
  not independent lifetime meters. Counters retain their kernel/worker/history
  reset semantics. Unknown is distinct from measured zero and boolean false.
- Release checks expose nullable latest/update/time and explicit
  disabled/pending/succeeded/error state. Sando exposes state/timestamps and
  cached host/skipped counts only; a source change hides old results, while
  failed/disabled sync can retain cached counts. No Sando host details/URL or
  raw errors/configuration are copied.
- Individual-source failures preserve available telemetry/health/alerts and
  keep affected dynamic entities unknown rather than deleting them. Authoritative
  empty lists remove obsolete entities. Stopped/error NetFlow workers no longer
  publish cached counters as current.

## 2026-10-30-01 Rule origins and frontend Sando replacement

- **Priority:** high. **Classification:** required frontend work.
- **Status:** Pending frontend review. Not sent, acknowledged or frontend-verified.
- **Backend availability:** Unreleased. Recommended SemVer bump: minor for
  additive rule/response metadata; release baseline unknown. No version changed.

### Current backend contract

All legacy filter, host/interface/input and NAT rule objects serialize
`origin:"manual"|"import"|"system"|"inherited"` and
`import_source:string|null`. Omission on input means manual/null.
Import origin requires a provider ID matching `[a-z][a-z0-9_-]{0,63}`; use
`"sando"` for Sando, not a URL. Other origins require null/omitted import_source.
Unknown/null origin or wrong field types return 400; validly typed but invalid
source/origin combinations return 422 in configuration transactions.

Before: rules had no persisted provider ownership. After: reads, transactions,
revision history, restoration and rollback preserve labels. Labels do not
change packet matching, operational hashes or counter generations. They are
descriptive, not permissions, verified upstream identity or backend protections
against editing/deleting rules.

Exact affected surfaces, with existing authentication/permissions unchanged:

| HTTP method/path | Impact / permission |
|---|---|
| `GET /api/v1/state` | Labels in desired/observed config; `state.read`. |
| `GET /api/v1/firewall/rules`, `GET /api/v1/firewall/hosts`, `GET /api/v1/firewall/interface-policies`, `GET /api/v1/firewall/nat` | Returned rule objects include labels; `state.read`. The rules endpoint returns the whole firewall object, including input. |
| `GET /api/v1/revisions/latest`, `GET /api/v1/revisions/{id}` | Revision config includes labels; `state.read`. The revision-list endpoint remains metadata-only. |
| `POST /api/v1/transactions` | Complete candidate accepts/preserves labels; `transactions.write` plus existing affected-component permissions (`firewall.write`, `nat.write`, and `sando.write` for import report changes). Returns normal 202/confirmation workflow. |
| `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}` | Any returned before/after config carries labels; `state.read`. |
| `POST /api/v1/revisions/{id}/restore` | Restores labels using `transactions.write`, `state.read`, affected-component authorization and normal confirmation. |
| `POST /api/v1/transactions/{id}/confirm`, `POST /api/v1/transactions/{id}/rollback` | Existing workflow preserves committed/restored labels; `transactions.write`. |
| `GET /api/v1/statistics/firewall` | Every logical row adds origin/import_source; `state.read`. Generated bypass/setting/default rows are system/null; configured rows retain their saved labels. Native sample failure remains 503. |

No new endpoints or permissions. Deny-log packet records are unchanged. No
backend fetch, replace, merge or reorder operation, no hourly firewall import,
and no effective-host-rule endpoint.
