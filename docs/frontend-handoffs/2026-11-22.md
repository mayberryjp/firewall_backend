# Frontend handoffs - 2026-11-22

## 2026-11-22-01 Unsampled flow exports

- Priority: high. Classification: **required**. Status: **Superseded** by
  [2026-11-22-02](#2026-11-22-02-configurable-flow-sampling).
  The following item records the earlier request, not the current contract.
- Backend availability: **Unreleased** working-tree changes; no approved release,
  commit, push or notification. Contract impact: **breaking configuration and
  validation constraint**; next automatic calendar version, no manual version bump.
- Summary: all flow export versions (NetFlow 1/5/9 and IPFIX 10) must be unsampled.
  Remove configurable packet sampling and collector/UI count extrapolation.
  Unsampled still does not guarantee complete capture or UDP delivery.

### Exact API and configuration contract

- `POST /api/v1/transactions`: complete candidate configuration; existing
  `transactions.write` and changed-area `softflowd.write` apply. Each
  `config.softflowd[].sampling_rate` remains a **required, non-null integer**,
  but the only valid value is now **1**. This applies to enabled **and disabled**
  entries and every export version.
- Previously, rates 1..1,000,000 were accepted, with v5 limited to 16,383.
  Now any other integer returns **422** with an explicit validation error
  containing `sampling_rate must be 1`. Missing or wrong-type fields retain
  **400**. Rejected candidates do not start a transaction or mutate networking.
  No silent normalization, compatibility shim or automatic saved-state rewrite.
- `POST /api/v1/transactions/{id}/confirm` retains existing confirmation,
  authorization and rollback behavior for valid candidates.
- `GET /api/v1/services/softflowd`, `GET /api/v1/services/softflowd/status` and
  `GET /api/v1/runtime` retain `state.read`, response shapes and error behavior.
  Worker runtime `sampling_rate`, when present, is always **1**. Disabled,
  simulated or unavailable rows may omit worker metrics as before.
- `exported_flow_packets` and `exported_flow_bytes` remain optional exact
  unsigned-decimal strings. They now explicitly mean unsampled observed
  packets/layer-3 bytes represented by successful local sends, not estimates.
  Existing MQTT projections use the same observations; no MQTT schema changes.
- `sampling_metadata: false` for v1 means metadata absent, **not** that capture
  is sampled or of unknown rate. v5's sampling header is zero; v9/IPFIX emit
  interval 1/algorithm 1. No transport, collector or capture-filter changes.

Synthetic valid exporter entry (inside the complete candidate configuration):

```json
{
  "name": "office",
  "enabled": true,
  "interface": "lan0",
  "collector": "198.51.100.50:4739",
  "export_version": 10,
  "sampling_rate": 1,
  "max_flows": 65536,
  "snaplen": 256,
  "promiscuous": false,
  "capture_filter": "",
  "timeouts": {}
}
```

### Frontend tasks and deployment

1. Change configuration client types to `sampling_rate: 1` and optional runtime
   `sampling_rate?: 1`. Keep the required request field; do not remove it.
2. Replace the sampling-rate form input with a read-only **Unsampled** indicator.
   Every new/edited entry must submit 1, regardless of version or enabled state.
3. Review saved drafts/full-configuration serializers. Surface entries with a
   non-one rate as requiring explicit correction before submission; do not
   silently change an existing draft or infer a permissive default.
4. Remove v5-specific sampling limits, sampling-based counter multiplication and
   estimates from flow/MQTT presentation. Preserve exact decimal-string counts
   and existing unknown/error handling.
5. Retain capture-drop warnings and label counts as observed, not delivery-verified
   or necessarily complete. Explain v1's metadata absence without implying sampling.
6. Coordinate backend/frontend deployment so clients and supplied saved
   configuration satisfy the new exact-one contract. Operators must provide valid
   current configuration; there is no compatibility window or automatic rewrite.
   Do not reset state or discard unrelated configuration.
7. Collector operators/developers must follow the
   [receiver requirements](../IPFIX_RECEIVER_SPEC.md); no count scaling is needed.

### Acceptance and validation

- Submit rate 1 for versions 1, 5, 9 and 10, enabled and disabled: valid.
- Submit 0, 2, 100 or other non-one integers: HTTP 422, explicit error and no
  transaction mutation. Missing/wrong-type field: HTTP 400.
- Confirm valid edits and verify existing rollback/permissions remain intact.
- Form cannot choose sampling; required field is preserved in complete submits.
- Observed 3 packets remains 3, never an extrapolated count.
- Show missing runtime metrics as unknown, and capture-drop warnings even with
  unsampled capture. V1 metadata absence does not change count interpretation.
- Backend focused validation passed: core rejection/validation tests and service
  configuration/encoder tests. Disposable Linux native tests passed: four flow
  fixtures including sustained unsampled capture for all four versions, and the
  IPv4/IPv6 export fixture with exact two-copy packet/byte totals and metadata.
  See the [journal](../journal/2026-11-22.md#unsampled-exports-for-all-versions)
  for final workspace checks and cleanup.
- External frontend/browser, collector interoperability and physical appliance
  performance remain unverified.

## 2026-11-22-02 Configurable flow sampling

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
- Backend availability: **Unreleased** working-tree changes; no release, commit,
  push or notification. Supersedes [2026-11-22-01](#2026-11-22-01-unsampled-flow-exports);
  its fixed-one-only controls and no-estimation instructions are no longer current.
- Contract impact: **additive accepted-rate expansion relative to the earlier
  unreleased restriction**, restoring configurable sampling for IPFIX and every
  NetFlow version. Next automatic calendar version; no manual version edits.

### Exact contract

- `POST /api/v1/transactions`: required non-null integer
  `config.softflowd[].sampling_rate` accepts **1..1,000,000**, except
  `export_version: 5` accepts **1..16,383**. This also applies to disabled entries.
  Previous unreleased behavior accepted only 1. Required `transactions.write`
  and changed-area `softflowd.write` are unchanged.
- **1 means unsampled**. N>1 means deterministic selection of every Nth received
  frame before parsing/filtering. Phase persists across receive batches and
  resets on worker execution, including supervised retry.
- Zero, negative and out-of-range integers return **422** with explicit
  validation errors. Missing/wrong-type fields retain **400**. Rejected
  candidates do not create transactions or mutate networking.
- `POST /api/v1/transactions/{id}/confirm` preserves confirmation,
  permission and rollback behavior. No silent clamping, defaults or rewriting.
- `GET /api/v1/services/softflowd`, `GET /api/v1/services/softflowd/status`
  and `GET /api/v1/runtime` retain `state.read` and response shapes. Configured
  and worker runtime `sampling_rate` now report the chosen integer; worker
  metrics may still be omitted when disabled/simulated/unavailable.
- `exported_flow_packets`/`exported_flow_bytes` remain optional exact unsigned
  decimal strings for sampled observed packets/layer-3 bytes in successful local
  sends. They are **not multiplied** by the backend. MQTT totals remain raw.
  No new HTTP path, permission, configuration field or MQTT schema.
- IPFIX/v9 records advertise the configured interval and algorithm **1**.
  V5 uses zero sampling header at rate 1, otherwise packet-interval mode `01`
  and a 14-bit rate. V1 has no wire sampling metadata: its collector needs the
  configured rate out of band, even though capture still samples.
- `statistics_complete` remains a capture-drop indicator. Sampling alone does
  not set it false; true does not mean unsampled or collector-delivery-verified.

Synthetic partial configuration values (not a complete transaction request):

```json
{"export_version":10,"sampling_rate":100}
```

At that rate, 3 raw sampled packets may represent an **estimated** 300 packets;
3 remains the observed count. At rate 1 no scaling is needed.

### Frontend tasks and deployment

1. Use `sampling_rate: number` in configuration types and optional
   `sampling_rate?: number` in runtime types; restore the required rate input.
2. Label 1 **Unsampled**, N>1 **1 in N**. Validate integers and version-specific
   bounds, preserving rates in complete configuration submits and saved drafts.
3. Switching a high-rate entry to v5 must visibly require a valid rate; never
   silently clamp or change the user's chosen sampling.
4. Show export counters as raw sampled observations. If providing optional
   full-traffic estimates, keep them separate, use exact/overflow-safe arithmetic,
   label them estimated and never scale twice. Do not guess absent rates.
5. Preserve capture-drop/unknown/error handling. Do not infer unsampled capture
   from v1 metadata absence, or complete full traffic from `statistics_complete`.
6. Coordinate backend/client deployment around this current bounded-rate
   contract; no compatibility window or migration is required. Existing rate-1
   entries remain valid and unsampled, with no configuration rewrite.
7. Collector developers must consume IPFIX's per-record rate and algorithm:
   [receiver requirements](../IPFIX_RECEIVER_SPEC.md#counters-and-sampling).
   Mixed-rate aggregates must estimate each record using its own interval.

### Acceptance and validation

- Enabled/disabled entries: rates 1, 4, 100 and each version's maximum validate.
- Rate 0 or maximum+1: HTTP 422 with no transaction mutation.
  V5 16,383 passes and 16,384 fails; IPFIX 1,000,000 passes and 1,000,001 fails.
- Rate-1 capture stays unsampled. Sampled records retain raw packet/byte values
  and correct wire intervals; counters and sequences are never multiplied.
- Counter 3 at rate 100 stays 3 observed; optional estimate is 300 estimated.
- No silent rate change on version switching, invalid drafts or failed submits.
- Backend validation and exact native sampling results are recorded in the
  [journal](../journal/2026-11-22.md#restoring-configurable-flow-sampling).
  External frontend/browser and collector interoperability remain unverified.

## 2026-11-22-03 MTU-safe byte-based flow export

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
- Backend availability: **Unreleased working tree**; no assistant commit, push,
  release, deployment or notification. Breaking contract; next automatic
  calendar version, no manual version bump.
- Supersedes the v1/v9 and per-message-template portions of earlier items.
  Item 02's configurable sampling/raw-counter requirements remain current
  for supported versions.

### Exact HTTP/configuration/runtime contract

- `POST /api/v1/transactions`: `config.softflowd[].export_version` now accepts
  only **5 or 10**. Previous accepted values 1/9 now return **422**, including
  disabled entries; no aliases, conversion, migration or compatibility window.
- New optional non-null integer `max_message_size`: **132..65,507**, default
  **1200**, in **UDP payload bytes**, including NetFlow/IPFIX headers, sets and
  padding, excluding UDP/IP/link headers. Responses serialize the configured
  value. Omission uses 1200; null/wrong types return **400** and invalid integer
  bounds **422**. Disabled entries receive the same validation.
- Sampling remains required: 1..1,000,000 (v5 <=16,383); 1 is unsampled.
  No automatic rate changes or counter scaling.
- Required submit permissions remain `transactions.write` and `softflowd.write`.
  `POST /api/v1/transactions/{id}/confirm` and rollback/recovery are unchanged.
  Invalid candidates must not create/apply transactions.
- `GET /api/v1/services/softflowd` and `GET /api/v1/state` expose the new
  configuration field; `GET /api/v1/services/softflowd/status` and
  `GET /api/v1/runtime` expose optional numeric worker `max_message_size`
  (configured cap), `message_size_limit` (current actual byte budget).
  These reads retain `state.read`; missing worker fields mean unknown.
  `sampling_metadata` is true for supported workers. Version unions become
  `5 | 10`; v5 remains IPv4-only, IPFIX dual-family when enabled.

Synthetic partial configuration (not a complete transaction):

```json
{"export_version":10,"sampling_rate":1,"max_message_size":1200}
```

Synthetic partial worker observation:

```json
{"export_version":10,"max_message_size":1200,"message_size_limit":548,"sampling_metadata":true,"exported_packets":"2","exported_bytes":"264","exported_flows":0}
```

### Transport and receiver coordination

- Fit complete due records by bytes immediately; no added fill timer. Actual
  cap is bounded by kernel route PMTU minus IP/UDP overhead (28 IPv4 / 48 IPv6).
  Unknown MTU uses a logged 512-byte total-packet fallback, not 512-byte payload.
- Linux disables fragmentation. `EMSGSIZE` strictly reduces the budget and
  retries/re-batches only unsent records within the existing deadline.
  Recovered errors are logged; terminal encode/send/query/deadline failures
  increment `export_errors` once and remain visible worker errors.
- IPFIX sends two separate initial 132-byte template-only datagrams, then one
  every **600 seconds or 20 successful data datagrams**, whichever first,
  including idle. These are fixed policy, not new configuration fields.
  Data-only messages have no templates. UDP ordering/delivery is not guaranteed.
- Collector developers must cache definitions per transport session/domain,
  accept identical refreshes/repeated sequence numbers, and explicitly bound
  unknown-template handling. Template sends count UDP packets/bytes, not
  flow totals or sequence. Idle UDP totals can therefore increase without flows.

### Frontend tasks/deployment/acceptance

1. Remove v1/v9 choices and update client unions. Require explicit correction
   of invalid draft/saved values; never silently switch versions.
2. Add the bounded byte-cap editor with clear server-default and units.
   Preserve chosen values in full configuration submits; do not silently clamp.
3. Show configured versus optional actual cap, retaining unknown/error states.
   Explain decreases after PMTU/EMSGSIZE and that local success is not delivery.
4. Keep exact string counters/raw sampled totals. Do not infer flow activity
   from template-only UDP increments or infer failure from idle data.
5. Coordinate current-contract backend/client deployment and update collectors
   to template caching before using data-only exports. Operators must permit
   suitable PMTU/ICMP behavior and account for tunnel overhead; no reliable or
   encrypted export transport is added.
6. Check enabled/disabled version rejection, byte bounds/default/wrong types,
   no silent version/rate/cap changes, partial success/error display, template
   cache recovery and record-only sequence arithmetic.

Backend validation results and limitations are recorded in the
[journal](../journal/2026-11-22.md#mtu-safe-byte-based-flow-export).
Frontend/browser, third-party collectors and physical routed/tunnel PMTU
acceptance remain unverified; this handoff has not been sent or acknowledged.
