  reduction or AppArmor disablement as a complete security baseline.
- Deployment coordination: script only; no daemon rebuild or state migration.
  Ubuntu amd64/systemd, APT/dpkg and an existing GRUB installation for the optional
  AppArmor step. Do not run alongside package/deployment jobs. Networking, Wi-Fi,
  SSH, time sync, security updates and build tools are not targeted. State records
  under `/var/lib/netcontrol/os-hardening.XXXXXX` are private, not full snapshots.
- Acceptance: preview has no mutations; apply touches only selected units/packages;

## 2026-10-24-02: Descriptive Object Metadata

- Priority: high. Classification: **required** client types/forms/preservation.
- Status: **Pending frontend review**. Backend availability: Unreleased.
  Recommended bump: minor for additive metadata; release baseline unknown.
- Previous: most objects only had technical identities (and firewall hosts had
  an existing human-readable `name`). New: configurable resource records accept
  optional `metadata: {display_name, description}`. Exact supported object paths
  and exclusions are in [the canonical table](../../FRONTEND_SPEC.md#14-descriptive-object-metadata).
  VLAN/WireGuard interface labels use the containing interface, not the nested
  VLAN tag/key-settings object. No kernel link/interface reference is renamed.

### Fields and Validation

Both fields are optional, non-null strings defaulting to empty. Metadata itself
is optional and non-null. Empty metadata is omitted on serialization; nonempty
metadata includes both fields, even if one is empty. Explicit `{}` clears the
annotation in a full submitted configuration. Unknown fields/null/wrong types
are `400`; semantic limits are `422`. Display names are empty or at most 128
Unicode scalar values with no control characters or whitespace-only nonempty
values. Descriptions allow at most 2048 scalar values, with newline/tab but no
other control characters. No byte/UTF-16 limits, uniqueness requirement, automatic
trimming, case folding, units or new identity syntax.

Synthetic complete VLAN interface example:

```json
{
  "name": "uplink.100",
  "kind": "vlan",
  "role": "lan",
  "mtu": 1500,
  "up": true,
  "addresses": ["192.0.2.10/24"],
  "vlan": {"parent": "uplink", "id": 100},
  "metadata": {"display_name": "Office LAN", "description": "Staff devices on VLAN 100"}
}
```

### API and Permissions

- `POST /api/v1/transactions`: metadata lives inside `config`; existing `202`,
  revision conflict `409`, validation `400`/`422`, permission `403` and native
  observation/apply error behavior remain. Metadata-only changes require
  `transactions.write` and the affected resource permission, not a new global
  annotation-write permission.
- `GET /api/v1/state`, `/api/v1/interfaces`, `/api/v1/interfaces/{name}`,
  `/api/v1/vlans`, `/api/v1/wireguard`, `/api/v1/routes`, `/api/v1/policy-rules`,
  `/api/v1/firewall/rules`, `/api/v1/firewall/hosts`,
  `/api/v1/firewall/interface-policies`, `/api/v1/firewall/nat`,
  `/api/v1/gateway-monitors`, `/api/v1/services/softflowd`,
  `/api/v1/services/ntp`, `/api/v1/services/syslog`, `/api/v1/services/vnstat`:
  existing `state.read` access, with metadata on their returned configurable
  objects when nonempty. DHCP/DNS metadata is available through desired state;
  no standalone DHCP/DNS metadata endpoint is invented.
- Existing transaction/revision detail and restore/confirm/rollback endpoints
  retain full configuration annotations and existing permissions/status codes.
  Interface/relay/client/DNS annotations use `interfaces.write`; peer annotations
  use `wireguard.write`. Other records use their existing routes/policy/NAT/
  firewall/NTP/syslog/vnStat/softflowd/gateway-monitor write permission.
- Discovery and runtime worker/peer identities remain technical. Observed
  metadata is copied from expected configuration, not observed kernel aliases
  or peer-provided labels. Normal networking drift checks remain unchanged.

## 2026-10-24-03: Per-Interface DHCPv4 Retry

- Priority: high. Classification: **required** client action/runtime feedback.
- Status: **Pending frontend review**. Backend availability: Unreleased.
  Recommended bump: minor for the new runtime action; baseline unknown. Existing
  broader breaking Unreleased changes are not downgraded.
- Previous: no dedicated DHCP-client retry endpoint; whole-service repair could
  affect other workers. New: `POST /api/v1/interfaces/{name}/dhcp/retry` retries
  only the selected committed, up interface with DHCP configured. API-key Bearer
  authentication and `interfaces.write` are required; unlike configuration and
  shared-service repair POSTs, no `transactions.write` or `state.read` is required
  for this action. Runtime polling still requires `state.read`.
- Request: no body or `{}`, no query parameters. Name is the technical interface
  identity, 1..15 ASCII bytes matching letters/digits/underscore/hyphen/dot,
  excluding `lo`, `.` and `..`. Unknown fields, wrong JSON types/null, malformed
  JSON, invalid names and queries return `400`. No optional fields/defaults/units.
- Response: `202`, `{"interface":"wan0","status":"retrying"}` with non-null
  strings; status is the literal `retrying`. It confirms worker initialization,
  not receipt of an offer/ACK, address, route or working connectivity. No attempt
  ID or completion event. Configuration/revision/history are unchanged.
- Errors: `401` invalid/missing key, `403` missing permission, `404` unknown
  committed interface, `405` unsupported method, `409` active/recovery transaction,
  down interface, absent DHCP client, native ownership/identity mismatch or native
  configuration recovery intent; `503` unsupported simulator/backend, native
  I/O/start/stop failure or unavailable engine. Standard `{error, transaction}`
  envelope with `transaction: null`. Existing worker errors do not block retry.
- Native behavior: bounded selected-worker stop/join (15 seconds), then startup
  acknowledgment (10-second wait); native reads/lease recovery can add time.
  Stop timeout retains ownership, never starts a competing client. Fresh DHCP
  discovery does not release a still-valid lease: keep address/routes/DNS until
  normal replacement, expiry or rejection. Lease intents retain normal recovery/
  rollback. Other DHCP clients and service workers are untouched.
- Frontend tasks: add a retry command in managed DHCP interface detail/status,
  separate from the draft editor/transaction submission; disable repeated clicks
  while pending, show `403`/`409`/`503` inline and preserve drafts. Use committed
  up/client state for availability. Poll `GET /api/v1/runtime` for per-interface
  lease/errors at existing cadence; show awaiting/current lease separately from
  acquisition success. Compare acquisition/expiry updates, do not interpret an
  already-present lease or `202` as completion. On HTTP timeout inspect runtime
  before another explicit retry; no automatic retry loop or daemon restart.
- Deployment: rebuild/deploy daemon/core/native together before exposing the
  control. No new service, key schema, state migration or privilege is added;
  existing native Linux/networkd/resolved ownership prerequisites remain. Console
  access is advised for live connectivity tests; requests can change a WAN lease.
- Acceptance: successful/no-lease and failed-worker retry, renewal with a valid
  lease retained, eventual lease/error display, authorization, invalid body/name/
  query, missing/down/non-DHCP interface, active/recovering transaction, native
  ownership drift, unavailable simulator, repeated requests, stop timeout with no
  duplicate client, and unrelated healthy/failed workers remaining untouched.
  Validate durable lease update/rollback and daemon shutdown on disposable Linux.
- Actual checks: standalone Rust formatting/parser, workspace formatting and
  editor diagnostics passed. Focused/workspace tests and workspace build blocked
  before project compilation by missing Windows MSVC `link.exe`; Clippy absent.
  Added core API and Linux worker-isolation/ownership/lease-retention regressions
  have not executed successfully here. Native live DHCP, packet/persistence/
  recovery acceptance and frontend integration remain unverified.
