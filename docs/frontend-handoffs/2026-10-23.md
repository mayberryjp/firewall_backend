# Frontend Handoff: 2026-10-23

## 2026-10-23-01: Physical NIC Inheritance, DHCPv4 and Resolver State

- Priority: high; required frontend changes.
- Status: Pending frontend review. Not sent, acknowledged or verified.
- Backend availability: Unreleased working tree, not a released/approved build.
  Linux compilation and runtime acceptance are outstanding. Recommended bump:
  major for initial ownership, persisted configuration and deployment contract;
  no approved baseline or release assigned.

### Contract

Previously a new native journal was empty, roles were WAN/LAN only, and no DHCP
client or resolver maps existed. First supported host startup now imports
physical NICs into a virgin journal with `unassigned` roles and takes exclusive
per-NIC IP/DHCP ownership from networkd. Configured/history-bearing journals are
not recaptured. A completed native receipt without its core journal now fails
explicitly rather than reconstructing stale configuration. No WAN guessing,
API-key/authentication or onboarding change.

Exact affected HTTP surfaces, unchanged methods/paths:

- `GET /api/v1/state`: embedded configurations contain optional `dhcp_clients`
  and `dns`; revision zero can already have managed NICs.
- `GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}`: role accepts
  `unassigned`; addresses remain verified static configuration, not DHCP leases.
- `GET /api/v1/interfaces/discovered`: unchanged read-only live inventory.
- `GET /api/v1/runtime`: native `dhcp_clients: { leases, errors }`; live lease
  address/server, finite Unix-second times, routes, DNS/domain and nullable MTU.
- `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}`,
  `GET /api/v1/revisions`, `GET /api/v1/revisions/{revision}`: embedded Config
  values preserve the maps and role, including frontend exports of those values.
- `POST /api/v1/transactions`, `POST /api/v1/revisions/{revision}/restore`:
  Config values include the maps. Confirmation/rollback and provisional/deadline
  handling do not change; dropping a map is a real configuration removal.
- Existing `POST /api/v1/services/{softflowd,dhcp-relay,gateway-monitoring,ntp,syslog,vnstat}/reconcile`
  additionally require `interfaces.write` when clients or DNS maps are
  configured, as well as existing selected/enabled-service permissions.

Reads retain API-key `state.read`; map changes use `interfaces.write` and normal
transaction authorization. Unknown/null fields are 400; invalid schema values
422; missing permissions 403; conflict 409 and existing transaction apply/recovery
and observation 503 handling remain. No new dedicated DHCP/DNS endpoints.

Canonical fields/defaults/limits: [spec](../../FRONTEND_SPEC.md#dhcpv4-and-resolver-configuration).
Maps default empty and may be omitted when empty; explicit null is invalid.
DHCP defaults are empty ID/hostname, metric 0, MTU false, domains `no`.
Client ID is 2..255 hex-decoded bytes or empty; hostname max 253; metric uint32.
DHCP requires Ethernet, no enabled relay and no static IPv4 on that NIC.
Static IPv6 may coexist. DNS allows 8 unique literal servers and 32 unique
domains per configured interface; domain `name` and `route_only` are required.
Dynamic MTU is nullable and, when applied, 1280..65535 bytes. Lease timestamps
are Unix seconds; lease/renew/rebind fields are seconds, not milliseconds.
Native leases are absent until obtained; simulator does not invent leases.

### Frontend Tasks

1. Update Config/role/runtime types and all round-trip/export/restore paths.
   Preserve maps on unrelated edits and handle empty-map omission.
2. Add Unassigned without guessing WAN/LAN; accept populated revision-zero
   baselines. Earlier role-only handoffs are superseded on this enum detail.
3. Add static/DHCP mode, ID/hostname/metric, DHCP MTU/domain and resolver controls.
   Enforce relay/static-IPv4 exclusivity and current numeric/domain limits.
4. Render dynamic leases/routes/resolver data separately from editable static
   state. Calculate expiry from Unix seconds, show unavailable/errors, and retain
   existing polling, independent connectivity verification and explicit confirm.
5. Update scoped-key repair messaging for the additional interface permission.
   Explain that stopping/removing Netcontrol configuration does not restart OS
   DHCP or remove its persistent networkd exclusions.

### Deployment and Acceptance

Deploy frontend/backend together for the changed Config and role contract, with
no compatibility window or state reset. First native host start needs root,
stable/private persistent state, networkd/resolved and active finite DHCPv4
leases. NetworkManager, active dynamic global IPv6, bridged/bonded ports, custom
policy rules and unsupported manager options fail explicitly. Wi-Fi association
remains with the existing supplicant; DHCP/IP is Netcontrol-owned. Keep console
access; automatic first-start handover can affect management reachability.

Required operator checks: Ubuntu build; static/DHCP first start; client identity,
route metric, DNS and connectivity preservation; renewal/rebind/NAK/expiry;
restart/reboot; provisional apply/rollback; interrupted adoption/lease update;
foreign-route/drift rejection; repeated start without recapture; scoped repair
403 and schema 400/422. No first-party test code added or tests run per user
direction. Local syntax checks passed; portable compile attempt was blocked by
missing Windows MSVC linker and does not validate Linux native code.

## 2026-10-23-03: Automatic Ports, DHCP WAN and Input Filtering

- Priority: high; required frontend work.
- Status: Pending frontend review. Not sent, acknowledged, implemented or verified.
- Backend availability: unreleased working tree; no approved release/build.
  Recommended bump: major for changed deployment defaults and input-policy
  configuration; release baseline unknown. Supersedes item 2026-10-23-02's
  bootstrap defaults/static-WAN support and lack of input protection, while
  retaining its optional egress-field requirements for user-configured policies.

### Default Device State and Deployment

The installer needs only `--run-id` beyond its existing prerequisites. It chooses
physical Ethernet ports by natural name order: first WAN, second LAN (`eno1`,
`eno2`, ...; `eno2` before `eno10`), excluding loopback, virtual and Wi-Fi links.
Paired explicit port overrides remain optional; partial overrides are errors.
LAN defaults to `192.168.0.1/24`, with HTTP management `http://192.168.0.1:8080/`.
WAN is configured as DHCPv4: static WAN addressing/routes/DNS are removed, and
existing DHCP identity is retained when available. The initial transaction waits
up to 30 seconds for a lease/default route and checks subnet overlap before
local confirmation; failure attempts rollback instead of confirming a broken WAN.
An upstream DHCP server and console recovery are operator prerequisites.

LAN has unrestricted forwarding and host-input accept rules. Other new forwarded
traffic is default-drop; return traffic is stateful. Host input defaults to drop,
with implicit loopback/reply acceptance, all LAN input allowed, and WAN IPv4 UDP
destination port 68 allowed for DHCP. Other unsolicited WAN input is denied,
including traffic addressed to the appliance's LAN IP. The global ICMP exception
is false initially; enabling it broadens WAN ICMP input. LAN-subnet IPv4 traffic
exiting WAN is masqueraded. IPv4 forwarding still enables after reconciliation
on each appliance startup. Local output is unrestricted. No LAN DHCP/DNS server,
IPv6 forwarding or TLS is provisioned; LAN clients need static addressing/gateway.

Use a reviewed backend build containing this contract. No compatibility/reset
path or existing-appliance migration is provided. Bind/origin changes still need
coordination with `/etc/netcontrol/appliance.env` and a service restart. Changing
roles or addresses in the API does not regenerate rules or rebind management.

### HTTP, Fields and Authorization

No new HTTP methods/paths, authentication or permissions. Relevant reads remain
API-key `state.read`: `GET /api/v1/state`, `GET /api/v1/firewall/rules`,
`GET /api/v1/interfaces`, `GET /api/v1/interfaces/{name}`,
`GET /api/v1/runtime`, `GET /api/v1/transactions`,
`GET /api/v1/transactions/{id}`, `GET /api/v1/revisions`, and
`GET /api/v1/revisions/{revision}`. Embedded configurations now include input
filtering and the new populated factory state; WAN lease addresses/routes stay
in runtime rather than static interface arrays.

`POST /api/v1/transactions` and
`POST /api/v1/revisions/{revision}/restore` accept the new input policy with
existing `transactions.write` and `firewall.write` (plus all other permissions
required by the configuration diff). Provisional 202, explicit confirm/rollback,
403 permissions, 409 conflicts and 503 native apply/observation errors remain.

New `config.firewall.input`:

- Optional object or null; omitted/null means no explicit host-input filter.
  Normalized reads omit it when absent. Previously this field was unknown (400).
  Removing it is an explicit loss of host-input protection, not a default drop.
- `policy`: required `"accept" | "drop"` string. `interfaces`: array, omitted
  defaults empty; each item has a required managed `interface` string (existing
  canonical interface-name validation, <=15 characters), and ordered `rules`
  array (omitted defaults empty). Null in these nonnullable fields is invalid.
- Rules reuse destination prefix, optional TCP/UDP protocol, optional integer
  destination ports in 1..65535 and required accept/drop action. Empty/omitted
  matches mean Any. Nonempty `out_interface` and `destination_host` are forbidden;
  there is no source-host identity lookup in input policy.
- Limits: 32 unique managed ingress entries, 64 ordered rules per entry,
  32 unique ports per TCP/UDP rule, 64 KiB policy metadata and <=4096 expanded
  entries counting the stateful rule, plus one implicit loopback entry. Interface
  entries and port lists normalize by sorting; ordered rule lists are preserved.
- Malformed types/null-in-required-fields/unknown fields return 400; invalid
  policy/name/reference/prefix/port/limit or forbidden matches return 422.
- Input precedence: global ICMP exception if enabled, loopback, established/
  related, ordered ingress rules, default. This is separate from forwarding.
  Input rules cannot authorize forwarded packets or filter local output.

## 2026-10-23-04: Saved Configuration Upgrades and Explicit Factory Reset

- Priority: high; required operator/deployment guidance and stale-draft handling.
- Status: Pending frontend review. Not sent, acknowledged, implemented or verified.
- Backend availability: Unreleased working tree; no approved release or delivery.
- Recommended bump: major for saved-only native host startup and removal of
  implicit service installation from upgrade; baseline unknown. No API schema bump.

### Contract and Availability

Previously ordinary native startup could initialize an empty journal from live
NIC settings, and upgrades could install a missing service. Now ordinary native
host startup loads saved configuration only; missing state/service is an explicit
startup/deployment error. Explicit first-install provisioning still initializes
the journal; simulator and explicit lab initialization are unaffected. Managed
host drift is reconciled to the saved plan, with live snapshots used only for
rollback and existing identity/foreign-resource checks retained.

`sudo bash reset.sh --yes` is a local console operation, not an HTTP endpoint.
Optional paired WAN/LAN arguments select physical Ethernet ports; default natural
order and LAN `192.168.0.1/24` match installation. It backs up network/service
state, retains credentials/key files and revision history, replaces current
configuration through a local transaction and increments revision. The script
reinstalls the canonical appliance unit, binds HTTP to the factory LAN and
starts/enables the daemon. No active core transaction is allowed; native recovery
intents are retained/replayed. A valid existing journal is required. Reset does
not wait for WAN DHCP; the LAN reset remains committed without upstream access.

Factory desired configuration has DHCP only on the selected WAN, static LAN,
factory input/forwarding/NAT policy and disabled/default protocol services.
Initial installation and reset share this clean factory builder; inherited OS
settings are handover/rollback data, not factory desired configuration.
Other saved Ethernet interfaces are up, MTU 1500, unassigned with no configured
addresses/DNS/DHCP; custom virtual interfaces/routes/policies/tunable overrides
are removed from desired configuration. Supplicant definitions remain unchanged.
This is not the two-DHCP-uplink configuration; Wi-Fi DHCP must be explicitly added
after reset if wanted. LAN clients still need static addressing; no server is added.

### HTTP and Authentication

No methods/paths or request/response field types, units, nullability or limits
change. There is no reset endpoint or new browser permission. Existing API-key
authorization and account/session identity remain; a network reset must not
restart onboarding or clear retained client credentials.

- `GET /api/v1/state`, `/api/v1/interfaces`, `/api/v1/interfaces/{name}` and
  `/api/v1/runtime`: existing `state.read` access; values reflect the new factory
  configuration and independently acquired DHCP leases.
- `GET /api/v1/transactions`, `/api/v1/transactions/{id}`, `/api/v1/revisions`
  and `/api/v1/revisions/{revision}` retain previous history. The local reset
  transaction has actor `local-factory-reset`, normal committed status and revision.
- `POST /api/v1/transactions` retains `transactions.write` plus affected component
  permissions; a stale `base_revision` remains `409`. Requests are not implicitly
  reset or rebased. Existing confirmation/rollback paths and authorization remain.
- During service replacement/reset, HTTP may be unavailable and its origin can
  change to `http://192.168.0.1:8080/`; this is transport/deployment behavior, not
  a new HTTP status code. Semantic factory validation remains local CLI failure.
