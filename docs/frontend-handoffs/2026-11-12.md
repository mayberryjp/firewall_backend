# Frontend handoffs - 2026-11-12

## 2026-11-12-01 Zero-source DHCP requests with existing client addresses

- **Priority:** normal; **classification:** optional diagnostics/help update.
- **Status:** Pending frontend review. Not sent, acknowledged or implemented.
- **Backend availability:** unreleased local changes; no publication or appliance
  deployment performed by this task.
- **Contract/recommended bump:** fix; next automatic calendar version.

### Affected APIs and previous/new behavior

`GET /api/v1/services/dhcp-relay/log` and
`GET /api/v1/statistics/dhcp-relay` retain `state.read`, existing methods,
queries, defaults, validation limits, field types/nullability, counter units,
status/error behavior, pagination and polling. No request/response field,
configuration, authentication or persisted-state schema changes.

Previously an IP source of `0.0.0.0:68` with a nonzero DHCP client-address field
(`ciaddr`) was always rejected as `invalid_client_address`. Now the relay accepts
that combination when `ciaddr` is on-link unicast on the receiving configured
interface and not its subnet network, broadcast or relay address. A nonzero
source must still equal `ciaddr`; zero `ciaddr` still requires zero source.
Unchanged packet/endpoint/upstream/reply checks continue to apply.

The relay preserves `ciaddr` rather than clearing it or substituting a source
address. Accepted requests produce ordinary forwarding events/counters, and
valid ACKs are delivered to that client address. Genuinely invalid addresses
still generate `invalid_client_address`. Docker is not identified by MAC
prefix, name or configuration; this is protocol-level source handling.

Synthetic existing event-field fragments, not a new response schema:

```json
{"event":"requests_received","peer":"0.0.0.0:68","message_type":3,"reason":""}
```

```json
{"event":"requests_forwarded","peer":"198.51.100.10:67","message_type":3,"reason":""}
```

### Frontend tasks and deployment

No client types, forms, validation or polling changes required. Optionally
clarify diagnostics help: a zero source is not itself invalid, and a rejection
does not identify Docker, an expired lease or the exact invalid header field.
Use actual event/reason values rather than inferring failure from `peer`.
Existing retained rejection events remain historical observations; do not
rewrite or hide them.

An approved backend build containing this fix is needed for changed admission.
No coordinated frontend deployment, Docker-specific setting, saved-state
conversion or automatic lease/container reset is required.

### Acceptance and validation

- Send raw zero-source DHCPREQUESTs with valid on-link `ciaddr`, both clear/set
  broadcast flag: server receives the preserved request with relay hops/giaddr,
  then ACK reaches the client address and forwarding events/counters advance.
- Off-link, subnet-network, broadcast and relay-address `ciaddr` remain rejected.
  Nonzero source/`ciaddr` mismatches remain rejected. Existing Discover and
  ordinary renewal behavior, restart, disable and rollback stay intact.
- Existing diagnostic API shape/permissions and rendering remain unchanged.

Backend: 11 focused DHCP/telemetry tests passed. The privileged native namespace
regression failed against the original admission check at the new zero-source
request, then passed after rebuilding the fix. Workspace tests, all-targets
Clippy with warnings denied, formatting and workspace build passed.
Real Docker DHCP-helper implementations, appliance traffic and frontend browser
acceptance were not tested; no claim about the currently deployed firewall.

## 2026-11-12-02 Installer disables sysstat collection

- **Priority:** low; **classification:** optional installation-help disclosure.
- **Status:** Pending frontend review. Not sent, acknowledged or implemented.
- **Backend availability:** unreleased local installer changes; no deployment.
- **Contract/recommended bump:** breaking installer host policy; next automatic
  calendar version.

Previously fresh installation left sysstat collection unchanged. It now
stops/disables and persistently masks `sysstat-collect.timer` and
`sysstat-collect.service`, including absent units, and verifies stopped state
and persistent masks. Inspection/control/readback failures abort installation.
Existing statistics and packages remain; these units no longer produce
historical activity samples. fwupd, cron, other sysstat units and custom jobs
are untouched. Source upgrades, binary updates, signed packages, hardening and
reset do not establish this policy.

**Affected HTTP methods/paths:** none. No request/response fields, types,
nullability, defaults, units, validation, status/errors, authentication,
permissions, configuration or saved-state changes. No JSON examples apply.

**Frontend tasks:** optionally explain missing future `sar` activity history
in installation/operator help. No client types, forms, rendering, state or
polling changes required. No coordinated frontend/backend deployment or new
operator prerequisites; policy takes effect only when the changed installer
runs. Operators can explicitly unmask both units and enable the timer again.

**Acceptance:** installed, absent, already-masked and repeated setup must leave
both names persistently masked and stopped; failures must abort before daemon
service installation. Mocked installer suite, shell syntax, help output and
whitespace checks passed. Real Ubuntu systemd/package-install/reboot acceptance
remains untested; no appliance was changed.

## 2026-11-12-03 DHCP relay reliability and diagnostic detail

- **Priority:** high; **classification:** required diagnostics client/view update.
- **Status:** Pending frontend review. Not sent, acknowledged or implemented.
- **Backend availability:** unreleased local changes; this task has not
  committed, published or deployed a build.
- **Contract/recommended bump:** fixes plus additive diagnostic fields;
  next automatic calendar version.

### Affected APIs and behavior

`GET /api/v1/services/dhcp-relay/log` and
`GET /api/v1/statistics/dhcp-relay` retain `state.read`, existing methods,
queries/defaults/limits, status/error envelopes, counter encodings, cursor/
epoch/generation, retention and polling. No editable configuration or
authentication change. Runtime/service status routes keep existing shapes.

Previously valid DHCPNAKs could fail exact request ciaddr/flag matching; one
send error could restart the shared worker and lose every pending transaction;
and equal transaction ID/MAC pairs on different VLANs could overwrite tracking.
Now valid NAKs with zero ciaddr/yiaddr are broadcast without requiring the
request's ciaddr/flag. Other server/packet/correlation checks remain. Tracking
includes unique relay address, isolating VLANs. Per-destination/client send
failures and classified asynchronous UDP transport errors preserve the worker/
pending state and allow healthy destinations to continue; genuinely broken
sockets and interface/receive lifecycle failures still invoke recovery.

Every log event adds these fields; do not make them configuration:

| Field | Type/current contract |
|---|---|
| `detail` | string, empty without extra explanation, maximum 512 characters; diagnostic text, not an enum |
| `client_address` | IPv4 string or null: packet ciaddr |
| `offered_address` | IPv4 string or null: packet yiaddr |
| `relay_address` | IPv4 string or null: packet giaddr |
| `broadcast` | boolean or null: packet broadcast flag |
| `hops` | integer 0..255 or null: packet hops |

Headers are populated for validated packets, otherwise null. `"0.0.0.0"` is a
valid header value, distinct from null/unavailable. Server-forward/send-error
events describe the attempted wire packet (including relay giaddr/hops), not
the original ingress header. Expiry events now retain tracked request identity/
headers; `peer` remains null and expiry remains housekeeping, not lease failure.
No packet bodies, hostnames or arbitrary DHCP option values are exposed.

Existing send-error reasons gain `socket_error`, for unattributed asynchronous
UDP transport errors (`interface`/`peer` and packet fields can be null).
`send_errors` remains a decimal-string counter but includes those observations;
it is not an exact lost-packet count. Existing `to_server`, `to_client` and
`to_client_layer2` meanings remain. Rejection categories remain unchanged;
`detail` adds the validation/transport explanation.

Synthetic event using the complete event shape:

```json
{"sequence":"42","generation":"1","timestamp":"2026-11-12T00:00:00Z","interface":"vlan10","event":"send_errors","reason":"to_server","detail":"DHCP send: Network is unreachable","peer":"198.51.100.10:67","message_type":3,"transaction_id":"0000002a","client_mac":"02:00:00:00:00:01","client_address":"192.0.2.20","offered_address":"0.0.0.0","relay_address":"192.0.2.1","broadcast":false,"hops":1}
```

### Concrete frontend tasks and deployment

1. Update `DHCPRelayLogPage` event types with the required fields above.
2. Show diagnostic detail and optionally expandable ciaddr/yiaddr/giaddr,
   broadcast and hops next to transaction/MAC/interface. Render text safely;
   distinguish unavailable fields from zero addresses and false/zero values.
3. Recognize `socket_error`; support unattributed events without inventing
   an interface/client. Keep polling/filter/cursor behavior unchanged.
4. A running worker can have increasing send errors while healthy peers work.
   Surface those counters/events as troubleshooting warnings, not automatic
   drift, a global editing lock or proof that all relays stopped.
5. Continue presenting tracking expiry as housekeeping even with the newly
   available transaction/client identity. Do not count it as a failed lease.

The packet ring remains RAM-only (2048 events). All error observations are
retained/counted until normal ring eviction; only duplicate normal Netcontrol
tracing warnings are rate-limited to one per interface/direction per 30 seconds,
reset each attempt (one shared bucket for unattributed socket errors). Those
warnings can persist in the existing Netcontrol diagnostics stream. Routine
packet-success tracing is not added; system syslog separation is unchanged.

Deploy a matched backend/client contract; no saved-state conversion, compatibility
window, new operator capability or DHCP-specific option is required. Existing
Linux namespace/raw-socket privileges and unique relay addresses remain required.
No deployment was performed by this task.

### Acceptance and validation

Check NAK delivery for clear-flag requests with zero/nonzero ciaddr while
invalid ACK flags still reject; same XID/MAC on two VLANs must receive both
ACKs independently. An unreachable first upstream must not block a healthy
second one. A downstream layer-2 oversized-packet error must not restart the
worker, change generation or prevent a later exchange. Validate detailed error
events and expiry identity, null handling, diagnostic truncation and persistent
warning throttling without dropping API events/counters.

The 15 focused DHCP/telemetry tests and the privileged raw-packet namespace
fixture passed. Workspace tests (732 passed, 100 ignored), all-targets Clippy
with warnings denied, formatting and workspace build passed. Validation
details and remaining limitations are recorded in the
[journal](../journal/2026-11-12.md#isolate-dhcp-failures-and-expand-relay-diagnostics).
Actual appliance, production DHCP-server interoperability and frontend browser
acceptance remain unverified.
