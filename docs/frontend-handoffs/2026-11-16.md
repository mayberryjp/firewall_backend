# Frontend handoffs: 2026-11-16

## 2026-11-16-01 Routed BGP speakers and authorized next hops

- Correction: the initial WireGuard exclusion below is superseded by
  [2026-11-16-02](#2026-11-16-02-wireguard-separate-speaker-and-next-hop-correction).
  Do not disable WireGuard's next-hop list based on this item's initial contract.
- Priority: high; classification: required configuration/types and diagnostic UI.
- Status: Pending frontend review. Backend availability: unreleased; not sent,
  deployed or UI-verified. Additive configuration/status fields; transmit TTL
  now explicitly defaults to 1 instead of the OS default. Recommended release:
  next automatic calendar version; no manual bump.
- Affected methods/paths: `GET /api/v1/services/bgp` returns the new saved neighbor
  fields; `POST /api/v1/transactions` accepts them in full `config.bgp` with
  existing confirmation/rollback. Reads require `state.read`; writes require
  `transactions.write`, `bgp.write` and permissions for any other changed areas.
  Bootstrap route/interface changes also need their normal write permissions.
  `GET /api/v1/services/bgp/status` adds nullable neighbor `last_rejection`.
  The same diagnostic is included in runtime BGP/statistics/MQTT summaries;
  no new endpoints, polling schedule, authentication or route-row fields.
- Previously non-WireGuard speakers had to be directly connected and all
  received NEXT_HOPs had to equal the peering address. Now:
  - `multihop_ttl`: non-null integer 1..255, default 1, transmitted IPv4 TCP hop
    budget for active/passive sessions, not an inbound TTL-security setting.
    Shared listeners use the maximum neighbor TTL for SYN-ACKs, then the
    accepted connection uses its specific neighbor's TTL.
  - `allowed_next_hops`: non-null IPv4 string array, 0..32 unique entries,
    default `[]`. Empty means peer address only. A nonempty list replaces that
    implicit authorization; it is not appended to a global list.
  - Listed gateways must be usable addresses in the selected interface's
    static IPv4 subnets, not any configured firewall address, multicast,
    loopback, network or broadcast address. `/31` hosts are valid.
    Recursive/off-link forwarding gateways are not supported.
  - An off-link non-WireGuard speaker requires TTL >1 and a nonempty list.
    Initially WireGuard required an empty list and retained peer-only NEXT_HOP;
    that restriction is superseded by item 02. AllowedIPs ownership remains.
- Semantic validation failures return `422`, normal `401`/`403` remain;
  malformed types fail existing deserialization handling. No permissive
  fallback to a different gateway or acceptance of unauthorized NEXT_HOPs.
  Import rejections increment `rejected_prefixes` and replace `last_rejection`:

```json
{"prefix":"203.0.113.0/24","next_hop":"192.0.2.3","reason":"next_hop_not_allowed"}
```

- Reasons: `as_path`, `next_hop_not_allowed`, `default_not_allowed`,
  `invalid_prefix`, `connected_route`. Null before any rejection and in the
  simulator. This is the latest rejected NLRI, not a received/installed route or
  current session failure. It survives successful updates/reconnects and resets
  with the counter when the worker restarts. Rejected routes are not retained
  in `GET /api/v1/routes/bgp`.
- Frontend tasks: add TTL and per-neighbor gateway-list controls/client fields;
  distinguish remote speaker, local session address and forwarding gateway.
  Enforce bounds/types, offer explicit peer-only versus listed-gateway help,
  enable listed gateways for WireGuard using item 02's validation, and show rejection prefix/next-hop/
  reason separately from session and installation errors.
- Deploy backend before submitting new fields. Operators must provision
  independent bootstrap routes through the chosen interface, return routing,
  TCP/179 permits and a host that actually forwards advertised destinations.
  Do not learn the bootstrap route over the session it establishes. No state
  migration, compatibility window, new service, package or privilege required.
- Synthetic neighbor fragment (merge into a complete configuration):

```json
{"name":"remote","address":"198.51.100.22","local_address":"192.0.2.2","interface":"lan0","remote_asn":65000,"multihop_ttl":8,"allowed_next_hops":["192.0.2.1"],"accept_default":false}
```

- Acceptance: establish active/passive routed sessions with independent routes;
  install a received prefix via the authorized on-link gateway, not the
  speaker; reject another neighbor's gateway with the diagnostic above;
  reject invalid/off-link/local gateways and missing multihop authorization;
  withdrawal/shutdown removes learned routes while preserving bootstrap/static
  routes and WireGuard ownership. Backend validation results and outstanding
  physical-appliance/FRR/browser checks are recorded in the journal below.
  Workspace tests: 834 passed, 109 ignored; strict Clippy, formatting and build
  passed. Both privileged BGP regressions passed, including three-namespace
  routed active/passive sessions and the existing WireGuard lifecycle fixture.
  The final test-only persistence/rollback extension passed four focused core
  tests, core all-targets Clippy and formatting. No actual FRR/browser acceptance.

## 2026-11-16-02 WireGuard separate speaker and next-hop correction

- Priority: high; classification: required. Status: Pending frontend review.
  Backend availability: unreleased correction; not sent, deployed or UI-verified.
  Supersedes only item 01's WireGuard exclusion and corresponding disabled UI
  control. Recommended release: fix, next automatic calendar version.
- The previous backend mistakenly rejected every nonempty WireGuard
  `allowed_next_hops` array. The same existing field now works on both interface
  types; no new fields, endpoints, permissions, polling or route-row schema.
  Affected: `POST /api/v1/transactions` full `config.bgp` requests and committed
  `GET /api/v1/services/bgp`; existing `transactions.write`/`bgp.write` and
  `state.read`. Static WireGuard/route changes require their normal permissions.
  Learned rows remain `GET /api/v1/routes/bgp`, authenticated `state.read`.
- `allowed_next_hops`: non-null array, 0..32 unique unicast IPv4 strings.
  Empty still means peering-address only; nonempty replaces that authorization.
  For WireGuard, every listed address must be covered by the referenced enabled
  peer's **static** AllowedIPs and must not overlap any other enabled peer's
  static AllowedIPs on the same interface. Local firewall addresses, duplicate,
  unspecified, loopback, multicast, limited broadcast and IPv6 values are invalid.
  Semantic failures remain `422`; malformed types use existing `400` handling.
- The BGP speaker's remote `address` must independently remain covered by that
  same peer's static AllowedIPs for bootstrap. Do not require a listed next hop
  to be in the local tunnel address's subnet: this is WireGuard peer ownership,
  not Ethernet gateway/ARP reachability. Ethernet's on-link rule is unchanged.
  Set `multihop_ttl` high enough for the inner-IP path (1..255, default 1).
- The configured WireGuard public key identifies the forwarding host, which
  must also provide reachability to the BGP speaker. Learned destinations still
  get device-only kernel routes and BGP-owned AllowedIPs on **that same peer**;
  no recursive lookup, another-peer selection, gateway override or prefix theft.
  The learned-route API's `next_hop` preserves the received advertised address.

Synthetic neighbor fragment; key is a synthetic public value, not a private key:

```json
{"name":"remote","address":"203.0.113.22","local_address":"10.10.0.1","interface":"wg0","remote_asn":65002,"wireguard_public_key":"AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI=","multihop_ttl":8,"allowed_next_hops":["10.10.0.2"],"accept_default":false}
```

- Operator prerequisites for this example: referenced peer statically covers
  `203.0.113.22/32` and `10.10.0.2/32`, independent route to the speaker through
  `wg0`, underlay/DNS/return routing and TCP/179 permits. The forwarding host
  must forward learned destinations. No automatic bootstrap AllowedIPs or
  route creation; no migrations or compatibility windows.
- Frontend tasks: remove the blanket WireGuard disable/rejection, retain the
  selected peer-key control, validate each listed gateway's static peer coverage
  and cross-peer conflicts, explain speaker/local/forwarding roles and device-only
  tunnel forwarding, and preserve the existing rejection diagnostic display.
  Deploy the corrected backend before enabling submissions; older deployed
  revisions still reject the list. This does not itself fix missing TCP SYN-ACKs.
- Acceptance: a session from a distinct speaker address over encrypted
  WireGuard imports the authorized host NEXT_HOP, installs only that peer's
  destination AllowedIPs, and passes request/reply traffic; an unlisted UPDATE
  is rejected with `next_hop_not_allowed`. Off-subnet but statically peer-covered
  next hops validate; missing static coverage, local addresses and another
  enabled peer's overlap fail. Empty-list peer-only behavior, withdrawal,
  shutdown, bootstrap preservation, audit/recovery and rollback remain covered.
  Validation: 835 workspace tests passed (110 ignored), all 3 privileged BGP
  regressions passed, workspace strict Clippy/format/build passed. Real
  FRR/appliance/browser acceptance remains unrun; details in the journal below.

## 2026-11-16-03 Per-neighbor BGP enable toggle

- Priority: normal; classification: required. Status: Pending frontend review.
  Backend availability: unreleased; no delivery/deployment/browser acceptance.
  Additive configuration/status contract; recommended release: next automatic
  calendar version, no manual bump.
- Previously every configured neighbor attempted peering. New
  `config.bgp.neighbors[].enabled` is a non-null boolean, default `true`.
  `false` retains all saved settings but stops active/passive BGP sessions,
  removes learned/advertised rows and owned kernel routes/dynamic AllowedIPs.
  Static routes, WireGuard peers and static AllowedIPs remain. Disabled entries
  still require the same valid up interface, enabled referenced WireGuard peer,
  bootstrap coverage and other validation; count them toward the 32-neighbor
  bound. Global `bgp.enabled` remains independent; all peers may be disabled.
- `GET /api/v1/services/bgp` returns the saved field; `POST /api/v1/transactions`
  accepts the complete configuration with it. Keep existing transaction
  confirmation and rollback endpoints. Reads require API-key `state.read`;
  writes require `transactions.write`, `bgp.write` and normal permissions for
  other changed/enabled services. No per-neighbor mutation endpoint.
  Existing `202` submission/`200` confirmation or rollback, `400` malformed
  boolean/null, `422` semantic validation, `401`/`403` authorization and
  transaction-conflict behavior remain unchanged.
- `GET /api/v1/services/bgp/status` adds boolean `enabled` to neighbor rows and
  enum value `state:"disabled"`. Running native disabled rows have zero
  received/advertised/rejected counts and null negotiated timers/router ID,
  error and latest rejection. Simulator disabled rows keep null unmeasured
  counts; no real sessions are claimed. No received/exported rows for that
  peer in `GET /api/v1/routes/bgp` or `GET /api/v1/routes/bgp/advertised`.
  Runtime/statistics/MQTT expose the status; configured-neighbor totals include
  disabled peers, established totals do not. Worker health ignores disabled
  peers; globally enabled/all-disabled is running/up with no BGP listeners.
- Synthetic neighbor fragment, merge into a complete valid configuration:

```json
{"name":"remote","enabled":false,"address":"203.0.113.22","local_address":"10.10.0.1","interface":"wg0","remote_asn":65002,"wireguard_public_key":"AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI=","multihop_ttl":8,"allowed_next_hops":["10.10.0.2"],"accept_default":false}
```

- Frontend tasks: add the per-peer toggle/client boolean; preserve all other
  fields when off, distinguish administrative disable from failure, include
  it in existing full-transaction apply/confirm/rollback, and refresh applied
  status/route views using existing polling. Warn that **the whole BGP worker
  currently restarts on apply**, so other enabled peers may briefly reconnect
  and counters/diagnostics reset. Re-enable/rollback starts fresh sessions and
  relearns routes, not stale-state restoration. Do not equate this toggle with
  disabling the WireGuard transport or its configuration.
- Deploy backend before exposing submissions. Operators keep bootstrap,
  return/underlay routing and TCP/179 permits ready; no migration or new
  packages/privileges. Acceptance: toggle off, confirm, reopen and observe
  persisted false/disabled/no learned forwarding additions while static state
  remains; re-enable/rollback and relearn; disabled peers do not degrade another
  established peer; all-disabled has no listener/reconnect. Permission denial
  must not change saved state. Validation results and remaining FRR/appliance/
  frontend acceptance limitations are recorded in the journal below.
- Backend validation: 836 workspace tests passed, 110 ignored; all 3
  privileged BGP regressions passed; strict workspace Clippy, formatting and
  build passed. Real FRR, appliance and frontend acceptance remain unrun.
