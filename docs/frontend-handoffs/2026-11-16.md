# Frontend handoffs: 2026-11-16

## 2026-11-16-01 Routed BGP speakers and authorized next hops

- Priority: high; classification: required configuration/types and diagnostic UI.
- Status: Pending frontend review. Backend availability: unreleased; not sent,
  deployed or UI-verified. Additive configuration/status fields; transmit TTL
  now explicitly defaults to 1 instead of the OS default. Recommended release:
  next automatic calendar version; no manual bump.
- Affected methods/paths: `GET /api/v1/services/bgp` returns the new saved neighbor
  fields; `POST /api/v1/transactions` accepts them in full `config.bgp` with
  existing confirmation/rollback. Reads require `state.read`; writes require
  `transactions.write`, `bgp.write` and permissions for any other changed areas.
  Bootstrap route/interface changes also need their normal write permissions.
  `GET /api/v1/services/bgp/status` adds nullable neighbor `last_rejection`.
  The same diagnostic is included in runtime BGP/statistics/MQTT summaries;
  no new endpoints, polling schedule, authentication or route-row fields.
- Previously non-WireGuard speakers had to be directly connected and all
  received NEXT_HOPs had to equal the peering address. Now:
  - `multihop_ttl`: non-null integer 1..255, default 1, transmitted IPv4 TCP hop
    budget for active/passive sessions, not an inbound TTL-security setting.
    Shared listeners use the maximum neighbor TTL for SYN-ACKs, then the
    accepted connection uses its specific neighbor's TTL.
  - `allowed_next_hops`: non-null IPv4 string array, 0..32 unique entries,
    default `[]`. Empty means peer address only. A nonempty list replaces that
    implicit authorization; it is not appended to a global list.
  - Listed gateways must be usable addresses in the selected interface's
    static IPv4 subnets, not any configured firewall address, multicast,
    loopback, network or broadcast address. `/31` hosts are valid.
    Recursive/off-link forwarding gateways are not supported.
  - An off-link non-WireGuard speaker requires TTL >1 and a nonempty list.
    WireGuard requires an empty list and retains peer-only NEXT_HOP and
    AllowedIPs ownership. Learned prefixes still install through its tunnel.
- Semantic validation failures return `422`, normal `401`/`403` remain;
  malformed types fail existing deserialization handling. No permissive
  fallback to a different gateway or acceptance of unauthorized NEXT_HOPs.
  Import rejections increment `rejected_prefixes` and replace `last_rejection`:

```json
{"prefix":"203.0.113.0/24","next_hop":"192.0.2.3","reason":"next_hop_not_allowed"}
```

- Reasons: `as_path`, `next_hop_not_allowed`, `default_not_allowed`,
  `invalid_prefix`, `connected_route`. Null before any rejection and in the
  simulator. This is the latest rejected NLRI, not a received/installed route or
  current session failure. It survives successful updates/reconnects and resets
  with the counter when the worker restarts. Rejected routes are not retained
  in `GET /api/v1/routes/bgp`.
- Frontend tasks: add TTL and per-neighbor gateway-list controls/client fields;
  distinguish remote speaker, local session address and forwarding gateway.
  Enforce bounds/types, offer explicit peer-only versus listed-gateway help,
  disable listed gateways for WireGuard, and show rejection prefix/next-hop/
  reason separately from session and installation errors.
- Deploy backend before submitting new fields. Operators must provision
  independent bootstrap routes through the chosen interface, return routing,
  TCP/179 permits and a host that actually forwards advertised destinations.
  Do not learn the bootstrap route over the session it establishes. No state
  migration, compatibility window, new service, package or privilege required.
- Synthetic neighbor fragment (merge into a complete configuration):

```json
{"name":"remote","address":"198.51.100.22","local_address":"192.0.2.2","interface":"lan0","remote_asn":65000,"multihop_ttl":8,"allowed_next_hops":["192.0.2.1"],"accept_default":false}
```

- Acceptance: establish active/passive routed sessions with independent routes;
  install a received prefix via the authorized on-link gateway, not the
  speaker; reject another neighbor's gateway with the diagnostic above;
  reject invalid/off-link/local gateways and missing multihop authorization;
  withdrawal/shutdown removes learned routes while preserving bootstrap/static
  routes and WireGuard ownership. Backend validation results and outstanding
  physical-appliance/FRR/browser checks are recorded in the journal below.
  Workspace tests: 834 passed, 109 ignored; strict Clippy, formatting and build
  passed. Both privileged BGP regressions passed, including three-namespace
  routed active/passive sessions and the existing WireGuard lifecycle fixture.
  The final test-only persistence/rollback extension passed four focused core
  tests, core all-targets Clippy and formatting. No actual FRR/browser acceptance.
