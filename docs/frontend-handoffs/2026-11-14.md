### Exact contract and previous versus new behavior

Previously only private webhook upload and read-only status existed.
Now `POST /api/v1/services/discord/test` requires API-key `discord.write`,
no query and an empty body (not `{}`). Uses the committed webhook reference;
no new request fields, raw URL, candidate configuration or secret export.
Automatic Discord alerts and drop capture may be disabled. Native Linux host
mode and an available Discord worker are required.

Synthetic success response:

```json
{"delivered":true,"backend_version":"2026.11.14.1","config_version":"2026.11.14.3","failed":"0"}
```

`delivered:boolean` means Discord accepted the test. Both version fields are
nonnull independent calendar-version strings captured from the compiled backend
and committed revision; `failed:string` is the reset decimal count.
The test embed also includes the configured firewall name, with mentions disabled.

`GET /api/v1/services/discord/status` (`state.read`) retains its schema:
`delivered:string` remains an alert-entry count, not the test response's boolean.
Successful tests reset `failed` and nullable `error`; ordinary successful alerts
clear only `error`. Preserve delivered-alert count, last drop ID, settings,
worker state and persistent deduplication. No reset of other warnings.
Platform health clears the delivery warning on its next normal two-second sample.
Later failures remain visible. A stopped/error worker is not repaired by a test.

Errors use the existing HTTP error envelope: `401`/`403`, `405` wrong method,
`400` query/body, `409` active transaction/upgrade or missing saved webhook,
`503` unavailable mode/worker/storage/manager, configuration changes during
delivery or delivery failure. Failed tests never clear counts; delivery failures
record redacted errors. Existing HTTPS/no-redirect/timeouts/rate-limit retries apply.
An error/interruption does not prove Discord received nothing.

## 2026-11-14-02 Startup durability and DNS readiness

- **Priority:** high; **classification:** required client/status review.
- **Status:** Pending frontend review; not sent or acknowledged.
- **Backend availability:** Unreleased; not committed, published or deployed.
- **Contract/recommended bump:** breaking native runtime nullability and Ubuntu
  logging policy, with startup/confirmation fixes; next automatic calendar version.

### Exact contract and previous versus new behavior

`GET /api/v1/state` retains `state.read`. Native `runtime.wireguard_dns.peers[]`
now permits null `resolved_endpoint`, `last_attempt_unix_ms` and
`last_success_unix_ms`. Endpoint is otherwise a numeric socket string; times
are otherwise Unix millisecond numbers. Identity, configured endpoint, IPv6
boolean, nullable error, worker `running`, and 60-second interval are unchanged.
Attempt is null before the first attempt; success/selection are null before a
successful resolution/install. Existing actual roaming endpoints remain under
`runtime.wireguard[].peers[].endpoint`.

Previously a cold DNS failure could fail apply/startup. Structural validation
and synchronous restoration now never query DNS. Valid peers retain keys,
AllowedIPs and keepalives and can await DNS while the daemon/configuration is
ready. Background resolution records failures and retries; cached successful
addresses survive outages. Worker/cache persistence failures remain explicit
worker errors; malformed configuration, unsafe/corrupt persistence and ownership
conflicts remain failures, not successful empty configuration.

Synthetic response excerpt after a failed first lookup:

```json
{"runtime":{"wireguard_dns":{"running":true,"refresh_interval_seconds":60,"error":null,"peers":[{"interface":"wg0","public_key":"AQAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=","endpoint":"vpn.example.test:51820","ipv6_enabled":false,"resolved_endpoint":null,"last_attempt_unix_ms":1794614400000,"last_success_unix_ms":null,"error":"synthetic DNS unavailable"}]}}}
```

`POST /api/v1/transactions` and
`POST /api/v1/revisions/{version}/restore` retain their existing authentication,
permissions, complete configuration validation and confirmation workflow.
A UTC date older than the committed revision now returns `503` before native
application, rather than allowing a candidate that cannot be committed.
No automatic replay or draft loss. Confirmation still uses the returned UTC
deadline and existing expiry `409`, but also enforces a monotonic process budget.
Restart reconstructs remaining time capped at the original 10..300 seconds;
elapsed monotonic time is not recoverable across reboot. Clock corrections do
not rewrite timestamp/deadline values. Same-day confirmation before submission
and archived rollback before initialization are valid observational metadata;
canonical revisions, not wall-clock chronology, order configuration history.

### Concrete frontend tasks and deployment

- Update native status types for the three nullable fields; do not render null
  as epoch time or assume a selected address exists.
- Render waiting/unavailable DNS and initial errors/retries separately from
  daemon readiness and tunnel handshake/traffic. `running:true` is not connected.
  Keep configured names, last successful selection and actual roaming transport
  distinct; a per-peer error is meaningful even with worker-level `error:null`.
- Preserve drafts and display actionable UTC-clock errors on submission/restore.
  Poll transaction state after clock corrections; countdowns are not authority.
  Do not classify history as corrupt or reorder revisions from timestamps.
- Coordinate these types/status changes with backend deployment. No new endpoint,
  permission, configuration flag, DNS interval setting, migration or alias.
- Full Ubuntu installation/source upgrade now establishes persistent journald
  retention (128 MiB use target, 256 MiB keep-free reserve, 32 MiB runtime target,
  seven-day age) and flushes the boot journal. Binary-only HTTPS updates do not
  change host policy. Operator overrides/disk pressure can still limit evidence.
- VLAN name conflicts identify intended/existing parent/tag names before managed
  networking removes routes/rules; foreign management links are not implicitly
  renamed/deleted. Operator ownership resolution may still be required.

### Acceptance and evidence

Verify cold DNS failure allows valid apply/startup, shows null selection/success
and a retry error, then converges when DNS returns; preserve static peer settings,
cached selections, authenticated roaming, rollback, disabled-peer behavior and
worker shutdown. Verify invalid keys/endpoints and persistence errors remain
explicit. Exercise UTC-date regression, same-day correction, restart/expiry and
unmodified historical timestamps. Verify conflict refusal retains live routes
and link identity. Check retained boot IDs after an authorized source deployment.

## 2026-11-14-03 Protected-host experience proposal

**Historical scope item:** implementation availability/details are superseded by
[item 2026-11-14-04](#2026-11-14-04-protected-host-experience-implementation).
The original proposal below is retained, not an assertion of current absence.

- **Summary:** future client-style protected-host table/graph backed by passive
  traffic measurements and one-hour per-IP SQLite history.
- **Priority:** normal; **classification:** required future client/design review.
- **Status:** Pending frontend review; not sent, acknowledged or implemented.
- **Backend availability:** **Proposal only, NOT IMPLEMENTED**. No deployed
  route, worker, database, approved commit or release is provided by this task.
- **Contract/recommended bump:** none for this documentation-only scope;
  eventual backend delivery is expected to be additive, with actual persistence/
  deployment impact recorded at implementation under the automatic calendar version.

### Scope and previous versus proposed behavior

Existing APIs provide interface, router-local TCP, connection, rule/drop and
Sando observations, not a protected-host ten-second time series or experience
rating. The proposed dashboard includes **explicit configured firewall hosts
behind managed LAN interfaces only**, one series per canonical IP, with the
derived interface (`vlan20`, `vlan40`, etc.) returned as metadata/sample evidence.
IPv4/IPv6 addresses stay separate; no physical-device merge by name/MAC.

The supplied UniFi table is a presentation reference. There is no promised
Wi-Fi/AP/vendor/radio-channel, OS uptime or 24-hour-usage integration.
Do not reproduce proprietary assets or claim the heuristic is UniFi's algorithm.

### Proposed HTTP methods, paths and schemas

- `GET /api/v1/statistics/host-experience/latest`: API-key `state.read`,
  no body. Optional canonical `address`, managed-LAN `interface`, `limit`
  1..256 (default 100) and opaque `cursor` for a coherent completed collection.
- `GET /api/v1/statistics/host-experience/history?address=192.0.2.20`:
  API-key `state.read`, no body, required canonical IP and no other query.
  At most 360 ten-second observed/missing slots in the retained hour.
- Both are read-only, no-store, with the normal security/CORS/error envelope.
  There are no new editable configuration fields or active probe controls.

Exact field types/nullability, units, full valid synthetic latest/sample examples,
pagination, retention, scoring and errors are defined in
[the API contract](../PROTECTED_HOST_EXPERIENCE_SPEC.md#8-http-apis).
These examples are **not actual backend responses**.

Host fields: canonical `ip_address`, `address_family`, configured host ID/name,
`currently_protected`, derived interface, nullable exact-IP Sando host name/icon/
`classification`, metadata freshness and `sample` (null before first bucket).
Classification remains original-case `local_description` text, not a category
enum; map icon IDs safely instead of fetching arbitrary URLs.

Sample counts/bytes are exact decimal strings or null, rates numeric bits/second,
latencies numeric milliseconds, ages/durations explicit milliseconds. Directions
are host-perspective: upload = sent, download = received. Samples include
traffic, managed drops, point-in-time connections, TCP repeat/window/passive ACK
timing, DNS response time/unanswered observations, actual last seen, activity,
source coverage, epoch and stored experience. No raw packets/DNS domain history.
The one-hour usage subtotal includes coverage and is not lifetime/24-hour usage.

Experience is a proposed Netcontrol heuristic:
`excellent|good|fair|poor|unknown`, nullable 0..100 score, confidence/status,
algorithm identity, contributors and reasons. It uses eligible passive evidence
from up to six contiguous completed buckets; no traffic/missing evidence/gaps
must not become excellent by default. Managed policy drops do not penalize
experience; windows/variation are advisory in v1. Distinguish remote-path
data/ACK timing from host-facing timing; neither is Wi-Fi diagnosis or RTP jitter.

Proposed errors: `401`/`403`, `405`, `400` malformed/noncanonical/duplicate query
or body, `422` wrong interface role, `404` no eligible/retained history IP,
`409` latest paging collection invalidated, `503` unsupported/simulator or
unavailable manager/storage. Readable retained observations may be `200`
partial/stale, with explicit source statuses rather than fabricated live data.

### Concrete future frontend tasks

1. Add the protected-host experience table: configured name/icon, description,
   LAN/VLAN, IP, experience/confidence, activity, upload/download, one-hour usage,
   last seen and optional connections/drop counts.
2. Poll latest non-overlapping every ten seconds while visible; preserve a
   single collection across pages and restart paging on `409`.
3. Load history for the selected row, not every IP each table tick. Plot missing
   slots as gaps; label bytes, bps, ms, connection gauges and managed drop counts
   independently. Reflect interface/epoch changes without merging identities.
4. Keep unknown/idle/not-recently-seen/stale/incomplete metadata or measurements
   explicit. Last seen is observed traffic, not device uptime/reachability.
5. Explain contributing score evidence and security-drop exclusions. A poor host
   experience does not make the daemon unhealthy or disable configuration edits.
6. Gate routes/UI behind confirmed backend availability. Mocks may use the
   proposal, but do not call or advertise these endpoints on today's daemon.

### Deployment, acceptance and remaining work

Backend development is deferred while another code effort is underway. Native

Deploy an accepting native build before wiring API calls; re-evaluate actual

## 2026-11-14-04 Protected-host experience implementation

- **Summary:** backend collection, one-hour history, passive TCP/DNS analysis and
  explainable host experience are implemented, replacing item 03's proposal-only
  availability.
- **Priority:** normal; **classification:** required frontend implementation.
- **Status:** Pending frontend review. Not sent, acknowledged or UI-verified.
- **Backend availability:** unreleased working tree; no approved release/commit
  or deployment is claimed.
- **Contract/recommended bump:** additive API/observed data and new native
  kernel/private-storage prerequisites; next automatic calendar version.

### Methods, permissions and previous versus new behavior

Previously there was no protected-IP time-series/experience endpoint. Now:

| Method and path | Authentication/query | Behavior |
| --- | --- | --- |
| `GET /api/v1/statistics/host-experience/latest` | `state.read`; optional canonical `address`, exact managed-LAN `interface`, `limit` 1..256 default 100, opaque `cursor` <=1024 bytes; no body | Latest completed ten-second collection, eligible metadata rows, null before observation, numeric-IP paging |
| `GET /api/v1/statistics/host-experience/history?address=192.0.2.20` | `state.read`; required canonical IP only; no body | 360 chronological ten-second observed/missing slots for at most one hour |

Use the existing authenticated transport/no-store behavior. There are no new
write permissions, editable settings or probes. Collection is independent of
polling and limited to explicitly configured firewall IPs behind actual managed
LANs, maximum 2048 addresses. IPv4/IPv6 remain separate IP series.

### Client types and rendering

Common fields: schema `netcontrol-host-experience/v1`, kind, interval/retention
seconds 10/3600, nullable collection ID/UTC collected time/age ms, status/error,
clock discontinuity and collector source/loss/eligibility diagnostics.

Latest rows contain configured host ID/name, canonical IP/family,
`currently_protected`, nullable derived `{name,index,kind,vlan_id}`, metadata,
nullable sample and one-hour observed usage totals with coverage/completeness.
Metadata has nullable `host_name`, `icon`, `classification`, `last_success_at`,
`error`, and `status:available|stale|unavailable`. Classification is original-case
local-description text, not an enum. Missing Sando does not hide traffic.

Samples retain configured identity/name/revision/epoch, scheduled UTC interval,
actual measured duration ms, interface and last observed traffic time, activity,
traffic/drop/connection/TCP/DNS/experience/coverage groups. Counts and traffic
bytes are **decimal strings or null**; rates are numeric bps; latency and
variation numeric ms. Upload = sent; download = received. Connection gauges
have nullable actual `observed_at` and `measurement_duration_ms`, not an invented
instantaneous bucket-close measurement. Stale/unready/failed gauges are null.
Timing percentiles are histogram estimates; ACK variation is not RTP jitter.

Selected synthetic nullable fields (JSON fragment, not a full response):

```json
{"ip_address":"192.0.2.20","metadata":{"host_name":null,"icon":null,"classification":null,"status":"unavailable","last_success_at":null,"error":null},"sample":null}
```

Experience uses stored `algorithm:"netcontrol-passive-v1"`,
`level:excellent|good|fair|poor|unknown`, nullable score, confidence/status,
basis seconds, components and reasons. Missing, idle, gaps and pressure do not
become excellent; successful security drops are advisory, not penalties.
No AP/vendor/OS-uptime/24-hour-usage or encrypted-DNS visibility is provided.

### Concrete frontend work

1. Add client types and a configured-host table: name/icon/description, LAN/VLAN,
   IP, experience/confidence, activity, last seen, upload/download and one-hour
   observed usage; offer connections/drop/TCP/DNS details.
2. Poll latest non-overlapping every ten seconds while visible. Finish all cursor
   pages for one snapshot before replacing the table; restart paging on `409`.
3. Fetch history only for selected rows. Plot missing/null as gaps, never zero;
   preserve sample epoch/interface/owner transitions and distinguish units.
4. Render unknown/incomplete/stale measurement and stale metadata separately.
   Last seen is traffic observation, not reachability. Treat icons/text safely.
5. Handle `400` strict query/body errors, `401`/`403`, `404` no attachment/history
   or unknown interface, `405`, `422` known non-LAN, `429` four reads already
   active, and `503` unsupported/failed/busy storage/worker or >4 MiB response.
   Reduce latest page size on response capacity errors; never silently truncate.

### Deployment and acceptance

namespaces are unsupported. Operators need nftables dynamic counter/last sets
and original conntrack ports, NFLOG group 101 timestamps/sequence/conntrack

six evidence buckets is under 80 MiB, excluding other daemon/queue/API/SQLite
and kernel memory. No migration/reset or compatibility window is provided.

Acceptance: verify populated latest/selected history, IPv4/IPv6/VLAN/NAT
