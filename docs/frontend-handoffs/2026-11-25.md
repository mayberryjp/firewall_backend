## 2026-11-25-01 Browser-compatible Sando policy mapping

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
- Backend availability: unreleased working-tree changes; not deployed or delivered.
- Contract impact: mapping/error contract fix, including expanded explicit
  wildcard support and multi-address host scope. Next automatic calendar version;
  no schema, permission or software-version-seed change.
- Summary: server Test sync was deleting browser-supported wildcard permits and
  rebuilding rules in global-list query order. Align supported rule semantics
  with the inspected browser mapper, suppress retained-rule duplicates, retain
  unchanged permit order and reject all-invalid replacements.

### Exact contract

- `POST /api/v1/sando/policies/preview`: unchanged bodyless, queryless API-key
  authentication with `state.read`, `sando.write`, `firewall.write`.
  Success remains `200`/`no-store`, full validated candidate and unchanged
  `base_revision`, `source_url`, `etag`, `imported_count`, `skipped_count`,
  `changed`, `config` fields/types. No apply/report/flag/status/cache writes.
- Automatic policy configuration remains full confirmed
  `POST /api/v1/transactions` / `POST /api/v1/transactions/{id}/confirm`,
  requiring `transactions.write`, `sando.write`, `firewall.write`.
  `GET /api/v1/sando` remains API-key/`state.read`, with existing policy
  counts/error/status fields and five-minute completion-relative polling.
- Previously server mapping skipped wildcard destination/port rows and hosts
  with multiple same-family addresses, duplicated retained matching permits,
  reordered all Sando permits and accepted all-invalid lists as deletions.
- Now explicit upstream `dst_ip:"*"` produces `0.0.0.0/0` or `::/0` in the
  source family; `dst_port:"*"` omits transport ports. ICMP/ICMPv6 accept
  integer/string zero or `"*"`. Transport zero, missing/null/invalid fields,
  wildcard sources, CIDRs and incompatible families remain unsupported.
- Source must match an existing configured host; the rule covers all that
  host's addresses in the matching family, as browser host rules do. Server
  policy sync/preview still do not import inventory or create new hosts.
- Duplicate comparison uses matching/action fields, not ownership/display
  metadata. Retained manual/other-provider rules prevent duplicate permits.
  Counts still separate unique Sando permits from skipped rows, not additions.
- Affected lists retain manual-first order, then other retained rules in
  relative order. Still-present Sando permits keep saved order and metadata;
  genuinely new permits append in source order. Pure source reordering returns
  `changed:false` after reconciliation and creates no automatic revision.
- `[]` still removes only Sando-owned host rules. A nonempty source with no
  supported existing-host rows now returns preview `422` with
  `{error,transaction:null}`; automatic sync reports an error, retains rules
  and does not advance its validator. Valid rows covered by retained rules
  are not an all-invalid failure. Other errors remain unchanged.

Synthetic upstream example:

```json
{"src_ip":"192.0.2.10","dst_ip":"*","protocol":"1","dst_port":"0"}
```

Generated host permit:

```json
{"origin":"import","import_source":"sando","destination":"0.0.0.0/0","protocol":"icmp","action":"accept"}
```

## 2026-11-25-02 Automatic firewall hosts and server-only Sando

- Priority: high. Classification: **required**. Status: **Pending frontend review**.
- Backend availability: unreleased working-tree changes, not committed/deployed.
- Contract impact: **breaking delegation/activation behavior**, additive status.
  Recommended bump: next automatic calendar version; no software seed or saved
  configuration/cache-schema changes.
- Summary: `sando.sync_enabled` now automatically adds new firewall hosts as
  well as fetching host/score metadata. With both flags enabled, the daemon
  owns hosts, threat scores and policies; browser imports are no longer required.
  This supersedes the previous metadata-only/no-host-creation statements,
  including item [2026-11-25-01](#2026-11-25-01-browser-compatible-sando-policy-mapping).

### HTTP, permissions and behavior

- `POST /api/v1/transactions`, `POST /api/v1/transactions/{id}/confirm`,
  `POST /api/v1/transactions/{id}/rollback` and revision restore retain API-key
  authentication, normal full configuration/base-revision requirements and
  transaction authority. Changing **either** Sando sync flag, or changing the
  URL while either is enabled before/after, now needs `sando.write` **and**
  `firewall.write`. Previously host/score enablement only needed Sando authority.
  Missing firewall authority returns `403`; malformed flags/URLs and stale/
  busy transactions retain existing `400`/`422`/`409` behavior.
- No new host-import endpoint, arbitrary-source proxy or request fields.
  Defaults remain both flags false; `sync_enabled` runs at startup/enablement/
  source change then hourly after each completed attempt. Policies remain an
  independent five-minute worker. Neither requires a browser to be open.
- New hosts are added from canonical unicast inventory addresses, IPv6 only
  when configured enabled. Stable ID is `sando_` plus first usable canonical
  address with dots/colons replaced by underscores. Name is the cached hostname,
  trimmed/UTF-8-truncated to 80 bytes, falling back to IP for blank/duplicate names.
  Default policy **`drop`**, empty rules, no raw inventory/threat-score fields in
  firewall configuration. Normal global/ingress rule precedence still applies.
- Existing host IDs/names/addresses/policies/rules are untouched, including
  manual edits. Missing inventory/source changes never delete configured hosts.
  Manually removed hosts still present upstream can be rediscovered next sync;
  disable host sync to prevent this.
  Existing-host rows proposing additional addresses or cross-host overlaps, and
  unresolved name/ID conflicts are skipped/countable, not destructive merges.
  Unusable/disabled-family addresses are omitted; rows with none usable are skipped.
- All valid additions are one durable apply/verify/immediate-confirm transaction
  as `system-sando-host-sync`, with one new revision. Repeated inventory, score/
  name-only updates and empty lists create none. Limits (128 configured hosts
  and ordinary expansion/metadata constraints) fail atomically, without partial
  activation. Remove legacy forwarding rules explicitly before host creation.
- Automatic host additions trigger immediate policy reconciliation when enabled;
  policy-only sync still needs existing hosts. Score changes never generate
  automatic block/permit decisions. Empty inventory clears metadata only.
- Busy/apply failures preserve previous configuration/metadata and report an
  error for hourly retry. Cache persistence errors after successful host commit
  leave committed hosts intact but retain old metadata and report the error;
  the next retry creates no duplicate host/revision. Shutdown waits for an
  already-running durable apply/rollback; acquisition is cancellable.

### Response additions

`GET /api/v1/sando` remains bodyless/queryless, API-key/`state.read`, `200`/
`no-store`; `401`/`403`/`400`/`405`/`503` are unchanged.

```ts
interface SandoHostSyncStatusFields {
  added_hosts: number; // uint32, latest successful host reconciliation, 0 initially
  skipped_firewall_hosts: number; // uint32, ineligible/conflicting rows, 0 initially
  last_changed_revision: string | null; // canonical yyyy.mm.dd.iteration
}
```

These fields are runtime-only/current-source scoped, reset on restart/source
change and may remain visible while disabled/after failure. Revision identifies
the latest automatic host addition, not the latest overall configuration.
`skipped_hosts` still counts omitted metadata rows; `hosts` still contains
metadata, not the configured firewall inventory. Existing timestamps, error and
state fields now cover host reconciliation and metadata persistence together.
Use normal state/revision reads for configured hosts.

Synthetic status fragment (not the complete response):

```json
{"enabled":true,"state":"succeeded","added_hosts":1,"skipped_firewall_hosts":0,"last_changed_revision":"2026.11.25.2"}
```

The `hosts[].threat_score` contract remains nullable integer `-1..100`; `-1` is
no traffic data, not zero risk. Existing import report configuration fields
remain untouched; do not increment them for automatic sync/Test sync. MQTT
retains metadata-only counts and does not add host-add counts/revisions.

### Concrete frontend and deployment tasks

1. Remove browser inventory/score/policy fetches and import mapping/buttons,
   new-host-policy selection, browser import progress and report increments.
   Direct Sando browser access/CORS/mixed-content setup is no longer needed.
2. Keep URL, **Sync hosts and scores**, **Automatically sync policies**, daemon
   status polling and server **Test sync** with explicit Save / Commit/discard.
   Extend client status types/rendering with the three response additions.
3. Update permission calculation/gates for host-sync enable/disable and enabled
   URL changes: require firewall authority, including confirm/rollback/rebase.
   Display that new hosts are added with `drop`, not immediately trusted.
4. Show host additions, skipped conflicts, applied revision and errors separately
   from cached-host count/threat metadata. Refresh committed host inventory when
   automatic revisions arrive; preserve unsaved drafts and use normal conflict
   handling, never overwrite or blind-submit them.
5. Test sync remains **policies only** and does not create hosts. For new hosts,
   enable/save host sync and await successful discovery before testing policies.
   Enable both flags for complete unattended operation; policy-only remains supported.
6. Deploy the fixed backend before removing the browser workflows. Existing
   `sync_enabled:true` starts adding hosts after deployment/startup: disable it
   beforehand if undesired. Operators must verify default-drop implications,
   daemon reachability, host limits and compatible host-policy mode.
   No migration/reset/compatibility window or credential forwarding.
