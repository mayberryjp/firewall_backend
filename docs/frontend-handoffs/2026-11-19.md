## 2026-11-19-02 Performance log purge

- Priority: medium. Classification: required frontend/proxy integration.
- Status: Pending frontend review.
- Backend availability: unreleased; no deployment or delivery claimed.
- Contract/recommended bump: additive HTTP DELETE and `logs.delete` permission;
  next automatic calendar version. Supersedes only the no-history-clear-API
  statement in [2026-11-17-02](2026-11-17.md#2026-11-17-02-durable-performance-evidence-log).

### Exact contract

Previously `/api/v1/logs/performance` supported GET only (`logs.read`).
GET and its schema/limits remain unchanged. New
`DELETE /api/v1/logs/performance` uses API-key Bearer authentication and
`logs.delete`, without also requiring `logs.read`. Device-account keys include
the new permission; scoped credentials must explicitly grant it.
Syslog, Netcontrol and firewall deny-history deletion remain unsupported.

DELETE accepts no body, including `{}`, and no query parameters. Do not copy
`limit` or `cursor` from the GET URL. Successful response is `200`:

```json
{"source":"performance","purged":true}
```

Both fields are required and non-null; `source` is the literal string
`performance`, `purged` is boolean true. No defaults, counts, units, filters
or time range. It purges all retained segments, not only the displayed page.
Collection continues with unchanged baselines, so new records can appear
immediately, including observations in flight before the purge.
Configuration, revisions and other logs are unaffected.

Existing GET cursors then yield `reset:true` under a new persisted stream
identity. Restart preserves deletion; a durable intent finishes interrupted
purges before exposing history. I/O failure can mean partial deletion and
unavailable storage until successful restart recovery, never a successful no-op.
This does not securely erase disk blocks, external archives or client copies.

Errors: missing/invalid credentials `401`, missing delete authority `403`,
body/query `400`, unsupported method `405`, unsupported backend or storage
failure `503`; existing `{error:string}` envelope and no-store policy.
An empty stream may be purged repeatedly. A network timeout does not establish
whether deletion occurred; do not automatically retry a destructive action.

### Frontend tasks and deployment

1. Add `logs.delete` to permission/client models. Offer an explicit
   "Purge performance log" action with confirmation explaining irreversible
   deletion of all retained evidence, not just the visible page.
2. Verify/implement DELETE forwarding through the separate device proxy:
   `/api/v1/devices/{device_id}/proxy/logs/performance`. Preserve authorization
   and upstream errors. This repository implements the device-side endpoint
   only; the proxy method/permission allowlist has not been verified.
3. Send an empty body with no query. Pause/drain in-flight GETs before the
   action, or invalidate their results so old responses cannot repopulate the
   cleared table. After success discard local performance entries/cursors and
   restart visible-only GET polling without a cursor.
4. Every viewer must replace rows on `reset:true`. Leave other log tabs intact.
   Surface errors and uncertain outcomes; never present `503` as empty history.

Deploy the accepting backend and update scoped credentials/proxy forwarding
before enabling the action. No configuration edits, migration, compatibility
window, new host privilege or collector restart is required.

Acceptance checks: read-only key cannot delete; delete-only key can purge;
body/query rejected; multi-segment history disappears across restart; old
cursors reset; concurrent producers continue; empty purge succeeds; other logs
and saved configuration remain intact. Failure stays explicit. Backend
validation results/limitations are in the journal. Real device-proxy/browser
integration remains outstanding.

### Installer behavior and operator prerequisites

Previously installation selected a physical WAN implicitly, asked only for
LAN/address and preserved imported WAN/firewall configuration. It now reviews
all physical Ethernet ports and existing 802.1Q VLANs, offers new VLANs with
explicit name/parent/ID, asks for WAN/LAN/unassigned roles and DHCP/static IPv4,

tagged WAN and multiple LANs; nested VLANs are supported. Exactly one WAN is

selected management IPv4:8080; SSH remains localhost:2222.

forwarding, router access from all LANs, new forwarding only LAN ingress to WAN

loopback/established/related handling remains; global ICMP bypass is false.
No new inter-LAN allowance, DHCP/DNS server, Wi-Fi association, bridge/bond,
PPPoE or IPv6 setup. LAN clients need addressing, gateway and DNS. Matching
upstream switch tags and a trusted management network remain operator work.
Unassigned planned links stay up/no IP for trunks, MTU 1500 for all planned links.
Other imported Ethernet outside discovery is down/unassigned; omitted virtual
topology is removed from desired configuration. Kernel ownership and system/
software metadata are retained.

Unattended command now uses `--network-plan FILE --yes`; old installer
`--wan`/`--lan`/`--lan-address` flags are rejected. Reviewed plan schema, field
limits, IPv4 validation and a complete synthetic example are in the
[operator guide](../BUILD_AND_INSTALL.md#installer-network-plan).
Every existing physical/VLAN identity must be included; invalid/cyclic/duplicate

DHCP uses installer route metrics WAN 100/LAN 600; other client defaults remain.

Run from a local console with initial internet/DNS, Ubuntu amd64 systemd,

- `POST /api/v1/interfaces/{name}/dhcp/retry`: existing `interfaces.write`,
  bodyless or `{}`, no query, existing `202` retrying response and errors.
  A configured up VLAN client is now eligible through the same worker.

```json

```

## 2026-11-19-04 Daily NTP and Force sync

- Priority: medium. Classification: required NTP settings/status UI work.
- Status: Pending frontend review.
- Backend availability: unreleased local changes; not pushed or published.
- Contract/recommended bump: changed polling cadence (breaking the documented
  fifteen-minute timing contract), additive frontend action using an existing
  API; next automatic calendar version. No schema or permission changes.
  Supersedes only the polling cadence in
  [2026-11-15-05](2026-11-15.md#2026-11-15-05-immediate-full-ntp-clock-correction);
  immediate full clock stepping remains required.

Previously NTP polled immediately at worker startup and waited fifteen minutes
after each completed round. It now waits 24 hours (86,400 seconds), measured
monotonically, not at midnight. Startup/configuration-driven worker restarts
still poll immediately. Missing/invalid samples wait for the next daily round;
existing preparation/socket/clock-adjustment failure supervision still retries
with its existing backoff. Both automatic and manual accepted corrections
immediately step the whole host clock forward/backward regardless of offset
size, with no gradual correction or offset cap.

### Existing API used for the button

`POST /api/v1/processes/restart`, bearer authentication and `system.restart`
permission, no query parameters, exact JSON body:

```json
{"target":"ntp"}
```

Only the NTP worker is joined/restarted. It immediately polls the saved enabled
NTP configuration and begins a new daily wait afterward. It does not enable
NTP, modify configuration/revisions or restart other services. Do not use
`POST /api/v1/services/ntp/reconcile`, which reconciles all enabled services.
NTP editing permission `ntp.write` alone does not grant this operational action.

Native success is HTTP `200`, for example (abbreviated worker snapshot):

```json
{"target":"ntp","status":"restarted","worker":{"name":"ntp","state":"running","sample_status":"warming_up","started_at":"2026-11-19T03:30:00Z"}}
```

The worker snapshot can already contain a fresh available sample or a recovering
error. This acknowledges restart, not successful time synchronization.
HTTP `401`/`403` reject missing credentials/permission; `400` rejects invalid
body/query, `405` rejects another method, `409` rejects disabled NTP or an active
configuration/recovery/upgrade/restart transaction, and `503` reports backend
or worker-controller unavailability. Errors retain the existing `error` string
envelope. Simulator `200` with `status:"simulated"` does not adjust a clock.
No new HTTP method/path, request/response field, unit, default or nullability
is introduced.

### Frontend tasks and acceptance

1. Change help from fifteen-minute to daily polling. Add **Force sync** on the
   NTP page, with a warning that correction is immediate and can affect logs,
   expiry, schedules and gateway measurement warmup. No gradual-mode selector.
2. Enable the button only for saved enabled NTP, appropriate permission and
   no active configuration/upgrade/restart operation; prevent duplicate
   submissions while this action is pending.
3. Show "Sync requested" after restart, not "Synchronized". Poll
   `GET /api/v1/services/ntp/status` with `state.read`, inspect the `ntp` instance
   and show its fresh `sample_status`, `server_time`, `collected_at`, signed
   millisecond `offset_ms`/`requested_step_ms`, nonnegative `delay_ms` and errors.
   The restart replaces prior sample state. Use its worker `started_at` to
   associate snapshots, not a numerically later `collected_at`: time can move
   backward. No request completion token is supplied.
4. Keep unavailable samples and supervisor errors visible without disabling
   unrelated configuration. Allow deliberate retry after failure. A disconnect
   or frontend polling timeout is not proof no clock step occurred; re-read
   status rather than automatically submitting another Force sync.
5. Accept immediate startup polling, daily waiting, manual polling before the
   daily deadline, full corrections in either direction including small
   offsets, disabled/forbidden/busy errors and explicit simulator labeling.
   Check only NTP restarts and current saved servers are used.

Deployment coordination: deploy the updated backend for daily scheduling and
the frontend button/help together; no migration or compatibility window.
Native opt-in host services, `CAP_SYS_TIME`, configured reachable servers and
exclusive clock ownership remain prerequisites. Invalid samples are still
rejected; an untrusted/wrong configured server can set the wrong appliance time.
Rollback restores configuration, not clock time.

Backend validation: all ten focused NTP fixtures passed; the complete services
suite passed (122 passed, 26 ignored), along with services strict all-target
Clippy/build and workspace formatting. The manual restart fixture interrupts
the real 24-hour condition-variable wait, removes stale sample state, polls a
local UDP fixture immediately and captures full zero/forward/backward clock
targets without changing the host clock. Actual appliance clock changes,
24-hour elapsed operation and frontend/browser acceptance remain unverified.

```json
{"index":13,"name":"tun_wg0","rx_errors":"5039","tx_errors":"3","rx_drops":"0","tx_drops":"51","rx_frame_errors":"5039","rx_length_errors":"0","rx_errors_delta":"2","tx_errors_delta":"0","rx_drops_delta":"0","tx_drops_delta":"0","rx_frame_errors_delta":"2","rx_length_errors_delta":"0"}
```

has a null delta independently; unchanged counters return `"0"`. Units are
kernel interface error/drop counts, not guaranteed unique packet counts.
Logging still emits only positive deltas, with one interface evidence row even
when RX total and a subtype both increase. No threshold, sampling interval,
aggregation/incident lifecycle or gateway-probe behavior changes.

No request/query validation, HTTP status/error, permission, polling or retention
changes. Existing `401`/`403`, invalid-request `400`, unsupported method `405`
and backend/log-storage `503` behavior remains. Detailed counter decode failures
use existing unavailable link-diagnostics/error handling, not zero counters.
Already persisted log records are not rewritten; unknown/historical diagnostic
details must remain safely viewable as opaque JSON, without fabricated fields.

## 2026-11-19-07 Live firewall clock

- Priority: medium. Classification: required client type and live-clock UI work.
- Status: Pending frontend review.
- Backend availability: unreleased local changes; not pushed or deployed.
- Contract/recommended bump: additive response field, next automatic calendar
  version. No new endpoint, configuration, permission or NTP scheduling change.

### Affected API and previous versus new behavior

`GET /api/v1/system/status`, bearer authentication with `state.read`, no query
parameters. Previously this returned only confirmed host settings and cached
apply-time observations. It now also returns required, non-null `current_time`:
an RFC3339 UTC string read from the daemon's current system clock on every
status read. Optional fractional seconds have up to nanosecond precision.
No default or null fallback; existing hostname/timezone fields and nullable
`last_applied_at_unix` keep their previous meaning.

Synthetic response:

```json
{"current_time":"2026-11-19T08:58:31.123456789Z","hostname":{"configured":"","observed":null,"state":"unmanaged","error":null},"timezone":{"configured":"","observed":null,"state":"unmanaged","error":null},"last_applied_at_unix":null}
```

This works without NTP enabled and in all host-setting modes. In simulated
mode it is the real daemon host clock, not a simulated appliance clock.
It is not a new upstream NTP query, proof of synchronization, or a monotonic
timestamp. An incorrect clock is reported as-is; accepted NTP corrections or
operator changes can move it backward or forward.

`GET /api/v1/services/ntp/status` is unchanged: `server_time` is the last
selected server's sampled reply-transmission time, `collected_at` is sample
publication time and `offset_ms` is the pre-step measurement. Preserve these
as historical evidence; do not make that sample appear to be a fresh NTP reply.

Existing HTTP behavior remains: `200` with manager status, `401`/`403` for
authentication/permissions, `400` for query parameters, `405` for other methods,
and `503` when the manager/status is unavailable. Timestamp-format failures
also follow the existing `503 {"error":"system status unavailable","transaction":null}`
path, not a fabricated time. No request-body, retention or storage changes.

### Frontend tasks, deployment and acceptance

1. Add required `current_time:string` to `SystemStatus` and show a distinct
   **Current firewall time** display. Convert UTC to the selected display
   timezone, without treating `last_applied_at_unix` or NTP `server_time` as now.
2. Anchor the returned time at response receipt, then advance locally with a
   monotonic timer such as `performance.now()`. Between refreshes this is an
   estimate with network/request latency, not a fresh upstream reading.
3. Refresh periodically, on visibility/resume, and after a newly accepted NTP
   sample (not merely the restart acknowledgment). Replace the anchor on each
   successful refresh, including backward clock corrections; prevent older
   in-flight responses from replacing newer anchors.
4. Preserve last-sample NTP timestamps, offset, age and availability separately.
   Surface refresh errors and stale/unavailable time; do not silently substitute
