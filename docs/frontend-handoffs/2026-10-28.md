# Frontend Handoffs - 2026-10-28

## 2026-10-28-02 Basic native IPv4 BGP

- Priority: normal. Classification: **required**. Status: **Pending frontend
  review**. Backend availability: **Unreleased**, not deployed/delivered.
  Recommended bump: minor for additive BGP config, permission, APIs and
  monitoring; baseline unknown. No release/version bump or compatibility window.
- Previously there was no native BGP, BGP route inventory or learned WireGuard
  AllowedIP management. New top-level `config.bgp` uses full configuration
  transactions, `transactions.write` plus **`bgp.write`**. Existing enabled-
  service repair permissions also include `bgp.write` when enabled.
- New API-key-authenticated **`state.read`** GET paths:
  - `/api/v1/services/bgp`: committed configuration.
  - `/api/v1/services/bgp/status`: applied worker/neighbor summary.
  - `/api/v1/routes/bgp`: learned accepted paths, source, selection and
    installation state. Existing `/api/v1/routes` remains static configuration.
  No query (`400`), read-only (`405`), normal `401`/`403`; unavailable backend/
  scope/cache is `503`. Session/install failures remain readable in status.
- Existing `POST /api/v1/processes/restart`, permission `system.restart`,
  accepts `{"target":"bgp"}`. Native `200` means supervisor restart, not
  established BGP; `409` if disabled or transaction/upgrade activity, `503`
  on unavailable restart. Simulator reports simulated. It withdraws/relearns.

### Form and client changes

Follow the [canonical BGP contract](../../FRONTEND_SPEC.md#native-ipv4-bgp)
for exact field types, limits, statuses, examples, ownership and protocol limits.
Synthetic configuration fragment (requires matching interface/address/peer):

```json
{"bgp":{"enabled":true,"local_asn":65001,"router_id":"10.10.0.1","keepalive_seconds":30,"hold_seconds":90,"max_prefixes":4096,"neighbors":[{"name":"remote","address":"10.10.0.2","local_address":"10.10.0.1","interface":"wg0","remote_asn":65002,"wireguard_public_key":"AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI=","accept_default":false}]}}
```

- Add a transactional BGP form: enable, uint32 local/remote ASN, IPv4 router ID,
  neighbor name/address, configured up interface and static local IPv4 address
  selector, WireGuard public-key selector, keepalive/hold seconds, max prefixes
  and per-neighbor warned default-route opt-in. No resolver/process helper or
  external integration configuration.
- Default disabled, ASN 0/router ID empty, timers 30/90 seconds, max prefixes
  4096, neighbors empty. Enabled requires identity and a neighbor. ASN nonzero,
  excluding AS_TRANS 23456, reserved 65535 and uint32 max; hold 3..65535, keepalive
  1..hold/3; max prefixes 1..16384 **across all neighbors**, max 32 neighbors.
  Normal descriptive metadata is supported on BGP config/neighbors.
- Neighbor must have a unique name/IPv4 address and an up configured interface.
  Local address must be statically assigned. Non-WireGuard peers are directly
  connected; WireGuard requires one explicitly referenced enabled peer and
  static AllowedIPs/bootstrap routes covering the BGP neighbor. Default import
  false; enabling it permits route 0/0, not default origination.
- All configured live-up IPv4 connected networks, including DHCP addresses,
  export automatically; there is no interface export checkbox in this version.
  Static and learned routes are not redistributed. Basic eBGP/iBGP uses TCP179;
  NEXT_HOP must equal the neighbor address (use next-hop-self for iBGP).

### Rendering, monitoring and ownership

- Add a BGP-specific route view showing prefix, neighbor, interface, next hop,
  AS path, ORIGIN, LOCAL_PREF/MED, source `"bgp"`, selected/installed booleans,
  nullable reason/error. Selected does not imply installed or kernel-best route.
  See canonical JSON example; accepted alternate paths are included. Filtered
  loops/defaults/etc. are counted, not returned as accepted rows.
- Show neighbor `active`, `open_sent`, `open_confirm`, `established`, effective
  hold timer/router ID, received/advertised/rejected counts and last error.
  Poll single-flight while visible; fetch routes separately from status.
  No pagination/history, no per-route MQTT publication.
- Worker `running` with an unavailable neighbor is `health:"degraded"` and a
  shared service warning, not a dead process or configuration-editing gate.
  Support disabled/starting/error/stopped/simulated states and absent active-
  only fields. Simulator has no learned routes, null unmeasured counts.
- `runtime.bgp`, aggregate statistics `bgp`, existing MQTT state `bgp`, and an
  appliance-services row named `bgp` carry summaries; shared process-health/
  active-alert publication needs no new broker integration. Existing health
  discovery sensors remain applicable.
- Learned Linux routes and WireGuard AllowedIPs are ephemeral **runtime** state.
  Do not copy learned prefixes into candidate/desired AllowedIPs or static
  routes. Show static prefixes in forms and dynamic additions read-only.
  Withdraw/session loss/restart/disable/apply/rollback/shutdown removes owned
  additions, preserving configured entries; startup recovers a private scoped
  ownership journal and relearns. Cross-peer overlap is rejected rather than
  moving a static prefix to another WireGuard peer.

### Deployment and acceptance

- Backend must be deployed before form/types/controls. Grant scoped permissions;
  provide native socket/netlink privileges, TCP179 input permits limited to
  trusted peers, WireGuard underlay UDP and bootstrap addressing/routes.
  Existing root service/kernel prerequisites suffice; no BGP helper package,
  eBPF setup, automatic input permit or supervision unit is introduced.
- WireGuard dynamic AllowedIPs authorize source addresses too; trust route
  sources accordingly. No TCP MD5/AO, IPv6/MP-BGP, recursive next hops, learned
  transit, route reflection/refresh, AS_SET/confederations, graceful restart,
  BFD, ECMP or full routing-policy engine.
- Acceptance: transaction permission/default/validation errors, enabled/disabled
  state, establishment/wrong ASN, connected export/withdrawal, default import
  opt-in, loop/capacity rejection, BGP-only route display and null/simulator
  rendering. Verify learned route/AllowedIP removal and static preservation on
  session loss/restart, restart unknown outcomes, rollback and status/MQTT.
- Backend tests execute two real isolated Linux routers with native BGP over
  WireGuard, kernel route/AllowedIP checks, session loss, durable ownership
  crash recovery, restart, network apply/rollback; protocol/API/CLI/health/MQTT
  tests also pass. Real appliance, independent-speaker interoperability, live
  broker, browser and high-route-count/load acceptance remain unverified.
- Final workspace validation: 373 tests passed, 43 privileged tests ignored;
  the BGP native fixture passed separately. Clippy, formatting and build passed.
  See the journal for exact commands, concurrent-tree context and limits.

## 2026-10-28-01 Managed restart and timed DNS actions

- DNS server-selection restriction below is superseded by
  [2026-10-28-04](#2026-10-28-04-explicit-dns-diagnostic-server): the request now
  accepts an optional explicit `server` IP. Other action semantics remain.

- Priority: normal. Classification: **required**. Status: **Pending frontend
  review**. Backend availability: **Unreleased**, not deployed or delivered.
  Recommended bump: minor for additive operational APIs/permissions and manager
  health entries; baseline unknown. No persisted configuration schema change.
- Previously there was no targeted managed-worker/daemon restart or timed DNS
  lookup action. New API-key-authenticated actions:
  - `POST /api/v1/processes/restart`, permission `system.restart`.
  - `POST /api/v1/diagnostics/dns-lookup`, permission `diagnostics.run`.
  Neither requires `transactions.write` or `state.read`, creates a revision or
  performs broad network repair. Device keys receive the permissions; scoped
  credential files need explicit grants. Existing read permissions still apply
  when subsequently polling status.
- Both require strict JSON, no query parameters; normal `401`/`403`, `405` for
  other methods, `400` for invalid payload/query, `409` during active transaction,
  recovery, upgrade or daemon restart, `503` for unavailable preparation/backend.
  Use the full
  [canonical contract](../../FRONTEND_SPEC.md#operational-restart-and-dns-diagnostics)
  for exact supported target IDs and all response fields/limits.

### Restart UI and client work

- Add a deliberate confirmation action on managed process/status views.
  Synthetic request: `{"target":"ntp"}`. This is not arbitrary PID/process
  killing. Native targets must be configured/enabled: unknown returns `404`,
  disabled returns `409`, unavailable returns `503`.
- Native completion is `200 {target,status:"restarted",worker:<status>}`;
  simulator is `status:"simulated"`. Completion does not promise protocol
  health, a new DHCP lease, synchronization or upstream delivery.
- Async manager example:
  `{"target":"mqtt","status":"restart_requested","generation":1}`, HTTP `202`.
  Generation is ephemeral, not a revision or completion token; requests during
  drain can coalesce. Poll existing status, do not automatically repeat.
- Daemon request: `{"target":"netcontrold"}`; `202` acknowledges graceful
  scheduling. It drains HTTP/SSH/workers and durably shuts down, then relies on
  the packaged native host-mode systemd/watchdog on-failure restart policy.
  Manual/simulator/OpenRC/namespace launches return `503`. No new installer
  prerequisites beyond that existing service policy are introduced.
- Warn about temporary management loss, DHCP connectivity effects, selected
  worker cache/counter resets and possible syslog delivery gaps. Preserve drafts,
  handle unknown outcomes without blindly resubmitting, and reconnect with
  bounded backoff. Persistent accounting databases/configuration remain intact.
- Existing platform/process-health/MQTT components gain `managed_processes`
  resources for the async runners. Accept `running`, `restarting`, `error`,
  `stopped`; errors remain visible while their controller accepts a new restart.
  Do not turn a service failure into a global draft/editing lock.

### DNS diagnostic UI and client work

- Provide required interface selection and hostname, A/AAAA selection, optional
  timeout. Synthetic request:
  ```json
  {"interface":"wan0","hostname":"example.test","record_type":"A","timeout_ms":2000}
  ```
- `record_type` defaults to A, only A/AAAA. `timeout_ms` is an integer 100..5000,
  default 2000. Hostname is ASCII, labels 1..63, total <=253 excluding optional
  final dot, alphanumeric ends and alphanumeric/hyphen interiors; no IP literals.
  Returned hostname is lowercase without final dot. No resolver override input.
- Selects that up configured interface's configured then valid matching DHCP
  servers, respecting DNS override and global IPv6 resolver policy. No public
  fallback or OS hosts/cache lookup; the queried resolver may cache.
- Render `status`, addresses, DNS `rcode`, chosen server/transport,
  numeric millisecond `rtt_ms`/`elapsed_ms`, attempts, opaque scope and captured
  revision. Null RTT is unavailable, not zero. RTT includes server processing;
  TCP fallback RTT excludes connect/earlier UDP, while elapsed includes them.
- First valid DNS response ends lookup, including NXDOMAIN/SERVFAIL/REFUSED;
  nonzero codes have empty answers but measured RTT. Only transport/protocol
  failures advance to the next server. All failed attempts are HTTP `200` with
  `status:"failed"`, null answer timing/server/transport/code, empty addresses,
  and explicit attempt errors. Simulator is `simulated` with null timing.
- Single-flight the form; do not continuously poll the lookup. Backend permits
  two concurrent operations; additional requests return `429`. DNS network I/O
  does not hold the engine lock or stop concurrent configuration workflows.

### Coordination and acceptance

- Deploy backend before enabling these controls. Grant scoped permissions,
  verify the supervised native daemon prerequisite before offering full restart,
  and select a configured up interface with effective DNS servers.
- Check authorized/unauthorized, strict payload/method/query errors, unknown/
  disabled targets, active-transaction/upgrade conflicts, targeted restart
  without revision changes, and management reconnection after daemon restart.
- Check A/AAAA, negative DNS answers, UDP/TCP fallback, timeout/server errors,
  null simulator values, `429`, attempt details and unchanged configuration.
- Backend validation: workspace tests, clippy, formatting and build passed;
  isolated real DNS/native collector restart fixture passed. API tests cover
  authorization, gating, daemon scheduling, revision/scope and concurrency with
  the engine lock released. Actual systemd restart, real-appliance WAN/DHCP/
  resolved selection and browser acceptance remain unverified.

## 2026-10-28-03 Destination rewrite

- Priority: normal. Classification: **required**. Status: **Pending frontend
  review**. Backend availability: **Unreleased**, not deployed or delivered.
  Recommended bump: minor (additive configuration/API fields and CLI); baseline
  unknown. No version bump, release or frontend notification.
- Previously NAT exposed only masquerading. New persisted configuration:
  `firewall.nat.destination_rewrite: DestinationRewriteRule[]`, defaults to `[]`
  when omitted; null is invalid. The API returns this collection, including empty.
- Exact affected API surfaces:
  - `POST /api/v1/transactions`: complete candidate under `config`, existing
    `transactions.write` plus `nat.write` for changes (including metadata).
  - `POST /api/v1/transactions/{id}/confirm` and
    `POST /api/v1/transactions/{id}/rollback`: existing permissions/workflow.
  - `POST /api/v1/revisions/{revision}/restore`: existing complete-package
    historical restore and changed-domain authorization.
  - `GET /api/v1/firewall/nat`: observed NAT object now has both `masquerade`
    and `destination_rewrite`. `GET /api/v1/firewall/rules`, state/config,
    transaction/revision views and exports include the new nested collection.
    Existing `state.read`/history permissions apply. Authentication is API-key
    Bearer, unchanged. No standalone write endpoint or permission was added.
- Required fields: `out_interface` (up managed WAN of the target family),
  `protocol` (`tcp` or `udp`), `destination_port` (one integer 1..65535),
  `target_interface` (up managed LAN), `target_address` (canonical usable unicast
  literal on its static subnet, another device, never the firewall's own IP).
  Family is inferred from target; IPv6 needs global enable and static WAN IPv6.
  IPv4 WAN can use DHCP. At most 256 rules; WAN/protocol/port/family matches
  must be unique. Standard optional `metadata` applies.
- Synthetic NAT fragment (assumes matching interfaces/subnet exist):
  ```json
  {
    "masquerade": [],
    "destination_rewrite": [
      {"out_interface":"wan0","protocol":"udp","destination_port":53,
       "target_interface":"lan0","target_address":"192.168.10.53"},
      {"out_interface":"wan0","protocol":"tcp","destination_port":53,
       "target_interface":"lan0","target_address":"192.168.10.53"}
    ]
  }
  ```
- Semantics: prerouting destination NAT matches the original WAN route before
  rewriting; normal forwarding filters then see the local target/actual LAN
  egress. Preserves source IP and destination port; conntrack reverses replies.
  Only forwarded traffic; local output, LAN-routed destinations, other ports/
  protocols/families do not match. No source filters, ranges, port translation,
  filter bypass, automatic source NAT or connection flush.
- **Required UI warning:** replies must return through the firewall. Same-subnet
  client/target direct replies normally break reverse NAT; require operator-set
  routed return paths or a separate target subnet. Existing explicit masquerade
  can still change sources. Edits/removal/rollback affect new connections, not
  existing translations; never imply immediate disconnection or silently flush.
- Errors: missing/wrongly typed required fields and port values outside u16
  return `400`; port zero, bad references/roles/subnet/family, duplicate matches
  and excess rules return `422`. Normal `401`/`403`, revision/transaction/drift
  `409` and native failure/recovery behavior remain. Transaction unknown-field
  pruning still reports `ignored_fields`; do not submit unsupported controls.
- Frontend work: update NAT/config/history/client types; ordered add/edit/delete/
  reorder and metadata UI; role/up/family-aware WAN/LAN choices; exact-port,
  subnet, uniqueness and interface dependency validation; separate TCP and UDP
  DNS rules; preserve masquerade/unrelated configuration. Show routing,
  source-preservation, new-connection and post-DNAT filter warnings during review.
  Warn that the target itself is not source-exempt: its forwarded upstream DNS
  must not match the same WAN/port, or it is redirected back to itself.
- Deployment: backend first. Operator must provide nftables inet FIB/NAT kernel
  support, working forwarding, target routing and reverse path. No new installer
  automatic module loading or forwarding settings; IPv6 forwarding remains
  operator-owned. No old-contract compatibility window is required.
- Acceptance: check both DNS transports, IPv4/IPv6 family separation, unrelated
  ports/LAN destinations/local output bypass, default-drop requiring explicit
  target allow, reply source appearing as the original Internet destination,
  source preservation, validation/auth errors, confirmed persistence/reopen,
  removal/rollback and retained existing conntrack mappings.
- Backend checks and limitations are recorded in the
  [journal](../journal/2026-10-28.md#destination-rewrite).
  Browser/frontend integration and physical appliance/reboot acceptance remain
  outstanding; no claim of deployment or delivery.
- Sources: [canonical spec](../../FRONTEND_SPEC.md#destination-rewrite),
  [model/validation](../../crates/netcontrol-core/src/model.rs),
  [transaction tests](../../crates/netcontrol-core/src/engine_tests.rs),
  [native compiler](../../crates/netcontrol-native/src/firewall_plan.rs),
  [DNAT encoding](../../crates/netcontrol-native/src/linux/destination_rewrite.rs),
  [packet tests](../../crates/netcontrol-native/src/linux/integration.rs),
  [CLI](../../docs/CLI.md), [example](../../examples/destination-rewrite.json).

## 2026-10-28-04 Explicit DNS diagnostic server

- The required-interface restriction below is superseded by
  [2026-10-28-05](#2026-10-28-05-optional-dns-diagnostic-interface), which also
  makes response `interface` nullable. Other explicit-server behavior remains.

- Priority: normal. Classification: **required**. Status: **Pending frontend
  review**. Backend availability: **Unreleased**, not deployed or delivered.
  Recommended bump: minor (additive request field); baseline unknown.
- API: `POST /api/v1/diagnostics/dns-lookup`, API-key Bearer authentication,
  existing `diagnostics.run` permission. Previously `server` was rejected as an
  unknown field (`400`); now optional `server: string | null` selects one IPv4
  or IPv6 literal. Omitted/null retains configured-first, valid matching DHCP
  resolver selection. No persisted configuration or response schema changes.
- Synthetic request:
  ```json
  {"interface":"wan0","hostname":"example.test","server":"192.0.2.53","record_type":"A","timeout_ms":2000}
  ```
  Interface remains required, configured and up. Explicit server needs no
  configured DNS and bypasses configured/DHCP resolver selection. Port is fixed
  at 53, UDP with TCP truncation fallback; only that server is attempted.
  Nonloopback servers bind to the selected interface; loopback uses local
  loopback routing. Never silently retry a configured server after failure.
- Validation: IP literal only; hostnames, URLs, IP:port, wrong types,
  unspecified/multicast/IPv4 limited-broadcast addresses return `400`.
  IPv6 server with global IPv6 disabled returns `503`, as do missing/down
  interfaces and unavailable backend/scope. `record_type` remains A/AAAA,
  default A; timeout remains integer milliseconds 100..5000, default 2000.
  Existing `401`/`403`, method `405`, query `400`, operational conflict `409`
  and concurrency `429` rules are unchanged.
- Response handling is unchanged: `200 status:"failed"` on exchange failure,
  null RTT/server/transport/rcode at top level, and the requested server/error
  in the single attempt. A valid negative response is `status:"answered"`
  with numeric rcode and measured RTT. Simulator remains `simulated` with
  null server/timings and no I/O, even when a server was requested.
- Frontend tasks: add optional DNS server IP to client types and lookup form;
  validate as an IP, omit when blank, retain required interface/A/AAAA/timeout.
  Do not save this diagnostic override into DNS configuration. Preserve existing
  answer/error/attempt rendering and single-flight submission; no polling.
- Deployment: deploy updated backend before enabling the field (prior backend
  rejects it). Existing native socket privileges, interface routing/firewall
  permits and IPv6 policy apply; no installer/dependency changes.
- Acceptance: explicit IPv4/IPv6 payload acceptance, invalid IP/type `400`,
  omitted/null configured behavior, override with no configured DNS, exactly one
  attempt on explicit failure, missing interface/IPv6-disabled `503`, unchanged
  revision and truthful simulator timing. Core input test, four HTTP operations
  tests and isolated native UDP selection/no-fallback fixture passed. Workspace
  tests (373 passed, 43 ignored), strict Clippy, formatting and build passed;
  exact commands are tracked in the journal. Actual appliance IPv6/WAN
  routing and frontend/browser acceptance remain unverified.

## 2026-10-28-05 Optional DNS diagnostic interface

- Priority: normal. Classification: **required**. Status: **Pending frontend
  review**. Backend availability: **Unreleased**, not deployed/delivered.
  Recommended bump: major for nullable response `interface`; baseline unknown,
  no version change. Request relaxation itself is additive.
- API: `POST /api/v1/diagnostics/dns-lookup`, unchanged API-key Bearer auth and
  `diagnostics.run` permission. Previously `interface` was a required string.
  Now request `interface?: string | null`; omit/null it with an explicit server
  to use normal kernel routing in the managed namespace, without device binding
  for UDP or TCP fallback. Does not require any configured interface or DNS.
- Synthetic request:
  ```json
  {"hostname":"example.test","server":"192.0.2.53"}
  ```
  Response `interface` is now `string | null`, echoing the requested interface
  or null when unspecified, including simulator responses. It is not measured
  egress identity. Other result/attempt fields, units and nullability remain.
- At least one of `interface` or `server` is required (`400` otherwise).
  Empty/invalid interface or wrong type is `400`; a supplied valid but
  missing/down interface is still `503`. Without `server`, interface selects
  configured/DHCP resolvers as before. Explicit IP server remains exclusive,
  port 53, no fallback. IPv6 server with global IPv6 disabled remains `503`.
  Hostname rules, A/AAAA default A, integer timeout 100..5000 ms default 2000,
  negative-response/failed-result behavior and `401`/`403`/`405`/`409`/`429`
  rules are unchanged.
- Frontend tasks: remove unconditional interface requirement, allow automatic
  routing with a server, omit/null an unset interface (never send empty string),
  and require a server when no interface is selected. Update response client
  type/rendering to accept null interface without inventing an egress device.
  Do not persist these diagnostic choices into saved network configuration.
- Deployment: updated backend first because older code rejects server-only
  requests. Existing native socket privileges and kernel routing/firewall
  permits apply; no installer/dependency changes. Operator must provide a route
  to the resolver; no auto-selection of a configured WAN or public DNS fallback.
- Acceptance: omitted/null interface with server returns a diagnostic result;
  null response interface, unbound native nonloopback query, UDP/TCP fallback,
  omitted both/empty interface `400`, supplied missing/down interface `503`,
  configured resolver selection and unchanged revision. Focused core, DNS
  transport and namespace-native tests passed. Workspace tests (373 passed,
  43 ignored), strict Clippy, formatting and build passed; commands are tracked
  in the journal. Real WAN/IPv6 paths and browser acceptance unverified.
