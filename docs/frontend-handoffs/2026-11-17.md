# Frontend handoffs: 2026-11-17

## 2026-11-17-01 Startup policy and event-driven managers

- Priority: medium. Classification: required client/status/help updates.
- Status: Pending frontend review. Backend availability: unreleased; not sent,
  deployed or browser-verified.
- Contract/recommended bump: breaking runtime removal and host-policy/status
  semantics; next automatic calendar version, no manual version bump.
- Supersedes the continuous-enforcement/runtime-status portions of
  [2026-11-10-01](2026-11-10.md#2026-11-10-01-mandatory-panic-reboot), not the
  mandatory startup/boot panic reboot setting.

### Exact contract changes

All existing authentication, permissions, request validation, HTTP status/error
envelopes, configuration defaults and units remain unchanged.

- `GET /api/v1/runtime` (`state.read`) omits `kernel_panic` entirely in every
  mode. Remove its former `state`, `retrying`, nullable `error`,
  `reboot_after_seconds`, nullable `observed_seconds`, nullable `drift`,
  `enforcement_interval_seconds` and `persistence_file` client fields.
  `GET /api/v1/state`, `GET /api/v1/runtime` and
  `GET /api/v1/platform/status` (`state.read`) no longer include a
  `component:"kernel_panic", resource:"host"` process-health/alert row.
  Other runtime/health fields remain.
- Native host startup still sets/verifies `kernel.panic=10` and persists
  `/etc/sysctl.d/99-netcontrol-panic.conf`; failures abort startup. There is no
  policy worker, drift polling, retrying/recovering state or subsequent external
  change reclamation. This is not a panic/crash detector. Panic triggers are
  unchanged, and no panic is induced for testing.
- `GET /api/v1/system/status` (`state.read`) retains the object/field types below,
  but `observed` is a cached application/verification observation, not a
  continuous live host measurement. `current` means the last application
  verified a match. Remove the former `applying` state from client types.
  Startup and a changed confirmed hostname/timezone apply and verify the value;
  unchanged successful values are not reclaimed after external changes.
  Failed application/verification retries after 30 seconds; changes notify the
  manager immediately. Unmanaged observations refresh on configuration events.

```json
{"hostname":{"configured":"fw-1","observed":"fw-1","state":"current","error":null},"timezone":{"configured":"UTC","observed":"UTC","state":"current","error":null},"last_applied_at_unix":1794870000}
```

Remaining system states are `unmanaged|current|error|paused|simulated|unavailable`;
`configured` is a nonnull string, `observed`/`error` nullable strings, and
`last_applied_at_unix` nullable Unix seconds. Empty configuration still means
unmanaged and does not restore an earlier host value. `system.domain` is still
only a display/reporting label. Existing full-configuration
`POST /api/v1/transactions` and `POST /api/v1/transactions/{id}/confirm`
authorization (`transactions.write`, `system.write`, other changed areas'
permissions), persistence, confirmation and rollback remain intact.

- `POST /api/v1/processes/restart` with `{"target":"system"}`
  (`system.restart`) still schedules `202` and now provides an explicit way to
  reapply the same saved host values, without changing configuration.
- MQTT, Dynamic DNS, Sando and Discord use configuration notifications rather
  than idle one-second configuration scans. Existing MQTT publication intervals,
  five-second reconnect retries, Dynamic DNS configured update intervals,
  hourly Sando refresh and enabled native Discord one-second drop sampling
  remain. Disabled integrations wait for changes. Their existing status APIs
  and schemas are unchanged; no frontend polling loops are needed.
- Platform health still refreshes approximately every two seconds and goes
  stale after 15 seconds. Collection is separate from transaction deadlines/
  watchdog progress and uses cached native worker snapshots rather than live
  runtime diagnostics. Contention is explicitly unavailable/retrying, never
  silently healthy. `runtime_available` refers to this cached health collection.
  The always-on packet/link diagnostics collector and sampling are unchanged.

### Frontend tasks and deployment

1. Remove the panic worker/recovery row and runtime model, retaining static help
   explaining startup/boot automatic reboot ten seconds after a genuine panic.
2. Label system status as last verified/applied, not continuously enforced/live.
   Remove drift-reclamation promises and `applying` rendering. Preserve errors,
   pending draft separation and the clear-value-does-not-revert explanation.
3. Keep existing intervals/polling and restart permissions; do not infer a real
   crash from policy configuration or remove unrelated diagnostic views.

Coordinate the client contract/help with the new backend. No compatibility
window, new endpoint, credential, privilege or persisted-state conversion.
Operators should avoid competing sysctl/hostname/timezone writers; changes they
make later are not automatically undone. Host panic startup still requires
writable procfs, trusted sysctl storage and accepted reboot policy.

Acceptance: startup policy persists/verifies without a worker row; system
changes apply only after confirmation and failures remain retryable; external
changes are left alone after success; integration enable/disable/source changes
take effect without a one-second configuration timer; stale/contended health
does not block transaction deadline progression; existing diagnostics remain.
Backend validation and outstanding appliance/browser checks are recorded in the
journal; no frontend implementation or delivery is claimed.
Final workspace tests: 843 passed, 110 ignored; strict all-targets Clippy,
formatting and build passed. Five selected isolated Linux lifecycle/hostname
integration tests also passed. Appliance boot, live providers and browser
acceptance remain unverified.

## 2026-11-17-02 Durable performance evidence log

- Priority: high for troubleshooting visibility. Classification: required.
- Status: Pending frontend review. Backend availability: unreleased; no
  approved release, deployment, notification or browser verification claimed.
- Contract/recommended bump: additive log endpoint/stream and native durable
  storage; next automatic calendar version, no manual version bump.

### Exact contract

Previously qdisc/interface/TCP interval evidence disappeared as diagnostic
snapshots refreshed, and gateway loss was a rolling snapshot rather than a
durable new-timeout history. Add bodyless `GET /api/v1/logs/performance`,
API-key Bearer authentication, `logs.read` (not `state.read` or
`firewall.logs.read`). Existing log endpoints are unchanged.

Use the existing log-page shape: `source:"performance"`, `entries` with
decimal-string `sequence`, UTC persistence `timestamp`, UTF-8 `message` text;
`next_cursor`, nullable `oldest_cursor`, booleans `gap`, `reset`, `has_more`,
numeric `retention_bytes:8388608`, `max_message_bytes:65000`, and
`capture:{state,retrying,error}`. Strict optional `cursor` and canonical integer
`limit` 1..500 (default 100), query at most 1024 bytes; no other parameters/body.
Unauthorized 401, missing permission 403, invalid query/body/ahead cursor 400,
non-GET 405, unavailable/corrupt storage or simulator 503 with `{error:string}`.
Responses are no-store. Separate stream identity/cursor; existing cursor gap/
reset, chronological numeric sequence, page byte limits and tail-first rules
apply unchanged. No configuration edits, new permission or history-clear API.

`message` contains JSON with schema `netcontrol-performance/v1`, event,
UTC RFC3339 `observed_at` and object `details`. Persistence time and observation
time differ. Event details/units/nullable fields are specified in the
[canonical contract](../../FRONTEND_SPEC.md#performance-evidence-log):

- `link_observation`: previous collection timestamp/null and actual interval
  seconds/null, with up to 32 individual evidence rows. Newly increased qdisc
  drops retain interface/index, kind, handle/parent and decimal-string delta/
  cumulative drops. Never sum parent/child qdiscs.
- Other link evidence: combined RX+TX interface errors/drops, router-local
  established TCP retransmissions, and distinctly labeled diagnostic-capture
  drops (lost monitoring coverage, not user packets). Existing counter row/
  summary shapes and units are reused.
- `gateway_probe_loss`: explicit/DHCP identity and resolved addresses/table,
  numeric `newly_lost`, timeout milliseconds, first/last probe sequence strings
  and UTC send timestamps, plus current rolling `window`. Count `newly_lost`,
  **not** repeatedly the rolling `window.lost`; first/last are bounds, not a
  claim that every intervening probe was lost. Report new timeouts during
  warm-up, without waiting for health holds.
- `gateway_health_change`: previous/current health, measured statistics and
  existing configured latency/loss/variation thresholds, including recovery.
  Correction: initial healthy `unknown` to `up` transitions are now omitted
  on each worker start; initial degraded/down states and recovery after
  established health remain logged. Runtime health/timestamps and event/page
  schemas are unchanged. No additional frontend implementation is needed.
- `gateway_unavailable`, `link_monitor_unavailable`, `link_monitor_recovered`:
  failed measurement/recovery rather than invented loss or silent health.
  Link duplicate failures are suppressed until changed/recovered; gateway
  worker retries can repeat failures.

Synthetic inner message (one interface evidence row):

```json
{"schema":"netcontrol-performance/v1","event":"link_observation","observed_at":"2026-11-17T01:00:01Z","details":{"previous_collected_at":"2026-11-17T01:00:00Z","interval_seconds":1.0,"evidence":[{"event":"interface_errors_or_drops","interface":{"index":2,"name":"wan0","errors":"0","drops":"9","errors_delta":"0","drops_delta":"2"}}]}}
```

### Frontend tasks and deployment

1. Add a separate Performance log view using the existing log client/page
   component. Extend `source` types and keep its cursor/history separate.
   Poll only while visible, non-overlapping at the existing 2-5 second cadence;
   drain `has_more`, preserve cursor on errors, and show gap/reset/retention.
2. Show observed time prominently, persistence time separately if useful,
   interface/qdisc or gateway identity, event meaning and new-count evidence.
   Optional structured formatting must retain safe raw-text rendering and
   tolerate unknown details/events. Bound visible history; no analytics,
   browser local-storage or shared-cache export of log contents.
3. Distinguish probe nonresponse from proven user/audio loss, local TCP from
   forwarded TCP/UDP, and diagnostic socket drops from network drops.
   `capture.state:"running"` confirms a readable sink, not all detector health.
   Empty history never proves uninterrupted traffic.

Deploy the backend before enabling the new view; existing clients/endpoints
continue working unchanged. Operators must retain private writable
`<services-state-dir>/logs/performance`. Initialization failures fail startup;
failed writes are traced, make storage unavailable, and do not stop monitoring.
No new launch option or active probe is enabled. Existing authorized monitors
and collectors write events directly, without another polling worker. Four
2 MiB segments survive restart; retention is volume-based, not a fixed duration.
Allow at least 24 MiB across all three log streams plus metadata/rotation space.
Synchronized storage and scheduling can extend observation intervals.
No compatibility window, migration, automatic tuning or arbitrary threshold.

Acceptance: require `logs.read`; show new qdisc/gateway events in one stream;
no first/reset-counter false loss or repeated rolling-window recount; keep
hierarchical queues separate; show new gateway timeouts during warm-up and held
health recovery; distinguish unavailable coverage; restart retains history/
cursors; demonstrate gap/reset and 503 without losing the last good view.
Backend: 849 workspace tests passed, 110 ignored; strict all-target Clippy,
formatting and build passed. Two selected isolated Linux tests passed, including
real DHCP gateway timeout logging and link collection/shutdown. Appliance
qdisc-drop correlation, storage-pressure performance and browser acceptance
remain unverified.
