# Frontend handoffs - 2026-11-10

## 2026-11-10-01 Mandatory panic reboot

- **Summary:** native host mode aggressively owns `kernel.panic=10`.
- **Priority:** high; **classification:** required operator-help disclosure;
  optional read-only status display.
- **Status:** Pending frontend review. Not sent or acknowledged.
- **Backend availability:** Unreleased; not deployed or published.
- **Contract/recommended bump:** breaking deployment policy, additive runtime
  metadata; next automatic calendar version.

### Contract and frontend tasks

Previously Netcontrol did not own the kernel panic reboot delay. Now native host
startup overwrites conflicts, verifies ten seconds and persists
`/etc/sysctl.d/99-netcontrol-panic.conf`. A Rust worker reclaims live/owned-file
drift every second. Startup failures abort native startup; later errors are
logged/retried and appear in existing platform health and alerts under component
`kernel_panic`, resource `host`. Retrying failure is degraded, stopped worker is
unhealthy. Unrelated valid configuration writes remain available.

**Affected HTTP method/path:** `GET /api/v1/runtime`, existing `state.read`
permission. Existing runtime/platform-health projections consume the component;
no new route, authentication, request body, status code or error envelope.
The native response adds:

```json
{"kernel_panic":{"state":"running","retrying":true,"error":null,"reboot_after_seconds":10,"observed_seconds":10,"drift":false,"enforcement_interval_seconds":1,"persistence_file":"/etc/sysctl.d/99-netcontrol-panic.conf"}}
```

Fields: `state` is `running|error`; `retrying` is worker liveness; `error` is
nullable diagnostic text. `reboot_after_seconds` is fixed 10 seconds;
`observed_seconds` is a live signed integer or null on read failure; `drift` is
boolean or null when unreadable. Interval is fixed 1 second; persistence path
is the fixed string above. Error state can have null diagnostic text when
drift/exited-worker evidence suffices. Native lab mode returns null; simulator
omits the field. No editable fields/defaults or persisted configuration changes.

Required: disclose automatic reboot ten seconds after genuine kernel panic,
writable host procfs and trusted root-owned sysctl directory prerequisites,
startup failure behavior, and console-access/operator acceptance requirements.
Optional: add client types/read-only measured status and reuse existing platform
alert rendering; label null/absent as not managed rather than healthy. Do not
add configuration controls, new polling loops or claim a reboot was tested.

### Deployment and acceptance

Policy takes effect on native host startup during install, restart, boot and
all upgrades that start the new daemon, including binary-only self-upgrades.
No frontend/backend ordering requirement. No compatibility window or migration.
No original foreign setting restoration on shutdown/configuration rollback.
The live value and owned boot file remain when stopped; continuous reclamation
does not. Competing writers can win between checks; foreign boot configuration
can override the owned file until daemon startup reclaims the setting.
Panic-on-oops, panic-on-warning, NMI/lockup triggers and hardware watchdog policy
are unchanged. Kernel reboot execution cannot be guaranteed in every failure.

Acceptance: host startup takes zero/negative/other-delay values to 10;
external drift and owned-file edit/removal converge; failures are visible and
recover; unrelated sysctl files remain intact; lab/simulator do not claim the
global control. Deployment acceptance should inspect live/boot settings and
health without deliberately panicking a shared or production machine.

[journal](../journal/2026-11-10.md#mandatory-kernel-panic-reboot-ownership).

## 2026-11-10-02 Fresh-install AppArmor removal

**Superseded policy:** [item 04](#2026-11-10-04-apparmor-disable-only)
replaces removal/pinning with disable-only behavior. The original details below
are historical, not the current installation contract.

**Scope extended:** [item 03](#2026-11-10-03-source-upgrade-apparmor-removal)
supersedes only this item's source-upgrade exclusion. Fresh-install behavior and
other exclusions remain unchanged.

- **Summary:** fresh Ubuntu installation requires disabled AppArmor and removes
  its policy/tooling, with persistent service/package/boot suppression.
- **Priority:** high; **classification:** required operator-help update.
- **Status:** Pending frontend review. Not sent or acknowledged.
- **Backend availability:** Unreleased local changes, not deployed/published.
- **Contract/recommended bump:** breaking installation/security policy;
  next automatic calendar version.

### Previous versus new behavior

Previously installation left AppArmor enabled; only the separate explicit
hardening opt-out scheduled boot disablement while retaining packages.
Now fresh `install.sh`, after installing prerequisites and before release
download/network provisioning, writes/verifies a GRUB `apparmor=0` drop-in.
If the running kernel still enables AppArmor, installation stops with an error
requiring a deliberate console reboot and rerun. No automatic reboot, AppArmor
package/profile purge or successful enforcement-disable claim occurs at that
stage. Existing enforcement can remain until reboot.

After confirming kernel disablement, stop/disable/persistently mask
`apparmor.service` even if absent; purge installed/residual-config policy/tooling
packages; remove standard profile/cache content; install an APT priority -1 pin
and verify no normal tooling package candidate remains. Package selectors,
paths and exact prerequisites are in the
[operator contract](../BUILD_AND_INSTALL.md#apparmor-disablement).
Required libraries/kernel code remain; collateral dependency removals are
errors. No broad filesystem search, custom kernel or unrelated package purge.

**Affected HTTP methods/paths: none.** No authentication/permissions, request/
response fields, types, defaults, validation, status codes, JSON examples,
configuration transactions, polling or persisted firewall-schema changes.
The error/reboot gate is installer exit failure, not an HTTP response.
`POST /api/v1/system/upgrade`, automatic HTTPS upgrades, source upgrades,
signed packages, reset and standalone hardening do not establish this policy.

### Required frontend/operator tasks

- Update fresh-install help to require supported GRUB and console/snapshot
  preparation. Explain the two-run workflow when AppArmor is active: boot
  configuration prepared, manual reboot, rerun the same installer.
- Disclose loss of mandatory-access-control confinement for every application.
  Do not describe this as security hardening or a prerequisite for native
  tracing/performance features on existing hosts.
- Warn that custom profiles/cache/state at the exact standard cleanup paths are
  deleted without automatic backup; save wanted policies elsewhere first.
- Explain package-plan/control/file failures abort installation and completed
  host mutations are not transactionally undone. Unsupported boot layouts must
  not be presented as a successful partial installation.
- Do not offer API controls or promise every AppArmor artifact is absent:
  required libraries/kernel support remain, and deliberate root/package/boot
  overrides can reintroduce enforcement. Normal APT reinstall is pinned out.

No client type/form/rendering/state/polling changes or frontend/backend rollout
ordering are required. Existing appliances are not automatically changed.

### Acceptance and evidence

Test enabled-kernel installation stops before AppArmor purge/network provisioning,
manual reboot disables AppArmor, and rerun removes targeted tooling/profiles,
retains unrelated packages/libraries, verifies persistent masks and APT pins.
Check repeat/absent cases, unknown kernel state, unsupported/unsafe GRUB paths,
failed/conflicting generated boot entries, collateral package plans, residual
packages, pin overrides and control/cleanup errors all fail explicitly.

Backend mocked installer suite and offline APT candidate results are recorded in
the [journal](../journal/2026-11-10.md#fresh-install-apparmor-disablement-and-removal).
Real Ubuntu GRUB boot/reboot, package purge, connectivity/login and frontend
integration remain unverified; mocks do not prove appliance acceptance.

## 2026-11-10-03 Source-upgrade AppArmor removal

**Superseded policy:** [item 04](#2026-11-10-04-apparmor-disable-only)
replaces removal/pinning with disable-only behavior. Source-upgrade scope and
abort-before-binary-replacement ordering remain.

- **Summary:** full source upgrades now apply the same AppArmor policy as fresh
  installation, including manual reboot/rerun gating and policy/tooling removal.
- **Priority:** high; **classification:** required source-upgrade operator help.
- **Status:** Pending frontend review. Not sent or acknowledged.
- **Backend availability:** Unreleased local changes, not deployed/published.
- **Contract/recommended bump:** breaking source-upgrade/security policy;
  next automatic calendar version.
- **Supersedes:** item 02's exclusion of source upgrades only.

### Contract and required frontend tasks

Previously `upgrade.sh` did not configure AppArmor. Now full deployment invokes
the shared installer helper after build but before other kernel/service setup,
old-daemon shutdown or binary replacement. Existing hosts require supported
GRUB and existing APT/dpkg/systemd tools; no prerequisite installation is added.

If AppArmor is enabled, prepare/verify `apparmor=0` boot configuration and stop
with failure requiring a manual console reboot and rerun of the same
`upgrade.sh` command. No automatic reboot, old-daemon shutdown, binary replacement
or AppArmor package/profile purge at this stage. Existing enforcement may
continue until reboot. Unknown state or failed inspection also aborts.

Once disabled, apply the same purge of policy/tooling and standard custom
profiles/caches, persistent service masks (including verification after purge),
APT priority -1 pins and candidate checks as fresh installation. An already
disabled kernel does not skip these checks. Required libraries/kernel code
remain; unsafe/collateral package operations are refused. No original foreign
policy restoration or transactional rollback of completed host changes.

Update source-upgrade instructions to disclose loss of confinement and custom
profile deletion, require console/snapshot/backup preparation and supported GRUB,
and distinguish reboot-required failure from successful deployment. This is not
a security improvement or an absolute guarantee against privileged overrides.
No new forms, client types, polling or UI state schema is required.

**Affected HTTP methods/paths: none.** In particular,
`POST /api/v1/system/upgrade` and automatic HTTPS binary self-upgrades remain
excluded. `--build-only`, signed-package deployment, reset and standalone
hardening do not establish this policy. No changes to authentication,
permissions, request/response fields/types/defaults/nullability, validation,
status/error envelopes or saved firewall configuration. No JSON payload or
frontend/backend rollout ordering requirement.

### Acceptance and validation

Verify enabled AppArmor stops full source deployment before subsequent setup/
binary replacement, then console reboot/rerun completes after verifying
disablement. Verify disabled/absent cases still reclaim masks/pins and remove
targeted tooling, while retaining required libraries and unrelated packages.
AppArmor failure/reboot requirement must not enter binary replacement/recovery;
other setup failures still abort, and existing binary rollback tests remain valid.

Bash syntax, full mocked installer/upgrade suite and real offline APT candidate
tests passed; see the [journal](../journal/2026-11-10.md#source-upgrade-apparmor-disablement-and-removal).
Real Ubuntu GRUB/reboot, package purge, service continuity, login/network and
frontend acceptance remain unverified.

## 2026-11-10-04 AppArmor disable-only

- **Summary:** disable AppArmor without removing any packages, profiles or caches.
- **Priority:** high; **classification:** required installation/upgrade help.
- **Status:** Pending frontend review. Not sent or acknowledged.
- **Backend availability:** unreleased working-tree changes; no approved release
  or deployment verified for this change.
- **Contract/recommended bump:** breaking deployment-policy correction;
  next automatic calendar version.
- **Supersedes:** items 02/03's purge, profile/cache cleanup, package pins and
  APT prerequisites. Their deployment scope and manual reboot gate remain.

### Current contract and frontend tasks

Fresh `install.sh` and full `upgrade.sh` prepare and verify GRUB `apparmor=0`.
An enabled running kernel stops deployment with a manual console reboot/rerun
requirement. Existing enforcement may remain until reboot; stopping a service
does not prove kernel disablement. Unknown state and boot/control/file errors
abort. Full upgrades stop before old-daemon shutdown or binary replacement.
Once disabled, stop/disable and persistently mask `apparmor.service`, including
an absent unit, and verify inactive/failed state plus persistent masking.

Previously the deployment policy purged AppArmor packages and profiles and
pinned out reinstallation. Now preserve **all packages**, including
`ubuntu-server-minimal`, and all profiles, caches and APT preferences. AppArmor
preparation performs no package queries, purge, autoremove, pin writing or
profile cleanup. Existing pins, if present, remain untouched. GRUB and systemd
remain prerequisites; APT/dpkg are no longer prerequisites of this helper.
Other installation/service policies are unchanged.

Required frontend tasks: replace removal/deletion/reinstallation-blocking help
with disable-only wording. Explain loss of host-wide confinement, retained
profiles/packages, console reboot/rerun when active, and explicit failure versus
successful completion. Do not promise permanent disablement against privileged
boot/service overrides. No new forms, client types, polling or status schemas.

**Affected HTTP methods/paths: none.** No authentication/permissions, JSON fields,
nullability/defaults/units/limits, status/error envelope or saved configuration
changes. No JSON examples apply. `POST /api/v1/system/upgrade`, automatic binary
updates, signed packages, reset, build-only and standalone hardening do not
establish this mandatory policy. No frontend/backend rollout ordering required.
Operators must use updated installer/upgrade scripts: a previously downloaded
purge-based script still has its former behavior. Do not force package removal
to bypass its collateral-dependency rejection.

### Acceptance and validation

Check active kernel -> prepared boot setting and failure -> manual reboot/rerun
-> verified disablement and persistent mask. Check disabled/absent and repeated
runs; retain profiles/cache content, existing APT preferences and package state,
with no package-manager calls from AppArmor preparation. Verify failures abort
before binary replacement and GRUB generation failures restore the prior drop-in.

Bash syntax and the full installer/upgrade regression suite passed unprivileged,
with mocked host controls and real temporary-root file/mode operations. Real
Ubuntu GRUB/reboot, service/package state and login/connectivity acceptance are
not verified locally.
