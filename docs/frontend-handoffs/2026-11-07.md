## 2026-11-07-01 Snap service disablement during install and hardening

- **Priority:** medium.
- **Classification:** required deployment/operator review; optional frontend
  installation/help wording. No client-type or form change.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not published or deployed.
- **Contract/recommended release:** breaking install/hardening deployment-policy
  change; next automatic calendar version.

**Superseded in part by [2026-11-07-02](#2026-11-07-02-disable-automatic-ubuntu-apt-updates):**
the APT-security-preservation statements below describe the initial Snap-only
change. The current install/hardening policy additionally disables automatic APT
security updates, as explicitly requested. Snap behavior is unchanged.

### Previous versus new behavior

Fresh Ubuntu installation previously left Snap alone. It now disables/stops
loaded `snapd.service` and `snapd.socket`, explicitly stops already-masked ones
and persistently masks present units before appliance network provisioning.
Absent units are skipped, including systemd's normal not-found failure status.
Inspection, action and verification errors stop installation.

Hardening preview lists Snap actions without changes. Only `--apply` disables/
stops loaded Snap units, stops already-masked units, persistently masks present
units and verifies the result. Pre-change active/enablement records include
present Snap units, including already-masked ones. Other profile/package guards
and the separate explicit AppArmor opt-out remain.

Success requires persistent `UnitFileState=masked` and `ActiveState=inactive`
or `failed`, not active or runtime-only masking. No Snap package/data purge,
explicit separate Snap application-unit stop, automatic reboot or appliance
state reset. This does not claim complete Snap-application removal/shutdown.
Snap management/installation and refreshes are blocked; APT security updates
are not targeted.

### Affected interfaces and frontend/deployment tasks

- **HTTP methods/paths:** none added or changed. API authentication, permissions,
  request/response fields/types/nullability/defaults, validation/status codes,
  runtime polling and saved firewall configuration are unchanged.
- Review Snap-dependent workloads before fresh install or hardening apply;
  use a local console and take a host snapshot before the optional profile.
- Update operator installation/help text to state Snap management/refreshes are
  unavailable afterward. Do not claim AppArmor or APT security updates are
  disabled, or that installed Snap application units were explicitly shut down.
- Keep hardening a console workflow, not an automatic browser action. Existing
  hosts must explicitly run the reviewed script; binary/source upgrades alone
  do not apply this policy.
- No binary/frontend rollout ordering requirement; deployment copy must match
  the reviewed installer/hardening script version, not merely daemon version.
  Downloaded scripts do not include unpushed local work.

### Acceptance and validation

- Installed units become stopped/disabled and persistently masked; repeat and
  already-masked-active cases stop safely. Missing units do not fail install.
- Preview is read-only. Hardening saves pre-change Snap states before mutation.
- Query/unknown-state, disable, stop, mask, verification-query, still-active and
  runtime-only-mask failures do not produce success or continue to later stages.
- Mocked systemd installer/hardening regression suite and Bash syntax checks
  passed; actual Ubuntu systemd, Snap workloads and post-reboot behavior still
  require operator acceptance.

## 2026-11-07-02 Disable automatic Ubuntu APT updates

- **Priority:** high.
- **Classification:** required operator patching/deployment coordination;
  optional frontend installation/help wording. No client-type or form change.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree, not published or deployed.
- **Contract/recommended release:** breaking install/hardening deployment-policy
  change; next automatic calendar version.
- **Supersedes:** item 01's APT security-preservation statements only.

### Previous versus new behavior

Previously installation/hardening left Ubuntu automatic OS updates intact.
Following explicit confirmation to disable checks, downloads and automatic
installation **including security updates**, fresh installation and hardening
`--apply` now:

1. Disable/stop and persistently mask present `apt-daily.timer` and
   `apt-daily-upgrade.timer`; disable/mask their `.service` jobs without stopping
   those jobs. Verify each present unit is inactive/failed and persistently
   masked. Missing units are skipped.
2. Refuse success while a service job is active, rather than interrupting it.
   Wait for completion and rerun. Earlier unit changes may already be applied.
3. Atomically write the root-owned mode-0644
   `/etc/apt/apt.conf.d/99-netcontrol-no-automatic-updates` fragment:
   `APT::Periodic::{Enable,Update-Package-Lists,Download-Upgradeable-Packages,Unattended-Upgrade}`
   all `"0"`; `Unattended-Upgrade::InstallOnShutdown` `"false"`.
4. Verify all five effective values using `apt-config dump`. Later conflicting
   settings, query errors, unsafe file paths and write/verification failures
   produce nonzero script exits, not a success notice.
5. In hardening, retain prior selected unit states and the owned fragment or
   its absence in the private state directory. No automatic rollback.

Preview remains read-only. APT/unattended-upgrades packages are not purged by
this policy. The shutdown watcher may remain running, but shutdown installation
is disabled by configuration. Manual APT operations, including installer
dependency setup, and Netcontrol's own release checks remain available.
Cached login update notices may remain. Arbitrary third-party schedulers and
graphical updaters are not covered by this standard Ubuntu APT policy.

### Interfaces, frontend tasks and deployment

- **HTTP methods/paths:** none added or changed. API fields/types/nullability,
  validation/status codes, authentication/permissions, saved firewall schema and
  polling are unchanged. No browser hardening/update toggle is introduced.
- Update installation/help messaging: automatic OS security patching is off;
  operators must schedule/review manual APT patching. Do not describe this
  deployment policy as a security improvement or claim all update notices vanish.
- Keep hardening an explicit console workflow, with preview and full profile
  review. Existing hosts need reviewed hardening apply; ordinary daemon upgrades
  and factory reset do not apply the policy.
- No frontend/backend binary ordering requirement. Help copy must match script
  availability, not merely daemon version. This unpushed work is not available
  from published script URLs. Use console recovery access and avoid concurrent
  install/upgrade/reset/APT/dpkg jobs.
- Do not automatically restart, reboot, reinstall or remove OS packages to apply
  this policy. Preserve manual recovery using recorded masks/states and fragment.

### Acceptance and validation

- Installer/hardening regression suite and Bash syntax checks **passed**:
  70 combined Snap/APT scenarios, mocked systemd/package commands and real APT
  configuration-parser checks. Covers preview, absent units, repeat runs,
  persistent/runtime masks, active-job no-interruption, backup retention,
  later-setting overrides including shutdown, write/query/action failures,
  symlink rejection and temporary-file cleanup.
- Manual APT access is preserved by limiting configuration to periodic/shutdown
  automation, not blocking APT executables or removing packages; actual online
  manual update/install and Ubuntu systemd/reboot acceptance remain untested.
- Operators must verify the four unit states and five effective settings, check
  management continuity and validate a manual patching schedule on the real host.

## 2026-11-07-03 IPv6 disabled by default and initial takeover

- **Priority:** high.
- **Classification:** required frontend default/validation/help updates and
  operator deployment review.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not published or deployed.
- **Contract/recommended release:** breaking default/startup/takeover contract;
  next automatic calendar version.

### Previous versus new behavior

`ipv6_enabled` previously defaulted to true. It now defaults to false in omitted
configuration, fresh install and factory reset. An explicitly saved true remains
enabled on ordinary restart; reset deliberately selects the disabled factory
policy. Normalized reads always include the boolean.

Initial physical-NIC capture no longer refuses DHCPv6/SLAAC merely because it
exists. Keep supported IPv4 state and DHCPv4 from networkd `DHCP=yes/true/both/ipv4`;
do not import IPv6 addresses, routes or literal DNS servers. IPv6-only DHCP does
not become a DHCPv4 client. Networkd exclusion relinquishes its IPv6 management;
startup reconciliation disables all/default/current-interface IPv6 controls.
Captured originals remain private for failed-handover recovery. Managed NIC
release baselines exclude IPv6 so retry/release does not resurrect it.

Empty host configuration no longer bypasses native reconciliation: startup
disables IPv6 and initializes the owned `inet/netcontrol` firewall through the
existing durable intent. Opening the backend/discovery alone remains passive.
Foreign firewall tables are not removed or imported.

### HTTP, types, permissions and errors

- No methods/paths added or removed. Read via `GET /api/v1/state`,
  `GET /api/v1/runtime`, configuration export and revision/transaction reads
  with their existing read permissions.
- `POST /api/v1/transactions`: `config.ipv6_enabled` remains a non-null boolean;
  omitted now means false. Explicit null/string/number remains `400`.
  IPv6 resource literals or filters without explicit enablement now produce
  the existing validation `422`, including disabled resource records.
- Toggle changes still require `transactions.write` and
  `kernel.namespace.write`; accompanying resources require their existing
  permissions. Confirmation, rollback, stale revision, active transaction and
  recovery errors are unchanged. No immediate-write toggle endpoint.
- Synthetic normalized response fragments:
  `{"ipv6_enabled":false}` and
  `{"ipv6":{"enabled":false,"status":"measured","disable_ipv6":{"all":"1","default":"1","lo":"1"},"drift":false}}`.
  These are fragments, not complete configuration/transaction payloads.

### Frontend and deployment tasks

1. Initialize new candidates/forms with IPv6 off. Never use a truthy fallback
   or silently turn a returned false into true. Preserve explicit saved values.
2. Before staging IPv6 addresses/routes, DNS/server literals, WireGuard peers,
   firewall/NAT references, monitors, collectors or IPv6-only capture filters,
   require explicit global enablement. Show same-candidate validation errors;
   do not delete conflicts automatically during normal edits.
3. Update install/reset/recovery warnings: use IPv4 management plus console;
   IPv6-only connectivity and `::1` dependencies stop when policy is disabled.
   The policy is enforced by the running daemon, not before daemon startup.
4. Do not claim full-host import/takeover. NetworkManager, custom policy rules,
   bridges/bonds and unsupported IPv4/networkd options still block capture.
   Virtual topology, unrelated routes, foreign firewall and external service
   managers are not automatically owned/disabled. Fresh install still selects
   a factory WAN/LAN plan instead of retaining every imported setting.

Deploy frontend default/help changes with the backend contract. Existing explicit
IPv6-enabled state needs no conversion. Do not automatically reset devices to
obtain the new default. This is not authorization to modify a running host.

### Acceptance and validation

- Empty/new/reset configuration reports false; explicitly saved true survives
  ordinary restart and transaction rollback. Invalid scalar types still fail.
- IPv6 resource edits without enablement fail; dual-stack examples explicitly
  enable it. CLI enable/disable, confirmation and rollback retain their workflow.
- Isolated privileged Linux tests passed for default empty-host enforcement,
  IPv4 retention, unmanaged/loopback/future links, restart, same-boot re-enable,
  managed IPv6 apply/interrupted recovery, Ethernet recovery/reboot, VLAN
  DHCP recovery, and dual-stack static/blackhole route operations.
- Workspace tests, Clippy, formatting and build passed offline with stable Rust.
  Real networkd DHCPv6/SLAAC handover, Ubuntu boot and physical management/
  connectivity acceptance remain untested; no complete takeover claim.

## 2026-11-07-04 Aggressive console host takeover

- **Priority/classification:** high; required frontend types, validation and
  deployment/help work.
- **Status:** Pending frontend review.
- **Availability:** Unreleased working tree, not published/deployed.
- **Contract/recommended bump:** breaking takeover/provisioning/runtime contract;
  next automatic calendar version.
- **Supersedes:** item 03's remaining-gap/help statements about conservative
  capture and factory replacement; its IPv6-off default remains.

### Previous versus new

Initial console provisioning now imports supported Ethernet/veth, dummy/VLAN,
static IPv4/routes, DHCPv4/DNS and representable nftables policy as owned state.
Networkd and active NetworkManager capture no longer require a current DHCP
lease. Unsupported topology/routing/firewall/traffic control/XDP/TCX and known
competing units/processes are disabled; units are persistently masked.
Original OS files and private capture remain, but connectivity loss does not
restore unsupported state. Resolved/SSH/Wi-Fi authentication are retained.

Provisioning preserves imported WAN addressing, MTU, routes, DNS, firewall and
other interfaces. It assigns WAN/LAN roles, enables those ports, and replaces
only the selected LAN's addresses/DHCP client. Empty WAN receives DHCPv4.
No WAN readiness timer, automatic connectivity rollback or substituted factory
NAT/allow-all policy. Literal firewall subnets are not automatically rewritten.
Explicit factory reset and normal confirmed API/SSH edits remain separate.
Unconfigured/released links stay down/address-cleared rather than returning to
OS management; explicit read-only parents retain link-level settings.

### Exact affected API/types

- `GET /api/v1/runtime`, `state.read`: native `host_takeover` is null without a
  receipt; otherwise the following shape. No raw captures/private OS files.

  ```json
  {"mode":"console","phase":"complete","error":"","connectivity_confirmation_required":false,"items":[{"resource":"ipv6","disposition":"disabled","reason":"IPv6 is disabled"}]}
  ```

  `phase` is `captured|applying|owned|failed|complete`; incomplete phases are not
  successful reconciliation. `error` is a string, empty without a recorded
  error. `items` contain string resource/reason and `imported|disabled`
  disposition. These are capture decisions, not live connectivity evidence.
- `GET /api/v1/transactions`, `GET /api/v1/transactions/{id}` and
  `GET /api/v1/state` transaction records retain existing authentication/
  read permissions. `status` additionally admits `applying_local`;
  `confirmation_deadline` is now timestamp-or-null. Only console provisioning
  uses null and resumes its candidate on restart; its final status is committed.
  Normal `POST /api/v1/transactions` remains `202`, non-null timed confirmation;
  confirm/rollback remain `200` with existing permissions/error semantics.
- Static `config.routes[].metric` accepts integers **0..2147483647**, formerly
  1..2147483647. Zero preserves imported kernel default priority; units are
  dimensionless route priority, not seconds. Negative/out-of-range candidates
  remain `422`. Apply to route editing, full transactions and revision drafts.
- No HTTP takeover mutation, new permission or browser manager-control API.
  Startup/capture errors are explicit command/startup failures with private
  evidence retained; do not invent a successful HTTP outcome for them.

### Frontend tasks and deployment

1. Update transaction types/null handling; never run a countdown or offer
   confirmation for null-deadline console transactions. Keep normal remote
   confirmation and draft retention unchanged.
2. Render takeover mode/phase/error and imported/disabled decisions in native
   diagnostics. Clearly distinguish incomplete/failed capture from complete;
   show console correction/retry, not an automatic retry button.
3. Accept/display zero static-route metric. Preserve imported policy, DHCP/DNS,
   additional/nested interfaces and metadata in complete drafts.
4. Replace factory-policy assumptions in install help. Review actual input/
   forwarding/NAT policy and chosen LAN subnet from console; do not promise
   WAN protection, client NAT or management continuity from role labels.
5. Deploy types/help with this backend contract. The installer rejects binaries
   without the `console-host-takeover` help marker. Require console access,
   root network/BPF administration, systemd/resolved, stable host identity and
   trusted core/native state; do not delete captures to retry or automatically
   reset configured devices. Known-owner lists do not sanitize every custom
   launcher, renamed program or unrelated namespace.

### Acceptance and validation

- Core tests prove immediate null-deadline commitment, no recapture, and
  candidate recovery after interruption beyond an ordinary deadline.
- Isolated privileged tests passed supported topology/static route/DNS/nft
  import, finite-address DHCP classification, unsupported bridge/address/
  policy/qdisc cleanup, exact owned-route/rule preservation, XDP, linked and
  nonlinked ingress/egress TCX detachment, legacy DROP-to-ACCEPT cleanup,
  repeat enforcement and same-namespace-only process termination.
- Workspace tests/build/Clippy/formatting, no-default-feature native check,
  installer regressions and selected restart/recovery/IPv6 tests passed.
- Remaining integration: real Ubuntu systemd mask/stop persistence, active
  NetworkManager/networkd D-Bus capture, physical DHCP/DNS continuity, interrupted
  full host takeover/reboot and frontend rendering. No production acceptance,
  publication, delivery or frontend acknowledgment is claimed.

## 2026-11-07-05 Home Assistant unknown numeric measurements

- **Priority:** medium.
- **Classification:** required backend deployment/Home Assistant validation;
  optional frontend/operator help. No client-type or form change.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not published or deployed.
- **Contract/recommended release:** MQTT discovery contract fix; next automatic
  calendar version.

### Previous versus new behavior

Numeric sensor discovery previously rendered missing/null metrics as the literal
`unknown`, which Home Assistant rejects for sensors declaring units or a state
class. Corrected templates render `None`, Home Assistant's unknown numeric
sentinel. Text sensors keep their existing `unknown` fallback.

For example, this synthetic **state fragment** remains unchanged:

```json
{"metrics":{"example_restart_count":null}}
```

Its numeric component's template is now:

```text
{{ value_json.metrics.get('example_restart_count') if value_json.metrics.get('example_restart_count') is not none else 'None' }}
```

The state payload does not replace null with a string or zero. Missing retained-
source keys stay absent. Real zero, fractional/negative values and exact 64-bit
decimal counter strings pass through unchanged, without floating-point coercion.
All numeric interface/gateway/host/protocol/worker/link sensors use the same
generator, including unit-only and unitless state-class sensors.

### Interfaces, frontend tasks and deployment

- **HTTP methods/paths:** none added or changed. API fields/types/nullability,
  permissions/authentication, validation/status codes and saved configuration
  are unchanged. No new browser action is introduced.
- MQTT topics, broker ACLs/authentication, retain/QoS, 32 MiB cap, discovery IDs,
  metric keys, units/classes, expiry and availability are unchanged. Discovery:
  `homeassistant/device/netcontrol_<device_id>/config`; state:
  `netcontrol/<device_id>/state`.
- Deploy the corrected daemon and let normal startup/reconnect/Home Assistant
  birth reannounce discovery. Do not manually edit Home Assistant sensor values
  or turn unavailable measurements into zero.
- Optional help: explain unknown numeric readings as unavailable measurements,
  not malformed/truncated transport, and distinguish them from actual zeroes.
- Old per-sensor discovery conflicts remain a separate broker-administrator
  concern under [handoff 2026-11-06-07](2026-11-06.md#2026-11-06-07-consolidated-mqtt-with-32-mib-payloads).
  This task does not authorize or perform retained-topic deletion, broker edits,
  private-store deletion or entity recreation.

### Acceptance and validation

- `cargo +stable test -p netcontrold --locked --offline mqtt::`: **22 passed,
  1 ignored**. Includes new emitted discovery/state regression cases for
  unit-only and unitless numeric sensors, null/absent data, real zeroes,
  fractions/negative values, exact counters and unchanged text/boolean readings.
  Existing 32 MiB transport, partial-source, lifecycle and manifest tests passed.
- Generated template-pattern rendering with Jinja2: **16 checks passed**, covering
  missing/null, zero, uint64 string/integer precision, fractions/negative values
  and false without coercion.
- Daemon all-target Clippy (`-D warnings`), build, package formatting and
  whitespace checks **passed** with stable Rust and the committed lockfile.
- Native privileged broker lifecycle fixture remains ignored; live Home
  Assistant ingestion and a deployed corrected binary have not been verified.
  Verify missing numeric sensors display unknown without nonnumeric-value log
  errors, available readings still update, and topic/ID continuity holds.

## 2026-11-07-06 Fivefold firewall policy limits

- **Priority:** medium.
- **Classification:** required frontend validation/help update.
- **Status:** Pending frontend review.
- **Backend availability:** Unreleased working tree; not deployed or published.
- **Contract/recommended release:** additive validation-capacity increase; next
  automatic calendar version. Supersedes earlier documented firewall size limits.

### Contract and affected interfaces

| Bound | Previous | New |
| --- | --- | --- |
| Ordered rules per host/forwarding ingress/input ingress | 64 | 320 |
| Expanded forwarding rules, including stateful and host defaults | 4096 | 20480 |
| Legacy port-expanded forwarding rules | 4096 | 20480 |
| Serialized policy representation | 65536 bytes (64 KiB) | 327680 bytes (320 KiB) |
| Total native input rules, including loopback/stateful/relay permits | 4096 | 20480 |
| Counter snapshot physical rules | 16384 | 81920 |

Unchanged: 128 hosts, 32 ingress policies, 16 addresses per host, 32 unique
destination ports per TCP/UDP rule (integers 1..65535), protocol choices,
accept/drop actions, rule order, defaults, fields/types/nullability and
counter response shape. Serialized policy size includes all policy JSON, not
only optional descriptions. UTF-8 bytes, not character count, determine size.
Host/address/port expansion can exhaust the total before reaching 320 rules.
Input core validation counts established/related; native compilation additionally
counts loopback and generated DHCP-relay permits against its final total.

- `POST /api/v1/transactions` and
  `POST /api/v1/revisions/{revision}/restore`: existing API-key authentication,
  `transactions.write`, `firewall.write` for changed firewall configuration,
  plus permissions required by other changes. Valid larger configurations can
  enter the existing provisional `202` confirmation workflow.
- `POST /api/v1/transactions/{id}/confirm` and
  `POST /api/v1/transactions/{id}/rollback`: unchanged transaction ownership/
  permissions and recovery semantics.
- `GET /api/v1/state`, `GET /api/v1/firewall/rules`,
  `GET /api/v1/transactions/{id}`, `GET /api/v1/revisions/{revision}`:
  existing `state.read`; embedded configurations can contain larger rule arrays.
- `GET /api/v1/statistics/firewall`: existing `state.read`; larger physical
  snapshots remain observable, with the same logical counter rows and decimal
  string totals. Over-limit or unavailable native snapshots remain explicit `503`.
- Core limit violations remain `422`; messages now identify `320`, `20480` or
  `327680` rather than the old caps. Malformed JSON/types remain `400`,
  permission failures `403`, conflicts `409`, native apply/observation failures
  `503`. No new route or authentication model.

Synthetic single-rule fragment (not a complete transaction):

```json
{"protocol":"tcp","destination_ports":[443],"action":"accept"}
```

### Frontend tasks and deployment

Raise rule-add/import/reorder form limits and validation/help strings to 320,
update expanded-rule budgets to 20480 and serialized policy budgets to 327680
UTF-8 bytes. Do not truncate arrays or treat the total as 20480 logical rules.
Keep backend errors authoritative, preserve drafts on rejection, and retain
confirmation/rollback UX and logical counter identity mapping.

Deploy the updated backend before permitting above-old-limit submissions.
No state reset, migration, automatic rule consolidation or data deletion.
Host capacity/performance and native kernel application at the new maximum
still require representative appliance acceptance; these numbers are not
benchmark-derived performance guarantees.

### Acceptance and backend validation

Accept 320 rules and reject 321 independently for hosts, forwarding ingress
and input ingress. Accept exactly 20480 forwarding expansions and reject one
extra; accept exactly 327680 policy bytes and reject 327681. Preserve ordering,
save/reopen, confirmation and rollback; retain meaningful `422` errors.
Counter tests accept 81920 physical rows and reject 81921.

Affected core/native suites and full workspace tests passed using cached stable
Rust in an unprivileged Linux Docker container: 626 passed, 93 ignored, 0 failed.
Workspace Clippy (`-D warnings`), formatting check and build passed. Privileged
native tests and a deployed frontend/backend integration check remain unexecuted.
